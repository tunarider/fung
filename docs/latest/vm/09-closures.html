함수와 클로저

함수를 부르면 VM 안에서는 프레임 하나가 쌓인다. 함수 안에서 만든 함수는 바깥 변수를 붙잡아야 하는데, fung은 그 값을 만들어질 때 복사하는 규칙 하나로 정했다.

  1. 소스
  2. 토큰
  3. 트리
  4. 코어
  5. 바이트코드
  6. 실행
이 장에서 배울 것
  • 함수 호출이 하는 일: 돌아올 자리, 인자, 지역 변수, 그리고 이것을 담는 프레임
  • 인자를 칸에 묶는 호출 규약과 기본값이 바이트코드로 바뀌는 모습
  • 클로저(closure)가 바깥 변수를 붙잡는 여러 방법과 fung이 고른 "복사"
  • 최상위 함수가 전역 변수를 보는 규칙과 그 구현상 이유
  • 꼬리 호출(tail call)이 스택을 쓰지 않는 원리와 깊이 한도

8장에서 VM이 명령을 하나씩 읽어 값 스택에 쌓고 꺼내는 모습을 봤다. 그때는 CALL을 "함수를 부른다"로만 읽고 넘어갔다. 이 장은 그 한 명령 안에서 일어나는 일을 연다.

함수 호출은 무엇을 하나

함수를 부르는 일은 생각보다 많은 것을 기억해야 한다.

  1. 돌아올 자리. 함수가 끝나면 부른 쪽의 다음 명령으로 돌아가야 한다.
  2. 인자. 부른 쪽이 넘긴 값을 받는 쪽의 매개변수 이름에 붙여야 한다.
  3. 지역 변수. 함수 안에서 만든 변수는 그 호출에만 속한다. 같은 함수가 재귀로 두 번 돌면 변수도 두 벌이다.

이 셋을 묶은 것을 프레임(frame, 활성 레코드라고도 한다)이라고 한다. 함수를 부를 때마다 프레임이 하나 쌓이고, 돌아올 때 하나 빠진다. 쌓인 프레임 전체를 호출 스택(call stack)이라고 부른다. 에러 메시지의 "call path"가 바로 이 스택을 위에서부터 읽은 것이다.

책 내내 따라온 예를 다시 보자.

fn double(x) = x * 2
print(double(21))
$ fung dump bytecode example.fung
== <main> ==
0000  1:1   CLOSURE      0    ; double
0001  1:1   STOREGLOBAL  0    ; double
0002  2:1   CONST        0    ; <fn print>
0003  2:7   LOADGLOBAL   0    ; double
0004  2:14  CONST        1    ; 21
0005  2:13  CALL         1    ; 1 positional, 0 named
0006  2:6   CALL         1    ; 1 positional, 0 named
0007  2:1   POP
0008  2:1   CONST        2    ; nil
0009  1:1   RETURN

== double ==
0000  1:16  MOVELOCAL    0
0001  1:20  CONST        0    ; 2
0002  1:18  MUL
0003  1:14  RETURN

<main>의 0005번 CALL 1이 실행되기 직전, 값 스택에는 아래에서부터 <fn print>, double, 21이 쌓여 있다. CALL 1은 "맨 위 인자 하나와 그 아래의 함수"를 뜻한다. VM은 double의 프레임을 새로 쌓고, 그 함수의 명령 0000번부터 실행한다.

CALL 1 직전                 double의 프레임이 쌓인 뒤
[2]  21
[1]  <fn double>            [1]  21           ← double 프레임의 슬롯 0(x), base = 1
[0]  <fn print>             [0]  <fn print>   (main이 계산 중인 값)

VM은 함수 값이 있던 칸을 빼고, 그 자리부터를 새 프레임의 슬롯으로 삼는다. double 안의 LOADLOCAL 0은 "내 프레임의 슬롯 0"을 읽는다. 슬롯 0은 값 스택의 base + 0번 칸이고, 인자 21이 이미 그 자리에 있으므로 따로 복사할 필요가 없다. MUL이 42를 올리고, RETURN이 42를 꺼낸 뒤 스택을 base까지 잘라 내고 42를 부른 쪽 스택에 올린다. 함수가 남긴 임시 값은 이렇게 새지 않는다. 그다음 <main>의 CALL 1이 다시 print를 부른다.

fn double(x) = x * 2
print(double(21))
42

프레임

fung의 프레임은 Rust 구조체 하나다(crates/fung-vm/src/vm/frame.rs의 Frame).

필드뜻
proto실행할 함수의 원형(8장): 명령열, 상수, 매개변수 표
ip다음에 실행할 명령의 번호. "돌아올 자리"는 부른 쪽 프레임의 이 값이다
base이 함수의 슬롯이 값 스택의 몇 번째 칸부터인가
closure실행 중인 함수 값. 붙잡은 값(아래 클로저 절)을 여기서 읽는다
globals이 함수가 속한 모듈의 전역 표(11장)
tail_calls꼬리 호출로 이 프레임을 몇 번 다시 썼나(아래 꼬리 호출 절)

프레임들은 태스크의 frames라는 Rust Vec에 들어 있고, 지역 변수와 계산 중인 값은 모두 태스크의 값 스택 stack 한 줄에 쌓인다. 둘 다 힙(heap)에 있는 배열이다. 그래서 fung 함수가 fung 함수를 부를 때 Rust 함수 호출은 일어나지 않는다. 실행 루프는 반복문 하나이고, CALL은 배열에 원소를 하나 더할 뿐이다. 이 사실이 뒤의 꼬리 호출, 그리고 12장의 스케줄러를 가능하게 한다.

호출 규약

호출 규약(calling convention)은 "부르는 쪽이 인자를 어디에 어떤 순서로 놓고, 받는 쪽이 그것을 어떻게 가져가는가"의 약속이다. fung의 CALL n은 스택에 [함수, 위치 인자…, (이름 심볼, 값)…]이 쌓여 있다고 약속한다. 피연산자 하나에 수 둘을 담는데, 아래 12비트가 위치 인자 수, 그 위 12비트가 이름 인자 수다. 그래서 이름 인자 하나가 있으면 피연산자가 4097(= 1 + 4096)이 된다.

fn greet(name, greeting = "hello") = "${greeting}, ${name}"

print(greet("fung"))
print(greet("fung", greeting: "hi"))

VM이 인자를 묶는 길은 둘이다(crates/fung-vm/src/vm/call.rs의 call_op).

  • 빠른 길. fung 함수를 위치 인자만으로, 매개변수 개수만큼 정확히 부르면 스택에 놓인 인자가 그 자리에서 새 프레임의 첫 슬롯이 된다. 나머지 지역 변수 칸은 비워 둔 채 이어 붙인다. 힙 할당이 없다. double(21)이 이 길이다.
  • 일반 길. 이름 인자, 기본값, ...rest가 있거나 개수가 맞지 않으면 bind_args가 매개변수 표를 보고 칸을 새로 배치한다. 위치 인자는 차례로, 이름 인자는 표에서 찾아 넣고, 남는 위치 인자는 ...rest 리스트로 모은다. 맞지 않으면 E0402(인자 수가 맞지 않음), E0405(같은 인자 두 번), E0406(없는 이름), E0407(빠진 인자)이다.
fn f(a, b) = a + b

print(f(1))
error[E0407]: missing argument `b`
  --> example.fung:3:8
  |
3 | print(f(1))
  |        ^
  |
 call path (innermost first):
   example.fung:3 <entry>

내장 함수도 같은 매개변수 표를 선언하므로(NativeParam) 같은 bind_args를 지난다. exec(cmd, cwd: dir)처럼 내장 함수에 이름 인자를 줄 수 있고, 에러 번호도 fung 함수와 같다.

기본값은 함수 서두에서

위 greet의 바이트코드를 다시 보자. 0000~0003번은 본문이 아니라 서두(prologue)다. "슬롯 1이 비었으면 "hello"를 넣어라"를 명령으로 적은 것이다.

  • LOADLOCAL 1이 슬롯을 읽고, JUMPIFSET 4가 "칸이 차 있으면 4번으로 건너뛰라"고 한다.
  • 비어 있으면 CONST와 STORELOCAL 1이 기본값을 채운다.

여기서 "비어 있음"은 fung의 nil이 아니다. 값 스택의 칸은 Rust의 Option<Value>이고, 아직 아무것도 들어가지 않은 칸은 None, fung의 nil은 Some(Value::Nil)이다. greet("x", greeting: nil)처럼 nil을 일부러 넘기면 기본값이 쓰이지 않는다. 기본값 식이 호출할 때마다 다시 평가되고 앞 매개변수를 참조할 수 있는 것도 기본값이 그냥 서두의 명령이기 때문이다. 타입 표기가 있으면 서두 끝에 CHECKTYPE이, 반환 타입이 있으면 RETURN 앞에 CHECKRETURN이 붙는다.

클로저

이제 이 장의 중심이다. 함수 안에서 함수를 만들면 무슨 일이 생기나.

fn adder(n) = x => x + n

add5 = adder(5)
print(add5(1))
print(map([1, 2, 3], adder(10)))
6
[11, 12, 13]

람다 x => x + n 안의 n은 람다 자신의 매개변수가 아니다. 바깥 함수 adder의 매개변수다. 이런 이름을 자유 변수(free variable)라고 한다. 문제는 adder(5)가 이미 돌아왔다는 점이다. adder의 프레임은 사라졌고 n이 있던 슬롯도 다른 값이 덮었다. 그런데 add5(1)은 여전히 5를 알아야 한다.

그래서 함수 값은 코드만이 아니라 자유 변수를 함께 들고 다녀야 한다. 코드와 그것이 본 바깥 변수를 묶은 값을 클로저(closure)라고 한다. 언어를 만들 때 정해야 하는 것은 "바깥 변수를 어떻게 들고 다니나"이고, 답에 따라 언어의 의미가 달라진다.

  • 변수를 공유한다. 클로저가 바깥 변수의 "자리"를 가리킨다. 나중에 바깥에서 그 변수를 바꾸면 클로저도 바뀐 값을 본다. 반대로 클로저가 바꾸면 바깥도 본다.
  • 값을 복사한다. 클로저가 만들어지는 순간의 값을 자기 안에 복사해 둔다. 그 뒤 바깥 변수가 무엇이 되든 클로저는 처음 값을 본다.
다른 언어는
  • Lua는 공유한다. 바깥 변수를 upvalue라는 작은 상자로 가리킨다. 바깥 함수가 살아 있는 동안 상자는 바깥 프레임의 칸을 가리키다가(열린 upvalue), 바깥 함수가 돌아오면 그 값을 상자 안으로 옮긴다(닫힌 upvalue). 같은 변수를 붙잡은 클로저 여럿은 상자 하나를 나눠 쓴다. 이 방식은 *Crafting Interpreters*의 clox도 그대로 쓴다.
  • CPython도 공유한다. 바깥 변수는 cell 객체에 담기고, 안쪽 함수는 그 cell을 가리킨다. 안쪽에서 바꾸려면 nonlocal을 적어야 한다.
  • JavaScript도 공유한다. 그래서 유명한 함정이 있다. 예전의 var로 반복문을 돌며 콜백을 만들면, 모든 콜백이 변수 하나를 공유해 마지막 값만 본다. let이 반복마다 새 변수를 만들게 된 것도 이 때문이다.
  • Java의 람다는 사실상 복사다. 다만 붙잡는 변수가 "사실상 final"(대입이 한 번뿐)이어야 한다는 조건을 컴파일러가 강제해서, 공유와 복사의 차이가 드러날 일 자체를 막는다.
fung의 선택: 만들어질 때 보이는 값을 복사한다

fung의 규칙은 한 문장이다. 함수는 만들어질 때 보이는 변수의 값을 복사한다(설계 03, "모델 C"). 이 규칙 하나가 함수 정의, 람다, 최상위, 블록 어디서나 같다.

  • 처음 구현은 "최상위 fn은 최상위 변수를 호출할 때 찾는다"(C·Python식)였다. 그러면 같은 코드가 최상위에서와 함수 안에서 답이 달랐다. 설계 원칙 7(규칙 하나에서 결과가 따라 나오고 예외 조항이 적을 것)에 따라 규칙을 하나로 합쳤다(background.md의 기각된 대안, 노트 M3).
  • 복사라서 Lua의 upvalue 상자가 필요 없다. fung에서 x = 2는 이름을 새 값에 붙이는 일이지 값을 고치는 일이 아니다. 블록은 바깥 변수를 다시 대입할 수 없고(E0205) 함수는 전역에 대입할 수 없으므로, 클로저가 가진 값을 누가 몰래 바꿀 길이 없다. 상자를 두어도 그 안이 바뀌는 것을 볼 사람이 없다(노트 M3).
  • 공유 상태가 정말 필요하면 이름 붙은 장치 하나, atom(12장)을 쓴다.

복사의 결과를 직접 보자.

fn make():
  x = 1
  f = () => x
  x = 2
  [f(), x]
;;

print(make())
[1, 2]

f가 만들어진 순간 x는 1이었다. 그 뒤의 x = 2는 f가 가진 1에 닿지 않는다.

  • 컴파일러는 람다를 adder의 자식 원형(== <lambda> ==)으로 따로 컴파일하고, 그 원형에 "무엇을 붙잡는가" 목록(captures)을 적어 둔다. 여기서는 "만드는 프레임의 슬롯 0"(n) 하나다.
  • 실행 중 adder의 CLOSURE 0은 자식 원형 0번을 꺼내 그 목록대로 값을 복사해 Closure{원형, 붙잡은 값들, 전역 표}를 만든다(crates/fung-vm/src/vm.rs의 make_closure).
  • 람다 안의 LOADCAPTURED 0은 실행 중인 클로저의 붙잡은 값 0번을 읽는다. 바깥 프레임이 이미 사라졌어도 상관없다. 값은 클로저 안에 있다.

붙잡는 출처는 네 가지다(fung-front의 tree::CaptureKind).

종류어디서 복사하나예
Local만드는 프레임의 슬롯adder의 n
Captured만드는 클로저가 이미 붙잡은 값x => y => x + y + n의 안쪽 람다가 보는 n
SelfFn만드는 프레임의 클로저 자신람다 안에서 바깥 함수 이름을 부를 때
Global그 순간의 파일 변수최상위에서 만든 람다가 보는 최상위 변수

두 겹 안쪽의 람다가 바깥의 바깥 변수를 쓰면 붙잡기 사슬이 생긴다. 가운데 람다가 그 값을 먼저 붙잡아 두고, 안쪽 람다는 가운데 람다의 붙잡은 값에서 다시 복사한다. 이름이 어느 칸에서 오는지는 6장의 이름 해석이 이미 정해 두었으므로, 실행 중에는 번호만 따라가면 된다.

자기 자신 부르기

함수가 자기를 부를 때는 한 가지 문제가 있다. 블록 안에서 fn go(…) = … go(…)를 만드는 순간, 이름 go가 들어갈 슬롯은 아직 비어 있다. 클로저를 다 만든 뒤에야 저장되기 때문이다. 복사할 값이 없다. 그래서 자기 참조는 슬롯이 아니라 "지금 실행 중인 클로저를 올려라"라는 명령 LOADSELF 하나로 푼다.

fn countdown(n):
  fn go(i, acc) = i == 0 then acc else go(i - 1, acc + [i])
  go(n, [])
;;

최상위 함수와 전역

파일 최상위의 fn은 끌어올려진다(hoisting). 이름 해석이 최상위 fn을 먼저 모아 전역 번호를 붙이고, 파일 본문의 맨 앞에서 CLOSURE·STOREGLOBAL로 만든다. 그래서 정의보다 위에서 불러도 되고, 두 함수가 서로를 불러도 된다.

그 대신 최상위 fn은 어떤 최상위 문장보다 먼저 만들어진다. "만들어질 때 보이는 변수를 복사한다"는 규칙대로라면 복사할 최상위 변수가 하나도 없다. 그런데 설정값 하나를 함수마다 인자로 넘기라고 하면 불편하다. 그래서 규칙을 하나 더 두지 않고 관찰 하나를 썼다. 최상위에서 한 번만 대입되는 이름은 바뀌지 않는다. 그런 이름은 상수와 같으므로, 이름 해석이 그 전역 칸을 미리 잡아 두고 최상위 fn이 부를 때 LOADGLOBAL로 읽게 한다(2026-10-20 검토의 결정 L9).

꼬리 호출

1 + f(n)에서 f(n)을 부른 뒤에도 할 일이 남는다(1 +). 반면 f(n)이 함수의 마지막에 오고 그 결과를 그대로 돌려줄 뿐이면, 부른 쪽 프레임에는 더 할 일이 없다. 이런 자리를 꼬리 위치(tail position)라고 하고, 거기서 하는 호출을 꼬리 호출이라고 한다.

꼬리 호출이라면 부른 쪽 프레임을 남겨 둘 이유가 없다. 새 프레임을 쌓는 대신 지금 프레임을 다시 쓰면 재귀가 아무리 깊어도 스택이 자라지 않는다. 이것을 꼬리 호출 최적화(TCO, tail call optimization)라고 한다. 함수형 언어에서는 반복문 대신 재귀를 쓰므로 이것이 사실상 필수다.

다른 언어는
  • Scheme은 언어 명세가 꼬리 호출 최적화를 요구한다. Lua도 "proper tail call"을 보장한다.
  • CPython은 하지 않는다. 재귀 깊이 기본 한도는 1,000이고, 넘으면 RecursionError다. 귀도 반 로섬은 에러의 호출 경로가 사라지는 것을 이유로 들었다.
  • JavaScript는 ES2015 명세에 들어갔지만 실제로 구현한 엔진은 Safari의 JavaScriptCore 정도다.
  • JVM은 바이트코드 수준에서 지원하지 않아서, Scala·Clojure는 자기 재귀만 반복문으로 바꾸는(@tailrec, recur) 길을 따로 둔다.
fung의 선택: 꼬리 위치의 호출은 모두 TAILCALL

fung은 함수형 언어이고 반복문 대신 재귀와 fold를 쓴다. 그래서 꼬리 호출 최적화는 처음부터 요구 사항이었다(설계 03). 트리를 직접 도는 인터프리터 대신 바이트코드 VM을 고른 이유 중 하나도 "꼬리 호출 최적화가 VM 쪽이 자연스럽다"였다(부록 내부 구조). 대가로 생기는 "호출 경로에서 사라진 프레임"은 횟수로 보여 준다.

컴파일러는 트리를 내려가며 tail 표시를 함께 넘긴다(crates/fung-front/src/compiler.rs). 함수 본문의 마지막 식은 꼬리이고, if·then … else의 두 갈래는 꼬리를 물려받으며, return의 피연산자도 꼬리다. 연산자의 피연산자와 호출의 인자는 꼬리가 아니다. 꼬리 위치의 호출은 CALL 대신 TAILCALL이 된다.

fn count(n, acc) = n == 0 then acc else count(n - 1, acc + 1)
fn depth(n) = n == 0 then 0 else 1 + depth(n - 1)

반환 타입과 꼬리 호출

반환 타입을 적은 함수(-> int)는 돌아오는 값을 CHECKRETURN으로 검사해야 한다. 그러려면 그 함수의 프레임이 남아 있어야 하므로, 다른 함수를 부르는 꼬리 호출은 CALL이 된다. 다만 자기 자신을 부르는 꼬리 호출은 예외 없이 TAILCALL로 남는다. 자기를 부른 값은 결국 같은 함수의 끝에서 같은 검사를 받기 때문이다(검토 결정 T4). 그래서 fn count(n, acc) -> int = …도 백만 번 돈다.

정리 장치와 꼬리 호출

많은 언어에 "이 함수가 끝날 때 이것을 실행하라"는 defer나 finally가 있다. fung은 defer를 두지 않았다. 할 일을 프레임에 매달면, 꼬리 호출이 그 프레임을 다시 쓰는 순간 매달린 일이 갈 곳을 잃는다(background.md). 정리는 평범한 내장 함수 with(acquire, use, release) 하나가 맡는다. 14장에서 자세히 본다.

반복문 안의 클로저

map(1..n + 1, i => () => i * 10)은 람다 셋을 담은 리스트를 만든다. 이것을 하나씩 불러 [10, 20, 30]이 나오는지 확인하고, JavaScript의 var 반복문 함정이 fung에서 왜 생기지 않는지 설명해 보자. 그리고 [x, ...rest] 패턴으로 리스트의 합을 구하는 함수를 꼬리 재귀로 써서 원소 20만 개짜리 리스트에서 돌려 보자.

풀이 보기 
fn makers(n):
  fs = map(1..n + 1, i => () => i * 10)
  map(fs, f => f())
;;

fn total(xs, acc) = match xs:
  []           => acc
  [x, ...rest] => total(rest, acc + x)
;;

print(makers(3))
print(total(map(0..200000, i => 1), 0))
[10, 20, 30]
200000

i => () => i * 10의 안쪽 람다는 만들어지는 순간의 i를 복사한다. map은 원소마다 바깥 람다를 새로 부르고, 그때마다 i는 그 원소의 값이다. 공유할 변수가 없으니 마지막 값만 보는 일이 없다. total의 재귀 호출은 꼬리 위치라서 TAILCALL이 되고, 20만 번 돌아도 프레임은 하나다.

정리

  • 함수 호출은 프레임 하나를 쌓는다. 프레임은 원형, 다음 명령 번호(ip), 슬롯의 시작(base), 실행 중인 클로저, 모듈 전역을 든다. 프레임과 값 스택은 힙의 배열이라 fung의 재귀는 Rust의 재귀가 아니다.
  • CALL n의 피연산자는 위치 인자 수와 이름 인자 수를 담는다. 개수가 맞는 위치 인자는 그 자리에서 슬롯이 되고, 나머지는 bind_args가 배치한다. 내장 함수도 같은 규약을 쓴다.
  • 기본값은 함수 서두의 JUMPIFSET이다. 빈 칸(None)과 nil은 다르다.
  • 클로저는 코드와 붙잡은 값의 묶음이다. fung은 만들어질 때 보이는 값을 복사하므로 upvalue 상자가 없다. 자기 참조는 LOADSELF다.
  • 최상위 fn은 끌어올려지고 최상위 변수를 복사할 수 없다. 한 번만 대입되는 이름만 LOADGLOBAL로 읽는다(비어 있으면 E0809).
  • 꼬리 위치의 호출은 TAILCALL이 되어 프레임을 다시 쓴다. 꼬리가 아닌 재귀는 100,000단계에서 E0804다.
