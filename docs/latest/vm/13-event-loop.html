이벤트 루프와 스레드 풀

소켓과 외부 명령은 kqueue·epoll 이벤트 루프 위에서, 파일과 이름 조회와 정규식 컴파일은 스레드 풀에서 기다린다. 어느 쪽이든 fung 값은 실행 스레드를 떠나지 않고, 그것을 Rust 타입이 지킨다.

  • 이벤트 루프: select에서 kqueue·epoll까지, 준비 상태 기반과 완료 기반
  • 소켓 연산을 "한 번 해 보고, 막히면 등록하고, 깨어나면 처음부터 다시" 하는 방식
  • 스레드 풀이 맡는 일, 그리고 취소될 때 일을 버리는가 기다리는가
  • 외부 명령의 끝과 파이프 셋을 함께 기다리는 법
  • fung 값이 실행 스레드에만 산다는 규칙과 그것을 지키는 Send·Sync

운영체제를 기다리는 일

12장의 주차는 다른 태스크를 기다릴 때의 이야기였다(채널, await). 실제 프로그램은 운영체제도 기다린다.

  • 소켓에 데이터가 올 때까지(read), 상대가 받을 자리가 날 때까지(write), 새 연결이 올 때까지(accept)
  • 외부 명령이 끝날 때까지, 그 명령의 출력이 나올 때까지
  • 파일을 읽거나 쓰는 동안, 디렉터리를 훑는 동안
  • 호스트 이름을 IP 주소로 바꾸는 동안(이름 조회, DNS)

이런 시스템 호출은 보통 막힌다(blocking). 답이 올 때까지 그 호출을 한 스레드가 돌아오지 않는다. 운영체제 스레드마다 태스크 하나라면 상관없다. 그 스레드만 잔다. 하지만 fung은 실행 스레드 하나가 모든 태스크를 돈다(12장). 한 태스크가 read에서 막히면 모든 태스크가 멈춘다. 그래서 M:1 런타임에는 운영체제를 기다리는 두 가지 장치가 필요하다.

  1. 이벤트 루프. 막히지 않는 모드로 시스템 호출을 하고, "준비되면 알려 달라"고 운영체제에 등록한 뒤 다른 일을 한다. 소켓과 파이프처럼 운영체제가 준비 상태를 알려 줄 수 있는 것에 쓴다.
  2. 스레드 풀. 준비 상태를 알 수 없는 것(일반 파일은 언제나 "준비됨"으로 보이지만 실제로는 디스크를 기다린다, 이름 조회 함수는 막히는 함수뿐이다)은 다른 운영체제 스레드에 맡기고 결과를 기다린다.
다른 언어는
  • Node.js의 libuv가 거의 같은 구조다. 소켓은 epoll·kqueue(Windows는 IOCP) 이벤트 루프에서, 파일 시스템·이름 조회(getaddrinfo)·일부 암호 연산은 스레드 풀(기본 4개)에서 돌린다.
  • Python의 asyncio도 소켓은 selectors 모듈(epoll·kqueue)로 기다리고, 막히는 일은 run_in_executor로 스레드 풀에 넘긴다.
  • Rust의 tokio는 mio라는 크레이트로 epoll·kqueue를 감싸고, 막히는 일은 spawn_blocking의 스레드 풀에 맡긴다.

이벤트 루프

select에서 epoll·kqueue로

오래된 방법은 select와 poll이다. "이 fd(파일 디스크립터, 열린 파일·소켓의 번호) 목록 중 준비된 것이 있으면 알려 달라." 문제는 부를 때마다 목록 전체를 커널에 넘기고, 커널도 전체를 훑는다는 점이다. 연결 1만 개를 쥔 서버라면 깨어날 때마다 1만 개를 훑는다.

그래서 운영체제들은 등록을 커널에 남겨 두는 API를 만들었다. Linux의 epoll, BSD와 macOS의 kqueue다. 한 번 등록해 두면 기다릴 때는 "준비된 것만" 받는다.

운영체제가 "여러 개를 한꺼번에 기다리기"를 주는 방식은 두 갈래다.

  • 준비 상태 기반(readiness-based; kqueue, epoll): "이 fd가 읽을 수 있게 되면 알려 달라." 알림이 오면 프로그램이 직접 read한다.
  • 완료 기반(completion-based; Linux io_uring, Windows IOCP): "이 버퍼에 읽어 두고, 다 되면 알려 달라." 운영체제가 읽는 동안 버퍼를 빌려 간다.
fung의 선택: 준비 상태 기반, one-shot, libc로 직접
  • 준비 상태 기반. 완료 기반은 일이 끝날 때까지 버퍼가 커널의 것이라, 태스크가 취소돼도 버퍼를 바로 놓을 수 없다. 그리고 macOS에는 완료 기반이 없다(노트 R7-scheduler의 R4a, 스펙 15절).
  • one-shot 등록. 알림이 한 번 오면 그 등록은 잠든다. 기다리던 태스크가 시스템 호출을 다시 해 보고, 여전히 막힐 때만 다시 등록한다. 그래서 아무도 기다리지 않는 fd가 루프를 깨우는 일이 없고, 알림 하나를 두 기다림이 나눠 받는 일도 없다.
  • libc로 직접 감싼다. 이벤트 루프 크레이트(mio)를 쓰지 않고 kqueue와 epoll을 같은 작은 API 뒤에 숨겼다(스펙 2절). fung은 의존성을 허용 목록으로 최소화하고, 운영체제 접근은 libc 하나로 한다.

그 작은 API는 crates/fung-vm/src/vm/poller.rs의 Poller다. 등록(register), 해제(deregister), 시간 제한 있는 기다림(wait), 다른 스레드에서 깨우기(Waker) 넷이다. 아래에 운영체제마다 한 파일이 있다(poller/kqueue.rs, poller/epoll.rs). kqueue는 (fd, 방향)마다 따로 등록되므로 한 연결의 읽기 기다림과 쓰기 기다림이 저절로 갈린다. epoll은 fd마다 등록이 하나뿐이라, 두 방향의 토큰을 따로 쥐고 알림이 오면 남은 방향을 다시 건다.

토큰: fd 번호는 다시 쓰인다

fd 번호는 닫히면 곧바로 다른 소켓이 가져간다. 등록을 fd 번호로 찾으면, 닫힌 연결을 기다리던 태스크가 새 소켓의 알림에 깨어날 수 있다. 그래서 fung은 주차할 때마다 새 토큰(번호)을 붙여 등록하고, "토큰 → (깨움 표시, fd)" 표(World::io)에 넣는다.

  • 기다림이 끝나면(알림, 기한, 취소, 다른 깨움) 토큰을 표에서 뺀다. 표에 없는 토큰의 알림은 버린다.
  • 소켓을 닫을 때는 그 fd의 등록을 먼저 지우고 기다리던 태스크를 깨운 뒤에 fd를 닫는다(drop_io_waits). 등록이 fd보다 오래 살지 않는다.

잠든 스케줄러 깨우기

할 일이 없으면 실행 스레드는 이벤트 루프의 wait 안에서 잔다(12장 스케줄러의 7단계). 그런데 스레드 풀의 일, 표준 입력 읽기 스레드, 신호 스레드는 루프 밖에서 태스크를 깨운다. 그 깨움은 루프의 깨우개를 당겨서 전한다. macOS는 kqueue의 EVFILT_USER, Linux는 eventfd다.

"자려는 순간 온 깨움"을 잃지 않는 순서는 12장의 잃어버린 깨움과 같은 모양이다.

  1. 실행 스레드는 대기열 잠금 아래에서 "비었음"을 확인하고 sleeping 표시를 세운다. 잠금을 풀고 루프에서 기다린다.
  2. 깨우는 쪽은 같은 잠금 아래에서 번호를 넣고, sleeping이면 깨우개를 당긴다.
  3. 깨우개는 기다리기 전에 당겨져도 남아 있다가 다음 기다림을 곧바로 끝낸다.

입출력을 기다리는 태스크가 있을 때는 자지 않을 때도 루프를 본다. 누가 차례를 넘겼을 때와 256바퀴마다(POLL_EVERY) 시간 제한 0으로 본다. 처음에는 매 바퀴 봤는데, 한 번이 시스템 호출 하나라서 소켓 기다림이 하나만 있어도 채널 주고받기가 25배 느려졌다(노트 R7-scheduler의 R4a 7절).

소켓 연산: 다시 해 보기

read_line(conn)처럼 막힐 수 있는 소켓 연산은 어떻게 주차하나. 운영체제 스레드였다면 "읽고, 막히면 기다리고, 이어서 읽는다"는 직선 반복이면 됐다. 기다림이 Rust 스택 위에 있었기 때문이다. M:1에서는 Rust 함수 한가운데서 기다릴 수 없다(12장).

fung은 연산을 상태 기계로 다시 쓰는 대신 처음부터 다시 해 보기로 했다(crates/fung-vm/src/native/net.rs).

  1. 연산을 한 번 해 본다(Attempt). 소켓은 막히지 않는 모드라서 막힐 자리에서 곧바로 "지금은 안 됨"(EAGAIN)을 받는다.
  2. 그러면 "이 fd를 이 방향으로 기다려야 한다"고 말하고 그대로 돌아온다(wait_io).
  3. 내장 함수는 그 fd를 새 토큰으로 루프에 등록하고 주차한다(vm/block.rs의 park_io).
  4. 준비되면 깨어나 연산을 처음부터 다시 한다(run_io).

처음부터 다시 해도 안전한 이유는, 그때까지 한 일이 Rust 스택이 아니라 다른 곳에 남아 있기 때문이다. 읽은 바이트는 연결의 버퍼에, 쓴 바이트 수는 내장 함수의 상태에, 어느 주소까지 연결해 봤는지와 TLS 핸드셰이크 상태는 연결 객체와 rustls 안에 있다. Rust의 Future::poll이 Pending을 돌려주는 방식과 같은 생각이다. 다만 상태를 컴파일러가 만들어 주지 않으므로, 무엇을 다시 해도 되는지는 사람이 지킨다.

한 연결을 두 태스크가 함께 읽으면 어떻게 되나. 읽는 쪽과 쓰는 쪽은 각각 차례 줄(Turnstile)이 있어서 한 번에 한 연산만 차지하고, 다음 연산은 주차해서 기다린다. Mutex로 기다리면 실행 스레드 전체가 멈추기 때문이다. 이 기다림도 주차라서 기한과 취소에 끊긴다.

결과는 이렇다. 한 프로그램이 HTTP 연결 2,000개를 동시에 쥐어도 운영체제 스레드는 넷이다(노트 R7-scheduler의 R4a 10절). 그 전 구현(기다림마다 스레드 하나)은 같은 시험을 60초 안에 준비하지 못했다. 아래는 같은 프로그램 안에서 서버를 띄우고 요청 셋을 동시에 보내는 예다. 느린 요청이 300 ms를 쉬는 동안 나머지 둘이 먼저 답을 받는다.

import conc
import http

fn slow():
  sleep(300ms)
  "slow done"
;;

fn handler(req) = req.path == "/slow" then slow() else "fast ${req.path}"

(port_tx, port_rx) = channel(1)
scope(fn(s):
  spawn(s, () => http.serve("127.0.0.1:0", handler, ready: a => send(port_tx, a)!))
  addr = recv(port_rx)!
  urls = map(["/slow", "/a", "/b"], p => "http://${addr}${p}")
  print(conc.pmap(urls, u => http.get(u)!.body))
  request_stop()
;;)
print("server drained")

검사만 하는 예제다. 아래 출력은 페이지를 만들 때 확인하지 않은 예상 출력이다.

["slow done", "fast /a", "fast /b"]
server drained

conc.pmap은 결과를 입력 순서대로 모은다. request_stop()은 14장의 정지 요청이다. 서버가 그것을 보고 리스너를 닫은 뒤 범위가 닫힌다.

스레드 풀

왜 풀인가

파일을 읽는 일은 이벤트 루프로 기다릴 수 없다. 일반 파일의 fd는 언제나 "준비됨"으로 보고되지만 실제 read는 디스크를 기다리며 막힌다. 이름 조회(getaddrinfo)는 막히는 함수만 있다. 이런 일은 다른 운영체제 스레드에서 해야 한다.

처음(R1b)에는 일마다 스레드를 새로 만들었다. 스레드 하나를 만들고 거두는 데 십몇 µs가 들어서, fs.exists를 5만 번 부르는 반복이 2.6배 느려졌다. 그래서 스레드를 만들어 두고 다시 쓰는 풀(pool)을 두었다(crates/fung-vm/src/vm/pool.rs).

  • 일이 들어왔을 때 노는 스레드가 없고 64개 미만이면 하나 더 만든다(POOL_MAX).
  • 64개가 다 바쁘면 일은 FIFO 줄에서 기다린다.
  • 10초 동안 일이 없는 스레드는 끝난다(POOL_IDLE). 런타임이 사라지면 노는 스레드는 곧바로 끝난다.

풀에서 도는 일(job)은 fung 값이 아닌 평범한 데이터만 가진다(Send + 'static). 경로 문자열을 복사해 가고, 파일 핸들은 Arc를 복제해 간다. 태스크는 그동안 주차하고, 일을 마친 스레드가 결과를 칸에 넣고 태스크를 깨운다. 결과를 fung 값으로 바꾸는 마무리는 실행 스레드에서 돈다(crates/fung-vm/src/vm/offload.rs의 offload_kind).

import fs
import path

fn double(x) = x * 2

fs.with_temp_dir(fn(dir):
  p = path.join(dir, "n.txt")
  fs.write(p, "21\n")!
  n = int(trim(fs.read(p)!))
  print(double(n))
  print(fs.exists(p), fs.exists(path.join(dir, "nope")))
;;)
42
true false

이 짧은 스크립트에서도 fs.write, fs.read, fs.exists, 임시 디렉터리 만들기와 지우기가 모두 풀의 일이다. 그동안 다른 태스크가 있었다면 그 태스크가 돌았을 것이다. 대가는 호출 하나의 왕복 비용이다. 파일 시스템 호출 하나가 약 9 µs다. 0.2.0은 태스크의 스레드가 그 자리에서 시스템 호출을 했으므로 하나씩 차례로 부르는 반복은 그때가 더 빨랐다(bench/fs.fung 0.082초 → 0.446초). 대신 파일을 기다리는 동안 다른 태스크가 돈다. 한 호출의 지연과 동시에 쥘 수 있는 일의 수는 함께 좋아지기 어렵다.

버리는 일과 기다리는 일

운영체제 스레드는 시스템 호출 도중에 멈출 수 없다. 그래서 기한이 지나거나 취소가 오면 "일을 끊는다"는 것은 태스크만 놓아준다는 뜻이다. 그런데 모든 일을 그렇게 놓아 버리면, timeout(1s, () => fs.write(p, x))가 시간 초과를 돌려준 뒤에 파일이 써질 수 있다. 재시도나 정리 코드와 경쟁하게 된다. 그래서 일을 둘로 나눴다(스펙 15절, 노트 R7-scheduler의 R3).

종류예취소·기한이 오면
버리는 일 (offload_abandoning)경로만 읽는 fs.read·list·glob·walk·exists·stat, 정규식 컴파일, 이름 조회태스크는 곧바로 되감는다. 일은 풀에서 끝까지 돌고 결과는 그 스레드에서 버린다
기다리는 일 (offload)쓰기·지우기·옮기기, 핸들 열기·닫기·읽기(읽은 만큼 위치가 옮겨지므로)이미 돌고 있으면 끝까지 기다린 뒤 되감는다

줄에서 아직 시작하지 않은 일은 종류와 상관없이 버린다. 일마다 표(Ticket)가 있고 상태는 "줄에 있음 / 도는 중 / 버려짐" 셋이다. 풀 스레드는 꺼낼 때 "줄에 있음 → 도는 중"을, 태스크는 "줄에 있음 → 버려짐"을 원자적 비교 후 교체로 시도한다. 둘이 동시에 와도 하나만 이긴다.

풀에 넣지 않는 것

소켓 기다림과 외부 명령은 풀에 넣지 않는다. 풀에 넣으면, 같은 프로그램 안의 HTTP 서버에 느린 클라이언트 64개가 붙었을 때 풀이 꽉 차고, 서버의 accept 일이 줄 뒤에서 영영 돌지 못한다. 교착 판정에도 보이지 않는 멈춤이다. "한정된 자원(스레드 64개)을 서로를 기다리는 일끼리 나눠 쓰면 교착이 생긴다"는 것은 스레드 풀을 쓰는 런타임이 늘 부딪히는 문제다. fung은 "다른 태스크가 끝내 줄 수 있는 기다림"을 풀에 넣지 않는 식으로 피했다. 파일과 정규식 컴파일은 fung 쪽 일에 기대지 않고 스스로 끝난다(노트 R7-scheduler의 R3 2절).

외부 명령

exec·sh로 띄운 명령도 이벤트 루프 위에서 기다린다. 처음에는 명령 하나에 스레드 넷을 썼다. 끝을 기다리는 스레드, 표준 출력을 읽는 스레드, 표준 에러를 읽는 스레드, 표준 입력을 넣는 스레드다. 출력 둘을 따로 읽어야 했던 이유가 있다. 한쪽만 읽으면 명령이 다른 쪽 파이프(버퍼는 64 KB 남짓)를 채운 채 멈추고, 우리는 명령이 끝나기를, 명령은 우리가 읽기를 기다리는 교착이 된다.

지금은 상자 하나(CommandWait, crates/fung-vm/src/native/process.rs)가 명령의 끝과 파이프 셋을 한꺼번에 루프에 등록한다. 깨어날 때마다 할 수 있는 만큼 읽고 쓰고, 끝났으면 거두고, 아직 올 것만 다시 등록한다. 셋을 동시에 보므로 위의 교착이 생기지 않는다. 명령의 끝을 루프에서 아는 법은 운영체제마다 다르다.

  • macOS: kqueue의 EVFILT_PROC에 pid를 직접 등록한다.
  • Linux 5.3 이상: pidfd_open(pid)이 주는 fd는 프로세스가 끝나면 읽을 수 있게 된다. 소켓처럼 epoll에 등록한다.
  • 더 오래된 Linux: 풀의 일 하나가 waitid로 기다렸다가 태스크를 깨운다.

출력을 아주 빨리 쏟는 명령 옆의 태스크가 굶지 않게, 한 번 볼 때 256 KiB까지만 옮기고 다시 주차한다(PUMP_BUDGET). 명령 50개를 동시에 기다려도 스레드는 다섯이다.

scope(fn(s):
  spawn(s, fn():
    r = exec(["sh", "-c", "sleep 0.3; echo deployed"])!
    print("cmd:", trim(r.out))
  ;;)
  spawn(s, () => each(1..4, i => print("other task:", i)))
;;)
other task: 1
other task: 2
other task: 3
cmd: deployed

첫 태스크가 명령을 기다리며 주차하는 동안 두 번째 태스크가 돈다.

표준 입력

표준 입력은 이벤트 루프에 올리지 않는다. fd 0에 "막히지 않는 모드"(O_NONBLOCK)를 켜면, 같은 열린 파일을 나눠 쓰는 부모 셸과 다른 프로세스에도 그 모드가 걸리기 때문이다(스펙 15절). 대신 읽기 전용 스레드 하나가 있다(crates/fung-vm/src/vm/stdin.rs).

  • 처음 읽을 때 생긴다. 대부분의 프로그램은 표준 입력을 읽지 않는다.
  • 어떤 태스크가 줄을 기다리고 줄 큐가 비었을 때만 읽는다. 그래서 프로그램이 달라고 하지 않은 입력은 그대로 남아, 셸에서 fung 다음에 오는 명령이 읽을 수 있다.
  • 읽은 줄을 큐에 넣고 기다리는 태스크를 깨운다. 바이트만 다루고, fung 문자열로 바꾸는 일은 실행 스레드에서 한다.

다른 스레드가 할 수 있는 일은 태스크 번호를 실행 대기열에 넣거나 사건을 게시하고 깨우개를 당기는 것뿐이다. 그래서 fung 값은 원자적이지 않은 Rc로 공유해도 된다(10장).

이 규칙을 사람이 지키면 언젠가 틀린다. Rust는 타입마다 두 가지를 따진다.

  • Send: 이 값을 다른 스레드로 옮겨도 된다.
  • Sync: 이 값을 여러 스레드가 함께 빌려도 된다.

컴파일러가 구성 요소를 보고 스스로 판단한다. Rc는 계수를 원자 연산 없이 세므로 둘 다 아니다. fung 값은 Rc로 이뤄져 있으므로 값을 품은 것은 모두 !Send다. fung은 이것을 그대로 쓴다(노트 R7-scheduler의 R5).

  • 값을 품은 런타임 상태 World는 Runtime 안의 RefCell에 있다. 그래서 Runtime은 !Send이고, 컴파일러가 그것을 다른 스레드로 옮기는 코드를 거절한다.
  • 다른 스레드가 보는 것은 Shared뿐이다. 실행 대기열, 이벤트 루프, 풀, 정지 표시, 취소 루트처럼 원래 스레드에 안전한 것만 들어 있어서 unsafe 없이 Send + Sync다.
  • 풀의 일은 Send + 'static이어야 컴파일된다. fung 값을 실수로 넘기면 빌드가 실패한다.

처음 Rust 런타임(태스크마다 스레드)은 값을 품은 World를 잠금 하나로 감싸고, "잠금을 쥔 스레드만 값을 만지므로 안전하다"는 약속을 unsafe impl Send로 컴파일러에게 손으로 적었다. M:1이 되면서 그 약속이 구조로 지켜지게 되었고, 마지막 단계(R5)에서 그것을 타입으로 드러내 손으로 쓴 unsafe impl Send·Sync를 0개로 만들었다. 저장소 시험이 다시 생기지 않게 지킨다.

다른 언어는
  • CPython은 GIL이 참조 계수를 지킨다. GIL을 없앤 free-threaded 빌드는 참조 계수를 스레드에 안전하게 세는 장치를 따로 들여야 했다.
  • JavaScript의 Web Worker와 Node.js의 worker_threads는 힙을 아예 따로 두고, 메시지로 값을 복사해 보낸다.
  • Erlang도 프로세스마다 힙이 따로이고 메시지를 복사한다(큰 바이너리만 공유).
  • fung이 여러 코어로 간다면 이 길(태스크마다 힙, 경계에서 복사)을 따를 것이 설계에 적혀 있다(설계 05). 불변 값이라 프로그램은 공유와 복사의 차이를 볼 수 없다.

열린 파일 수

연결마다 fd 하나다. 셸에서 띄운 프로그램은 열린 파일의 소프트 한도가 256인 경우가 많아서, 스레드 문제를 풀어도 수백 연결에서 too many open files에 걸린다. 그래서 fung은 시작할 때 소프트 한도를 하드 한도까지 올리고(macOS는 kern.maxfilesperproc, Linux는 fs.nr_open을 넘지 않게), 자식 프로세스에는 원래 값을 돌려 넘긴다(crates/fung-vm/src/rlimit.rs). select()를 쓰는 옛 프로그램이 1024 넘는 fd에서 깨지지 않게 하려는 것이다.

서버 셋을 동시에 점검하기

sh -c "sleep 0.5; echo web1 ok" 같은 명령을 서버 셋에 대해 부르는 점검 함수가 있다. 하나씩 부르면 1.5초, 동시에 부르면 0.5초 남짓이다. 전체 기한 1.2초를 걸어서, 동시에 부르면 결과 리스트가, 하나씩 부르면 시간 초과가 나오는지 확인해 보자. 그동안 운영체제 스레드는 몇 개가 필요했을까?

풀이 보기 
import conc

hosts = ["web1", "web2", "web3"]

fn check(h) = trim(exec(["sh", "-c", "sleep 0.5; echo ${h} ok"])!.out)

print(timeout(1200ms, () => conc.pmap(hosts, check)))
print(timeout(1200ms, () => map(hosts, check)))
["web1 ok", "web2 ok", "web3 ok"]
Err({kind: 'timeout})

conc.pmap은 원소마다 태스크를 띄운다. 각 태스크는 명령을 띄우고 그 끝과 출력 파이프를 이벤트 루프에 등록한 뒤 주차한다. 명령 셋이 동시에 돌아도 기다리는 데 스레드가 더 들지 않는다. 기다림은 실행 스레드 하나가 이벤트 루프에서 한꺼번에 한다. 하나씩 부르는 map은 1.2초 기한에 걸려 Err({kind: 'timeout})이 되고, 기한이 왔을 때 돌던 명령은 SIGTERM을 받아 끝난다(14장).

정리

  • M:1 런타임에서 막히는 시스템 호출은 모든 태스크를 멈춘다. 그래서 소켓·파이프·명령의 끝은 이벤트 루프로, 파일·이름 조회·정규식 컴파일은 스레드 풀로 기다린다.
  • 이벤트 루프는 kqueue·epoll을 libc로 직접 감싼 준비 상태 기반, one-shot 등록이다. 주차마다 새 토큰을 붙여 재사용된 fd 번호의 알림을 걸러 낸다.
  • 소켓 연산은 한 번 해 보고, 막히면 fd를 등록하고 주차했다가, 깨어나면 처음부터 다시 한다. 진행 상태는 연결과 내장 함수가 쥔다.
  • 풀은 필요할 때 최대 64개, 10초 놀면 끝, 꽉 차면 FIFO다. 읽기만 하는 일은 취소 때 버리고, 무엇을 바꾸는 일은 끝까지 기다린다. 서로를 기다릴 수 있는 일은 풀에 넣지 않는다.
  • 외부 명령은 끝과 파이프 셋을 한 상자가 함께 등록한다. 표준 입력은 전용 스레드가 필요할 때만 읽는다.
  • fung 값은 실행 스레드에만 산다. Runtime은 !Send이고 다른 스레드는 값이 없는 Shared만 본다. 손으로 쓴 unsafe impl Send는 없다.
