# 다른 언어와의 성능 비교 (2026-10-21)

fung 0.4.0 이후(main `df396d0`)의 속도와 메모리를 Python·Lua·Ruby·Node와 같은 작업으로 견준 기록이다.
무엇을 쟀고, 어떻게 쟀고, 결과를 어떻게 읽는지, 그리고 그 결과에서 나온 다음 할 일을 남긴다.
다음 할 일 목록 자체는 `docs/design/open-questions.md`의 "성능" 절(P8~P13)에서 추적한다.

## 1. 왜 이렇게 쟀나

성능 비교에서 가장 흔한 실수는 "각 언어에서 가장 빠른 코드"와 "그 언어에서 보통 쓰는 코드"를 섞는 것이다.
여기서는 **그 언어로 스크립트를 쓰는 사람이 보통 쓰는 방식**으로 짰다. fung은 `fold`·`map`·`split`, Python은 `for`와
내장 함수, Node는 `for`와 `Map`, Lua는 `for`와 테이블, Ruby는 블록이다. 같은 알고리즘(한 번 훑기, 같은 자료구조
종류)을 지켰고, 다섯 언어의 출력이 모두 같아야 표에 넣는다(`run.py`가 검사한다).

작업은 fung의 용도(SRE·DevOps 스크립트)에 맞춰 네 묶음으로 골랐다.

| 묶음 | 프로그램 | 재는 것 |
|---|---|---|
| 시작 | `startup` | `print(1)`: 프로세스 시작부터 끝까지 |
| 기본 계산(core) | `fib`·`loop`·`str`·`map`·`list` | 함수 호출, 산술 반복, 문자열 잇기, 문자열 키 맵, 리스트 고차 함수와 정렬 (`bench/`의 같은 이름과 같은 크기) |
| 텍스트(text) | `text`·`regex`·`json` | 로그 20만 줄(14.5MB)을 줄·단어로 나눠 레벨별 집계, 같은 로그에서 정규식으로 숫자 뽑기, JSON 8.6MB 읽고 다시 쓰기 |
| 동시성(conc) | `chan`·`spawn` | 버퍼 없는 채널로 값 10만 개, 태스크 2,000개 띄우고 기다리기 |
| 시스템(sys) | `fs`·`exec` | `exists`+`stat` 5만 번, 외부 명령 `true` 500번 |

언어마다 다른 점(공정성에 영향을 주는 것):

- **동시성은 모델이 다르다.** Python은 asyncio(`Queue(maxsize=1)`, 태스크), Node는 Promise(채널은 손으로 짬),
  Lua와 Ruby는 코루틴·Fiber를 직접 이어 준다. Lua·Ruby 쪽에는 스케줄러가 없어서 가장 싼 경우다.
  fung은 M:1 스케줄러가 진짜 태스크를 돈다.
- **Lua 표준 라이브러리에는 정규식·JSON·`stat`이 없다.** `regex`는 Lua 패턴으로 대신했고, `json`·`fs`는 비웠다.
  `exec`는 `os.execute`라 셸을 하나 더 띄운다.
- **fung의 `text`·`regex`는 파일을 통째로 읽는다**(`fs.read` + `lines`). Python·Ruby·Lua는 한 줄씩 읽는다.
  fung으로 한 줄씩 읽으면 훨씬 느려서(3.1절) 보통 쓰는 방식이 통째 읽기다. 이 차이가 메모리 열에 그대로 보인다.
- 버전: Python 3.14.3, Lua 5.5.1(LuaJIT 아님), Ruby 2.6.10(macOS 시스템 Ruby, YJIT 없음), Node 24.13.0(V8 JIT).
  Ruby는 오래된 판이다. 3.4 + YJIT라면 호출·반복이 2~3배 빠를 수 있다.

방법: 프로그램마다 언어마다 준비 1회 뒤 7회 실행한 벽시계 시간의 중앙값, 최대 상주 메모리(RSS, `wait4`).
기계 Apple M2 Max, macOS 27, fung은 `cargo build --release --locked -p fung-cli`. 같은 날 세 번 돌려 차이는 3% 안이었다
(부하 평균 약 2.5인 상태였으므로 절대값보다 비율을 본다).

```
python3 -I bench/compare/run.py target/release/fung
```

입력 데이터는 `run.py`가 처음 돌 때 `bench/compare/data/`에 결정적으로 만든다(커밋하지 않는다).

## 3. 읽는 법: 잘하는 것과 약한 것

**잘하는 것**은 스크립트 언어의 용도에 맞는 지표들이다.

- 시작 6ms: Lua 다음, Python·Node의 약 4분의 1, Ruby의 10분의 1. 자주·짧게 도는 스크립트(cron, 훅)에서 가장 체감된다.
  시작이 빠른 이유는 prelude가 바이너리 안에 있고 컴파일이 수 ms라 캐시가 필요 없기 때문이다(open-questions "성능").
- 외부 명령: 다섯 중 가장 빠르다(Node와 비슷). 이벤트 루프가 프로세스 끝과 파이프를 함께 기다린다(R4b).
- 동시성: 채널은 Node 수준, Python asyncio의 55배. 태스크 생성은 스케줄러 없는 Lua 코루틴과 비슷하다.
  M:1 스케줄러가 주차·깨우기만 하고 운영체제 스레드를 바꾸지 않아서다(`docs/notes/R7-scheduler.md`).
- 산술 반복은 Python보다 빠르고 JIT가 있는 Node와 같다. JSON은 Python과 같다(둘 다 네이티브 파서).
- 빈 프로그램의 메모리 9MB(Python 14, Ruby 30, Node 45).

**약한 것**은 아래 프로브로 원인을 쪼갰다(같은 기계, 5회 중앙값, 프로그램은 짧은 것이라 여기 적는다).

### 3.1 파일 한 줄 읽기와 `fs` 호출: 건당 약 6~8µs

| 프로브 | 시간 |
|---|---|
| `fs.read`로 14.5MB 통째로 | 0.018 |
| 같은 파일을 `fs.with_open` + `read_line`으로 20만 줄 | 1.264 |
| 같은 내용을 표준입력 `read_lines()`로 | 0.055 |
| `fs.exists("/")` 5만 번 | 0.385 |

파일 핸들의 한 줄 읽기와 `exists`·`stat`은 **호출마다** 스레드 풀에 일을 넘기고(`nat::offload`), 실행 스레드는 그동안
태스크를 주차했다가 결과가 오면 깨운다(`native/file.rs`·`native/fs.rs` 머리 주석). 막히는 일이 실행 스레드를 붙잡지
않게 하는 올바른 설계지만, 일 자체가 1µs도 안 되는 경우 왕복 비용(채널 보내기, 풀 스레드 깨우기, 결과 돌려받기,
태스크 깨우기)이 일보다 훨씬 크다. 그래서 큰 로그를 메모리에 다 올리지 않고 흘려 읽는 길이 사실상 없다.
SRE 스크립트의 주된 작업과 정면으로 겹치므로 **가장 먼저 고칠 것**이다(P8).

고치는 방향의 후보: 한 번에 큰 덩어리(예: 64KiB)를 풀에서 읽어 와 줄은 실행 스레드에서 버퍼에서 바로 내주기
(덩어리가 바닥날 때만 왕복), 로컬 경로의 `exists`·`stat`처럼 짧은 호출은 그 자리에서 하기(느린 네트워크 파일 시스템에서
실행 스레드가 막힐 위험과 맞바꾸는 결정이라 선택지로 묻는다).

**고친 뒤 (같은 날, P8의 앞부분).** 핸들은 이미 64KiB 버퍼(`BufReader`·`BufWriter`)를 갖고 있었는데, 다음 줄이 버퍼에 다 있어도
풀에 넘기고 있었다. 이제 실행 스레드가 핸들의 잠금을 기다리지 않고 한 번 시도해(`try_lock`), 버퍼 안에 `\n`이 있으면 그 줄을
바로 꺼낸다(`native/file.rs`의 `read_buffered_line`). 쓰기도 줄이 버퍼의 남은 자리에 들어가면 바로 쓴다(`write_buffered_line`).
이 길에는 시스템 호출이 없으니 실행 스레드가 막히지 않고, 줄이 섞이지 않는 보장(잠금 하나가 한 줄을 덮음)도 그대로다.
다른 태스크의 풀 일이 잠금을 쥐고 있거나 버퍼가 바닥나면 예전처럼 풀에 간다. 한 태스크가 읽기만 돌아도 스케줄러가
명령 수로 차례를 넘기게 하므로 다른 태스크를 굶기지 않는다.

| 프로브 | 전 | 후 |
|---|---|---|
| `read_line`으로 20만 줄 | 1.232 | 0.093 |
| `fs.write_line`으로 20만 줄 | 1.244 | 0.118 |
| 로그 집계를 한 줄씩 읽어서 (시간 / 메모리) | 1.48 / 9MB | 0.45 / 9MB |
| 같은 집계를 통째로 읽어서 (`text`, 비교용) | 0.46 / 90MB | 0.45 / 92MB |

이제 큰 파일은 한 줄씩 읽는 쪽이 같은 속도에 메모리는 파일 크기와 상관없다. 비교 표(2절)의 `text`·`regex`는 같은 조건으로
다시 견주려고 통째 읽기 판을 그대로 두었다.

**`exists`·`stat` (2026-10-25, P8의 나머지).** 이 둘은 일 자체가 1µs도 안 되는데 풀 왕복이 그 몇 배다. 실행 스레드에서 바로 부르면
느린 파일 시스템(멈춘 NFS)에서 모든 태스크가 멈추므로, **태스크가 혼자일 때만** 바로 부른다(사용자 결정). 혼자라는 것은
차례를 기다리는 다른 태스크(대기열, 다른 스레드가 깨운 것, 이번 차례에 띄운 것)도, 타이머나 바깥(풀 일·소켓·외부 명령·표준 입력·정지 신호)을
기다리는 태스크도 없고, 그 태스크에 기한이 없다는 뜻이다(`vm::alone`). 채널이나 `await`에서 주차한 태스크는 이 태스크가 움직여야 깨므로
막아도 잃는 것이 없다. 이 조건이면 실행 스레드가 막혀도 붙잡히는 태스크가 없고, 끊어야 할 기한도 없다. 남는 대가는 그동안 온 정지 신호가
호출이 끝난 뒤에 처리된다는 것 하나다. 함수를 막히는 것과 아닌 것으로 나누는 안(`exists_now` 같은 짝)은 05의 "I/O는 평범한 함수 호출"과
어긋나고, 서버에서 잘못 고르면 파일 서버가 느려질 때만 드러나는 장애가 되어 기각했다.

| 프로브 (릴리스, M2 Max, 9회 중앙값) | 전 | 후 |
|---|---|---|
| `fs.exists("/")` 5만 번 | 0.404 | 0.061 |
| 비교의 `fs`(`exists`+`stat` 5만 번) | 0.447 | 0.082 (Python 0.084) |

`sys` 묶음의 기하평균이 Python 대비 0.89가 되었다. 다른 벤치마크(`chan`·`spawn`·`wait`·`exec`·계산)는 그대로다.

### 3.2 맵: Python의 3.4배

| 프로브 | 시간 |
|---|---|
| 키 20만 개 맵을 `put`으로 쌓기만 | 0.305 |
| 키 4개 맵을 20만 번 `get`+`put` | 0.138 |
| 같은 횟수의 빈 `fold` | 0.014 |

맵은 영속 구조라 `put`마다 경로를 복사한다. 아무도 중간 결과를 볼 수 없는 `fold` 누적 중에 제자리 수정(transient)하는
것은 open-questions에 이미 있는 항목이고, 이번 측정으로 우선순위가 올라갔다(P9). 작은 맵의 갱신도 건당 약 0.6µs다.
`get`이 fung으로 쓴 prelude 함수(`match type_of(m)` → `in` → 인덱스, 명령 여러 개)인 것도 몫이 있다.
(2026-10-24 덧붙임: `get`은 보수 작업에서 네이티브로 옮겼다. 같은 꼴의 `get`+`put` 20만 번이 0.11 → 0.08초.)

**고친 뒤 (2026-10-25, P9).** 프로파일을 보니 시간의 대부분이 HAMT 노드 복사(`Rc::make_mut`의 복제)와 옛 판의 해제였다.
제자리 수정 장치는 이미 있었는데 쓰이지 않았다. `(m, i) => put(m, k, i)`에서 `put`이 받는 맵을 지역 변수 `m`도 문장이 끝날 때까지 쥐어
참조 수가 늘 2였기 때문이다(03의 L7 규칙: 마지막으로 읽는 **문장 뒤**에 놓음). 그래서 지역 변수의 **마지막 읽기는 값을 넘기게** 했다(새 명령 `MOVELOCAL`,
컴파일러가 함수 본문을 평가 순서의 뒤에서 앞으로 걷는 생존 분석, `compiler/moves.rs`). Rust의 move, Koka·Lean의 "functional but in-place"와 같은 생각이다.

| 프로브 (릴리스, 9회 중앙값) | 전 | 후 |
|---|---|---|
| 비교의 `map`(쌓기 20만 + 찾기 20만) | 0.380 | 0.193 (Python 0.110) |
| `bench/map.fung` | 0.380 | 0.193 |

`core` 묶음의 기하평균이 Python 대비 1.51 → 1.31이 되었다. 다른 벤치마크는 그대로다.

### 3.3 텍스트 경로의 군살

| 프로브 | 시간 |
|---|---|
| 통째 읽기 + `split(_, "\n")` | 0.044 |
| 통째 읽기 + `lines` | 0.086 |
| 20만 줄마다 `split(l, " ")` | 0.179 (줄당 약 0.65µs) |
| `regex.find` 20만 번 | 0.208 |
| `regex.is_match` 20만 번 | 0.055 |

- `lines`는 prelude의 fung 함수(`split` 뒤 줄마다 `_chomp` 람다)라 날 `split`의 두 배다. 네이티브로 옮길 후보(P10).
  → 2026-10-25 옮김: 0.080 → 0.034초(같은 파일의 날 `split` 0.042초보다 빠르다: 끝의 빈 조각을 만들지 않고, 줄마다 `\r`을 떼는 것도 복사 없이 한다).
  비교의 `text` 0.375 → 0.336, `regex` 0.307 → 0.265초. `split`을 프로파일하면 시간이 조각마다의 할당 두 번(`Rc<String>`)과
  네이티브 호출마다 인자를 모으는 `Vec`에 든다. 값 표현과 호출 규약을 바꾸는 일이라 이번에는 하지 않았다.
- `regex.find`는 맞을 때마다 맵 두 개(`{text, start, end, groups, named}`, `named`)와 리스트를 만들고, 바이트 위치를
  글자 위치로 센다(`native/regex.rs`의 `match_value`). 컴파일은 캐시되므로 원인이 아니다. 그룹 하나만 필요한 흔한 경우를
  위한 싼 길(필드를 늦게 만들기, 또는 그룹만 돌려주는 함수)을 검토한다(P11).
  → 2026-10-25 API는 그대로 두고 할당만 줄였다: 키 다섯(`Rc` 상자와 버퍼 열 개)과 빈 `named` 맵을 실행 스레드마다 한 번 만들어 나눠 쓰고,
  결과 맵의 자리를 미리 잡는다. 20만 줄의 `find` 0.242 → 0.179초(`is_match` 0.081), 비교의 `regex` 0.266 → 0.200초.
  다시 프로파일하면 남은 시간의 대부분이 정규식 엔진의 캡처 검색(one-pass DFA)이라, 새 함수를 더할 이유는 아직 없다.

### 3.4 함수 호출: Python의 1.9배, Lua의 6배

`fib`는 호출이 전부인 프로그램이다. 0.2.0 때 기록(`bench/README.md`, 0.201초)보다 지금(0.226초)이 약 12% 느려서
퇴행인지 확인했다(P12). 호출 자체를 크게 줄이는 일은 open-questions의 레지스터 VM·인라인 캐시 항목이다.

`fs`의 남은 왕복은 P8의 나머지(`exists`·`stat`)다(2026-10-25에 고침, 3.1절 끝). **새로 찾은 것은 `fib`의 0.3.0 → 0.4.0 퇴행 하나**(약 11%)이고, 나머지는 그대로다.

**어느 커밋인가.** 0.3.0과 0.4.0 사이의 코드 커밋을 각각 빌드해 `fib`만 다섯 개 바이너리를 번갈아 3바퀴(각 5회) 쟀다.

| 커밋 | `fib` 중앙값 |
|---|---|
| 0.3.0 | 0.203 |
| `b651d38` (검토의 버그 묶음) | 0.203 |
| `4372c19` (검토의 결정 묶음) | 0.227 |
| `b3803f6` | 0.225 |
| 0.4.0 | 0.226 |

**원인.** `4372c19` 전후로 `fib`의 바이트코드는 한 글자도 다르지 않다(`fung dump bytecode`, 다른 것은 `<main>` 끝의
`POP`·`CONST nil` 두 줄뿐). 그러니 컴파일러가 아니라 명령 해석 루프(`vm.rs`의 큰 `match`)가 같은 명령을 더 느리게 돈다.
그 커밋은 `fib`가 쓰는 명령(`LOADLOCAL`·`CONST`·`LT`·`SUB`·`ADD`·`CALL`·`RETURN`)을 바꾸지 않았고, 루프 안에 **거의 일어나지
않는 에러 경로를 새로 인라인으로** 넣었다. 하나는 `POP`의 버려지는 `Err` 검사(E0606)이고, 하나는 `LOADGLOBAL`의 E0808·E0809로,
이름을 찾고 문자열을 만들어 `span`을 붙인다.

인터프리터의 해석 루프는 함수 하나가 매우 커서, 갈래 하나가 커지면 컴파일러(LLVM)가 레지스터를 나누는 방식과
코드 배치가 루프 전체에서 바뀐다. 그러면 그 갈래를 지나지 않는 명령도 느려질 수 있다. 확인 실험으로 두 에러 경로를
`#[cold] #[inline(never)]` 함수로 루프 밖에 빼기만 했더니(동작은 같음), 같은 조건에서 `fib` 0.224 → 0.203(0.3.0과 같음),
`loop` 0.203 → 0.200이 되었다. 실험은 커밋하지 않았다.

**고치는 법(P12의 남은 일).** 위 실험 그대로다. 해석 루프 안의 드문 에러 경로는 `#[cold]` 함수로 빼 둔다. 이미 있는
다른 갈래(E0403·E0404 등 `err(…)`을 바로 만드는 곳)도 같은 방식으로 정리하면 조금 더 얻을 수 있는지 함께 잰다.
같은 일이 다시 생기지 않게, 해석 루프를 고치는 변경에는 `scripts/bench.sh <전> <후>`의 `fib`·`loop`를 붙이는 것을
규칙으로 삼는다.

### 3.4.1 고친 뒤 (2026-10-24)

위 실험대로 `POP`의 E0606과 `LOADGLOBAL`의 E0808·E0809를 `#[cold] #[inline(never)]` 함수로 뺐다(`vm.rs`의 `discarded_stop`·`unset_global`).
`POP`은 이제 모든 값에 `discarded_err`(그 안의 `result_kind`는 `Ok`면 안의 값을 복제한다)를 부르지 않고 `Err` 태그인지만 본다.
0.3.0 바이너리를 다시 빌드해 같은 시각에 `scripts/bench.sh`를 두 번씩 돌렸다(부하 평균 3~5). 실험 때(0.203초)만큼 돌아오지는 않았다.

| 바이너리 | `fib` | `loop` |
|---|---|---|
| 0.3.0 | 0.206~0.211 | 0.199~0.205 |
| 고치기 전(`0a05f60`) | 0.232~0.233 | 0.205~0.210 |
| 고친 뒤 | 0.215~0.218 | 0.206~0.211 |

남은 차이를 줄이려고 더 해 본 것은 모두 효과가 없거나 거꾸로였다: 루프의 에러 도우미 `err`·`at`에도 `#[cold]`(`fib` 0.232로 되돌아감),
`CHECKBOOL`의 E0505도 빼기(0.218, 차이 없음), `Instr::op`에 `#[inline]`(`fib` 0.226, `loop`만 0.204로 조금 빠름). 프로파일(`sample`)로는
`step_loop` 표본이 0.3.0보다 약 9% 많았고, 두 버전 모두 `Instr::op`가 명령마다 함수 호출이었다(표본의 약 13%; 다른 크레이트의 함수라 인라인되지 않음).
해석 루프는 함수 하나가 아주 커서, 무엇을 넣고 빼든 LLVM의 레지스터 배정과 배치가 통째로 흔들린다.

**LTO.** `CARGO_PROFILE_RELEASE_LTO=fat CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1`로 빌드하면 크레이트 경계를 넘어 함께 최적화한다.

| 바이너리 | `fib` | `loop` | `list` | `map` | `str` | 크기 |
|---|---|---|---|---|---|---|
| 0.3.0 | 0.204~0.211 | 0.196~0.199 | 0.212~0.217 | (흔들림) | 0.078~0.080 | |

LTO에서는 `#[cold]` 변경의 차이가 측정 오차 안이다. 대가는 빌드 시간이다: 한 파일을 고친 뒤 `fung-cli` 릴리스 빌드가 6초에서 31초가 된다.

시험 빌드까지 견줬다(같은 날, 부하 평균 7 안팎이라 실행은 비율로 본다).

시험 실행 파일이 수십 개이고 LTO는 그 하나하나를 링크할 때마다 전체를 다시 최적화한다. 지금은 넣지 않기로 했다(open-questions P12b, 2026-10-24 사용자 결정).
배포용 프로필을 따로 두는 길은 시험한 바이너리와 배포하는 바이너리가 달라지는 예외라 두지 않는다.

### 3.5 메모리

`text`·`regex`에서 fung은 14.5MB 파일에 약 92MB를 쓴다. 파일 문자열 + 줄 리스트(줄마다 문자열 하나)를 한꺼번에 쥐기
때문이다. Node도 같은 방식이라 120MB다. 3.1절의 수정 뒤에는 한 줄씩 읽는 판이 같은 속도에 9MB다.

## 4. 종합

기본 계산은 Ruby 2.6과 Python 3.14 사이, JIT가 있는 Node와 아주 가벼운 Lua와는 약 2배 차이다. 바이트코드 인터프리터로서
정상 범위다. 시작·외부 명령·동시성은 이미 비교 대상 중 상위권이다. 약점은 **파일·텍스트 처리량**에 몰려 있는데,
이것이 fung이 겨냥하는 스크립트의 핵심 작업이다. 그래서 다음 최적화는 VM 명령 해석 루프보다 이쪽(P8 → P9 → P10·P11)이
효과가 크다.

  전체를 다시 검사했고, 글자 수도 `utf8_chunks`로 셌다. 유효한 글은 `String`으로 들고 있게 바꾸자 검사가 없어지고 `str::chars().count()`의 빠른 길을 쓴다(0.037초).
- **`regex`**(+5~9%): 빈 매치를 거르려고 `is_match`를 `find_iter`로 바꿨는데, `is_match`는 매치의 끝을 찾지 않아 훨씬 싸다. 패턴이 빈 문자열에 맞을 수 없으면
  (`regex_syntax`의 `minimum_len`) 거를 일이 없으므로 원래의 빠른 호출을 쓴다.

## 4.3 LTO를 다시 잰 것 (2026-11-08, L15 P12b)

L15의 결정 규칙: 통합 시험을 한 실행 파일로 모은 뒤 `cargo test --release --no-run`의 증가가 15초 이하면 fat LTO를 `[profile.release]`에 넣고, 넘으면 기각으로 닫는다.
먼저 어디서 시간이 드는지 쟀다(macOS, `vm.rs`를 `touch`한 뒤, 시험 실행 파일 28개).

| 빌드 | LTO 없음 | fat LTO |
|---|---|---|
| `cargo test --release --no-run` 전체 | 22초 | 78초 |
| `cargo build --release`(실행 파일 하나) | — | 35초 |
| `cargo test --release --no-run -p fung-vm`(단위 시험 실행 파일 하나) | — | 64초 |

`fung-vm`의 단위 시험 실행 파일 **하나**가 LTO로 64초다. 그래서 `fung-cli`의 통합 시험을 모아도 증가는 40초를 넘는다(통합 시험은 대부분 `fung`을 자식으로 띄울 뿐이라
모을 몫이 작다). 규칙대로 **기각**하고 시험 모으기도 하지 않았다(그것만으로 줄일 몫이 기준에 못 미침).

같은 때 잰 실행 이득(`scripts/bench.sh`, 9회 중앙값, 초): `fib` 0.218 → 0.208(−5%), `loop` 0.210 → 0.188(−10%), `str` 0.084 → 0.079, `map` 0.195 → 0.186,
`list` 0.231 → 0.218, `heads` 0.736 → 0.675, 실행 파일 6.8 → 5.3 MB. 3.4.1절의 값과 같은 크기다.
다시 볼 길: 배포 판만 LTO로 빌드하는 프로필(`[profile.dist]`, 사용자가 2026-10-24에 두지 않기로 함), 또는 해석 루프의 속도가 급해질 때.

## 4.4 glibc 판이 느린 이유 (2026-11-08, L15 P14)

**재현 조건.** macOS의 Docker Desktop(arm64 VM)에서 이미지 `fung-bench-linux`(Ubuntu 26.04, Rust 1.94.1, `musl-gcc`)에 저장소를 읽기 전용으로 붙이고
(`-v $PWD:/src:ro`, 크레이트는 `-v ~/.cargo/registry:/home/runner/.cargo/registry:ro`로 `--offline`), 같은 소스를 두 대상으로 빌드했다:
`cargo build --release --locked --offline -p fung-cli --target aarch64-unknown-linux-gnu`와, `rustup target add aarch64-unknown-linux-musl` 뒤
`CC_aarch64_unknown_linux_musl=musl-gcc`로 `--target aarch64-unknown-linux-musl`. Mac의 부하 평균이 4~6이라 절대값이 흔들려, 바이너리들을 라운드마다 번갈아 11~15번 돌린 중앙값만 견줬다.

| 실험(같은 컨테이너, 번갈아) | `fib` | `loop` | 결론 |
|---|---|---|---|
| glibc(동적 PIE) / 정적 glibc(`+crt-static`) / 비PIE | 0.330 / 0.356 / 0.328 | 0.444 / 0.444 / 0.443 | 링크 방식(PLT)은 원인 아님 |
| glibc / musl | 0.332 / 0.227 | 0.447 / 0.281 | 재현됨 |
| glibc LTO / musl LTO | 0.304 / 0.216 | 0.382 / 0.220 | 우리 코드의 배치만의 문제가 아님 |
| glibc + 단순한 `memcpy`·`memmove`(`LD_PRELOAD`) | 0.331 | 0.442 | 작은 복사의 ifunc는 원인 아님 |
| 실행 스레드 스택 64 MiB(4 GiB 대신) | 0.327 | 0.447 | 스택 예약은 원인 아님 |
| `GLIBC_TUNABLES=glibc.malloc.arena_max=1` | 0.323 | **0.284** | **`loop`의 원인** |

**찾은 것: glibc malloc의 아레나.** glibc는 주 스레드가 아닌 스레드에 malloc 아레나를 따로 주는데, fung은 모든 일을 실행 스레드(주 스레드가 아님)에서 한다.
그 아레나에서의 할당이 여기서는 눈에 띄게 느렸다(할당이 많은 `loop`가 0.447초, 아레나 하나로는 0.284초). 그래서 `fung_vm::stack`이 실행 스레드를 띄우기 전에
`mallopt(M_ARENA_MAX, 1)`을 한 번 부른다(Linux glibc만). 그 뒤 같은 조건에서 glibc 판은 `loop` 0.287(musl 0.280)이고, `list`·`map`·`str`·`chan`·`wait`·`fs`는 musl보다 빠르다
(musl의 할당기가 느린 것은 원래 알려진 대로).

**못 찾은 것: `fib`.** 0.327 대 0.225로 남는다. 할당·`memcpy`·스택·링크 방식·LTO 어느 것도 아니다. 남은 후보는 표준 라이브러리 쪽에서 호출마다 지나는 무엇(스레드 지역 변수의 접근 방식 같은 것)인데,
가리려면 `perf`로 두 판의 표본을 견줘야 한다. 계획의 상한(하루)에 따라 여기서 닫는다. 배포 판은 musl이라 사용자에게 닿지 않고, `cargo install`로 glibc 판을 쓰는 사람만 함수 호출 위주의 계산에서 느리다.

## 4.5 `swap` 안의 차례 끝 (2026-11-10, 두 번째 전체 점검 CC11)

`swap`의 함수가 한 차례 몫(호출 1,000번)보다 오래 돌면, 몫이 끝난 뒤 예산을 1로 남겨 그 뒤의 모든 호출이 `end_turn`의 차가운 경로(Ready 잠금, 기한이 있으면 시계 읽기)를 탔다.
고친 뒤에는 몫마다 예산을 다시 채우고 "넘길 차례가 밀림"(`turn_owed`)만 남겨 `swap`이 끝날 때 넘긴다.

재는 법: 고치기 전(ef61ef8)과 뒤를 따로 빌드해(기준은 저장소 밖 `CARGO_TARGET_DIR`), 프로그램마다 두 바이너리를 번갈아 9번씩 돌린 CPU 시간(user+sys) 중앙값.

| 프로그램 | 고치기 전 | 고친 뒤 |

`swap` 안의 군살(+17%, 기한이면 +39%)이 사라져 그냥 도는 것과 같아졌다(차이는 잡음 안).

## 4.6 prelude의 컬렉션 함수를 Rust로 (2026-11-10, 두 번째 전체 점검 VA25)

`reverse`·`keys`·`values`·`sum`·`min`·`max`는 `extras/prelude.fung`에서 원소마다 람다를 부르거나(`fold`·`map`) `ys[n - 1 - i]`로 색인했다.
`keys`·`values`는 `pairs`로 튜플 리스트를 만든 뒤 다시 훑었고, `sum`은 범위를 끝까지 접었다. 이제 `prelude/collections.rs`의 Rust 함수이고,
긴 입력은 다른 내장 함수처럼 조각(`vm/pieces.rs`의 `Work`, 리스트·받는 끝은 `drain_with`)으로 나눠 차례를 넘긴다. 범위의 `sum`은 원소를 돌지 않고 i128로 계산하되, 리스트를 `+`로 접은 것과 같게 중간 합의 넘침도 본다(중간 합 `P(k) = k*a + k(k-1)/2`는 k에 대해 아래로 볼록해서 가장 큰 값은 양 끝, 가장 작은 값은 꼭짓점 `k = 1/2 - a` 옆의 두 정수에서 나온다).

재는 법: 고치기 전(ec159a7)과 뒤를 따로 빌드해(기준은 저장소 밖 `CARGO_TARGET_DIR`), 두 바이너리를 번갈아 9번씩 돌려 호출마다 앞뒤 `time.monotonic()`의 차(ms)를 재고 중앙값을 취했다.
입력은 200만 원소 리스트(`reverse`·`sum`은 `map(0..2_000_000, x => x)`, `sort`·`min`·`max`는 `(x * 7919) % 2_000_003`), 100만 키 맵(`fold(0..1_000_000, {}, (acc, i) => put(acc, "k${i}", i))`). 기계는 Apple Silicon Mac.

| 호출 | 고치기 전 | 고친 뒤 |
|---|---|---|
| `reverse(xs)` | 171.1 ms | 20.7 ms |
| `max(ys)` | 142.2 ms | 17.1 ms |
| `min(ys)` | 125.1 ms | 17.2 ms |
| `sum(xs)` | 107.8 ms | 25.4 ms |
| `sum(0..2_000_000)` | 100.7 ms | 0.001 ms |
| `keys(m)` | 238.7 ms | 19.6 ms |
| `values(m)` | 236.0 ms | 18.2 ms |
| `sort(ys)` (비교용, 그대로) | 205.9 ms | 210.4 ms |
| `pairs(m)` (비교용, 그대로) | 43.8 ms | 46.6 ms |

`reverse`가 더는 `sort`와 비슷하지 않고, `keys`·`values`가 `pairs`의 절반 밑이다(튜플을 만들지 않음). `sort`·`pairs`의 차이는 잡음 안이다.

## 4.7 값 층의 군살 (2026-11-10, 두 번째 전체 점검 VA22~VA24·VA26)

- VA22: `==`의 E0517 검사(`sym_meets_str`)와 비교(`equal`)가 컬렉션을 따로 두 번 훑었다. 이제 `compare.rs`의 `walk` 하나가 "E0517 켬/끔" 표지를 받아 한 번에 걷는다(패턴용 `equal`은 끔). 멈추는 쌍은 그대로다.
- VA23: `Sort`가 자연 병합 정렬이다. 이어진 오름차순(안 줄어듦)이나 엄격한 내림차순(뒤집음, 같은 키가 없어 안정성 유지) 달리기를 찾고, 32개보다 짧으면 이분 삽입(같은 키 뒤에 넣음)으로 늘린 뒤, 달리기 경계로 쌍씩 병합한다. 정렬된 입력은 n-1번 비교와 병합 없음이다. 조각 실행·비교 예산은 그대로.
- VA24: `sort_by`는 원소를 `Rc<Vec<Value>>`로 쥐고 걷기 커서와 `Sort`가 함께 읽는다(복사 없음). `unique`는 남긴 원소를 `list` 한 벌만 쥐고 비교 때 `list.at(i)`로 읽는다.
- VA26: `check_returned`·`+`가 `Text`가 기억한 글자 수(`char_len`)를 쓴다. `+`의 결과는 두 쪽 다 유효한 UTF-8이고 글자 수를 이미 알면 합을 기억한다.

재는 법: 고치기 전(53ef633)과 뒤를 따로 빌드해(기준은 저장소 밖 `CARGO_TARGET_DIR`), 두 바이너리를 번갈아 5번씩 돌려 호출마다 앞뒤 `time.monotonic()`의 차를 재고 중앙값을 취했다(메모리는 `/usr/bin/time -l`의 최대 상주). 200만 원소 입력, 기계는 Apple Silicon Mac.

## 4.8 내장 함수 인자와 해석 루프의 고정 비용 (2026-11-11, 두 번째 전체 점검 VM15·VM16)

- VM15: 내장 함수가 인자를 `Vec<Value>` 대신 `Args`(`value/args.rs`)로 받는다. 네 개까지는 값 안에 담아(빈 자리는 `nil`) 호출마다의 할당과 해제가 없다. 더 많으면 `Vec` 하나. `unsafe`는 없다.
- VM16 (a): 링크 때 명령을 `Code {op, arg}`(8바이트)의 배열로 한 번 풀어 둔다. 실행 루프가 명령마다 다른 크레이트의 `Instr::op`(표 조회와 `expect`)를 부르지 않는다.
- VM16 (b): 비꼬리 `CALL`이 피호출자 칸을 `Vec::remove`로 지우지 않고 빈 채로 둔다. 프레임의 `floor`(보통 `base`, `CALL`로 들어온 프레임은 `base - 1`)까지 돌아갈 때 자른다.
  처음에는 `floor: usize`를 더해 프레임이 48바이트에서 56바이트가 되었는데, 그것만으로 `fib`가 20% 느려졌다(프레임을 쌓을 때 Rust 스택을 거쳐 복사하는 코드가 바뀜). `base`와 `floor`를 32비트 둘로 두어 48바이트를 지키고, 크기를 시험(`a_frame_is_48_bytes`)이 지킨다.
- VM16 (c): 실행 루프가 명령마다 위치 표(`pos[ip]`, 12바이트)를 읽지 않는다. 에러를 만드는 자리와 위치를 남겨야 하는 명령(내장 함수 호출, `import`, 패턴·`assert`)만 `Task::here`(프레임의 `ip - 1`)로 찾는다. 에러 위치·호출 경로·`dump`는 그대로다(골든·기대 출력·매뉴얼 펜스 변화 없음).

재는 법: 점검 전 기준(857db0f), 바로 앞 커밋(018e635), 단계마다의 바이너리를 저장소 밖 `CARGO_TARGET_DIR`로 따로 빌드해 프로그램마다 여섯 바이너리를 번갈아 7번씩 돌린 CPU 시간(user+sys) 중앙값(초). 기계는 Apple Silicon Mac.
`fib35`는 `fib(35)`(`bench/fib.fung`의 30을 35로), `len` 루프는 `fn loop(i, acc, xs) = i == 0 then acc else loop(i - 1, acc + len(xs), xs)`를 3천만 번, 호출 루프는 `fn inc(x) = x + 1`을 꼬리 재귀 안에서 천만 번 부른다(점검 문서 VM15·VM16의 프로그램).

|---|---|---|---|---|
| 857db0f (점검 전) | 1.928 | 3.056 | 0.920 | 0.214 |
| 018e635 (바로 앞) | 1.955 | 3.060 | 0.913 | 0.207 |
| + VM15 `Args` | 1.942 | 2.561 | 0.924 | 0.210 |

## 4.9 macOS FIFO 읽기 (2026-11-11)

macOS에서 `head -c 1000000 /dev/zero | cat > f`처럼 버퍼보다 큰 조각으로 쓰는 쪽의 FIFO를 `fs.read`로 읽으면 1 MB에 3초, 4 MB에 12초였다(약 330 KB/s).
한 번에 20 MB를 쓰는 쪽(`head -c 20000000 /dev/zero > f`)이나 `dd bs=8k`는 빨랐다.

원인은 fung이 아니라 macOS 커널의 알림이다. fung 없이 Python으로 FIFO를 비차단으로 열고 kqueue(`EV_ONESHOT`)로 기다리면 같은 모양이 나온다:

- 쓰기 크기만 바꿔 보면 4 KiB·8 KiB 쓰기는 빠르고, 16 KiB·64 KiB 쓰기는 느리다. FIFO의 버퍼는 8 KiB(읽기가 늘 8,192바이트씩 나온다).
  남은 자리보다 큰 쓰기 하나는 조각으로 들어가는데, 쓰는 쪽이 막혔다 깨어나 넣은 둘째 조각부터는 **kqueue도 poll도 읽을 준비를 알리지 않는다**.
  `EV_ONESHOT`·계속 등록(level)·`EV_CLEAR`·`poll()` 모두 기다림의 절반쯤이 시간 초과로 끝났다.
- 데이터는 와 있다: 같은 읽기를 쉬지 않고 돌리면 1 MB가 0.00초, 1ms씩 쉬면 0.15초다. 막힌 `read`(`wc -c f`)도 0.00초다(잠든 읽기는 깨운다).
- 익명 파이프, 소켓 쌍(버퍼 8 KiB), Linux의 FIFO(docker, epoll)는 같은 쓰기에서 시간 초과가 0번이다.

fung의 FIFO 읽기는 막히면 그 fd에 주차하고, macOS에서는 쓰는 쪽이 떠난 것도 알리지 않아 이벤트 없이 50ms마다(`pipe::RELOOK`) 다시 본다.
알림이 빠지면 이 50ms가 유일한 깨움이라 한 번에 버퍼 하나(8~16 KiB)씩 읽었다(1 MB ÷ 16 KiB × 50ms ≈ 3초).

고친 것(`native/pipe.rs`): 데이터를 받은 읽기의 다음 다시 보기를 50 µs로 하고, 아무것도 없이 볼 때마다 배로 늘려 50ms에서 멈춘다(`backoff`).
쉬지 않고 쓰는 쪽은 수십 µs 안에 다음 조각을 넣으므로 바짝 따라가고, 쉬는 쓰는 쪽에는 열한 번 본 뒤 전처럼 50ms마다 본다(이벤트가 오면 언제나 곧바로 깬다).
Python으로 시작 간격을 견주면(4 MB, `head | cat`) 10 µs 0.009초, 50 µs 0.013초, 200 µs 0.035초, 1ms 0.146초라 50 µs를 골랐다. Linux는 다시 보기가 없으니 바뀌지 않는다.
쓰는 쪽(`fs.write`로 FIFO에 4 MB)은 이 문제가 없었다.

재는 법: 고치기 전(7f5b00a)과 뒤의 릴리스 바이너리를 저장소 밖 `CARGO_TARGET_DIR`로 따로 빌드하고, fung이 먼저 읽는 끝을 연 뒤 쓰는 쪽을 띄워 둘이 끝날 때까지의 벽시계 시간(앞 3번·뒤 5번의 중앙값, 초). Apple Silicon Mac, macOS 27.0.1.

| 경우 | 전 | 뒤 |
|---|---|---|
| `fs.read` 1 MB, `head -c … \| cat` | 3.032 | 0.021 |
| `fs.read` 4 MB, `head -c … \| cat` | 12.176 | 0.025 |
| `fs.read` 20 MB, 한 번에 쓰기 | 0.083 | 0.028 |
| `read_line` 4 MB(17바이트 줄 235,295개), `yes \| head \| cat` | 0.183 | 0.134 |

줄 읽기는 전에도 느리지 않았다: 줄마다 값을 만드는 읽는 쪽이 쓰는 쪽보다 느려 버퍼가 거의 늘 차 있으므로 비울 때가 드물었다.
시험 `perf.rs`의 `a_fifo_read_keeps_up_with_a_streaming_writer`가 4 MB를 1초 안으로 지킨다(전 12초).

## 4.13 다섯 번째 점검의 성능 묶음 (2026-11-14, VA69·VA68·VM51·VM52, VA59 뒤의 리스트 자르기)

점검 문서(`docs/plans/2026-11-14-full-review.md`)의 성능 항목을 고친 기록이다. 언어가 보이는 동작(출력, 에러와 그 위치)은 바꾸지 않았다.
재는 법: 바로 앞 판(512fd966)과 항목마다의 릴리스 바이너리를 저장소 밖에 두고 같은 프로그램을 번갈아 5~7번 돌린 CPU 시간(user+sys, `getrusage`) 중앙값(초). Apple Silicon Mac.

- VA69 문자열 보기: 유효한 UTF-8의 자르기가 원본 바이트 위의 보기(`Repr::View`)다. 64바이트 이하이거나 원본의 4분의 1보다 작은 조각은 복사한다. 조각의 글자 수는 자른 범위에서, ASCII 여부는 원본에서 물려받는다(원본이 ASCII가 아니면 "모름"으로 두고 필요할 때 한 번 본다).

| 프로그램 | 512fd966 | VA69 |
|---|---|---|
| `eat(s[1..])` ASCII 20만 글자 | 0.948 | 0.028 |
| `eat(s[1..])` `"한"` 20만 글자 | 12.826 | 0.030 |
| `eat(s[..len(s) - 1])` `"한"` 10만 글자 | 3.203 | 2.364 |
| `"x" + acc` 20만 번 | 0.872 | 0.851 |
| `s[i]` 10만 번(`"가b"` × 5만) + `"k${i}"` 30만 개 `join` | 0.076 | 0.078 |

끝에서 먹는 고리는 VA69만으로는 여전히 이차다: 끝 자리를 찾느라 처음부터 센다(VA68에서 고침). 앞에 붙여 쌓기(`"x" + acc`)는 이 묶음의 범위가 아니라 그대로다(매번 전체를 복사, 매뉴얼 VM 10장 "남은 n²").

- VA68 글자 자리: 비ASCII 문자열의 `offset_of`가 커서에서 앞(64글자까지는 곧바로)·뒤로, 끝에서 거꾸로, 처음부터 중 가장 가까운 곳에서 걷는다. 그 거리가 64글자를 넘고 커서보다 뒤로 가는 접근이면 64글자마다의 바이트 자리 표(`marks`)를 한 번 만들고, 그 뒤로는 표에서 64글자 안쪽만 걷는다. 앞으로 읽기만 하는 고리는 표를 만들지 않는다. `index_of`의 글자 세기는 `char_count`(UTF-8 검사 + 디코딩) 대신 유효한 UTF-8이면 `str::chars().count()`(단어 단위)다.
  같은 표의 VA68 열은 VM51·VM52의 커밋 전 변경이 함께 든 빌드로 쟀다(둘은 컴파일과 `TAILCHECKBOOL`만 건드려 이 프로그램들과 무관).

| 프로그램 | 512fd966 | VA69 | VA68 |
|---|---|---|---|
| `s[i]` 앞으로 40만 번(`"한"` × 40만) | 0.066 | 0.070 | 0.071 |
| `s[n - 1 - i]` 거꾸로 10만 번(`"한"` × 10만) | 2.330 | 2.325 | 0.023 |
| 회문 검사 `all(0..n // 2, i => s[i] == s[n - 1 - i])` 20만 글자 | 6.925 | 6.923 | 0.039 |
| `eat(s[..len(s) - 1])` `"한"` 10만 글자 | 3.154 | 2.317 | 0.023 |
| 맞음 없는 `index_of` 1,000번(한글 50만 글자, 1.5 MB) | 0.895 | 0.902 | 0.105 |

거꾸로 40만 번은 0.072초(점검 때 40.4초). 맞음 없는 `index_of` 한 번은 0.90 → 0.10 ms로 `in`(0.044 ms)의 약 2.3배다. 남은 차이는 글자 세기(찾은 만큼 세는 것은 위치를 돌려주는 함수의 몫)다. ASCII는 그대로(0.157 ms, `in` 0.066 ms).

- VM51 컴파일 시간: `fung check`의 CPU 시간(3번 중앙값). 표의 VM51 열은 VM52의 커밋 전 변경이 함께 든 빌드다(VM52는 실행만 건드림).
  (1) 상수 접기가 자식의 상수를 부모가 접히지 않을 때만 표에 적고(옮김, 복제 없음), 문자열끼리의 `+`는 왼쪽에 제자리로 덧붙인다. (2) 문장 뒤·가지 앞의 놓기가 놓을 칸이 있을 때만 시작 위치(줄 처음부터 글자 세기)를 찾는다. (3) 점프 잇기가 `JUMP` 사슬의 끝을 뒤에서 앞으로 한 번에 구한다. (4) 진단의 발췌가 줄의 글자 수를 파일마다 한 번 세어 둔 것으로 ASCII인지 안다.

| `check`할 프로그램 | 512fd966 | VM51 |
|---|---|---|
| `"a" + "a" + …` 10만 항 | 0.977 (최대 상주 5,984 MB) | 0.149 (337 MB) |
| `{a: {a: …}}` 5,000겹 | 1.008 | 0.014 |
| `x ?? x ?? …` 10만 항 | 1.113 | 0.149 |
| 한 줄의 `print(u0, …, u159999)`(에러 16만 개) | 9.478 | 1.318 |
| `then … else`를 4,900겹 품은 값 | 0.057 | 0.043 |
| `else if` 5만 개 | 0.210 | 0.211 |

`else if` 5만 개는 512fd966에서 이미 선형이었다(20만 개 0.83초, 점검 때의 2.0초는 재현되지 않음). 같은 줄의 에러는 이제 에러 수에 선형이다(4만 0.30, 8만 0.61, 16만 1.31초). 남은 상수는 진단마다의 비슷한 이름 찾기와 출력이다.

- VM52 `TAILCHECKBOOL` 지름길: 프레임의 마지막 검사가 같은 함수·같은 자리의 bool 검사면 아무것도 만들지 않는다(넣어도 검사 목록이 그대로이므로). 7번 중앙값, 바로 앞 판은 VA69 커밋의 빌드(VM52 전).

| 프로그램 | 512fd966 | VA69 | VM52 |
|---|---|---|---|
| `fn loop(n) = n == 0 or loop(n - 1)` 2천만 번 | 0.925 | 0.930 | 0.800 |
| 같은 고리를 `if … else`로 | 0.703 | 0.697 | 0.698 |

남은 차이(+15%)는 `or`의 점프와 `TAILCHECKBOOL` 명령 하나를 해석하는 몫이다. 두 함수가 번갈아 부르면(`a`의 `or`는 `b`, `b`의 `or`는 `a`) 마지막 검사가 매번 다르므로 지름길을 타지 않는다(1.06 → 1.05초, 잡음 안).

- VA59 뒤의 리스트 자르기: VA59(350e0825)가 큰 리스트의 자르기를 늘 트리 사본 자르기로 바꾸어 `xs = xs[1..]` 고리가 느려졌다. SLICE가 스택에서 꺼낸 리스트를 아무도 쥐지 않고(`Rc::get_mut`) 잘려 나가는 것이 `RELEASE_PIECE`(8,192) 이하면 제자리에서 자른다(`index::slice_owned`, `List::cut`). 머리 잎은 제자리에서 앞을 덜어 내고(`drain`), 메모의 "없다"를 지킨다(`Node::drop_vals_front`). `Pvec::holds`가 머리·꼬리도 메모로 답하고, `suffix`는 이미 자리 표시인 칸을 새로 할당하지 않는다.
  프로파일에서 늘어난 시간의 대부분은 자르기가 아니라 걸음마다의 `holds`(D116의 `==` 함수 검사 등)가 새로 만든 머리 잎(메모 없음)을 훑는 몫이었다.

| 프로그램 | VA59 앞(350e0825^) | VM52 | 고친 뒤 |
|---|---|---|---|
| `go(xs[1..])` 20만 개(만들기 0.013 포함) | 0.040 | 0.091 | 0.037 |
| 같은 고리 20만 + 160만 개 | 0.319 | 0.794 | 0.287 |
| `go(xs[..len(xs) - 1])` 20만 개 | 0.053 | 0.083 | 0.042 |
| `[_, ...rest]` 20만 개 | 0.041 | 0.070 | 0.066 |

나머지 패턴은 `MATCH`가 주제를 쥔 채 자르므로(다른 대안이 주제를 다시 볼 수 있음) 제자리 자르기를 쓰지 못한다. 0.070 → 0.066초는 `suffix`의 자리 표시 몫이다.

- 마지막으로 `scripts/bench.sh`(512fd966 → 이 묶음, 9번 중앙값 벽시계)로 넓게 보았다. `str`(50만 개 `str`과 `join`)이 0.083 → 0.089초, `heads`가 0.275 → 0.281초였다. 문자열에 커서·표(`marks`)를 그대로 더해 `Text`가 커진 탓으로 보고, 커서와 표를 처음 필요할 때 만드는 상자(`Seek`, 한 단어)로 옮겼다. 처음 64글자 안쪽을 찾는 동안은 상자를 만들지 않는다(자르기가 찾는 첫 글자들). `Text`는 56바이트 이하로 시험이 지킨다. 그 뒤 CPU 시간 11번 중앙값: `str` 0.081 → 0.085, `heads` 0.255 → 0.261, `map` 0.194 → 0.192초. 문자열 300만 개 만들기 0.42 → 0.44초(+3~4%)는 남았다. 원인은 찾지 못했다(문자열 하나의 할당 크기는 그대로다). 나머지(`chan`·`exec`·`fib`·`fs`·`list`·`loop`·`spawn`·`wait`)는 잡음 안이다.

## 5. 다시 잴 때

- 같은 기계에서 다른 무거운 작업 없이 돌린다. 결과는 기계마다 다르므로 표의 절대값보다 언어 사이의 비율을 본다.
- 최적화 하나를 넣은 뒤에는 이 비교와 함께 `scripts/bench.sh <전> <후>`로 fung 바이너리 둘을 나란히 잰다.
- Ruby는 판과 YJIT 여부를 적는다(`RUBY="ruby --yjit"`). 다른 언어의 명령도 `PYTHON`·`LUA`·`NODE`로 바꿀 수 있다.
- **다른 언어의 결과는 기록을 다시 쓴다**(사용자 요청, 2026-10-25). `run.py`는 fung만 매번 재고, 다른 언어는 `bench/compare/records/<기계>.json`에
  적어 두었다가 재는 방식(`METHOD`), 프로그램, 입력 데이터, 명령, 해석기 판이 그대로면 그 기록을 쓴다. 하나라도 바뀐 것만 다시 잰다.
  재는 방식을 바꾸면(준비 운전, 횟수, 무엇을 취하는지) `METHOD`를 올린다. 일부러 모두 다시 재려면 `--remeasure`.
  기록은 커밋한다(기계 이름이 파일 이름이라 다른 기계의 기록과 섞이지 않는다).
- 프로그램을 더하면 다섯 언어 판을 같이 더하고, 출력이 같은지 `run.py`가 확인한다. `bench/compare/fung/`의 `.fung`
  파일은 dump 기대 출력(`crates/fung-cli/tests/expected/dump/`)에도 들어가므로 함께 갱신한다.
