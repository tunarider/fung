# M3. 함수 — 무엇을 만들었고 왜 그렇게 했나

M3는 함수다. `fn` 정의(짧은 형·블록 형·익명)와 람다, 호출 규약(위치·이름 인자, 기본값), 프레임과 클로저,
`return`, 재귀와 꼬리 호출 최적화, 타입 표기 검사, `at_exit`, 스택 한도, 그리고 런타임 에러의 호출 경로 출력.
`count(1000000, 0)`이 돈다.

## 1. 한눈에

```
fn add(a, b = 1) = a + b
print(add(1))
```

`fung dump bytecode`:
```
== <main> ==
0000  1:1   CLOSURE      0    ; add
0001  1:1   STOREGLOBAL  0    ; add
0002  2:1   CONST        0    ; <fn print>
0003  2:7   LOADGLOBAL   0    ; add
0004  2:11  CONST        1    ; 1
0005  2:10  CALL         1    ; 1 positional, 0 named
0006  2:6   CALL         1    ; 1 positional, 0 named
0007  1:1   RETURN

== add ==
0000  1:1   LOADLOCAL    1
0001  1:1   JUMPIFSET    4
0002  1:15  CONST        0    ; 1
0003  1:1   STORELOCAL   1
0004  1:20  LOADLOCAL    0
0005  1:24  LOADLOCAL    1
0006  1:22  ADD
0007  1:18  RETURN
```

함수는 컴파일 시점에 **자식 Proto**(`== add ==`)가 되고, 실행 시점에 `CLOSURE 0`이 그 Proto와 붙잡은 값들을 묶은
**클로저 값**을 만든다. `add`라는 이름은 전역 0번 칸에 저장된다. 호출은 `CALL`이고, `add`의 서두(0~3번)가 기본값을 채운다.

## 2. 프레임과 슬롯

M2에서 지역 변수는 "스택의 아래쪽 칸"이었다. M3에서는 함수마다 **프레임**이 생긴다. 프레임은 `{Proto, ip, base, closure, tailCalls}`이고,
`base`는 이 함수의 슬롯이 시작되는 스택 위치다. `CALL`이 하는 일:

| 단계 | 스택 (아래 → 위) |
|------|------|
| 호출 직전 | `… add 1` |
| 인자를 떼어내고 | `…` |
| 새 프레임, 슬롯 2개를 붙임 (`a=1`, `b=비어 있음`) | `… 1 ∅` |
| 본문이 값을 계산 | `… 1 2 2` |
| `RETURN`: 값을 꺼내고 `base`까지 자른 뒤 값을 올림 | `… 2` |

`∅`는 Go의 `nil` 인터페이스로, "아직 대입되지 않음"을 뜻한다 (fung의 `nil` 값과 다르다). 기본값 서두의 `JUMPIFSET`이 이것을 본다:
칸이 비어 있으면 기본값 식을 실행해 채우고, 이미 값이 있으면(호출자가 넘김) 건너뛴다. 기본값이 **호출마다** 평가된다는 03의 규칙이 이렇게 공짜로 나온다.

`RETURN`이 스택을 `base`까지 자르므로 함수가 남긴 임시 값이 새지 않는다. 메인 프레임의 `base`는 0이다.

## 3. 호출 규약

`CALL`의 피연산자 한 단어에 위치 인자 수(아래 12비트)와 이름 인자 수(위 12비트)를 담는다. 스택에는
`[함수, 위치 인자…, (이름 심볼, 값)…]` 순서로 쌓여 있다. `bindArgs`가 새 슬롯 배열에 묶는다:

1. 위치 인자가 인자 수보다 많으면 E0402.
2. 위치 인자를 차례로 넣는다.
3. 이름 인자마다 인자 표에서 이름을 찾아 넣는다. 없으면 E0406, 이미 찼으면 E0405.
4. 기본값이 없는 인자가 비어 있으면 E0407.

네이티브 함수(`print`, `fail`)는 이름 인자를 받지 않는다(E0406). 타입 검사는 서두 끝에서 `CHECKTYPE`으로 한다. 기본값을 채운 **뒤**에 검사하므로
`fn f(s: str = 1)`은 `f()`에서 E0403이다. 반환 타입은 `RETURN` 직전의 `CHECKRETURN`.

## 4. 클로저: 값을 복사한다

```
fn mk():
  x = 1
  f = () => x
  x = 2
  f()
;;
print(mk())    # 1
```

`f`가 만들어지는 순간 `x`의 값 1이 클로저 안으로 **복사**된다. 그 뒤 `x = 2`는 이름을 새 값에 붙이는 것이지 클로저가 가진 1을 바꾸지 않는다 (03).
Lua나 Crafting Interpreters의 "upvalue 상자"(여러 클로저가 한 변수를 공유하며 바꾸는 장치)가 필요 없는 이유는 fung의 변수가 바뀌지 않기 때문이다.

resolve가 이름을 어디서 가져올지 정한다. 함수 안에서 이름을 찾는 순서는: 자기 블록들 → 자기 이름(`self`) → 바깥 함수들 → 전역 → prelude.
바깥 함수의 지역이면 **캡처 사슬**이 생긴다:

```
fn outer(y) = x => z => x + y + z
```
`z => …` 안의 `y`는 `x => …`의 캡처 0번(`captured 0`)이고, `x => …`의 캡처 0번은 `outer` 프레임의 슬롯 0(`local 0`)이다.
`CLOSURE`를 실행하는 프레임이 자식 Proto의 `Captures` 목록을 보고 "내 슬롯에서", "내 클로저의 캡처에서", "내 클로저 자체를" 복사한다.

**최상위 변수도 복사한다** (2026-10-13 스코프 재논의로 바뀐 부분). 처음 구현은 "최상위 `fn`은 최상위 변수를 호출 시점에 찾는다"였고,
그러면 `x = 1; f = () => x; x = 2; f()`가 최상위에서만 2가 되어 함수 안과 답이 달랐다. 원칙 7(예외 조항 최소화)에 따라 규칙을 하나로 합쳤다:
**함수는 만들어질 때 보이는 변수의 값을 복사한다.** 최상위 람다는 그때까지 대입된 전역을 `CaptureGlobal`로 복사하고, 최상위 `fn`은
프로그램 시작 전에 만들어지므로 변수를 하나도 볼 수 없다 (E0204 + "인자로 넘기세요" 힌트). 다른 최상위 `fn`은 상수라 직접 참조해도 복사와 같다.
E0207은 도달할 수 없게 되어 폐기했다. 최상위 코드 자체는 여전히 위에서 아래다.

**`LOADSELF`**: 블록 안의 이름 있는 `fn loop(…)`가 자기를 부를 때, `loop`라는 슬롯은 클로저를 만드는 시점에 **아직 비어 있다**(만든 뒤에 저장되므로).
복사할 값이 없다. 그래서 자기 참조는 슬롯이 아니라 "지금 실행 중인 클로저"를 올리는 명령 하나로 푼다. 람다 안에서 바깥 함수의 자기 이름을 쓰면
`CaptureSelf`로 그 클로저를 복사한다.

## 5. 끌어올리기와 상수

최상위 `fn`은 **전역 상수**다. resolve가 루트 블록의 `fn` 문장을 먼저 모아 전역 번호를 붙이고 맨 앞으로 옮긴다. 그래서
`print(f(1))`이 `fn f` 정의보다 위에 있어도 되고, `even`과 `odd`가 서로를 부른다. 같은 이름을 두 번 정의하면 E0210, `f = 2`로 덮으면 E0209.
끌어올려진 함수가 변수를 못 보는 것도 여기서 나온다: 그 본문은 최상위 문장이 하나도 실행되기 전에 해석되고 만들어진다.

블록 안의 지역 `fn`은 끌어올리지 않는다. 자기 자신만 볼 수 있고(위의 `LOADSELF`), 같은 블록의 **뒤에** 정의된 지역 fn을 부르면 E0208에
"최상위로 옮기세요" 힌트가 붙는다. resolve가 블록에 들어갈 때 그 블록의 지역 fn 이름을 미리 적어 두고, 문장을 지날 때마다 지우며, 못 찾은 이름이 그 목록에 남아 있는지 본다.

## 6. 꼬리 호출 최적화

```
fn count(n, acc) = n == 0 then acc else count(n - 1, acc + 1)
count(1000000, 0)      # 1000000
```

컴파일러가 `tail` 플래그를 트리 아래로 흘려보낸다. 함수 본문의 마지막 식은 꼬리, `if`와 `then`의 두 가지는 꼬리를 물려받고, `return`의 피연산자도 꼬리다.
연산자의 피연산자(`1 + f(n)`)와 호출 인자(`print(f(n))`의 안쪽 `f(n)`)는 꼬리가 아니다. 꼬리 위치의 호출은 `TAILCALL`이 된다.

`TAILCALL`은 새 프레임을 밀지 않고 **현재 프레임을 재사용**한다: 스택을 `base`까지 자르고 새 슬롯을 붙이고 `Proto`와 `ip`를 바꾼다.
프레임 수가 늘지 않으므로 백만 번 재귀해도 괜찮다. 상호 재귀(`even`/`odd`)도 같은 명령으로 된다.

**반환 타입 표기가 있으면 TCO를 끈다.** `CHECKRETURN`이 돌아온 값을 검사하려면 프레임이 남아 있어야 하기 때문이다 (03). 그래서
`fn count(n, acc) -> int = …`는 깊은 재귀에서 E0804가 난다.

호출 경로에서 재사용된 프레임은 보이지 않는다. 대신 프레임의 `tailCalls` 카운터를 `(N tail calls elided)`로 보여 준다.

## 7. 스택 한도

```
fn f(n) = n == 0 then 0 else 1 + f(n - 1)
print(f(200000))       # error[E0804]: stack overflow: call depth exceeded 100000
```

`1 + f(n - 1)`은 호출 뒤에 할 일(`1 +`)이 남아 꼬리가 아니다. 프레임이 쌓이고 100,000에서 E0804가 난다.
Go 스택이 터지지 않는 이유: VM의 실행 루프가 **반복문**이고 fung 프레임은 Go 슬라이스의 원소라서, fung의 재귀가 Go의 재귀가 아니기 때문이다.
Go 함수가 fung 함수를 부를 때(아래 `Call`)만 Go 스택이 한 층 깊어진다.

## 8. 호출 경로

```
error[E0502]: division by zero
  --> -e:1:13
  |
1 | fn f(x) = x / 0
  |             ^
  |
 call path (innermost first):
   -e:1       f
   -e:2       g
   -e:3       <entry>
```

에러가 실행 루프를 빠져나갈 때 프레임 목록을 안쪽부터 읽어 `CallSite{파일, 줄, 함수 이름, 생략된 꼬리 호출 수}`로 붙인다.
각 프레임의 "현재 줄"은 `ip - 1`번 명령의 위치다 (호출 명령이 실행 중이므로). 프레임이 열두 개를 넘으면 안쪽 8개와 바깥 2개만 보여 준다.
이 출력은 09에서 M5로 잡혀 있었지만 프레임이 생긴 지금이 싸서 당겼다.

## 9. `at_exit`와 재진입 `Call`

`at_exit(f)`는 네이티브 함수다. 등록만 하고, 프로그램이 끝난 뒤(정상이든 에러든) `RunExitHandlers`가 **등록 역순**으로 부른다.
핸들러가 실패해도 다음 핸들러는 실행되고, 종료 코드는 1이 된다.

이를 위해 **Go 코드가 fung 함수를 부르는 길**(`Task.Call`)이 생겼다. 프레임을 밀고 "프레임 수가 지금 깊이로 돌아올 때까지" 실행 루프를 돈다.
실행 루프가 `stopDepth`를 받는 이유다. 이 길은 M4의 `map`·`filter`가 사용자 람다를 부를 때 그대로 쓰인다 (06: Go로 만든 컬렉션 함수가 람다를 재진입 호출).
