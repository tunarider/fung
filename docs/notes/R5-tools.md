# R5 도구(check·test·fmt·REPL): 무엇을 옮겼고 왜 그렇게 했나

2026-10-17. 계획 `docs/plans/2026-10-17-rust-tools-5.md`, 스펙 `docs/superpowers/specs/2026-10-17-rust-tools-5-design.md`,
결정과 남은 차이는 `docs/design/open-questions.md`의 "Rust 이전"(5단계 항목). 커밋 `02765ea..2a5472a`.

4단계까지 Rust CLI는 `dump`·`run`·`-e`만 있었다. 이번 단계로 Go CLI의 명령이 전부 Rust에 생겼다.
- `fung check`, 경고 W0101~W0104, `version`, `help`
- `test` 블록을 돌리는 `fung test`
- `fung fmt`
- 인자 없는 `fung`, 곧 REPL

옮기기 전에 Go 포매터를 먼저 고쳤다(Task 0). "이식 중 Go는 고치지 않는다"의 예외로, 정답지의 명백한 버그는 사용자 승인을 받아 고친다(스펙 결정).
옮기는 중에 두 개가 더 나와 Go와 Rust를 함께 고쳤다(Task 3b, 2절).

도구는 언어 의미보다 **경계**를 많이 다룬다. 파일과 파일 사이, 테스트 블록 사이, REPL 입력 사이, 그리고 터미널과 프로그램 사이다.
이번 단계의 사용자 결정 셋(4절, 5절)도 모두 그 경계에서 나왔다.

## 1. 무엇을 옮겼나

| 무엇 | 어디 | 기준(Go) |
|---|---|---|
| 경고 W0101~W0104 | `crates/fung-front/src/resolve/warn.rs`, 로더의 `Build.warnings` | `internal/resolve/warn.go` |
| `check`·`version`·`help` | `crates/fung-cli/src/{check,version}.rs`, `main.rs` | `cmd/fung/check.go`·`version.go`·`main.go` |
| 경로 순회 | `crates/fung-cli/src/paths.rs`(`test_files`·`fung_files`) | `cmd/fung`의 `testFiles`·`fungFiles` |
| `fung test` | `crates/fung-cli/src/test.rs`, `Runtime::hold`·`release`·`deadlocked` | `cmd/fung/test.go` |
| `fung fmt` | `crates/fung-front/src/format.rs` + `format/{lines,layout,spacing,align}.rs`, `crates/fung-cli/src/fmt.rs` | `internal/format`, `cmd/fung/fmt.go` |
| REPL | `crates/fung-cli/src/repl/{mod,editor,history,line}.rs`, `crates/fung-vm/src/term.rs` | `internal/repl`, `cmd/fung/repl.go` |

앞단의 `test` 블록 컴파일과 VM의 `TEST`·`ASSERT`(E0807)는 이미 있었다. `fung test`는 명령 쪽만 새로 짰다.

`fung check`는 Go와 똑같이 **파일 하나** 또는 `-e`만 받는다. 디렉터리를 주면 읽기 에러, 경로 둘이면 사용법 에러다.
`version`은 빌드할 때 넣은 `FUNG_VERSION`(`option_env!`)을 쓰고, 없으면 `0.0.0-dev`다. `CARGO_PKG_VERSION`은 일부러 쓰지 않았다.
크레이트가 모두 `0.0.0`이라 개발 빌드가 `0.0.0-dev` 표시를 잃기 때문이다. 6단계 릴리스 스크립트는 `FUNG_VERSION=$version cargo build --release`로 넣는다.

비교로 확인한 것은 테스트 파일에 있다.
- `crates/fung-cli/tests/tools_parity.rs`(테스트 20개): `check`·`test`·`fmt`·REPL·경로 순회를 Go와 바이트 단위로 비교한다.
  REPL 비교는 파이프로 넣는 세션 33개와 잘못된 UTF-8 바이트 하나다.
- `crates/fung-cli/tests/repl_tty.rs`(4개): 가짜 터미널(`openpty`)에서 편집기를 돌린다. 하나는 같은 키를 Go와 Rust 편집기에 쳐서 화면 바이트와 기록 파일을 비교한다.
- `crates/fung-cli/tests/fmt_repo.rs`(1개): Rust `fung fmt --check`로 저장소 `.fung`을 검사한다. Go `tests/fmt_test.go`가 하던 일이다.
- 포매터 대조는 저장소의 모든 `.fung`(`tests/lang`·`examples`·`extras`·`crates/fung-cli/tests/data`)에 일부러 흐트러뜨린 **21가지 변형**을 더해 돌린다.
  그리고 Go `format_test.go`의 입력, 특이한 바이트 입력, 매뉴얼 예제를 표준 입력으로 넣는다.

## 2. 포매터: 토큰 재배치, 고친 버그, 안전장치

### 원리 (M9와 같음)

포매터는 AST에서 코드를 다시 찍지 않는다. **토큰 열은 그대로 두고 토큰 사이의 공백·들여쓰기·빈 줄만 다시 정한다**(`docs/notes/M9-formatter.md` 1절).
줄바꿈은 사용자가 쓴 대로다.
- 줄 묶기(`lines`): 토큰을 원래 줄로 묶는다. 여러 줄에 걸친 문자열은 한 줄로 친다.
- 들여쓰기 상태 기계(`layout`): 열린 것(블록과 괄호)의 스택을 둔다. 각 항목은 그것을 연 줄의 들여쓰기를 기억한다.
  블록 키워드(`fn`·`if`·`match`·`for`·`test`)를 보면 "같은 괄호 깊이의 다음 `:`"을 기다린다고 적어 둔다(`pend`).
- 공백 표(`spacing`): 이웃한 토큰 쌍마다 0칸인지 1칸인지 정한다.
- 정렬(`align`): 연속 줄의 꼬리 주석과 `match` 절의 `=>`를 맞춘다.

Rust판은 Go를 줄 단위로 옮겼다. 다른 점은 바이트다. Go 포매터는 바이트를 다루고 Rust 렉서는 `&str`를 받는다.
그래서 `lex_bytes`가 Go처럼 잘못된 바이트마다 U+FFFD 하나로 풀면서 위치표를 남긴다. 토큰과 주석은 **원래 바이트**로 되돌려 쓴다.
안 그러면 주석 속 Latin-1 바이트가 사용자 파일에서 U+FFFD로 바뀐다. 정렬 너비도 Go `utf8.RuneCount`처럼 잘못된 바이트 하나를 글자 하나로 센다.

### 고친 버그 셋

**(1) 타입 표기 `fn` 뒤의 몸통이 내어쓰였다(Task 0).** `fn f(h: fn, x = 1):` 다음 줄들이 0칸으로 떨어졌다.
상태 기계가 타입 이름 `fn`(07: `fn`은 타입 이름이기도 하다)도 블록 키워드로 보고 괄호 깊이 1에서 `pend`에 쌓았다. 괄호 안에서는 그것을 가져갈 `:`이 없었다.
그래서 괄호가 닫힌 뒤 깊이 0의 진짜 블록 `:`이 왔을 때 스택 맨 위가 깊이 1이라 블록이 열리지 않았다.
`fn f(a: fn, c: str)`에서는 반대로 `c:`의 `:`이 그 `fn`을 가져가 가짜 블록을 열었다. 출력은 우연히 맞았는데, 괄호를 닫을 때 스택을 잘라 냈기 때문이다.
고침: `fnHead`는 `fn` 다음이 이름이나 `(`일 때만 함수 머리로 본다. 파서와 같은 규칙이다(`fn NAME`, `fn(`).
줄 끝의 `fn`은 타입으로 본다. 함수 머리는 여러 줄에 걸칠 수 없기 때문이다.
4d에서 이 버그를 피하려고 `extras/rust/http.fung`에 둔 `serve = _serve(...)` 감싸개도 걷어냈다.

**(2) BOM 파일을 거절했다(Task 3 리뷰에서 발견, 3b에서 고침).** Go 렉서는 맨 앞 BOM 하나를 건너뛴다. 그런데 `Format`은 **BOM을 떼지 않은 소스**를 렉서가 준 오프셋으로 잘랐다.
모든 조각이 3바이트씩 밀렸다. 그래서 BOM + 코드 파일은 안전장치에 걸려 E0801 "formatter changed the code"로 거절되었다.
주석만 있는 파일에서는 BOM이 말없이 사라졌다. 고침: 렉싱·파싱 뒤에 BOM을 떼고 포맷한다. 출력에는 BOM을 쓰지 않는다.
렉서는 여전히 원래 소스를 읽으므로, BOM이 두 겹이면 두 번째가 코드가 되어 렉서처럼 E0101이다.

**(3) `fmt --check -`가 `--check`를 무시했다(3b).** 포맷 결과를 찍고 0으로 끝났다.
이제 파일에 하는 `--check`와 같다. 바뀔 게 있으면 `<stdin>`을 찍고 1로 끝나고, 없으면 아무것도 찍지 않고 0이다.

(2)와 (3)은 처음에 Rust가 Go를 그대로 흉내 냈다. Task 3 리뷰가 "이건 Go의 버그"라고 짚었고, 사용자가 둘 다 고치기로 했다.

### 안전장치

출력을 다시 렉싱해 두 가지를 비교한다. 줄바꿈을 뺀 모든 토큰의 바이트, 그리고 주석의 글(끝 공백은 뗀다)이다.
하나라도 다르거나 다시 렉싱이 실패하면 쓰지 않는다. `E0801 formatter changed the code of NAME; nothing was written`로 끝난다.
그래서 위 (1)과 같은 버그도 **보기만 나빠질 뿐 코드를 망가뜨리지는 못한다**. 안전장치가 하는 일이 바로 이것이다.
(2)는 거꾸로 안전장치가 버그를 드러낸 사례다. 밀린 조각이 다른 토큰이 되었고, 안전장치가 그것을 잡아 거절했다.

## 3. 경고 분석: 사용과 가림

경고는 이름 해석(resolve) 단계에서 같이 모은다. 따로 패스를 돌리지 않는다.
- **W0102 안 쓰는 지역 변수**: 스코프마다 이름의 위치(`pos`), 읽혔는지(`used`), 매개변수인지(`param`)를 적는다.
  `lookup`이 이름을 찾으면 그 스코프에 "읽힘"을 표시한다. 블록 스코프를 닫을 때 읽히지 않은 이름을 보고한다.
- **W0101 안 쓰는 import**: 파일 블록을 닫기 직전에 import로 묶인 전역 중 읽히지 않은 것을 본다.
- **W0103 prelude 가리기**: 새 이름이 생기는 모든 자리에서 그 이름이 prelude에 있는지 본다. 그 자리는 최상위 `fn`, import, 대입, 패턴의 새 이름, 매개변수다.
- **W0104 값 자리의 블록이 대입으로 끝남**: 대입 오른쪽, 호출 인자, `return`에 온 `if`·`match`·블록만 본다.

경고는 에러가 있으면 버린다(Go `check`와 같다). 위치(줄, 열) 순서로 안정 정렬한다.
Go는 W0102를 맵을 돌며 모은다. 그래서 **같은 위치에** 이름이 둘 이상이면 순서가 정해지지 않는다. Rust는 이때 이름 순서로 정한다.

### 거짓 양성의 함정

경고는 틀리게 나면 무시당한다. 그래서 "경고가 나면 안 되는 파일"(`crates/fung-cli/tests/data/check/no_false_positives.fung`)을 따로 두고 Go와 비교했다. 함정은 이렇다.
- **클로저가 쓰는 이름**: `x = 1; fetch = () => x`에서 `x`는 람다가 읽는다. 모델 C(03)는 람다를 만들 때 값을 복사한다(capture).
  그러니 capture가 일어날 때 **바깥 스코프에서 그 이름을 찾은 블록**에 "읽힘"을 표시해야 한다. 람다 안쪽 사본에만 표시하면 바깥의 `x`가 안 쓰인 것으로 나온다.
  `fn g():` 안의 `fn h() = x`처럼 두 겹이어도 같다.
- **재대입**: `x = x + 1`의 오른쪽이 `x`를 읽는다. 대입 자체는 읽기가 아니다.
- **패턴 안의 이름**: 구조 분해, `match` 절, guard(`when`), `...rest`, `Ok(n) | Err(n)`.
- **`_`로 시작하는 이름**과 desugar가 만든 숨은 이름(`$`): 보고하지 않는다.
- **매개변수**: 안 써도 경고하지 않는다. 기본값이 앞 매개변수를 읽는 것(`b = a + 1`)도 사용이다.
- **최상위 이름**: W0102는 파일 블록이 아닌 블록을 닫을 때만 보므로 최상위의 안 쓴 이름은 경고하지 않는다. `test` 블록 안의 사용도 사용으로 센다. `check`는 `test` 블록까지 컴파일한다(`tests: true`).
- **내장 표준 라이브러리의 경고**: 사용자가 손댈 수 없으므로 로더가 감춘다.

W0103은 구현마다 자기 prelude 목록을 쓴다. 그래서 Rust에서 `atom`·`agent`라는 이름을 가리는 경고는 Go와 다르다(3b의 `# only:`와 같은 뿌리).

## 4. 테스트 실행기의 런타임 경계

### 파일 하나 = 런타임 하나

`fung test`는 파일마다 새 `Runtime`을 만든다. 한 파일의 상태가 다음 파일로 새지 않게 하는 것이 핵심이다(스펙 Review Focus 2).
새면 안 되는 것은 에이전트, 배경 태스크, `at_exit`, `exit`, 교착, 꺼내지 않은 실패다. 파일 하나의 순서는 이렇다.

1. 최상위를 돌리고, 이어서 테스트 블록을 차례로 돌린다(그동안 `hold`).
2. `cancel_all` → `wait`.
3. `release`.
4. 종료 핸들러. 에러는 표준 에러에 찍지만 집계에는 넣지 않는다(Go와 같다).
5. `end_background`. 에이전트를 끝낸다. 핸들러가 에이전트를 쓸 수 있으니 핸들러 **뒤**다(3b 순서).
6. `wait` → `report_unretrieved`. 실패가 있으면 `FAIL P: <tasks>`.

`end_background`를 빼먹으면 에이전트는 `Runtime`이 버려질 때에야 취소된다. 3b가 open-questions에 "도구를 옮길 때 잊지 말 것"으로 적어 둔 바로 그 일이다.

### hold/release: 블록 사이의 틈

Rust는 교착을 **정확하게** 판정한다. 살아 있는 태스크가 끝나는 순간, 남은 태스크가 모두 막혀 있으면 교착이다.
Go는 50 ms 유예를 두고 감시한다. 그 차이가 테스트 파일에서 드러났다.
최상위가 `t = spawn(() => recv(c))`를 남기고 끝났고, 다음 테스트 블록이 `send(c, 1)`을 할 예정이라고 하자.
그러면 최상위가 끝나는 순간 Rust는 "남은 태스크가 모두 막힘"을 보고 E0702를 낸다. Go는 다음 블록이 50 ms 안에 시작되므로 아무 일도 없다.

`Runtime::hold()`는 **명령 자신을 "살아 있고 막히지 않은 태스크 하나"로 센다**. 블록 사이의 틈에서는 그래서 교착이 아니다.
블록이 도는 동안에는 그 블록의 태스크가 그 몫을 이어받는다(`Task::driven`). 그래서 블록 **안의** 교착은 평소처럼 판정된다.
한 번에 한 태스크만 이어받는지는 `hold_taken`의 `debug_assert!`가 지킨다.
`release()`는 태스크들을 취소하고 기다린 뒤, 핸들러 **앞**에서 부른다. 핸들러 안의 교착도 판정해야 하기 때문이다.

이것은 Go의 우연을 흉내 낸 것이 아니다. 리뷰는 **진짜 의미상 필요**라고 판단했다. 명령이 아직 블록을 더 돌릴 참이면 그 틈은 교착이 아니다.
REPL도 같은 이유로 세션 내내 `hold`한다(5절).

### 교착이나 태스크의 `exit` 뒤에는 나머지를 건너뛴다 (사용자 결정 B)

같은 파일의 앞 블록에서 교착이 보고되거나, 띄운 태스크가 `exit(n)`을 불렀다고 하자. 그러면 그 파일의 프로그램은 취소된 상태다. 남은 블록을 어떻게 할까?
- Go는 취소된 루트 위에서 남은 블록을 그대로 돌린다. **호출이 없는 블록은 통과하고, 호출하는 블록은 E0701로 실패한다.**
  처음에는 이것을 "경쟁(racy)"이라고 적었다. 그런데 리뷰가 확인해 보니 호출이 있느냐 없느냐로 **결정적**이었다(6절 (4)).
- 선택지는 셋이었다. (A) Rust의 그때 동작, 곧 E0701로 실패. (B) 직접 `exit(n)`처럼 나머지를 건너뜀. (C) 새 루트에서 계속. 사용자는 **B**를 골랐다.
  08이 이미 "테스트 파일 안의 `exit(n)`은 그 파일의 나머지를 건너뛴다"고 정해 두었고, 교착 보고도 결국 `exit(1)` 요청이다.

규칙은 다음과 같다.
- 지금 돌던 블록은 자기 `ok`/`FAIL` 줄을 그대로 낸다.
- 남은 블록이 있을 때만 메모 한 줄을 붙인다. 교착이면 `  a deadlock was reported; the rest of the file was skipped`, 태스크의 exit이면 직접 `exit`과 같은 줄이다.
- 건너뛴 블록은 세지 않는다. 대신 **건너뛰기 자체를 실패 하나로 센다.** 메모 앞의 블록이 통과했으면 `FAIL P: <rest of file>` 줄을 먼저 낸다.
  블록이 이미 실패했으면 그 실패로 충분하다. 처음에는 메모만 냈는데, 최종 리뷰가 "블록이 통과한 뒤 띄운 태스크가 exit를 부르면
  `1 passed, 0 failed`에 종료 코드 0으로 끝난다"는 것을 찾았다. 블록이 돌지 않았는데 초록불이면 08의 "조용히 끝나는 테스트 실행은 없다"를 어긴다.
- 종료 코드는 n이 되지 않는다. 핸들러, `end_background`, 실패 보고는 그대로 돈다.
- 최상위가 정상으로 끝났는데 exit나 교착이 이미 걸려 있고 테스트가 있으면, `FAIL P: <top level>`에 메모를 붙이고 실패 하나로 센다.

두 갈래 모두 `test_rust/`의 고정 파일(`rest_skipped`·`top_pending`)이 **상태로** 순서를 정해 지킨다. 처음에는 "상태만으로 만들 수 없다"고 적었지만 방법이 있었다.
- `go`는 칸이 하나 있는 채널이라 블록(또는 최상위)은 거기서 기다리지 않는다. 실행권을 쥔 채 곧장 `recv(c)`에서 기다리게 된다.
- 태스크는 `go`의 값을 받은 뒤에야 `c`로 보낼 수 있다. 그때 블록은 이미 기다리고 있으니, 태스크는 기다리지 않고 값을 넘긴다.
  그리고 같은 실행권 차례 안에서 `exit(3)`을 요청한다.
- 블록은 값을 받은 채 깨어나 호출 없이 끝난다. 그래서 통과한다. 명령이 다음을 볼 때는 exit 요청이 이미 걸려 있다.
- `go`가 칸 없는 채널이면 순서가 갈린다. 태스크 스레드가 늦게 뜨면 블록이 `send(go)`에서 기다리고, 그 사이 태스크가 `send(c)`에서 기다리게 되기 때문이다.
  리뷰어의 원래 예시도 출력 시점(시간)에 기대어 우연히 안정적이었다. 테스트는 두 파일을 20번씩 돌려 출력과 종료 코드 1을 확인한다.

마지막 블록에서 일어나면 메모가 없다. 그래서 그런 경우를 파일 끝에 둔 Go 대조 고정 파일은 Go와 바이트가 같다.
Rust만의 동작은 `crates/fung-cli/tests/data/test_rust/`(`after_cancel`·`task_exit`)가 고정한다.

### 그 밖에 Go와 맞춘 것

- 로드 에러는 파일을 넘어 중복을 없앤다. 키는 `(소스 이름, 줄, 열, 코드)`이다. `FileId`가 아니라 소스 이름을 쓴다.
  `FileId`는 파일마다 따로 하는 컴파일 안의 번호라서, 같은 라이브러리의 같은 에러가 파일마다 다른 키가 될 수 있다.
- 경고는 "테스트가 있는가" 검사 **뒤에** 찍는다. 테스트 없는 파일은 경고도 내지 않는다.
- 경로 순회는 규칙이 둘이다. `test`는 `.` 디렉터리로 들어가지만 `fmt`는 건너뛴다. 심볼릭 링크 루트를 `fmt`는 따라가고 `test`는 따라가지 않는다. Go가 두 함수를 따로 짰기 때문이다.

## 5. REPL

### 입력 사이에 남는 전역

입력마다 따로 컴파일하지만 실행은 런타임 하나에서 한다.
- 런타임은 세션 전역 표 하나를 둔다(`Runtime::prepare_repl`). 표는 `Rc<RefCell<Vec<_>>>`이다.
- 입력을 컴파일할 때는 앞 입력들의 전역 이름을 **같은 번호로 미리 묶어 둔다**. 로더의 `globals` 옵션이고, Go의 `Options.Globals`다.
- `run_repl`이 표를 새 길이로 늘리고 그 위에서 입력을 돌린다.

클로저는 표를 같은 `Rc`로 쥔다. 그래서 1번 입력에서 만든 클로저가 3번 입력의 재정의를 본다. Go는 같은 효과를 얻으려고 용량이 고정된 표를 쓴다.
65536개 한도(E0806)는 Go와 맞추려고만 남겼다.

해석기 옵션은 둘이다(`resolve::Options`).
- `globals`: 앞 입력의 이름을 보통 이름으로 미리 묶는다. Go처럼 처음부터 "읽힘"으로 표시해 둔다.
- `redefine`: 이미 있는 이름에 `fn`이나 `import`를 다시 묶게 해 준다. `fn` 이름을 보통 변수로 되돌리는 것도 된다.

두 옵션은 진입 파일(입력 자신)에만 걸린다(Go `load.go`). 입력이 `import`한 파일은 평소 규칙대로 해석한다.
위치는 `Loader::compile_after`로 매긴다. 앞서 있던 파일들 뒤에 이어서 번호를 매기므로, 위치마다 세션의 파일 하나를 가리킨다.

### `end_background`는 세션 끝에 한 번 (사용자 결정 A)

스펙은 처음에 "입력 하나마다 `end_background`"라고 적었다. 구현해 보니 그러면 에이전트를 쓸 수 없었다.
- `end_background`는 배경 루트를 취소한다. 그 뒤에 띄우는 배경 태스크는 **처음부터 취소된 채** 시작한다.
  그러면 두 번째 입력부터는 어떤 에이전트도 일하지 않는다.
- 전역에 담은 에이전트(`a = agent(0)`)도 루프가 죽는다. 다음 입력의 `swap(a, f)`은 아무도 받지 않는 채널에 보내고 멈추거나 교착이 된다.

입력 사이에 **정의가 남는** 것이 REPL의 뜻이다. 에이전트도 정의의 하나이니 남아야 한다.
그래서 `end_background`는 세션이 끝날 때 한 번만 부른다. 끝나는 경우는 `:quit`, 입력 끝, `exit(n)`이다.
그렇다고 에이전트가 쌓이지는 않는다. 아무 전역도 붙잡지 않은 에이전트(`deref(agent(5))`)는 핸들이 사라지는 순간, 곧 그 입력 끝에 끝난다(닫개, 3b).
`repl_tests::agents_live_while_referenced`가 배경 태스크 수를 세어 확인한다.

### 교착 회복과 태스크의 `exit` (사용자 결정 B)

Go에서는 한 입력이 교착을 일으키면 세션 전체가 취소된 채로 남는다. 끝날 때 종료 코드도 1이다.
REPL은 실수하라고 있는 곳인데 실수 하나에 세션이 죽는다. 사용자는 이렇게 정했다.
- **교착은 그 입력만 실패시킨다.** 보고는 Go와 같다(감시자 줄, 그리고 발췌가 붙은 E0702).
  그다음 `Runtime::recover_deadlock()`이 세션을 되살린다.
  1. 보고가 이미 루트를 취소했으므로, 앞 입력들이 막힌 채 남긴 태스크까지 모두 풀려 끝나기를 기다린다.
  2. 교착 표시와 그것이 요청한 exit(1)을 지운다. **보고가 건 exit(1)만** 지운다(최종 리뷰).
     보고 뒤에 어떤 태스크가 `exit(n)`을 요청했으면 그 n은 따로 적어 두었다가(`World::exit_by_deadlock`·`exit_after_deadlock`) 이때 되살린다.
     처음 구현은 exit 요청을 통째로 지워서 그런 n을 잃을 수 있었다.
  3. 새 실행 루트를 단다(`Shared::root`가 `Mutex<Arc<CancelNode>>`로 바뀌었다). 단, 2에서 n이 남았으면 루트를 바꾸지 않고 세션을 n으로 끝낸다.
     지금 fung 코드로는 그 틈에 exit을 부를 길이 없다. 보고가 프로그램의 태스크를 모두 취소하고, 배경 태스크는 고정된 코드(에이전트 루프)이거나
     요청한 태스크를 따라 함께 취소되기 때문이다. 그래서 `repl_tests::a_recovery_keeps_a_later_exit`는 그 요청을 Rust에서 직접 넣어 규칙을 시험한다.
  전역은 세션 표에 있으니 남는다. 에이전트는 배경 루트에 매달려 있고 그것은 바꾸지 않으니 남는다. 회복한 세션의 종료 코드는 0이다.
- **띄운 태스크의 `exit(n)`은 세션을 n으로 끝낸다.** 프롬프트에서 직접 친 `exit(n)`과 같다. 잘린 입력의 E0701 보고와 값은 찍지 않는다.
  이 검사는 입력마다 끝에서 하고, 루프 맨 위와 줄을 읽은 직후(`:` 명령보다 먼저; 최종 리뷰 전에는 `:load`가 그 뒤에 돌았다)에도 한다.
  터미널에서는 줄 읽기가 사용자를 기다리며 막혀 있다. 그래서 입력 사이에 일어난 exit은 **다음 줄을 친 뒤에야** 효과를 낸다. 그 줄은 실행하지 않는다.

`hold` 덕에 "다음 입력을 기다리는 태스크"는 교착이 아니다(4절). Go는 파이프처럼 줄이 빨리 올 때만 50 ms 유예로 같은 결과를 낸다.
사람이 천천히 치면 Go는 입력 사이에서 교착을 보고하고 세션을 취소한다. Rust는 그러지 않는다.

### raw 모드 터미널과 되돌리기

줄 편집은 표준 입력이 문자 장치일 때만 켠다. 그때 터미널을 raw 모드로 바꾼다. raw 모드에서는 커널이 줄을 모으지 않고 반향하지 않는다.
글자 하나하나가 프로그램에 바로 오고, 화면은 편집기가 직접 그린다(`\r` + 프롬프트 + 글 + `\x1b[K` + 커서 되돌리기).
- `fung_vm::term`(유닉스): `is_char_device`(`fstat`)와 `RawMode` 가드(`tcgetattr`·`tcsetattr`, Go와 같은 플래그)가 있다. 모든 `unsafe`에 `// SAFETY:`가 붙어 있다.
  `fung-cli`는 작업 공간 크레이트에만 기댈 수 있어서(`tests/deps.rs`) `libc`를 쓰는 `fung-vm`에 두었다.
- **raw 모드는 `read_line` 한 번 동안만 켠다(Go와 같다).** 가드는 줄 읽기를 시작할 때 만들고, 돌아오거나 되감길(unwinding) 때 `Drop`으로 원래 설정을 되돌린다.
  그래서 입력이 도는 동안에는 터미널이 항상 보통 모드다. `exit(n)`, 에러, 내부 오류 모두 마찬가지다. 편집기 안의 패닉도 되감기에서 터미널을 되돌린다.
- ISIG가 꺼져 있어 Ctrl-C와 Ctrl-\는 신호가 아니라 키로 온다. Ctrl-C는 줄을 지운다.
- 파이프는 문자 장치가 아니다. 그래서 `PlainReader`를 쓰고 termios를 건드리지 않는다. `/dev/null`은 문자 장치다. Go처럼 터미널 읽기로 가서 `tcgetattr`가 실패하고, 보통 줄 읽기로 물러난다.
- 신호 처리기는 없다. Go에도 없다. 그래서 프롬프트에서 밖으로부터 SIGTERM·SIGHUP을 받거나 출력이 EPIPE로 죽으면 터미널이 raw로 남는다. 두 구현이 같다.
  고친다면 `tcsetattr`(async-signal-safe)로 되돌리는 처리기 약 40줄이다.

가짜 터미널 테스트(`repl_tty.rs`)는 `openpty`가 필요하다. 그 도우미(`term::pty`)는 `#[doc(hidden)]`으로 `fung-vm` 라이브러리에 들어 있다.
테스트 전용 feature로 감추려 했지만 `tests/deps.rs`가 막았다. 그 울타리는 `path` 말고는 아무것도 허락하지 않고, `{ path, features }`를 위반으로 친다.
울타리를 푸는 것은 정책 변경이라 하지 않았다. Linux에서는 `openpty`를 위해 libutil을 링크한다(glibc 2.34 전에는 거기에 있다).
명령은 `pty`를 부르지 않는다(릴리스 바이너리에 `openpty` 기호가 없다).

## 6. 실제로 부딪힌 함정

진행 기록(`.superpowers/sdd/2026-10-17-rust-tools-5/progress.md`)과 작업 보고서, 리뷰에 적힌 것만 적는다.

**(1) `sleep`으로 순서를 정한 고정 파일이 흔들렸다.** `fung test`의 `unretrieved.fung`는 실패할 태스크를 띄우고 `sleep(10ms)`로 그 태스크가 먼저 돌기를 기다렸다.
리뷰가 sleep 없이 돌려 보니 20번 모두 `<tasks>` 줄이 없었다. 순서가 시간에 기대고 있었다는 뜻이다.
고친 방법은 만나는 점(rendezvous)이다. 태스크가 `send(ch, 1)` 뒤에 **호출 없이** 실패하고(`[1][5]`), 테스트 블록은 `recv(ch)`로 그 `send`를 기다린다. Go·Rust 모두 20번 중 20번 나왔다.
REPL 대조의 "a failure nobody awaited"도 같은 병이었다. 세션 끝의 `cancel_all`이 태스크의 첫 호출보다 먼저 닿으면, 호출 시점 검사가 그 실패를 E0701로 바꾼다.
200번 병렬로 돌리면 보고가 빠진 횟수가 Rust 175번, Go 29번이었다. 같은 모양(버퍼 채널 + 호출 없는 실패)으로 바꾸자 둘 다 200번 중 200번 나왔다.
교훈은 CLAUDE.md의 규칙 그대로다. 동시성 테스트는 `sleep`이 아니라 상태로 순서를 정한다. "실패 직전에 호출이 없게"도 그 상태의 일부다.

**(2) 가짜 터미널의 준비 판정이 경쟁했다.** `repl_tty.rs`는 키 묶음을 보내기 전에 세 가지를 기다린다. 터미널이 raw인지, 출력이 늘었는지, 출력이 빈 프롬프트 그리기로 끝나는지다.
그런데 묶음 **중간에도** 빈 프롬프트가 그려진다. 빈 줄에서 Home을 누를 때, Ctrl-C 뒤의 줄이 그렇다.
그래서 `ready()`가 "묶음이 끝난 뒤의 새 프롬프트"와 그것을 구분하지 못했다.
고침: `send()`가 그때까지의 `\r\n` 수에 묶음 안의 Enter(`\r`)와 Ctrl-C(`^C\n`을 씀) 수를 더해 `lines_due`로 적는다. `ready()`는 그만큼의 줄 끝을 본 뒤에야 프롬프트를 확인한다.
경쟁을 마음대로 재현할 수 없어 실패(RED)는 확인하지 못했다. 순서대로 30번, 부하 아래 병렬 30번 돌려 확인했다.
같은 테스트에서 macOS의 함정도 하나 있었다. 보통 모드로 돌아오면 커널이 lflag에 PENDIN을 켠다. 그래서 "원래와 같은가" 비교에서 이 비트를 가린다.

**(3) BOM이 떨어지지 않은 소스를 잘랐다.** 2절 (2)다. Rust는 처음에 이것을 Go와 같게 흉내 냈다.
`lex()`가 BOM을 떼므로, 포매터는 이미 뗀 몸통에 `lex_at`을 불러 두 번째 BOM까지 떼지 않게 하는 데까지 맞췄다. 그다음 리뷰가 그것이 버그라고 짚었다.
교훈: 오프셋을 내주는 쪽(렉서)과 그 오프셋으로 자르는 쪽(포매터)이 **같은 바이트열**을 보는지 확인한다.

**(4) Go의 "경쟁"이 사실은 결정적이었다.** 교착 뒤의 테스트 블록(4절)을 Task 2와 Task 4 모두 처음에 "Go는 경쟁"이라고 적었다.
Go는 새 태스크의 취소 플래그를 `context.AfterFunc`가 띄운 고루틴에서 세운다. 그래서 늦게 서는 것은 맞다.
그러나 플래그는 **호출할 때만** 검사한다. 호출이 없는 블록은 취소를 볼 기회가 없어 늘 통과하고, 호출하는 블록은 그때쯤 이미 선 플래그를 봐 E0701로 실패했다.
리뷰가 이를 확인했다. 그래서 선택지를 "경쟁을 흉내 낼까"가 아니라 "어떤 규칙이 맞나"로 놓고 물을 수 있었다(사용자 결정 B).
교훈: "경쟁"이라고 적기 전에, 무엇이 그 결과를 정하는지 한 번 더 본다.

**(5) 에이전트와 `end_background`.** 스펙의 "입력마다"를 그대로 했다면 두 번째 입력부터 에이전트가 죽었다(5절).
구현자가 스펙을 벗어나 세션 끝에 부르고, 그 이탈을 보고서 맨 위에 적어 사용자에게 물었다. 스펙도 고쳤다.

**(6) Go 쪽 로그 한 줄로 실패한 대조.** `http_parity::redirects_match_go`가 몇 번 실패했다.
Go `net/http`가 표준 에러에 "Unsolicited response received on idle HTTP channel"을 쓴 탓이다. Go 클라이언트의 시점 문제라 이번 작업과 관계없고, 다시 돌리면 통과했다. 최종 검토로 넘겼다.

**(7) 여럿이 한 작업 트리를 썼다.** Task 3b와 Task 4 수정이 한 작업 트리에서 동시에 돌았다. 3b 구현자가 작업 공간 전체에 `cargo fmt`를 돌렸고, 남의 커밋 전 파일이 다시 쓰였을 수 있었다(공백만, 검사 통과).
3b는 `git apply --cached`로 자기 조각만 골라 올렸다. 4d의 교훈 (17)과 같다. 경로를 하나씩 적고, 남의 파일에 닿는 명령을 조심한다.

### 알고 남긴 동작

모두 open-questions "Rust 이전"의 "5단계(도구)에서 알고 남긴 차이와 잔가지"에 적었다. 큰 것만 꼽으면 이렇다.
- 일부러 Go와 갈라진 것: 테스트 파일의 나머지 건너뛰기, REPL의 교착 회복과 태스크 exit, 세션 끝의 `end_background`, 천천히 친 입력 사이의 교착 없음.
- Go를 흉내 낸 것: REPL 발췌는 지금 입력에서 가져오고, 태스크 실패 보고에는 발췌가 없다. E0806이 세션을 망가뜨리는 동작, 표준 입력 읽기 에러의 `/dev/stdin`, 개발 빌드 버전.
- 두 구현이 같이 가진 한계: `align_runs`의 O(n²), 제자리 쓰기가 원자적이지 않음, 신호·EPIPE 뒤 raw로 남는 터미널.

## 7. 다음

- 6단계: 동등 도달, 릴리스 전환(`FUNG_VERSION`을 넣는 릴리스 스크립트), Go 삭제. 예제와 매뉴얼의 `atom` → `agent`, CHANGELOG, 과도기 잔가지 걷어내기.
- R7: 스케줄러(그린 스레드).

이 단계를 한 줄로 줄이면, **도구는 프로그램과 프로그램 사이의 경계를 정하는 일이다.**
한 파일, 한 블록, 한 입력이 끝날 때 무엇을 끝내고 무엇을 남길지 정해야 했다. Go는 그것을 50 ms 유예와 GC에 맡겨 두었고, Rust는 하나씩 규칙으로 적어야 했다.
