# L5. 앞으로도 자라는 리스트, 리터럴 상수 접기, 노드 단위의 `send` 검사

0.5.0 큰 문제 L5(`docs/plans/0.5.0/05-collections.md`)를 고치며 배운 것. 세 가지가 모두 영속 컬렉션의 비용 약속에 걸렸다.

## 1. 앞에 붙이기가 왜 n²였나

fung의 큰 리스트는 Clojure의 PersistentVector다. 32갈래 트리의 잎에 원소 32개씩 두고, 마지막 32개 이하는 트리 밖의 `tail` 배열에 따로 둔다.
뒤에 붙이기는 `tail`에 넣기만 하고, `tail`이 차면 잎 하나를 트리 끝에 끼우며 그 길(노드 log₃₂ n개)만 복사한다. 그래서 상각 O(1)이다.

이 구조는 **뒤로만** 자란다. 인덱스 `i`가 곧 트리 안의 위치(5비트씩 끊어 내려감)라서, 앞에 하나를 넣으면 모든 원소의 위치가 하나씩 밀린다.
그래서 `[x] + acc`는 새 벡터를 처음부터 만들었고(`acc` 전체 복사), 누적하면 1 + 2 + … + n = n²/2다. 4만 개에 4.6초.

함수형 언어마다 어느 쪽이 싼지가 관용구를 정한다. Lisp·Erlang·Haskell의 연결 리스트는 앞이 O(1)이고 뒤가 O(n)이라 "앞에 쌓고 마지막에 뒤집기"가 관용구다.
fung은 반대로 뒤가 싸서 매뉴얼이 "뒤에 쌓고 `reverse`"를 안내했다. 양쪽 다 싸면 안내가 필요 없다.

## 2. 고치는 길: 트리의 위치에 기준점을 둔다

선택지는 셋이었다(계획 문서). Scala 2.12의 `Vector`처럼 **앞쪽 버퍼와 시작 위치**를 두는 길을 골랐다. RRB 트리(크기 표를 두어 이어 붙이기도 O(log n))는
더 일반적이지만 구현이 크고 색인이 조금 느려지며, 노드의 기억(`Memo`)과 자르기를 다시 짜야 한다. 실제 문제는 "작은 왼쪽 + 큰 오른쪽"뿐이었다.

바꾼 것(`value/pvec.rs`):

- **`head`**: `tail`의 거울. 처음 32개 이하를 트리 밖에 둔다. 앞에 붙이기는 `head`의 맨 앞에 넣는다(최대 32칸 밀기, 상수).
- **위치 공간과 `org`**: 트리 안의 원소는 위치 `org..end`에 있다(둘 다 32의 배수). `head`가 차면 그 배열이 통째로 잎이 되어 위치 `org - 32`에 들어가고 `org`가 32 줄어든다.
  원소 `i`의 위치는 `org + (i - head 길이)`다. 그래서 색인은 전처럼 5비트씩 내려가는 O(log₃₂ n)이다.
- **빈 자리표**: `org` 앞의 칸은 원소가 없는 빈 가지(`Branch([])`)다. 트리의 노드를 훑는 코드(기억 계산, 해제, 자르기)는 원소가 없으니 그대로 지나간다.
- **앞으로 자라기**: `org`가 0인데 또 넣어야 하면, 새 뿌리를 `[빈 자리표, 옛 뿌리]`로 만들고 위치를 모두 옛 뿌리의 용량만큼 민다. 옛 뿌리가 둘째 자식이 되어 그 앞에 같은 크기의 빈 자리가 생긴다.
  뒤로 자랄 때 옛 뿌리를 첫째 자식으로 두는 것의 거울이다. 앞자리는 자랄 때마다 32배로 커지므로 상각 O(1)이다.

`truncate`(뒤 자르기, P3)의 거울인 `drop_front`도 더했다. 원소 `k`를 품은 잎의 나머지가 새 `head`가 되고, 그 앞의 칸은 빈 자리표가 되며, 그 길만 복사한다.
그러면 `[x] + xs[1..]`처럼 보기(view) 앞에 붙일 때도 벡터를 복사하지 않는다(보기를 자기 원소로 잘라 낸 뒤 붙인다). 큐처럼 앞에서 빼고 뒤에 넣으면 위치가 끝없이 커지므로,
`drop_front`는 뿌리의 자식이 통째로 빈 자리표면 떼어 내고 위치를 그만큼 내린다(트리가 영원히 깊어지지 않게).

리스트의 `+`(`value/list.rs` `concat`)는 **짧은 쪽을 긴 쪽에 붙인다**: 왼쪽이 짧으면 오른쪽 벡터의 앞에 하나씩, 아니면 왼쪽 벡터의 뒤에 하나씩.
비용이 "오른쪽 길이"에서 "짧은 쪽 길이"가 되었다. 둘 다 길면 여전히 O(n)이고, 이것은 RRB 트리의 몫이라 0.5.0 범위 밖으로 남겼다.

결과: `fold(0..40000, [], (acc, i) => [i] + acc)` 4.6초 → 0.02초. 색인·뒤 붙이기·자르기의 perf 사례와 벤치는 그대로다.

### 시험: 모델과 견주기

이런 자료 구조는 경계(32, 1024, 32768, 뿌리가 자라는 순간)에서 틀리기 쉽다. 그래서 무작위 연산(앞·뒤 붙이기, 앞·뒤 자르기, `set`)을 6만 번 섞어 Rust의 `Vec`과 견주고,
중간 판들을 모아 두었다가 나중에 다시 읽어 **옛 판이 바뀌지 않았는지**(영속성)도 본다(`value/tests.rs` `pvec_both_ends_match_the_model`).
노드의 기억이 앞쪽 변경 뒤에도 맞는지도 같은 시험이 본다: 시험에서 음수를 "찾는 것"으로 정하고(`Probed for i64`), `holds`·`holds_in`의 답을 모델과 견준다.

## 3. 상수 접기: 한 종류가 두 뜻이면 규칙이 꼬인다

P7(2026-10-20)은 원소가 모두 상수인 리스트 리터럴을 상수 하나로 만들었다(`CONST` 한 번이면 끝, 매번 만들지 않음). 값이 불변이라 안전하다.
그런데 맵·튜플은 상수 종류가 없어서 매번 만들었고, 빈 리스트를 품은 리스트(`[[], [1]]`)도 접지 않았다. 이유가 재미있다:
컴파일러는 prelude의 `args`(실행 인자 리스트, 컴파일 때는 모름)를 "빈 리스트 상수"로 내고, VM은 빈 리스트 상수를 보면 `args`로 바꿔 끼웠다.
그러니 진짜 빈 리스트를 상수로 접으면 `args`로 읽혀 버린다. **상수 종류 하나가 두 뜻을 가진 것**이 뿌리였다.

`Const::Args`를 따로 두자 빈 리스트가 평범한 상수가 되었고, 접기의 규칙이 "모든 부분이 상수인 리터럴은 상수 하나"로 단순해졌다.
그래서 `Const::Map`·`Tuple`·`Tag`도 더했다(`fung-front/src/consts.rs`, 컴파일러의 `constant`, VM의 `vm/link.rs` `constant`).
상수 표의 해시 색인(`ConstKey`)도 이것들을 구조대로 키로 만들어, 같은 리터럴은 한 칸을 나눠 쓴다.

```
$ fung dump bytecode -e 'b = {x: 1, y: 2}; c = (1, "a"); d = [[], [1]]'
0000  1:5   CONST        0    ; {x: 1, y: 2}
0002  1:23  CONST        1    ; (1, "a")
0004  1:37  CONST        2    ; [[], [1]]
```

남는 비용 하나: 상수는 `Rc` 하나로 공유되므로 "참조가 하나면 제자리에서 고친다"(`Rc::make_mut`)가 상수에는 닿지 않아, 첫 `put`에서 복사가 한 번 생긴다. 리스트 상수도 전부터 같았다.

## 4. `send` 검사: 펼친 크기가 아니라 나눠 쓰는 노드로

채널에 그 채널의 끝을 보내면 참조 계수로 회수할 수 없는 고리가 생기므로 `send`가 값을 훑어 막는다(E0705, L7). 변하는 것을 품지 않은 값은 노드의 기억으로 O(1)에 건너뛰지만,
품은 값은 원소를 하나하나 봤다. 그리고 "이미 본 것" 표에 **컨테이너의 `Rc` 주소**를 넣었는데, 같은 벡터의 보기는 보기마다 `Rc<List>`가 따로라
20만 원소 벡터의 조각 4000개를 보내면 같은 원소를 4000번 봤다(0.56초).

이제 큰 리스트·맵은 **노드 단위로** 훑는다(`Pvec::each_holding`): 기억이 "품지 않음"인 하위 트리는 건너뛰고, 범위 안에 통째로 든 공유 노드는 "이미 본 것" 표에
**노드 주소**를 넣어 한 번만 들어간다. 보기의 경계가 자르는 잎만 원소 단위로 본다. 비용이 "펼친 크기"에서 "품은 노드 수 × 깊이 + 보기마다 경계의 잎"이 되어 0.01초다.
맵은 항목을 영속 벡터에 두므로 같은 함수를 그대로 쓴다. 검사의 뜻은 그대로라 기존 E0705 시험이 모두 통과하고, 큰 리스트의 트리 깊숙이·`head`·보기 여럿·큰 맵에 숨긴 끝도 잡는지 더했다.

배운 점: 영속 구조의 약속은 "나눠 쓰는 것은 공짜"다. 값을 훑는 코드가 그 약속을 지키려면, 훑기의 단위도 값이 아니라 **나눠 쓰는 단위(노드)**여야 한다.
