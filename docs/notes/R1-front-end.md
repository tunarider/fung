# R1 Rust 앞단: 무엇을 옮겼고 왜 그렇게 했나

2026-10-15. 계획 `docs/plans/2026-10-14-rust-front-end.md`, 결정은 `docs/design/open-questions.md`의 "Rust 이전".

fung을 Rust로 다시 구현하는 첫 단계가 끝났다. 이 단계는 **앞단**만 옮겼다.
앞단은 소스 글자를 받아 바이트코드까지 만드는 부분이다. 실행(VM)은 아직 Go에만 있다.
이 노트는 두 가지를 다룬다.
- 무엇을 옮겼고 어떻게 맞는지 확인했나.
- 이 과정에서 Rust의 어떤 개념을 썼나. Rust가 처음인 독자를 위한 설명이다.

## 1. 왜 Rust로, 무엇을 옮겼나

왜 Rust인가는 open-questions에 길게 적었다. 여기서는 이 단계의 범위만 적는다.

옮긴 것 (`crates/fung-front`):
- `source`, `diag`: 소스 파일, 위치, 에러 번호와 출력 형식.
- `consts`: 실수·기간·문자열을 Go와 같은 글자로 찍는 함수.
- `lexer`: 글자를 토큰으로.
- `tree`, `parser`: 토큰을 하나의 균일한 트리로.
- `desugar`: 편의 문법을 코어 문법으로 풀기.
- `builtins`, `resolve`: 이름이 어디서 왔는지(지역, 전역, 캡처, 내장) 결정.
- `bytecode`, `compiler`: 트리를 명령 열로.
- `loader`, `extras`: `import`를 따라 모듈 그래프를 읽고, 바이너리에 포함된 표준 모듈(`prelude.fung` 등)을 꺼냄.

그리고 `crates/fung-cli`가 `fung dump ast|core|bytecode`를 제공한다.

옮기지 않은 것:
- 경고(W01xx), REPL, 런타임 값, VM. 모두 2단계 이후다.

이 단계의 성공 기준은 하나였다. **같은 소스에 대해 Go 버전과 Rust 버전의 출력이 바이트 단위로 같다.**
성공 기준이 "잘 돌아간다"가 아니라 "정답지와 같다"라서, 판정이 기계적이다. 8절에서 설명한다.

## 2. 크레이트, 워크스페이스, cargo

Rust의 빌드 단위는 **크레이트**(crate)다. 라이브러리 크레이트 하나, 실행 파일 크레이트 하나로 생각하면 된다.
- Go의 패키지와 모듈을 합친 느낌이다. 다만 크레이트 하나가 여러 파일과 하위 모듈(`mod`)을 가진다.
- `cargo`는 `go build`, `go test`, `go mod`를 합친 도구다. 설정은 `Cargo.toml`에 쓴다.

이 저장소의 루트 `Cargo.toml`은 **워크스페이스**다. 여러 크레이트를 한 덩어리로 빌드하고 테스트한다.

```toml
[workspace]
resolver = "3"
members = ["crates/fung-front", "crates/fung-cli"]
```

- `fung-front`는 라이브러리다. 앞단 전부가 여기 있다.
- `fung-cli`는 실행 파일이다. `fung-front`를 불러 쓰기만 한다.
- 앞단과 명령줄을 나눈 이유는 2단계 이후에 VM 크레이트가 앞단을 그대로 가져다 쓰기 위해서다.
- 외부 크레이트 의존성은 **0개**다. 표준 라이브러리만 쓴다. 이는 open-questions의 의존성 정책(허용 목록)에서 앞단에는 아무것도 허용하지 않는다는 결정이다.

`rust-toolchain.toml`은 컴파일러 버전(1.94)과 `rustfmt`, `clippy`를 고정한다. Go의 `go.mod`의 `go 1.27` 줄에 해당한다.

cargo가 주는 검사 세 가지가 이제 커밋 전 관문에 들어간다.
- `cargo fmt --check`: `gofmt -l`과 같은 역할.
- `cargo clippy --all-targets -- -D warnings`: `go vet`보다 훨씬 말이 많은 린터. 경고를 에러로 취급한다.
- `cargo test`: 단위 테스트와 `crates/fung-cli/tests/parity.rs`.

CI에는 `rust` 작업이 추가됐다. 우분투와 macOS에서 위 세 가지를 돈다.
`parity` 테스트가 Go 바이너리를 빌드하므로 이 작업도 Go를 설치한다.

## 3. 소유권과 트리

Rust를 배울 때 가장 먼저 부딪히는 개념이 **소유권**이다. 값에는 주인이 한 명 있고, 주인이 사라지면 값도 사라진다.
- Go는 가비지 컬렉터가 "아무도 안 가리키면 치운다"를 대신 해 준다. 포인터를 마음대로 복사해도 된다.
- Rust는 컴파일 시점에 "누가 이 값을 치우나"를 정한다. 그래서 같은 값을 두 곳에서 마음대로 들고 있을 수 없다.

앞단의 트리 노드가 좋은 예다 (`crates/fung-front/src/tree.rs`).

```rust
pub struct Node {
    pub head: Head,
    pub pos: Pos,
    pub lit: Lit,
    pub kids: Vec<Node>,
    pub off: usize,
    pub end: usize,
}
```

Go 버전의 `Kids []*Node`는 노드 포인터의 슬라이스다. Rust의 `kids: Vec<Node>`는 **자식 노드를 부모가 직접 소유한다.**
- 부모가 사라지면 자식도 따라서 사라진다. 따로 치울 코드가 없다.
- 트리 안에서 같은 노드를 두 부모가 공유하지 않는다. 앞단의 트리는 원래 그런 모양이라 이 제약이 거의 공짜다.

더 중요한 설계는 **단계가 트리를 받아 새 트리를 돌려준다**는 점이다. `desugar.rs`의 시그니처를 보자.

```rust
pub fn desugar(n: &Node) -> Result<Node, Diag> { ... }
```

- `&Node`는 **빌려 읽기**다. 소유권은 호출자에게 남고, `desugar`는 읽기만 한다.
- 돌려주는 `Node`는 새로 만든 트리이고, 소유권이 호출자에게 넘어온다.
- 그래서 `desugar`가 끝난 뒤에도 원래 파서 트리가 그대로 있다. `fung dump ast`와 `dump core`를 한 번에 비교할 수 있는 이유다.

왜 제자리에서 고치지 않고 새로 만드나:
- 단계마다 입력은 건드리지 않는다는 규칙이 있으면 버그 찾기가 쉽다. "이 값이 언제 바뀌었지?"를 묻지 않아도 된다.
- Rust에서는 트리를 읽으면서 동시에 고치려 하면 빌림 검사기가 막는다. 새 트리를 만드는 방식이 언어와 잘 맞는다.
- 비용은 복사다. 스크립트 언어의 앞단에서는 문제가 되지 않는다.

한 가지 비용은 있다. 아주 깊은 트리를 만들면 **버릴 때도** 재귀가 깊어진다. 9절의 스택 이야기와 이어진다.

## 4. `enum`과 `match`

Go에는 `enum`이 없어서 정수 상수(`iota`)와 `switch`로 흉내 낸다. Rust의 `enum`은 **종류마다 다른 데이터를 담을 수 있는 합타입**이다.

토큰, 노드 머리, 리터럴이 모두 `enum`이다.

```rust
pub enum Lit {
    None,
    Int(i64),
    Float(f64),
    Bool(bool),
    Str(String),
    Dur(i64),
    Fn(Box<FnInfo>),
    Alias(Box<TypeAlias>),
    Import(Box<Import>),
}
```

Go 버전은 노드마다 `Lit any` 같은 빈 인터페이스에 담고, 꺼낼 때 타입 단언을 한다. 틀려도 실행해 봐야 안다. Rust는 다르다.
- `Lit::Int`에는 항상 `i64`가 있다. 다른 것이 들어갈 수 없다.
- `match`는 **모든 경우를 다뤘는지** 컴파일러가 검사한다. 새 종류를 추가하면 처리하지 않은 `match`가 전부 컴파일 에러가 된다.

`diag.rs`의 작은 예:

```rust
fn plain(&self) -> String {
    match self {
        Arg::Str(s) => s.clone(),
        Arg::Int(n) => n.to_string(),
    }
}
```

바이트코드 명령도 `enum`이다. `bytecode/op.rs`의 `Op`는 데이터를 담지 않는 `enum`이고, 번호는 Go의 `iota` 순서와 같다(`#[repr(u8)]`).
명령 한 개는 32비트 단어로, 위 8비트가 `Op`, 아래 24비트가 피연산자다.
open-questions에서 "Rust에서는 처음부터 `enum`으로 해결된다"고 한 것이 이 부분이다.

언어를 만들 때 이 선택은 중요하다. 컴파일러는 종류가 수십 개인 데이터를 계속 다룬다. 종류를 하나 추가했을 때 **빠뜨린 곳을 기계가 찾아 주면**, 사람이 찾는 것보다 훨씬 안전하다.

참고로 `Box<FnInfo>`의 `Box`는 힙에 값을 두고 가리키는 소유 포인터다. `enum`의 가장 큰 종류가 전체 크기를 정하므로, 큰 데이터는 `Box`로 빼서 `enum`이 커지지 않게 한다.

## 5. `Result`와 `?`

Go는 `value, err := f()`를 쓰고 `if err != nil { return err }`를 반복한다. Rust는 `Result<T, E>`라는 `enum`을 쓴다.
- `Ok(값)` 또는 `Err(에러)` 둘 중 하나다.
- `?`를 붙이면 `Err`일 때 곧바로 그 에러를 돌려주며 함수를 끝낸다. Go의 세 줄이 한 글자가 된다.

파서의 예 (`parser/pattern.rs`):

```rust
let first = self.pat_term()?;
```

그리고 `parser.rs`는 에러 타입에 이름을 붙였다.

```rust
type PResult<T> = Result<T, Box<Diag>>;
```

`Diag`를 `Box`에 넣은 이유는 크기다. `Result`는 `Ok`와 `Err` 중 큰 쪽의 크기를 가진다. 에러 값이 크면 재귀 함수의 스택 프레임마다 그만큼 늘어난다.
`desugar.rs`는 주석에 "Errors are boxed to keep the recursive frames small."이라고 적었다. 깊이 10,000짜리 입력을 견디려면 프레임 크기도 설계 대상이다.

공개 함수 `desugar`와 `parse`는 `Result<Node, Diag>`로 바깥에 상자를 풀어 돌려준다. 안쪽은 작게, 바깥은 쓰기 좋게 하는 방식이다.

같은 에러 목록은 `Vec<Diag>`로 모은다. `resolve`는 이름 에러를 한꺼번에 여러 개 보고하고, 렉서와 파서는 첫 에러에서 멈춘다. 이것도 Go와 같다.

## 6. `&str`과 `String`, UTF-8, 문자 단위 열

Rust의 문자열은 두 가지다.
- `&str`: 어딘가에 있는 UTF-8 글자들을 **빌려 보는** 읽기 전용 뷰. 파일 내용을 읽을 때 쓴다.
- `String`: 자기가 글자를 소유하는 늘어나는 문자열. 저장하거나 만들어 낼 때 쓴다.

이식 규칙에 "입력은 `&str`, 저장은 `String`"이라고 적은 이유다. 함수 인자는 되도록 `&str`로 받으면 호출자가 `String`이든 리터럴이든 상관없다.

Go와 가장 다른 점은 **바이트와 문자를 섞지 못하게 한다는 것**이다.
- Go의 `s[i]`는 바이트다. 한글 한 글자는 UTF-8로 3바이트다.
- Rust는 `s[i]`로 글자를 얻을 수 없다. `.chars()`로 글자를 순회하거나, 바이트 위치로 조각(`&s[a..b]`)을 낸다. 글자 경계가 아닌 곳을 자르면 패닉이다.

fung의 에러 위치 열(column)은 **문자 수**로 센다. `print(없는)`에서 `없는`은 열 7이고 밑줄은 `^^`다. 바이트로 세면 틀린다.
렉서의 `advance`가 이를 지킨다 (`lexer.rs`).

```rust
let Some(c) = self.src[self.off..].chars().next() else { ... };
self.off += c.len_utf8();
```

- `off`는 **바이트** 위치(소스를 조각낼 때 쓴다)이고, `col`은 **문자** 위치(사람에게 보여 줄 때 쓴다). 둘을 따로 들고 간다.
- `c.len_utf8()`가 이 글자가 몇 바이트인지 알려 준다.

이 단계에서 Go와 같게 맞추려고 신경 쓴 UTF-8 관련 규칙:
- 열은 문자 단위.
- 줄 끝이 CRLF여도 위치가 같다.
- 파일 맨 앞 BOM(U+FEFF)은 위치를 셀 때 무시한다. 단 에러 발췌에는 BOM이 그대로 남는다 (9절).
- 탭은 발췌에서 공백 4칸으로 펴고 밑줄 위치도 펴진 쪽에 맞춘다.
- 잘못된 UTF-8: Go는 문자열을 글자 단위로 읽을 때 **잘못된 바이트 하나마다** U+FFFD 하나를 만든다. Rust의 `String::from_utf8_lossy`는 잘못된 바이트가 이어진 덩어리를 U+FFFD 하나로 합치므로 열 번호와 출력이 달라진다. 그래서 `source::decode_go`가 바이트마다 U+FFFD를 넣는다. 스크립트 파일, `import`한 모듈(로더의 기본 `read_file`), 명령행 인자(`std::env::args_os`) 모두 이 함수로 읽는다. 인자를 메시지에 그대로 되찍을 때(예: `cannot read` 뒤의 경로)는 Go처럼 원래 바이트를 쓴다.

### 숫자와 기간은 Go의 글자 모양을 따른다

`consts.rs`의 `format_float`와 `format_dur`는 Go가 찍는 모양을 그대로 만든다. 이식 중에 문제가 된 적은 없고, 규칙만 정리해 둔다.
- 실수: 10의 -4제곱 이상 21제곱 미만이면 평범한 표기, 밖이면 지수 표기(`1e21`, `1e-07`, 지수는 두 자리). 정수처럼 보이면 `.0`을 붙인다.
- 기간: `1h30m`, `0.5ms`처럼 큰 단위부터 쓴다.

## 7. 반복자

Go의 `for i := 0; i < len(xs); i++`에 해당하는 것이 Rust에서는 **반복자**(iterator)다. 값들의 흐름을 만들고, 변환(`map`, `filter`, `take`)을 이어 붙이고, 마지막에 모은다(`collect`).

렉서 코드의 두 예:

```rust
let three: String = rest.chars().take(3).collect();
```

- `rest.chars()`는 글자 흐름, `.take(3)`는 앞 세 개만, `.collect()`는 모아서 `String`으로.

```rust
let got: Vec<Kind> = toks.iter().map(|t| t.kind).collect();
```

- `|t| t.kind`는 **클로저**(익명 함수)다. 토큰 목록에서 종류만 뽑는다.
- 반환 타입 `Vec<Kind>`를 적어 주면 `collect`가 그 모양으로 모은다.

반복자의 장점은 인덱스 실수가 없다는 것이다. 범위를 벗어난 접근이 구조적으로 일어나지 않는다.
이 코드가 항상 빠른 것은 아니다. 렉서의 연산자 처리가 토큰마다 `String`을 여러 번 만드는 점은 리뷰에서 "나중에 고칠 점"으로 기록만 했다. 지금은 Go와 같은 출력이 먼저다.

또 하나의 규칙: 출력 순서가 드러나는 곳에서 `HashMap`을 순회하지 않는다. `HashMap`의 순서는 매번 다르다(Go 맵도 그렇다). 순서가 필요하면 `Vec`이나 `BTreeMap`을 쓴다. 9절의 별칭 에러가 이 이야기다.

## 8. 명세 파일과 정답지 비교

두 구현이 같은지 어떻게 아나. 이 단계에서 쓴 방법은 두 가지다.

**(1) 명세 파일.** 사람이 두 구현에 같은 목록을 따로 옮겨 적으면 어긋난다. 그래서 Go가 목록을 **생성**하고 Rust가 읽는다.
- `spec/builtins.txt`: 내장 이름과 매개변수 표. 이름 해석(resolve)이 "이 이름이 내장인가"를 물을 때 쓴다.
- `spec/errors.txt`: 에러 번호, 메시지 틀, 힌트.
- 갱신: `go test ./tests -run TestSpecFiles -update`. 일반 `go test`는 파일이 최신인지만 검사한다.

Go 쪽 코드가 바뀌면 명세가 바뀌고, 테스트가 실패하며 알려 준다. 정답이 한 곳에만 있다.

**(2) 정답지 비교(parity 테스트).** `crates/fung-cli/tests/parity.rs`가 Go 바이너리를 빌드하고, 같은 입력을 두 바이너리에 넣어 비교한다.
- 비교 대상: `dump ast|core|bytecode`의 표준 출력, 표준 에러, 종료 코드. 모두 바이트 단위다.
- 입력: `tests/lang`, `examples`, `extras`, 벤치마크의 모든 `.fung`를 세 단계로, 사용법 에러, 별난 파일(BOM, CRLF, 탭, 잘못된 UTF-8), 깊은 중첩, 20만 단의 긴 사슬(`1 + 1 + ...`, `x.b.b...`, `f()()...`, `|> f`), UTF-8이 아닌 인자. 합쳐서 599건이다.

이 방식의 강점은 "무엇이 맞는 출력인가"를 내가 판단하지 않아도 된다는 점이다. Go가 정답이다.
약점도 있다. 599건이 건드리지 않는 곳은 검증되지 않는다. 그래서 단위 테스트도 Go 테스트를 이름까지 옮겨 함께 두었다.

언어를 만들 때의 교훈: 재구현은 **이미 있는 구현을 오라클로** 두면 크게 쉬워진다. 처음 만드는 구현에는 이런 오라클이 없어서 골든 테스트를 직접 만들어야 한다 (M0부터 한 일).

## 9. 실제로 부딪힌 함정

이 단계에서 실제로 겪은 것만 적는다. 대부분 "Go가 해 주던 일을 Rust에서는 직접 해야 한다"는 형태였다.

**(1) Go의 `%q`와 `unicode.IsPrint`.**
- 에러 메시지의 따옴표 문자열은 Go의 `strconv.Quote` 규칙이다. 줄바꿈은 `\n`, 눈에 보이지 않는 글자는 `\u00a0`(NBSP) 식의 이스케이프로 쓴다.
- "눈에 보이는 글자인가"는 `unicode.IsPrint`가 정하는데, Go는 유니코드 범주표를 내장하고 있다. Rust 표준 라이브러리에는 그 표가 없다. 외부 크레이트는 0개 규칙으로 못 쓴다.
- 해결: `diag.rs`의 `is_print`가 범주표 없이 근사한다. 제어 문자와 공백 계열을 뺀 뒤, 눈에 안 보이는 서식 문자(U+200B 등), 사설 영역, BOM 등의 구간을 직접 열거한다. U+FDD0..FDEF와 태그 문자(U+E0001, U+E0020..E007F), 그리고 Go 표의 나머지 서식 문자(Cf: U+0890..0891, U+110BD, U+110CD, U+13430..1343F, U+1BCA0..1BCA3, U+1D173..1D17A)는 리뷰 뒤에 목록에 넣었다. 이제 Go 표의 서식 문자는 전부 들어 있다. 남은 차이는 그 밖의 **미할당 코드 포인트**다. Go는 범주표로 이스케이프하지만 Rust는 표가 없어 그대로 찍는다. 실제 소스에 나올 가능성이 거의 없어 알고 받아들였다.
- 후속(2단계 Task 12): 근사를 없앴다. Go가 `unicode.IsPrint` 등의 구간을 `spec/unicode.txt`로 생성하고 `fung_front::unicode`가 읽는다. 미할당 코드 포인트도 이제 Go처럼 이스케이프한다(R2 노트 8절 (9)).
- 같은 함수가 두 곳(`diag.rs`, `consts.rs`)에 따로 있었고 서로 어긋나 있었다. 리뷰에서 하나로 합쳤다.

**(2) 따옴표 함수가 또 중복.**
- 트리 출력 쪽(`import` 경로를 찍는 부분)에 `go_quote`라는 사본이 또 생겼다. 이것도 리뷰에서 `diag::quote` 하나로 바꿨다.
- 교훈: Go의 한 함수를 옮길 때 이미 옮긴 것이 있는지 먼저 찾는다. 옮긴 사본이 둘이면 언젠가 어긋난다.

**(3) 고정된 스레드 스택 대 자라는 고루틴 스택.**
- Go의 고루틴은 스택이 필요한 만큼 자란다. Rust의 스레드 스택은 크기가 정해져 있다(메인 스레드는 보통 8 MiB).
- 앞단은 트리 모양을 따라 재귀한다. 괄호를 만 단 겹쳐도 Go는 `E0802 expression nesting too deep (limit 10000)`을 내고 끝난다. 그대로 옮긴 Rust는 스택 넘침으로 **프로세스가 죽는다.**
- 해결 첫째: 파서가 깊이를 세다가 10,000단에서 `E0802`를 낸다. 에러 프레임이 커지지 않도록 `Box<Diag>`를 쓴다.
- 해결 둘째: `fung-cli`는 모든 일을 4 GiB 스택의 스레드에서 한다 (`main.rs`의 `STACK`). 스택은 주소 공간만 예약하고, 실제로 쓴 만큼만 메모리를 쓴다. 처음에는 512 MiB였는데, 최종 리뷰에서 `1 + 1 + ...`처럼 긴 평평한 사슬이 뒤 단계(변환·컴파일)에서 고리 하나마다 한 번씩 재귀해 디버그 빌드에서 9만 단 근처, 릴리스 빌드에서 80만 단에서 죽는 것이 드러났다. Go는 고루틴 스택 한도가 1 GB라서 80만 단을 통과한다. 4 GiB는 그 한도보다 넉넉하다. 남은 차이: 디버그 빌드는 한 단에 약 6 KB를 써서 80만 단에서는 여전히 죽는다(릴리스 빌드는 Go가 죽는 200만 단도 통과한다).
- 놓치기 쉬운 부분: 깊이 한도가 세지 않는 모양이 있다. 뒤에 계속 붙는 호출·인덱스·`.` 접근과 왼쪽 결합 연산자는 트리를 입력 길이만큼(20만 단 이상) 깊게 만들 수 있다. 이 트리는 **출력할 때, 변환할 때, 버릴 때**도 재귀한다. 그래서 `Drop`까지 큰 스택 스레드 안에서 일어나게 했다.
- 그래서 깊은 입력을 쓰는 단위 테스트도 같은 큰 스택 스레드에서 돈다.

**(4) BOM은 발췌에 남는다.**
- 소스 맨 앞 BOM은 렉서가 떼어 내고, 위치(줄·열)는 BOM이 없는 것처럼 센다.
- 그러나 에러 발췌 줄은 원문 그대로 찍으므로 BOM 글자가 줄 앞에 남는다. Go가 그렇게 동작하고, 정답은 Go라서 Rust도 남긴다. `diag.rs`에 이를 고정하는 테스트가 있다.

**(5) `$PWD`로 경로를 만든다.**
- 에러 메시지의 파일 경로는 현재 디렉터리 기준으로 만든다. Go의 `os.Getwd`는 `$PWD`가 현재 디렉터리를 가리키면 그 값을 쓴다. 로더의 `cwd()`도 같게 `$PWD`를 따른다.
- macOS에서는 `$PWD`를 쓰지 않으면 `/var/...` 대신 `/private/var/...`처럼 심볼릭 링크가 풀린 경로가 찍힌다. 그래서 `$PWD`를 따르게 했다.

**(6) Go의 무작위 맵 순서.**
- 타입 별칭 에러가 둘 이상일 때 Go는 맵을 순회해서 보고 순서가 실행마다 다르다. Rust는 선언 순서로 낸다. 결정적인 쪽이 더 낫고 Go의 출력은 어차피 재현할 수 없다.
- 같은 파일에 별칭 에러가 둘 이상 있는 경우는 말뭉치에 없어서 parity 테스트에는 걸리지 않는다.

**(7) 비함수 prelude 값 `args`.**
- 내장 이름 목록에서 `args`만 함수가 아니라 값이다. Go의 `dump`는 스크립트 인자 없이 prelude를 띄우므로 `args`가 빈 리스트이고, 덤프에 `; []`로 보인다.
- 명세 읽기 쪽은 매개변수 표가 없는 줄을 받아들여야 했고, 컴파일러에는 상수 `Const::List`를 추가해 빈 리스트를 표현했다.

**(8) `Stage::Ast`는 import를 읽기 전에 멈춘다.**
- 계획에는 "어느 단계든 모듈 그래프 전체를 읽는다"고 적혀 있었다. Go의 `load.go`는 `ast` 단계에서 import를 읽기 전에 돌아온다.
- 정답은 Go이므로 Rust도 같게 했다. 문서와 정답지가 충돌하면 정답지를 따르고 판단을 기록해 둔다.

**(9) 마지막 결과.**
- CLI(`main.rs`)를 쓰고 parity 테스트를 처음 돌렸을 때 차이가 하나도 없었다. 561건이 모두 통과했다.

## 10. 다음: 2단계

2단계는 값과 VM이다. 동시성 없는 골든 테스트를 목표로 한다.
- 값 표현: 영속 컬렉션(M10)을 Rust로. 참조 계수(`Rc`)와 `Rc::make_mut`로 제자리 수정까지.
- 명령 실행기: `Op`를 `match`로 처리하는 루프.
- 이번 앞단의 `Proto`와 `Op`가 그대로 입력이 된다.

비교 방법도 이어진다. 골든 테스트(`tests/lang`)의 기대 출력이 Go와 Rust를 같은 기준으로 판정한다.
이 단계에서 배운 것을 한 줄로 줄이면, **정답지가 있는 이식에서는 오라클 비교를 먼저 만들고 그 위에서 작게 옮긴다.**
