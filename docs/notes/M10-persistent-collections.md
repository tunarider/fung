# M10 영속 컬렉션 — 무엇을 만들었고 왜 그렇게 했나

2026-10-14. 계획 `docs/plans/2026-10-14-m10-persistent-collections.md`, 스펙 `docs/superpowers/specs/2026-10-14-persistent-collections-design.md`.

fung의 리스트와 맵은 불변이다. M9까지는 "바뀐 사본"을 만들 때마다 전체를 복사했고, 그래서 `fold`로 `put`을 쌓거나
`[x, ...rest]`로 재귀하면 n²이었다. M10은 사본이 원본과 구조를 공유하는 **영속 자료구조**로 바꿨다. 언어의 의미는 하나도
바뀌지 않았고(값, 순서, `==`, 출력), 바뀐 것은 비용뿐이다.

## 1. 문제: 불변 + 통째 복사 = n²

`put(acc, k, v)`가 맵을 통째로 복사하면, n개를 쌓을 때 복사량이 1 + 2 + … + n ≈ n²/2다. 2만 개면 2억 번의 복사다.
측정(같은 기계, fung 스크립트, 2만 개):

| 패턴 | M10 전 | M10 후 |
|---|---|---|
| `fold` + `put` (새 키) | 7525ms | 61ms |
| `fold` + `put` (기존 키) | 3073ms | 31ms |
| `fold` + `acc + [i]` | 797ms | 13ms |
| `[_, ...rest]` 재귀 | 763ms | 14ms |
| `ys[1..]` 재귀 | 745ms | 14ms |

고칠 길은 셋이었다.
- (A) **영속 자료구조**: 사본이 원본의 대부분을 공유한다. Clojure·Scala·Haskell·Elixir의 길.
- (B) **소유자 확인 후 제자리 수정**: 참조가 하나뿐이면 몰래 고친다(Swift의 copy-on-write, Koka·Lean의 참조 계수).
  fung은 Go GC 위에 있어서 "참조가 하나뿐"을 알 방법이 없다. 참조 계수를 새로 붙이는 건 VM 전체를 바꾸는 일이다.
- (C) 일괄 구성 원시(`from_pairs` 등)만 추가: 사용자가 "느린 방법"과 "빠른 방법"을 외워야 한다. 원칙 7(예외 조항 최소화)에 어긋난다.

(A)를 골랐다. 사용자가 아무것도 바꾸지 않아도 빨라지고, 동시성(M7)에서 잠금 없이 값을 나눠 쓸 수 있다는 성질도 그대로다.

## 2. 구조 공유와 길 복사

값을 배열 대신 **가지 32개짜리 얕은 트리**에 담는다. 하나를 바꾸면 루트에서 그 값까지의 **길에 있는 노드만** 새로 만들고,
나머지 가지는 원본 노드를 그대로 가리킨다. 원본은 하나도 바뀌지 않는다 — 노드가 한 번 만들어지면 절대 고치지 않으니까.

왜 32인가:
- 깊이가 log₃₂ n이라 얕다. 100만 개여도 4단계, 바꿀 때마다 노드 4개(포인터 약 128개)만 복사한다.
- 2⁵라서 인덱스나 해시를 **5비트씩 잘라** "몇 번째 가지"를 비트 연산(`>>`, `&`)으로 바로 구한다.
- 노드 하나가 포인터 32개 = 256바이트로 캐시 줄 몇 개에 들어간다. 가지를 늘리면 복사량이, 줄이면 깊이가 커진다.
  Clojure가 실험으로 정한 값이고, 여러 언어가 그대로 쓴다.

## 3. 리스트: 영속 벡터 + 보기

`internal/value/pvec.go`는 Clojure의 PersistentVector다.
- 인덱스 `i`의 위치: `(i >> shift) & 31`로 한 단계씩 내려간다. shift는 5, 10, 15…
- **tail**: 마지막 ≤32개는 트리 밖 배열에 둔다. 덧붙이기는 대부분 tail만 복사(최대 32개)하면 끝이다. tail이 차면 잎 하나로
  트리에 끼우고(`pushTail`), 그 길만 복사한다. 루트가 가득 차면 한 단계 높인다.
- 결과: 덧붙이기가 "거의 O(1)"(정확히는 O(log₃₂ n)이지만 32번 중 31번은 tail 복사뿐).

`List`는 큰 경우 `{vec, lo, hi}` **보기**다. `Slice(a, b)`는 같은 벡터에 범위만 바꾼 보기를 만든다(상수 시간). 그래서
`...rest`와 `xs[1..]` 재귀가 선형이 된다.
- 보기에 덧붙이기: 보기의 끝이 벡터의 끝이면 벡터를 그대로 키운다. 아니면(앞쪽 조각) 그 조각을 새 벡터로 복사한 뒤 붙인다.
  어느 쪽이든 원본은 그대로다 — 영속 벡터의 `push`는 새 벡터를 돌려주므로 "끝에서 이어 키우기"가 다른 보기를 망치지 않는다.
- **1/4 규칙**: 잘라 낸 결과가 바탕 벡터의 1/4보다 작으면 복사해서 떼어 낸다. 100만 개 리스트에서 3개를 잘라 들고 다니면
  100만 개가 메모리에 남기 때문이다(Go의 슬라이스, Java의 옛 `substring`이 겪은 문제).

## 4. 맵: 항목 벡터 + HAMT

**HAMT**(Hash Array Mapped Trie, Bagwell 2001)는 키의 32비트 해시를 5비트씩 끊어 내려가는 트리다.
- 노드 = 32비트 **비트맵**(어느 칸이 차 있나) + 찬 칸만 담은 배열. 32칸을 다 잡지 않아 메모리가 적다.
- 칸 `b`의 배열 위치 = "b보다 앞에 찬 칸의 수" = `bits.OnesCount32(bitmap & (bit-1))`. CPU 명령 하나(popcount)다.
- 해시 32비트를 다 써도 같으면(진짜 충돌) 마지막에 작은 목록(충돌 노드)에 둔다. 테스트는 `hashKey`를 바꿔치기해
  모든 키가 충돌하는 경우까지 확인한다.

그런데 fung 맵은 **넣은 순서**로 순회·출력한다(02). HAMT는 해시 순서라 순서를 모른다. 그래서 둘을 짝지었다(`omap.go`).
- 항목 벡터(`pvec[entry]`, 넣은 순서) + HAMT 색인(키 → 항목 위치).
- 새 키: 벡터 끝에 붙이고 색인에 위치를 넣는다. 기존 키: 그 위치의 항목만 바꾼다(순서 유지, 02의 규칙).
- 삭제: 항목을 "죽은 칸"으로 표시하고 색인에서 뺀다. 죽은 칸이 산 칸보다 많아지면 한 번 다시 만든다(`compact`) — 지운 만큼만
  비용을 나눠 내므로 평균은 상수다(분할 상환).
- Python 3.7+의 dict가 "순서 배열 + 해시 색인"으로 넣은 순서를 지키는 것과 같은 생각을 영속 구조로 옮긴 것이다.
- 해시 시드는 실행마다 다르다(`hash/maphash`, 해시 충돌 공격 방지). 순서는 항목 벡터가 정하므로 출력은 항상 같다.

## 5. 작은 컬렉션은 예전 그대로 — 경계는 측정으로

스크립트의 컬렉션은 대부분 작다. 작을 때는 평평한 배열이 트리보다 빠르고 단순하다. 그래서 두 표현을 둔다.
- 리스트 32개 이하: `[]Value`. 넘으면 영속 벡터.
- 맵 16개 이하: 키 순서 배열 + Go 맵. 넘으면 항목 벡터 + HAMT.

경계를 정한 방법이 이번 마일스톤의 교훈이다.
- Go 마이크로벤치로는 평평한 배열 읽기가 트리보다 몇 ns 빠르다. 그런데 **fung 스크립트로 재면 경계 16·32·64 어디서도 읽기 차이가
  없었다**(±3%). 명령 하나를 해석하는 비용이 그 차이를 덮는다. 사용자가 느끼는 것은 fung 수준이므로 그쪽 숫자로 정했다.
- 평평한 맵의 `put`은 Go 맵 전체를 복제하므로 커질수록 비싸다. 맵 경계를 16으로 낮추니 48개짜리 맵 만들기가 M10 전보다
  31% 빨라졌다(32일 땐 12%). 그래서 스펙의 32를 16으로 바꿨다.
- 리스트는 32와 64가 같아서 노드 하나 크기인 32로 두었다.
- 결과: 크기 8·24·48의 작은 컬렉션 만들기·읽기는 M10 전 대비 ±3% 안(48개 맵 만들기는 −31%).

## 6. 인터페이스를 먼저 바꾼 이유

M9까지 바깥 코드(VM, prelude, native)는 `list.Items`(Go 슬라이스)를 직접 읽고 고쳤다. 내부 표현을 바꾸려면 먼저 그 길을 막아야 했다.
Task 1이 표현은 그대로 두고 **API만** 바꿨다: `Len`·`At`·`All`(Go 1.23 range-over-func 반복자)·`Slice`·`Append`·`Concat`·`Put`·`Remove`·`Merge`,
그리고 내장 함수가 결과를 쌓을 때 쓰는 `ListBuilder`·`MapBuilder`(제자리로 키우다가 `List()`/`Map()`으로 굳힌다).
이후 Task 3·5는 `internal/value` 안만 바꿨다. "구현을 바꾸기 전에 경계를 먼저 세운다"는 순서 덕분에 바꾸는 범위가 한 패키지로 줄었다.

## 7. 테스트 전략

- **참조 모델 대조**: 무작위 연산 수만 번을 평범한 Go 슬라이스·맵(참조 모델)과 나란히 돌리고, 중간중간 저장해 둔 **옛 버전을 다시 읽어**
  하나도 바뀌지 않았는지 본다. 영속성(옛 값이 살아 있음)은 이렇게만 확인할 수 있다.
- **경계값**: 0, 1, 31, 32, 33, 64, 65, 1056(= 32 + 32×32, 루트가 한 단계 높아지는 지점).
- **비용 고정**: `tests/perf_test.go`가 다섯 패턴을 2만 개로 돌려 0.3초를 넘으면 실패한다. 처음엔 1초로 잡았는데 리스트 패턴의 옛 값
  (0.75초)이 통과해 버려서 낮췄다. "회귀를 잡는가"를 확인하려면 기준을 옛 구현에 대고 실패하는지 봐야 한다.
- **동시성**: 고루틴 8개가 같은 큰 맵·리스트에서 각자 새 값을 만들고 서로의 변경을 보지 않는지(`-race`로도).

## 8. 겪은 문제

- **인라인 예산**: `List.At`에 큰 경우 분기를 넣었더니 Go 컴파일러의 인라인 비용 한도(80)를 넘어(87) 모든 인덱스 접근이 함수 호출이 됐다.
  큰 경우를 `//go:noinline atBig`로 떼어 내 작은 경우의 빠른 길을 지켰다. `go build -gcflags=-m`으로 확인한다.
- **이중 복사**: `Concat`이 `ToSlice` 뒤에 `append`하느라 두 번 복사해 작은 리스트 만들기가 30% 넘게 느려졌다. 정확한 크기로 한 번만
  복사하도록(`appendTo`) 고쳤다. fung 수준 측정이 없었다면 놓쳤을 것이다.
- **첫 실행 비용**: 비용 테스트의 첫 패턴이 런타임 시작 비용까지 재서 들쭉날쭉했다. 데우기 실행을 넣었다.

## 9. 남은 것

- 문자열 `acc + s`는 여전히 n²다. 문자열은 Go `string`이라 공유 구조를 넣으려면 rope가 필요하다. 지금은 매뉴얼에서 "리스트에 모아 `join`"을 안내한다.
- 앞에 붙이기 `[x] + xs`는 O(n)이다. 앞쪽 삽입까지 싸게 하려면 RRB 트리(Relaxed Radix Balanced)가 필요한데, 스크립트에서 드문 패턴이라 미뤘다.
