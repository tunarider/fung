# R4c `regex`, 첫 크레이트, SIGPIPE: 무엇을 옮겼고 왜 그렇게 했나

2026-10-16. 계획 `docs/plans/2026-10-16-rust-regex-crates-4c.md`, 스펙 `docs/superpowers/specs/2026-10-16-rust-regex-crates-4c-design.md`
(끝의 "2026-10-16 구현 중 개정"이 사용자 결정), 결정과 남은 차이는 `docs/design/open-questions.md`의 "Rust 이전".

4단계(네이티브 원시 기능)의 세 번째 조각이다. 4a·4b까지는 표준 라이브러리만 썼다. 4c에서 처음으로 **외부 크레이트**를 들였다.
정규식 엔진(`regex`)과 운영체제 신호 함수(`libc`)다. 그래서 이 단계의 일은 셋이다.
1. 크레이트를 들이기 전에 "무엇을 들여도 되는가"를 지키는 장치부터 세운다(4절).
2. 닫힌 파이프에 쓰면 Go처럼 **신호로 죽는다**(5절).
3. `_native.regex`를 옮긴다. 엔진은 크레이트에 맡기되 **문법은 Go 것**을 그대로 옮겼다(2·3절).

## 1. 무엇을 옮겼나

사용자에게 보이는 것:
- `import regex`가 Rust에서도 된다(4b까지는 E0805 "지원 안 함"). `extras/regex.fung`는 Go와 같은 파일이다. 이제 지원 안 하는 네이티브 모듈은 `http`뿐이다.
- `fung run x | head -1`처럼 읽는 쪽이 먼저 닫히면, 이제 Rust도 Go처럼 신호 13(SIGPIPE)으로 죽는다. 전에는 `exit(141)`로 흉내 냈다.

내부:
- `crates/fung-vm/src/native/regex_go.rs`: Go 1.27 `regexp/syntax/parse.go`를 단계 그대로 옮긴 파서(약 2,000줄). 결과를 `regex_syntax`의 HIR로 바꿔 `regex` 엔진에 넘긴다(3절).
- `crates/fung-vm/src/native/regex.rs`: `_native.regex` 5개(`is_match` `find` `find_all` `replace` `split`), 패턴 캐시 256개(차면 통째로 비움),
  Go `allMatches`·`replaceAll`·`Split`·`Expand`를 옮긴 반복 코드, 바이트 → 글자 위치를 앞으로만 가는 커서(`RuneCursor`)로 선형 변환.
- `spec/regex_unicode.txt`(96 KB): Go가 만드는 유니코드 표(범주, 문자 체계, 대소문자 접기). `tests/spec_test.go`의 `regexUnicodeSpec`이 생성하고 `TestSpecFiles`가 지킨다.
- `crates/fung-vm/src/sigpipe.rs`: `die()`. 표준 출력·에러의 EPIPE에서 부른다(5절).
- `deny.toml`, `crates/fung-cli/tests/deps.rs`, CI의 `cargo-deny`·`cargo-audit`(4절).

비교로 확인한 것:
- 골든 테스트 `regex`·`err_regex`가 Go 대조와 Rust 골든 실행기에 들어갔다. 실행 비교 189건(`tests/lang` 142개 중 133개: `# only:` 표시 9개 제외),
  Rust 골든 138개(`# only: go` 3개와 `http_serve` 제외). 실행 비교에서 빠지는 것은 이제 `http_serve.fung` 하나다.
- 정규식 Go 대조(`crates/fung-cli/tests/regex_parity.rs`): 주어 16개 × 패턴 50개 = 800쌍을 다섯 함수와 바꿈 문자열 35개로, 프로그램 47개(잘못된 패턴 29개 포함)를 표준 에러·종료 코드까지.
- 파서 단위 테스트: 컴파일 표 334개(Go의 `SubexpNames` 또는 에러 문구 그대로), 매치 표 173쌍, 시드를 고정한 무작위 패턴 2,000개와 겹친 반복 패턴 600개.
  기대값은 모두 Go가 뽑았고, 생성기 `tests/regex_fixtures_test.go`가 `crates/fung-vm/src/native/regex_go_fixtures.rs`를 만든다(`go test ./tests -run TestRegexFixtures -update`).
- 커밋하지 않은 무작위 대조: 유효한 패턴 8,861개·주어 쌍 27,972개와 잘못된 패턴 639개가 Go와 바이트 단위로 같았다. 리뷰어의 퍼징 패턴 약 4만 7천 개도 차이 0.
- SIGPIPE(`crates/fung-cli/tests/sigpipe.rs`, 11개): 진입 태스크·`spawn`한 태스크·표준 에러·에러 보고·`at_exit` 처리기에서 쓰다가 Go와 Rust 모두 신호 13으로 죽는지,
  fifo·자식 표준 입력의 EPIPE는 Go와 같은 에러 값인지.

## 2. 정규식 엔진은 어떻게 도나

**유한 오토마타.** 정규식 `ab*c`는 "상태 몇 개와 화살표"로 바꿀 수 있다. 시작 상태에서 `a`를 읽으면 다음 상태로, 거기서 `b`는 제자리, `c`면 끝 상태로.
이것이 유한 오토마타(finite automaton)다. 정규식이라는 이름 자체가 "유한 오토마타가 알아볼 수 있는 언어"라는 수학 개념에서 왔다.
- **NFA**(비결정적): 한 글자를 읽고 갈 수 있는 상태가 여럿일 수 있다. `a|ab`는 `a`를 읽은 뒤 두 갈래가 동시에 살아 있다. 정규식에서 바로 만들기 쉽다(Thompson 구성).
- **DFA**(결정적): 언제나 갈 곳이 하나다. 빠르지만 상태 수가 패턴에 따라 폭발할 수 있다.

**선형 시간.** NFA를 돌리는 방법은 둘이다.
- **되돌아가기**(backtracking): 갈래마다 하나를 골라 끝까지 가 보고, 실패하면 돌아와 다른 갈래를 고른다. Perl·PCRE·Python `re`·JavaScript가 이 방식이다.
  `(a+)+$`에 `aaaa…ab`를 주면 `a`들을 묶는 방법마다 다 시도하므로 입력 길이에 **지수적**으로 느려진다. 외부 입력으로 서버를 멈추는 공격(ReDoS)이 여기서 나온다.
- **모든 갈래를 동시에**(Thompson 시뮬레이션): 지금 살아 있는 상태의 **집합**을 들고 한 글자씩 앞으로만 간다. 집합의 크기는 상태 수(패턴 길이)를 넘지 않으므로,
  시간은 최악에도 "패턴 길이 × 입력 길이"다. 입력을 두 배로 늘리면 시간도 두 배. 이것을 선형 시간이라고 부른다.

**역참조가 없는 이유.** `(a+)\1`("앞에서 잡은 것과 똑같은 것이 한 번 더")은 앞에서 무엇을 잡았는지 **기억**해야 한다. 유한 오토마타는 상태 개수가 정해져 있어
임의 길이의 문자열을 기억할 수 없다. 역참조가 들어간 매칭은 일반적으로 NP-완전 문제로 알려져 있어서, 선형 시간 보장과 함께 가질 수 없다.
그래서 선형 시간을 약속하는 엔진은 역참조와 앞뒤 보기(lookaround)를 **문법에서 뺀다**. fung의 정규식에도 없다(Go에도 없다).

**RE2 계열.** 구글의 RE2(Russ Cox)가 "되돌아가지 않는 엔진 + 그에 맞춘 문법"을 정리했고, Go `regexp`와 Rust `regex` 크레이트가 같은 계열이다.
실제 엔진은 오토마타 하나가 아니라 여러 개를 상황에 따라 고른다. `regex`(정확히는 `regex-automata`)에는 집합을 들고 가는 PikeVM, 짧은 입력용 제한된 되돌아가기,
게으르게 만드는 DFA 등이 있고, 패턴에 고정된 글자열이 있으면 먼저 그것을 빠르게 찾는다(`memchr`·`aho-corasick`, 4절). 어느 쪽을 골라도 결과와 선형 시간 보장은 같다.

fung이 Go `regexp`를 쓰는 동안 이미 "선형 시간, 역참조 없음"을 약속하고 있었으므로, Rust에서도 같은 계열의 `regex`를 고르면 그 약속이 이어진다
(open-questions "의존성 정책"의 "RE2 계열이라 지금 의미 유지"). 엔진을 직접 짜는 것(Thompson NFA)은 나중의 공부 과제로 남겼다.

## 3. RE2 계열 안의 차이, 그리고 왜 Go 파서를 옮겼나

같은 계열이어도 **문법과 뜻은 다르다.** 스펙은 처음에 "`regex-syntax`가 만든 구문 트리(AST)를 훑어 Go와 다른 곳만 고치는 얇은 층"을 계획했다.
그런데 실제로 같은 패턴 묶음을 두 쪽에 넣어 보니(Task 3 보고서의 표) 차이가 세 종류였다.
- **Go는 거부, Rust는 받음**: `(?x)`, `\Z`, `\e`, `x{1001}`, `a**`, `[[:foo:]]`, `[a--b]`, `\p{Alphabetic}`, `(?<é>x)` 등.
- **Go는 받음, Rust는 거부**: `x{,5}`·`x{`(Go에서는 글자 `{`), `\0`(8진수), `\Q..\E`(그대로 인용), `[\d-z]`, `(?i-i)`, `(?)`, 이름이 같은 그룹 둘, `(?<1a>x)`처럼 숫자로 시작하는 이름.
- **둘 다 받지만 뜻이 다름**: `\<`(Go는 글자 `<`, Rust는 단어 시작), `[[a]]`(Go는 `[[a]` 뒤에 글자 `]`, Rust는 중첩 클래스), `[a-z&&b]`(Go는 글자 `&`, Rust는 교집합),
  `\w` `\d` `\s` `\b`(Go는 ASCII만, Rust는 유니코드), `(?i)`(Go의 `SimpleFold` 유니코드 17, Rust 유니코드 16), `(a){0}`(Go는 그룹을 세고 Rust는 지운다).

AST를 고쳐 가는 방식으로는 세 가지를 맞출 수 없었다. 하나, 잘못된 곳이 여럿일 때 Go가 **먼저** 내는 에러. 둘, 에러 문구에 들어가는 Go의 "문제 부분"(`Expr`) 문자열.
셋, 뜻이 다른 패턴. 셋째는 Rust 파서가 이미 다른 트리를 만들어 버린 뒤라 되돌릴 수 없다.

그래서 **Go의 파서를 그대로 옮겼다**(`regex_go.rs`). 같은 스캔, 같은 부분식 스택, 같은 선택지 인수분해(`factor`), 같은 한도
(반복 곱 1000, 중첩 깊이 1000, 명령 수 3,355,443, 클래스 글자 수). Go의 한도 계산은 노드 주소를 열쇠로 하는 캐시를 쓰는데, 노드를 재사용하면 캐시가 낡는다.
그것까지 같게 하려고 노드를 배열(arena)에 두고 Go의 LIFO 재사용 순서를 따랐다. 파서가 만든 트리는 모든 것을 풀어 쓴 HIR이 된다.
클래스는 Go 표로 계산한 코드 포인트 구간, 대소문자 무시 글자는 접기 궤도(`k`·`K`·U+212A), `.`은 `[^\n]`, `\b`는 ASCII 단어 경계.
그 HIR을 글자로 찍어서 `RegexBuilder`에 넘긴다. **매칭은 크레이트가, 문법은 Go가** 하는 구조다.

**사용자 결정(2026-10-16).** 계획에서 크게 벗어나서 사용자에게 물었고, 이렇게 정했다.
- 옮긴 파서는 **fung 정규식 문법의 정의**로 본다. 크레이트를 올려도 fung이 받아들이는 문법은 바뀌지 않는다. Go를 지운 뒤에도 남기고, 6단계 뒤에 다시 판단한다.
- 유니코드 표는 Go가 만드는 `spec/regex_unicode.txt`를 쓴다(앞단 `spec/unicode.txt`와 같은 방식). 이것은 과도기 잔가지다.
- 무작위 패턴의 Go 기대값은 저장소에 두어, Go를 지운 뒤에도 회귀 검사로 쓴다.

**함정: 트리를 글자로 다시 찍으면 뜻이 바뀔 수 있다.** 처음 구현은 `regex-syntax`의 HIR 출력기(`Display`)를 썼다. 리뷰에서 `(?:a{1,2})?`가 조용히 틀린 결과를 내는 것을 찾았다.
- 트리는 "`a`를 1~2번" 전체를 "있어도 없어도 됨"으로 감싼 것이다. 출력기는 반복 안의 반복을 괄호로 묶지 않아 `a{1,2}?`로 찍었다.
- 그런데 `a{1,2}?`를 다시 읽으면 "`a`를 1~2번, **게으르게**"라는 전혀 다른 뜻이다. `x`에서 Go는 빈 매치 두 개를 내는데 Rust는 매치가 없었다.
- 에러가 아니라 **틀린 답**이 나오는 종류라 위험했다. 해결은 직접 쓴 출력기(`print_hir`)다. 반복의 대상, 글자열, 이어 붙이기, 선택지는 모두 `(?:…)`로 감싸고,
  ASCII 영문·숫자 밖의 글자는 모두 `\x{..}`로 쓴다. 이렇게 하면 어떤 트리든 다시 읽었을 때 같은 트리가 된다.
- 지키는 장치: 디버그 빌드에서는 찍은 글자를 다시 해석해 원래 HIR과 같은지 `debug_assert!`로 확인한다. 무작위 표에 겹친 반복 패턴 600개를 더했고,
  옛 출력기로 되돌리면 이 표가 "17 differences"로 실패하는 것을 확인했다.
- 교훈: 트리 → 글자 → 트리 왕복은 공짜가 아니다. 컴파일러의 `dump` 출력도 같은 문제를 가질 수 있다. 왕복을 테스트로 고정해야 믿을 수 있다.

그 밖의 맞춤:
- **그룹 이름**: Go는 같은 이름 둘과 숫자로 시작하는 이름을 허락하고 Rust는 둘 다 거부한다. 그래서 엔진에는 `_<번호>_<Go 이름>`으로 넘기고 `go_capture_names`가 Go의 `SubexpNames()`로 되돌린다.
- **`x{0}` 안의 그룹**: Go는 세는데 Rust HIR은 지운다. 그래서 절대 지나가지 않는 갈래(`(?:|[a&&b](sub))`, `[a&&b]`는 빈 클래스)에 넣어 그룹 칸만 살린다.
- **빈 매치 규칙**: `find_all`·`split`은 Go `allMatches`(직전 매치가 끝난 자리의 빈 매치는 건너뜀, 빈 매치 뒤에는 한 글자 전진), `replace`는 Go `replaceAll`의 다른 규칙을 따른다.
  엔진이 아니라 이 반복 코드가 정하는 것이라 `regex.rs`에 옮겼다.
- **바꿈 문자열**: Go `Regexp.Expand`를 그대로 옮겼다. `$1a`는 이름 "1a"로 읽고, 앞자리 0이 있으면 이름, 1억 이상은 자름, 잘못된 참조는 `$`를 남김.
  이름 글자 판정은 Go `unicode.IsLetter || IsDigit`(Go 표, `go_letter_or_digit`)다. Rust `char::is_alphanumeric`과 다르기 때문이다.

## 4. 의존성을 고르는 기준과 공급망 점검

**왜 허용 목록인가.** 크레이트 하나를 들이면 그 크레이트가 끌고 오는 크레이트도 모두 내 프로그램에 들어온다. 그 코드는 내가 읽지 않았고, 누가 올렸는지도 모른다.
악성 코드를 심은 새 버전(공급망 공격), 알려진 취약점, 맞지 않는 라이선스가 모두 이 길로 들어온다. fung의 정책은 "기본은 표준 라이브러리, 크레이트는 이유를 적은 것만"이다
(open-questions "의존성 정책"). 4c에서 들인 크레이트와 그 이유는 open-questions "Rust 이전"의 허용 목록 표에 있다. 요약하면:
- 직접 들인 것: `regex`(엔진; 선형 시간 엔진과 최적화는 직접 짜기에 크고, 직접 구현은 공부 과제로 남김), `regex-syntax`(HIR·출력·클래스 타입; 원래 `regex`가 끌고 오는 것이라 새 코드가 늘지 않음),
  `libc`(유닉스 대상만; `signal`·`raise`·`pthread_sigmask`는 표준 라이브러리에 없고, `sigset_t`의 배치가 운영체제마다 달라 손으로 선언하면 틀리기 쉬움).
- 따라온 것: `regex-automata`(실제 엔진들), `aho-corasick`(여러 글자열 동시 찾기), `memchr`(빠른 바이트 찾기).

`fung-front`(앞단)는 의존성 0개를 유지하고, 새 크레이트는 `fung-vm`에만 들어갔다. `regex`는 기본 기능을 끄고 `std`·`perf`만 켰다.
엔진에 넘기는 패턴은 클래스를 모두 코드 포인트 구간으로 풀어 쓰므로 크레이트의 유니코드 표가 필요 없다.

**지키는 장치 세 겹.**
1. `deny.toml`이 허용 목록의 **유일한 원본**이다. `[bans] allow`에 직접 들인 것과 따라온 것을 모두 적고, 한 크레이트의 두 버전 공존(`multiple-versions`)과
   `*` 버전(`wildcards`)을 금지하고, 라이선스는 실제로 필요한 `MIT` 하나, 출처는 crates.io만.
2. 저장소 테스트 `crates/fung-cli/tests/deps.rs`: 표준 라이브러리만으로 `Cargo.lock`의 모든 패키지가 목록에 있는지, `fung-front`의 `Cargo.toml`에 의존성 표가 없는지 본다.
   도구를 설치하지 않아도 `cargo test`에서 돈다. 리뷰에서 `[dev-dependencies]`·`[build-dependencies]`·`[dependencies.이름]` 형태를 못 보는 것이 드러나 고쳤다.
3. CI(`.github/workflows/ci.yml`의 `rust` 작업, Ubuntu에서만): `cargo-deny` 0.20.2와 `cargo-audit` 0.22.2를 버전 고정으로 설치해 `cargo deny check`(목록·라이선스·출처·권고)와
   `cargo audit`(RustSec 취약점 데이터베이스)을 돈다. 잠금 파일과 권고 데이터베이스는 운영체제와 무관하므로 한 곳이면 된다.

**2주 규칙.** 새로 들이는 크레이트와 도구는 **올라온 지 2주 넘은 버전**만 쓴다. 악성 버전은 대개 올라온 뒤 며칠 안에 발견되어 내려가므로, 조금 기다리는 것만으로 많이 걸러진다.
실제로 `libc`는 최신 0.2.190이 2026-10-02에 올라와 아직 2주가 안 되어 `cargo update -p libc --precise 0.2.189`로 그 전 버전(2026-07-21)에 고정했다.
`regex` 쪽 다섯 개는 최신판이 모두 2주를 넘었다.

**함정: 빈 허용 목록은 "모두 허용"이다.** `cargo-deny`는 `allow`가 비었거나 없으면 아무것도 막지 않는다. 비어 있지 않으면 목록 밖을 모두 막는데,
그때는 **작업 공간 크레이트 자신**(`fung-cli` 등)도 막는다. 그래서 크레이트가 하나도 없던 Task 1부터 목록에 작업 공간 크레이트 셋을 적어 목록을 비우지 않았다.
`"fung-cli"`를 빼면 `bans FAILED`가 나는 것으로 검사가 진짜인지 확인했다. 또 `wildcards = "deny"`가 작업 공간끼리의 경로 의존성(버전 없음)을 막아서,
세 크레이트에 `publish = false`를 붙이고 `allow-wildcard-paths = true`를 켰다. 교훈: 검사 도구는 "통과"보다 "막아야 할 것을 막는가"를 먼저 확인한다.

## 5. 신호와 종료 코드

**141과 "신호 13으로 죽음"은 다르다.** 유닉스 프로세스가 끝나는 방법은 둘이다. 스스로 `exit(n)`하거나, 신호를 받아 운영체제가 죽이거나.
부모는 `wait`로 둘을 구분해서 받는다. 셸은 신호로 죽은 경우를 `128 + 신호 번호`로 보여 주므로 SIGPIPE(13)로 죽으면 `$?`가 141이다.
그래서 `exit(141)`과 신호 13은 셸에서는 같아 보이지만, 프로그램이 부모라면 다르게 본다(Rust의 `ExitStatusExt::signal()`이 `Some(13)`인지 `None`인지).
테스트는 이 차이로 판정한다. 고치기 전 Rust는 wait 상태 36096(= 141 << 8, 정상 종료 코드 141)이었고 `signal()`은 `None`이었다.

**SIGPIPE는 왜 있나.** `cat 큰파일 | head -1`에서 `head`가 끝나면 `cat`은 더 쓸 곳이 없다. 운영체제는 닫힌 파이프에 쓰는 프로세스에 SIGPIPE를 보내 조용히 끝낸다.
파이프라인의 앞 단계가 쓸데없이 계속 도는 것을 막는 장치다. Go도 표준 출력·에러(디스크립터 1·2)에 쓰다 EPIPE를 만나면 일부러 SIGPIPE로 죽는다(`os` 패키지의 `epipecheck` → 런타임 `sigpipe`).

**Rust는 왜 SIGPIPE를 무시하나.** Rust 표준 라이브러리는 시작할 때 SIGPIPE를 무시로 둔다. 그러면 닫힌 파이프 쓰기가 죽음 대신 `BrokenPipe` 에러로 돌아온다.
서버처럼 소켓 하나가 끊겼다고 프로세스 전체가 죽으면 안 되는 프로그램에는 이쪽이 맞다. fung에도 필요한 성질이다. 자식 프로세스의 표준 입력이나 읽는 쪽이 떠난 fifo에 쓸 때는
**에러 값**이어야 하기 때문이다(Go도 그렇다). 그래서 무시 설정은 그대로 두고, 표준 출력·에러에서 EPIPE가 날 때만 `die()`를 부른다.

**`die()`가 하는 일**(Go `dieFromSignal`과 같은 순서):
1. `signal(SIGPIPE, SIG_DFL)`: 처리 방식을 기본(죽음)으로 되돌린다.
2. `pthread_sigmask(SIG_UNBLOCK)`: **이 스레드에서** SIGPIPE 막힘을 푼다. 신호 막힘(mask)은 스레드마다 따로라서, 막혀 있으면 `raise`해도 배달되지 않는다.
3. `raise(SIGPIPE)`: 부른 스레드에 신호를 보낸다. 막힘을 풀었으므로 `raise`가 돌아오기 전에 배달되고, 기본 동작은 커널이 **프로세스 전체**를 끝내는 것이다.
4. 그래도 살아 있으면 `exit(141)`. Go도 마지막에 `exit(128+13)`을 한다.

**스레드 질문.** fung은 태스크마다 운영체제 스레드가 있고(3a), `die()`는 아무 태스크의 스레드에서나, 실행권이나 표준 출력 잠금을 쥔 채 불릴 수 있다.
그래도 안전하다. 쓰는 함수들은 스레드 안전하고 지역 `sigset_t` 하나만 만지며, fung 값도 건드리지 않고 되감기(unwind)나 버퍼 비우기도 하지 않는다.
프로세스가 커널에서 끝나므로 다른 스레드가 쥔 잠금이 교착을 만들 틈이 없다. 처리 방식을 프로세스 전체에서 기본으로 바꾸므로 그 순간 다른 태스크의 자식 표준 입력 쓰기도
신호로 죽을 수 있지만, 어차피 죽는 중이라 상관없다. `at_exit` 처리기는 돌지 않고 아무것도 보고하지 않는다(Go와 같음).

**Go를 따라 한 부분.** 부모가 SIGPIPE를 무시로 둔 채 fung을 띄워도 Go는 신호 13으로 죽는다(실험으로 확인, `sh -c "trap '' PIPE; exec ..."`). `die()`가 기본 동작으로 되돌리므로 Rust도 같다.
C 프로그램이라면 이때 EPIPE를 받았을 것이다. 이것과 141 대비책은 언어 규칙이라기보다 Go 런타임의 선택이라 과도기 잔가지에 적었다.
자식 프로세스는 SIGPIPE 기본 동작으로 시작한다. std `Command`가 되돌려 주므로 Go와 처음부터 같았다(`(yes; echo …) | head -1`이 둘 다 `yes-exit 141`).

## 6. 실제로 부딪힌 함정

진행 기록(`.superpowers/sdd/2026-10-16-rust-regex-crates-4c/progress.md`)과 작업 보고서에 적힌 것만 적는다.

**(1) 얇은 층으로는 Go가 안 됐다.** 3절. 계획을 벗어나 Go 파서를 옮겼고, 사용자 결정으로 그것을 fung 문법의 정의로 삼았다.
계획 단계에서는 "두 엔진이 같은 계열"이라는 사실이 "문법이 같다"로 읽히기 쉬웠다. 실제로 같은 패턴을 넣어 보기 전에는 차이의 크기를 알 수 없었다.

**(2) 겹친 반복이 조용히 틀렸다.** 3절. 리뷰가 찾았다. 에러가 아니라 틀린 매치를 내는 종류라, 패턴 표에 그런 모양이 없었다면 오래 숨어 있었을 것이다.

**(3) 빈 허용 목록 = 모두 허용, 경로 의존성 = 와일드카드.** 4절.

**(4) 의존성 검사가 일부 표를 못 봤다.** `deps.rs`의 첫 판은 `[dependencies]`와 `[target.*.dependencies]`만 셌다. 리뷰가 `[dev-dependencies]`·`[build-dependencies]`·
`[dependencies.이름]` 형태를 지적했고, 여러 줄 값 안의 `[`가 표를 끝내지 않게 고쳤다. 검사 도구도 "무엇을 못 보는가"를 테스트로 고정해야 한다.

**(5) 2주가 안 된 `libc`.** 최신판 0.2.190이 규칙에 걸려 한 단계 낮췄다(4절). 나중에 `cargo update`를 하면 다시 올라가므로 그때 날짜를 확인한다.

**(6) 앞 단계가 남긴 포맷 실패.** 4b 마지막 수정 커밋이 `crates/fung-cli/tests/time_parity.rs`를 포맷하지 않은 채 남겨서 Task 1의 `cargo fmt --check`가 막혔다.
보고서에는 통과라고 적혀 있었다. 이후 컨트롤러가 작업마다 `fmt --check`를 직접 확인했다.

**(7) Go는 SIGPIPE를 무시해도 죽었다.** 처음 테스트는 보통 시작만 봤다. Go 바이너리로 실험해 보니 무시로 시작해도 신호로 죽어서, 두 가지 시작 방식을 모두 비교하게 했다.

**(8) fifo의 `'write`는 EPIPE를 못 본다.** `'write` 모드는 Go `os.Create`라서 읽기·쓰기(O_RDWR)로 연다. 자기 자신이 읽는 쪽이기도 하므로 fifo에 써도 EPIPE가 나지 않는다. 테스트는 `'append`를 쓴다.

**(9) 깊은 패턴은 큰 스택이 필요하다.** 중첩 약 999단계에서 `regex` 크레이트의 컴파일러가 디버그 빌드의 2 MB 스택을 넘친다. fung의 명령 스레드(4 GiB)와 태스크 스레드(1 GiB)에서는 괜찮고,
테스트는 깊은 경우를 1 GiB 스레드에서 돌린다. 내 코드의 재귀는 Go의 깊이 한도 1000으로 묶여 있다.

**(10) 디버그 왕복 검사가 테스트를 느리게 했다.** 망가진 패턴 테스트(모든 앞부분·뒷부분, 위치마다 메타 글자 삽입, 약 30만 입력)에 (2)의 왕복 검사가 붙자 45초쯤 걸렸다.
메타 글자 삽입을 손으로 고른 패턴에만 하도록 줄여 7.4초가 되었다.

**(11) 짐작으로 쓴 기대값이 또 틀렸다.** `SimpleFold(U+212A)`(켈빈 기호)는 `k`가 아니라 `K`였다. `\b` 위치 테스트에 바이트 위치 대신 글자 위치를 적었다.
`${`의 출력이 `\${`인 것을 몰랐다. 모두 코드가 아니라 기대값의 실수였다. 4b와 같은 교훈이다. 기대값은 Go를 돌려 얻는다.

### 알고 남긴 동작

모두 open-questions "Rust 이전"의 "4c단계(regex·SIGPIPE)에서 알고 남긴 차이"에 적었다.
- Go는 받지만 Rust 엔진의 크기 한도(128 MiB)를 넘는 아주 큰 패턴(`[a-z]{1000}`을 3,355번, `\pL`을 약 5,000번 넘게)은 Go의 `expression too large` 문구로 실패한다.
  Rust의 NFA는 유니코드 클래스마다 UTF-8 오토마타를 만들어 Go의 명령 수 예산보다 빨리 커지기 때문이다. 실패까지 몇 초 걸릴 수 있다(`\pL` × 20,000이 릴리스 약 3초, 디버그 약 30초).
- 깊은 중첩의 스택(6절 (9)).
- 엔진이 크기 밖의 이유로 거부하면 Go의 `regexp/syntax: internal error` 문구가 나온다. Go는 이 문구를 내지 않고, 테스트로 닿는 경우도 없다.
- 내부 에러 경로(`crates/fung-vm/src/vm/task.rs`의 `eprintln!`)는 표준 에러가 닫혀 있으면 SIGPIPE 대신 패닉한다.
