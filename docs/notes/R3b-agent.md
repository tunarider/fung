# R3b atom을 agent로, 채널 규칙: 무엇을 바꿨고 왜 그렇게 했나

2026-10-15. 계획 `docs/plans/2026-10-15-rust-agent-3b.md`, 스펙 `docs/superpowers/specs/2026-10-15-rust-agent-3b-design.md`,
결정과 남은 차이는 `docs/design/open-questions.md`의 "Rust 이전".

Rust 이식 3단계의 뒤 절반(3b)이 끝났다. 3a(`docs/notes/R3a-runtime.md`)는 동시성을 **Go와 같은 의미로** 옮겼다.
3b는 이식 중 처음으로 **Go와 Rust가 언어 규칙에서 일부러 갈라지는** 단계다.

이 노트는 네 가지를 다룬다.
- 왜 `atom`을 없앴고, 무엇으로 대신했나.
- 그 대신하는 것(에이전트)을 fung 코드와 작은 Rust 도우미로 어떻게 짰나. 배경 태스크, 닫개, 에러 다시 내기.
- 채널에 자기 자신을 보내는 것을 어떻게 막았나(E0705).
- 두 구현이 갈라질 때 테스트를 어떻게 다루나. 그리고 실제로 부딪힌 함정.

## 1. 무엇을 바꿨나

사용자에게 보이는 것:
- `atom`·`swap`·`deref`(Go의 네이티브 함수)가 Rust에서 사라졌다. 대신 prelude에 `agent(v)`·`swap(a, f)`·`deref(a)`가 있다.
  옮겨 쓰기는 `atom(` → `agent(`이면 대개 끝난다. 타입 표기 `atom`도 `agent`가 된다(`fn f(a: agent)`).
- 에이전트는 `<agent>`로 출력된다(atom은 `<atom 1>`처럼 값을 보였다). `type_of`는 `'agent`, `==`는 같은 에이전트인지.
- 새 에러 번호 둘. E0704 `agent called from inside its own swap`, E0705 `channel sent into itself`.

내부에서 바뀐 것:
- `extras/rust/agent.fung`: 에이전트 자체. fung 코드 약 70줄이다. Rust 부팅만 이 파일을 읽고, 공개 이름 셋을 prelude에 더한다.
- `crates/fung-vm/src/vm/agent.rs`: fung 코드만으로는 못 하는 일을 하는 내부 도우미. `_native.conc` 모듈의 멤버라서 사용자 코드는 부를 수 없다(E0310).
  - `spawn_background(f)`: 배경 태스크를 띄운다(4절).
  - `agent_handle(ch)`, `agent_channel(a)`: 닫개 핸들을 만들고, 그 안의 요청 채널을 꺼낸다(5절).
  - `try_call(f, x)`, `raise(e)`: `f`의 에러를 값으로 잡고, 나중에 다시 낸다(6절).
  - `check_swap(a, f)`, `agent_busy(ch, on, state)`, `agent_peek(a)`: 인자 검사와 E0704, "지금 이 에이전트의 `f` 안인가"(6절).
  - `agent_ask(a, request, reply)`: 요청을 보내고 답을 기다린다. 기다리는 동안 핸들을 쥔다(9절 (2)).
  - `send_unchecked(ch, v)`(`conc.rs`): E0705 검사 없이 보내기. 에이전트 내부 요청용(7절).
- 지운 것: `vm/atom.rs`, `Value::Atom`과 그 쓰임새(출력, `type_of`, 비교, 해제), 네이티브 `atom`·`swap`·`deref`, atom 전용 테스트 탐침.
- 새 값 종류 둘: `Value::Agent`(핸들), `Value::Caught`(잡은 에러, `<error>`로 출력, `type_of`는 `'error`). `Value`의 크기는 여전히 16바이트다.
- E0705: `crates/fung-vm/src/vm/channel.rs`의 `contains`가 보내는 값을 훑고, `conc.rs`의 `send`가 부른다(7절).
- 테스트: `tests/lang` 파일 맨 위 `# only: go|rust` 표시와 **Rust 골든 실행기**(`crates/fung-cli/tests/golden.rs`, 8절).

Go 구현은 바뀌지 않았다. Go가 고친 것은 에러 카탈로그(E0704·E0705를 명세로 추가, Go는 쓰지 않음)와 골든 실행기의 `# only:` 처리뿐이다.

## 2. atom을 없앤 이유

`atom`은 **여러 태스크가 함께 보고 바꾸는 칸**이다. `swap(a, f)`는 자물쇠를 잡고 `f(현재 값)`으로 칸을 바꾼다. 편하지만 두 가지가 걸렸다.

**공유되는 변경 칸.** fung의 값은 불변이다. 그런데 atom 하나가 "어디서 누가 언제 바꿨는지 모르는 값"을 언어에 들인다.
그리고 태스크 사이에서 상태를 나누는 방법이 채널과 atom 둘이 된다. 배경 문서의 원칙 5(언어 핵심은 최소, 나머지는 fung으로)·6(같은 일을 하는 방법은 하나로)과 어긋난다.
상태가 필요하면 그 상태를 **한 태스크가 지역 변수로 들고**, 다른 태스크는 그 태스크에게 채널로 편지를 보내 부탁하면 된다.
상태를 바꾸는 쪽이 하나뿐이니 자물쇠가 필요 없고, 이 패턴은 fung 코드로 짤 수 있다.

**순환.** Rust 구현은 메모리를 **참조 계수**(`Rc`: 값을 가리키는 곳의 수를 세다가 0이 되면 해제)로 회수한다. 참조 계수의 약점은 **순환**이다.
A가 B를 가리키고 B가 A를 가리키면 둘 다 계수가 0이 되지 않아 영원히 해제되지 않는다. Go는 가비지 컬렉터(GC: 닿을 수 없는 값을 주기적으로
찾아 회수)가 있어서 순환을 걱정하지 않는다.

불변 값만으로는 순환을 만들 수 없다. 값을 만들 때 그 값은 아직 없으니 자기 자신을 가리킬 수 없기 때문이다. 순환은 **나중에 바꿀 수 있는 칸**에서만 생긴다.
- `swap(a, _ => [a])`: atom의 칸에 그 atom을 담은 리스트를 넣는다. 순환.
- `send(c, c)`: 채널의 버퍼(바꿀 수 있는 칸)에 그 채널을 넣는다. 순환.

3a에서는 이 둘이 새어 나갔다(R3a 8절 뒤 목록). 3b는 첫째를 atom 자체를 없애서, 둘째를 E0705로 막아서 푼다.

대가도 있다. 읽기와 쓰기가 자물쇠 한 번이 아니라 **편지 왕복**(보내고, 그 태스크가 처리하고, 답을 받기)이라 느리다. 개인용 스크립트 언어에서
카운터 하나 세는 정도에는 문제되지 않는 크기로 봤다.

## 3. Erlang의 원칙과 채널로 짠 에이전트

### Erlang은 어떻게 하나

Erlang의 프로세스(fung의 태스크에 해당)는 메모리를 나누지 않는다. 상태는 프로세스가 재귀 함수의 인자로 들고 돈다.

```
loop(State) ->
  receive
    {get, From}    -> From ! State, loop(State);
    {update, F}    -> loop(F(State))
  end.
```

다른 프로세스는 이 프로세스의 **메일박스**(프로세스마다 하나 있는 받은 편지함)에 편지를 넣는다. Elixir의 `Agent`는 이 모양을 감싼 라이브러리이고,
fung의 `agent`도 이름과 모양을 거기서 가져왔다.

### fung에서는 채널로

fung에는 메일박스가 없고 **채널**이 있다. 그래서 요청 채널 하나를 메일박스 대신 쓴다. `extras/rust/agent.fung`의 뼈대는 이렇다.

```
fn _serve(ch, state) = match recv(ch):
  Ok(('swap, f, reply)) => _serve(ch, _apply(ch, state, f, reply))
  Ok(('deref, reply))   => _serve(ch, _answer(reply, state))
  Err(_)                => nil
;;
```

- 상태는 `_serve`의 인자다. 바꾸는 일은 "새 상태로 다시 부르기"다. 이 부르기는 **꼬리 호출**이라(M3의 TCO) 요청을 몇 번 받아도 스택이 자라지 않는다.
  단위 테스트가 프레임 한도(`MAX_FRAMES`)보다 한 번 더 많은 요청을 보내 확인한다.
- 요청은 튜플이다. `('swap, f, reply)`와 `('deref, reply)`. `reply`는 요청마다 새로 만드는 빈 칸 하나짜리 채널(`channel(1)`)이고, 답장이 거기 온다.
- 요청은 들어온 순서대로 하나씩 처리된다. 그래서 `swap` 400번을 8개 태스크에서 동시에 해도 결과는 정확히 400이다(`tests/lang/agents.fung`).
- `Err(_)`는 요청 채널이 닫혔다는 뜻이다. 그때 반복문이 끝나고 태스크도 끝난다(5절).

### 메일박스와 무엇이 다른가

- **누구에게 보내나.** Erlang은 프로세스 번호로 보낸다. fung은 채널로 보낸다. 에이전트 핸들 안에 요청 채널이 들어 있다.
- **골라 받기.** Erlang의 `receive`는 메일박스에서 원하는 모양의 편지만 골라 꺼낼 수 있다. fung의 `recv`는 맨 앞 것을 꺼낸다.
  에이전트는 모든 편지를 처리하므로 이 차이가 문제되지 않는다.
- **끝나는 때.** Erlang 프로세스는 누가 자기를 가리키는지 모른다. 그래서 할 일이 없어도 스스로 끝나지 않는다(link·monitor 같은 따로 된 장치가 필요).
  fung은 참조 계수 덕분에 "이 에이전트를 가리키는 핸들이 하나도 없다"는 순간을 정확히 알고, 그때 에이전트를 끝낸다(5절).

메일박스 모델(태스크 번호 + 골라 받기)은 이번 범위 밖이다. 나중에 가더라도 `agent`의 겉모습은 그대로 두고 안만 바꿀 수 있다.

## 4. 배경 태스크와 종료 순서

에이전트는 태스크다. 그런데 보통 태스크와 똑같이 다루면 두 문제가 생긴다.
- **프로그램이 끝나지 않는다.** fung 프로그램은 진입 파일이 끝나도 남은 태스크를 기다린다(05). 에이전트는 다음 편지를 기다리며 영원히 `recv`에서 막혀 있다.
- **거짓 교착.** 모든 태스크가 막히면 교착(E0702)이다(R3a 6절). 진입 파일이 에이전트의 답을 기다리는 순간, 에이전트가 아직 편지를 꺼내기 전이라면 둘 다 "막힘"으로 보일 수 있다.

그래서 **배경 태스크**라는 종류를 새로 만들었다. 차이는 셋이다.
- **프로그램이 끝나기를 막지 않는다.** 따로 센다(`World::background`). 프로그램은 보통 태스크만 기다린다.
- **취소 트리의 다른 뿌리에 매달린다**(`Shared::background`). 그래서 자기를 띄운 태스크보다 오래 살고, `exit`·진입 파일 에러가 보통 태스크를 모두 취소해도 살아남는다.
- **교착 집계를 따로 한다**(`Census::bg_blocked`·`bg_waking`).

### 교착 판정에 붙은 조건

3a의 판정 조건(`live > 0`, `blocked == live`, `waking == 0`)에 하나가 붙었다.

> 배경 태스크도 모두 막혀 있고 타이머로 깰 것도 없다(`bg_blocked == background && bg_waking == 0`).

말로 하면 "**배경 태스크가 하나라도 돌 수 있으면 판정하지 않는다**". 이것이 왜 옳은가.
- 배경 태스크의 수도 3a와 같은 규칙으로 정확히 센다. 잠들기 전에 스스로 세고, 깨우는 쪽이 실행권 아래에서 뺀다.
- 그래서 조건이 참이면 보통이든 배경이든 모든 태스크가 막혀 있고 아무것도 오는 중이 아니다. 진짜 교착이다.
- 배경 태스크가 돌 수 있다면 그것이 보통 태스크를 깨울 수 있다. 판정하지 않는 게 맞다. "요청을 보냈고 답을 기다리는" 구간이 바로 이 경우다.
- 반대로 보통 태스크가 아무도 보내지 않는 채널에서 막혀 있고, 옆에 놀고 있는 에이전트가 `recv`에서 막혀 있으면 모두 막힘이다. E0702가 난다.
  배경 태스크가 진짜 교착을 가리면 안 된다는 리뷰 요구를 이렇게 지켰다.

배경 태스크가 막히거나 끝날 때도 판정한다. 둘 다 조건을 참으로 만들 수 있는 사건이기 때문이다(3a의 "조건이 참이 될 수 있는 순간에만 판정"과 같은 원리).
이 판정 조각을 하나씩 일부러 지워 보니, 배경 조건을 빼면 거짓 E0702가 8건 나고, 막힘·끝남 때의 판정을 빼면 테스트가 멈췄다.

### 종료 순서

`crates/fung-cli/src/run.rs`(그리고 테스트의 `testutil::finish`)는 이 순서로 끝난다.
1. 진입 파일
2. 보통 태스크 기다리기(에러나 `exit`면 취소하고 기다리기)
3. `at_exit` 핸들러
4. 배경 태스크 취소하고 기다리기(`Runtime::end_background`)
5. 배경 태스크가 띄운 태스크 기다리기
6. 꺼내지 않은 실패 보고

배경 태스크를 핸들러 **뒤에** 끝내는 이유: 핸들러에서 카운터를 읽는 일이 흔하다(`at_exit(() => print(deref(counter)))`). 핸들러가 돌 때 에이전트는 아직 살아 있다.

### 배경 태스크가 띄운 태스크

에이전트의 `f`는 사용자 코드다. `f` 안에서 `pmap`을 부르면 보통 태스크가 생긴다. 이 태스크는 어떤 종류여야 할까. 9절 (1)의 함정 끝에 정한 규칙:
- 배경 태스크가 (직접이든 손자든) 띄운 태스크는 **배경 종류를 물려받는다**. 세는 법과 수명이 배경 태스크와 같다.
- 다만 실패 보고는 남긴다. 사용자가 띄운 태스크의 실패는 꺼내지 않으면 보고하고 종료 코드를 1로 한다. 보고를 끄는 것은 `spawn_background` 자신이 띄운 태스크(에이전트 반복문, 내부 코드)뿐이다.
- 대가: 에이전트의 `f`가 띄운 태스크가 끝없이 돌면, 그 태스크는 프로그램이 끝나기를 막지 못하고 4번에서 취소된다.

## 5. 닫개: 참조 계수로 자원 수명을 정확히 잡기

에이전트는 언제 끝나야 할까. "아무도 그 에이전트에게 편지를 보낼 수 없게 되었을 때", 곧 **핸들이 하나도 남지 않았을 때**다.
GC 언어에서는 이 순간을 정확히 알 수 없다. GC가 언제 돌지 모르기 때문이다. 참조 계수는 안다. 마지막 사본이 사라지는 순간 Rust의 `Drop`이 불린다.

에이전트 핸들(`Value::Agent`)은 요청 채널을 감싼 값이고, `Drop`에서 그 채널을 **닫는다**(`close(ch)`와 같은 길이라서 기다리던 쪽도 깬다).
이런 값을 이 노트에서는 **닫개**라고 부른다. 파일 핸들을 닫는 Rust의 `File`, C++의 RAII(자원 획득은 초기화, 자원 수명을 값의 수명에 묶는 기법)와 같은 생각이다.

```
a = agent(0)        # 핸들 하나
b = a               # 같은 핸들의 사본(계수 2)
# a, b가 모두 사라지면 → 요청 채널 닫힘 → _serve가 Err(_)를 받고 끝 → 배경 태스크 끝
```

이것이 동작하려면 **에이전트 자신은 핸들을 쥐면 안 된다.** 반복문이 핸들을 쥐면 계수가 0이 되는 날이 오지 않는다. 그래서:
- 반복문(`_serve`)은 요청 채널만 쥔다. 핸들은 `agent(v)`가 마지막에 만들어 돌려준다.
- "지금 이 에이전트의 `f` 안인가"를 기록하는 표시도 핸들이 아니라 **채널**에 단다(`agent_busy(ch, …)`). 6절.
- 첫 상태도 반복문의 함수가 붙잡지 않게 한 칸짜리 채널 `first`로 건넨다(9절 (3)).

테스트 전용 탐침(배경 태스크 수)으로, 핸들이 모두 사라진 에이전트가 **프로그램 도중에** 끝나 태스크가 쌓이지 않음을 확인했다.

남는 경우: 상태 안에 그 에이전트 자신을 넣으면(`swap(a, _ => a)`) 핸들이 사라지지 않아 그 에이전트는 프로그램 끝까지 남는다.
배경 태스크라서 프로그램을 멈추게 하지는 않고, 4번 단계에서 취소된다.

**일반 채널은 자동으로 닫지 않는다.** 처음 결정(open-questions)은 "보낼 쪽이 모두 사라진 채널은 자동으로 닫힌다"였지만, fung의 채널 값은
보내는 쪽과 받는 쪽이 같은 값이라 "보낼 쪽만" 셀 수 없다. 에이전트처럼 보내는 쪽만 들고 있는 핸들이 따로 있을 때만 정확히 된다. 일반 채널은 지금처럼 `close`로 닫는다.

## 6. `f`의 에러를 부른 쪽에서 다시 내기

`swap(a, f)`의 `f`는 **에이전트의 태스크에서** 돈다. 그런데 `f`가 실패하면 그 에러는 누구의 것인가.
- 에이전트의 것이 되면 안 된다. 에러 하나로 에이전트가 죽으면, 그 에이전트를 쓰는 모든 태스크가 영원히 기다린다.
- `swap`을 부른 쪽이 받아야 한다. 사용자가 보기에 실패한 것은 자기가 쓴 `swap(…)` 줄이다.

그래서:
1. 에이전트는 `try_call(f, state)`으로 `f`를 부른다. 결과는 `Ok(새 값)` 아니면 `Err(잡은 에러)`.
   잡은 에러(`Value::Caught`)는 번호·문구·도움말은 그대로 두고 위치와 호출 경로는 지운다. 에이전트 태스크의 위치가 새어 나가지 않게.
2. 실패면 상태를 그대로 두고 `Err(e)`를 답장한다.
3. 부른 쪽 `swap`이 `raise(e)`로 다시 낸다. `raise`는 위치 없는 에러를 내고, VM이 이것을 **사용자의 `swap(` 위치**로 옮긴다.
   `swap`은 내장 파일(`extras/rust/agent.fung`) 안의 함수이고, 내장 파일 안의 에러는 가장 가까운 사용자 프레임의 호출 위치로 옮긴다는 규칙(M7.5)이 이미 있다.

```
a = agent(1)
swap(a, x => x / 0)     # error[E0502] … 이 줄의 swap( 위치. 에이전트는 살아 있고 상태는 1
```

`try_call`이 잡지 않는 것: 취소(E0701)와 교착(E0702). 이것은 `f`의 실패가 아니라 런타임의 일이다.
`exit()`은 잡는다. `f` 안의 `exit(n)`은 부른 쪽에서 `exit(n)`으로 다시 나고, 에이전트는 상태를 그대로 둔 채 계속 일한다(9절 (5)).

### E0704와 `f` 안의 `deref`

에이전트의 `f` 안에서 같은 에이전트에 `swap`하면 어떻게 될까. 에이전트는 지금 `f`를 돌리느라 바쁘다. 새 요청은 `f`가 끝나야 꺼낼 수 있고,
`f`는 그 요청의 답을 기다린다. 영원히 끝나지 않는다. atom의 재진입 에러를 이어 E0704 `agent called from inside its own swap`으로 막는다.

그러려면 "지금 이 태스크가 그 에이전트의 `f` 안인가"를 알아야 한다.
- 에이전트는 `f`를 부르기 전 `agent_busy(ch, true, state)`로 채널에 **표시**를 단다. 표시는 새로 만든 꼬리표(`Mark`)와 바꾸기 전 상태다. 그리고 그 꼬리표를 자기 태스크의 목록에도 넣는다.
- `spawn`은 띄우는 쪽의 꼬리표 목록을 자식에게 물려준다. 그래서 `f` 안에서 `pmap`이 띄운 태스크도 "안"이다.
- `check_swap(a, f)`는 인자를 검사하고(E0403), 지금 태스크가 `a`의 현재 꼬리표를 갖고 있으면 E0704를 낸다.

`f` 안의 `deref(a)`는 기다리지 않고 **바꾸기 전 값**을 돌려준다(atom에서 `swap` 안의 `deref`와 같은 의미). `agent_peek(a)`가 안이면 `Ok(state)`, 밖이면 `Err(nil)`을 준다.

## 7. E0705와 깊이 훑기

`send(ch, v)`에서 `v` 안 어디에든 `ch`가 들어 있으면 E0705 `channel sent into itself`. 버퍼에 자기 자신을 넣어 생기는 순환을 막는다.

### 무엇을 훑나

| 값 | 훑나 | 이유 |
|---|---|---|
| 리스트(영속 벡터·보기 포함), 맵의 값, 튜플, 태그 인자 | 예 | 값을 담는 그릇 |
| 클로저가 붙잡은 값 | 예 | 모델 C에서 클로저는 보이는 변수를 복사해 붙잡는다. `f = () => ch; send(ch, f)`도 잡힌다 |
| 에이전트 핸들 | 그 요청 채널을 비교 | 핸들 안에 채널이 있다 |
| 다른 채널 | 같은 채널인지만 비교, 그 버퍼는 훑지 않음 | 두 채널이 서로를 담는 간접 순환은 잡지 않는다(스펙에서 정함) |
| 모듈, 클로저의 전역 | 아니오 | 런타임이 끝날 때 `World::release_values`가 이 순환을 끊는다. 훑으면 보낼 때마다 프로그램 전체 상태를 훑게 된다 |
| 태스크 핸들 | 아니오 | 끝난 태스크의 결과를 보면 에러가 시점에 달려 결정적이지 않다 |
| 문자열, 숫자, 심볼, 기간, 범위 등 | 아니오 | 다른 값을 담지 않는다 |

에이전트 내부 요청은 검사하지 않는다(`send_unchecked`). `f`가 에이전트를 붙잡고 있어도(`swap(a, x => x + len([a]))`) 요청은 곧 꺼내지므로 순환이 남지 않는다.

### 재귀 대신 반복

깊이 훑기를 재귀 함수로 짜면, 백만 단계로 겹친 리스트에서 Rust 스택이 넘친다(R2 6절의 깊은 해제와 같은 문제). 그래서 **명시적 스택**(`Vec<&Value>`)으로 반복한다.
- 그릇(리스트·맵·튜플·태그·클로저)만 스택에 넣는다. 채널과 에이전트는 그 자리에서 비교하고, 나머지는 건너뛴다.
- 백만 단계 중첩 리스트가 디버그와 릴리스 모두에서 통과한다.

### 공유된 부분을 두 번 훑지 않기

불변 값은 부분을 자유롭게 공유한다. `x = [x, x]`를 40번 하면 값은 40단계지만 길은 2^40개다. 길을 따라 그대로 훑으면 끝나지 않는다.
- 이미 본 그릇의 주소를 집합(`HashSet<*const ()>`)에 적고 다시 만나면 건너뛴다.
- 다만 **공유된 그릇만**(`Rc::strong_count > 1`) 적는다. 계수가 1인 그릇은 거기로 가는 길이 하나뿐이라 두 번 만날 수 없다. 그래서 갓 만든 보통 값에서는 집합이 비어 있다.
- 집합을 끄면 40단계 테스트가 60초 시간 제한에 걸려 죽는 것을 확인했다.

### 비용

`send`의 비용이 보내는 값의 크기에 비례하게 되었다(릴리스 빌드에서 쟀다).

| 보내는 값 | 전 | 후 |
|---|---|---|
| 정수 100만 개짜리 리스트 | 거의 0 | 한 번에 약 0.75 ms |
| 원소 하나짜리 리스트 100만 개의 리스트 | 거의 0 | 한 번에 약 4.75 ms |

큰 값을 자주 보내는 반복문은 느려진다. 에이전트 내부 요청은 검사하지 않으므로 영향이 없다.
또 하나: 같은 영속 벡터를 공유하는 여러 보기(슬라이스)는 보기마다 자기 범위를 다시 훑는다. 보기 자체가 공유 그릇이 아니라서 집합이 막아 주지 못한다.

## 8. Go와 갈라지는 테스트: `# only:`와 Rust 골든 실행기

지금까지 `tests/lang`의 골든 파일(`# expect` 주석에 기대 출력을 적은 fung 파일)은 Go가 정답지였다. Rust는 "Go와 바이트 단위로 같나"(실행 대조)로 검사했다.
3b부터는 두 구현이 일부러 다른 파일이 생긴다. Rust에는 `atom`이 없고, Go에는 `agent`가 없다.

**표시.** 파일 맨 위에 `# only: go` 또는 `# only: rust`. 알 수 없는 값이나 두 번 쓴 표시는 두 실행기 모두 에러다.
- Go 골든 실행기(`internal/golden`, `tests/golden_test.go`)는 `# only: rust`를 건너뛴다.
- Go 대조(`run_parity.rs`)는 표시된 파일을 모두 건너뛴다. 같을 리 없기 때문이다.
- dump 대조(`parity.rs`)는 표시된 파일과 atom을 쓰는 예제(`examples/api.fung`·`serve.fung`)에서 `dump ast`만 비교한다. 이름 해석 뒤의 `core`·`bytecode`는 갈라진다.

**Rust 골든 실행기**(`crates/fung-cli/tests/golden.rs`). Go `internal/golden`의 규칙(`# expect`, `# expect-error`, `# expect-exit`, `# args`, `# stdin`, `# only:`)을 옮겼다.
`# only: go`가 아닌 파일을 Rust `fung run`으로 돌려 **파일에 적힌 기대값**과 비교한다. Go 바이너리 없이 돈다. 그래서 6단계에서 Go를 지운 뒤에도 남는 검사다.
- 지금: 130개 확인, `# only: go` 3개(`atoms`, `err_atom_reentry`, `conc_atoms`), 네이티브 모듈 때문에 건너뛴 9개(`http_serve`는 `# only: go`이면서 이 목록에도 있다. 4단계가 `http`를 들여도 atom을 쓰므로 6단계까지 Go 전용).
- `# only: rust` 파일: `agents`, `agent_errors`, `agent_handles`, `err_agent_reentry`, `err_channel_self`.
- 확인 수의 바닥은 127이다. 목록이 잘못 늘어 검사가 빠지면 여기서 걸린다.

두 종류의 검사가 서로를 보완한다. 실행 대조는 "Go와 같나"를, 골든 실행기는 "파일에 적은 언어 규칙과 같나"를 본다. 갈라진 파일은 후자만 지킨다.

## 9. 실제로 부딪힌 함정

이번 단계에서 실제로 겪고 진행 기록(`.superpowers/sdd/2026-10-15-rust-agent-3b/progress.md`)과 작업 보고서에 적힌 것만 적는다.

**(1) 배경 태스크가 띄운 보통 태스크가 `exit`와 교착 판정을 멈춰 세웠다.**
- 처음 구현(Task 3)에서 배경 태스크가 띄운 태스크는 **취소 트리로는** 배경 뿌리 아래에 있었지만, **세기로는** 보통 태스크였다.
- 그러자 `exit`, 진입 파일 에러, 교착이 모두 멈췄다. 명령은 보통 태스크 수가 0이 되기를 기다리는데, 그 태스크는 보통 뿌리를 취소해도 닿지 않는 배경 뿌리 아래에 있었다.
  교착 판정은 이 태스크를 보통 집계에 넣어 조건이 맞지 않았다.
- 해결: 배경 태스크가 (전이적으로) 띄운 태스크는 배경 종류를 물려받는다(4절). 네 재현 사례(`exit`, 진입 파일 에러, 교착, 잠든 자식이 있는 `exit`)가 고치기 전에는 모두 시간 초과였고, 고친 뒤에는 모두 끝난다(잠든 자식 사례는 1초 안에).
- 교훈: 태스크의 "종류"는 한 곳(세기)이 아니라 **세기·취소 트리·수명** 세 곳이 함께 맞아야 한다. 한 곳만 바꾸면 그 틈에서 멈춘다.

**(2) 마지막 핸들로 `deref`하면 꼬리 호출이 닫개를 불러 교착이 됐다.**
- `deref(agent(5))`나, 지역 에이전트를 꼬리 위치에서 `deref`하는 함수. 핸들의 사본이 하나뿐이다.
- `deref`가 요청을 보낸 뒤 답을 기다리는 함수를 **꼬리 호출**하면, 꼬리 호출은 지금 프레임을 버린다. 그 프레임이 쥐고 있던 마지막 핸들이 사라지고, 닫개가 요청 채널을 닫는다.
  에이전트는 `Err('closed)`를 받고 끝나고, 부른 쪽은 오지 않을 답을 기다린다.
- 해결: `agent_ask(a, request, reply)` 도우미 하나가 보내기와 기다리기를 함께 한다. 그 인자 목록이 답이 올 때까지 핸들 사본을 쥔다.
- 교훈: 참조 계수로 수명을 잡으면 "언제 마지막 사본이 사라지나"가 프로그램 동작이 된다. TCO처럼 **프레임을 일찍 버리는 최적화**가 그 시점을 앞당긴다.

**(3) 첫 상태를 띄우는 클로저가 붙잡아 평생 남았다.**
- 처음에는 `spawn_background(() => _serve(ch, v))`였다. 태스크는 자기의 첫 함수를 평생 쥔다. 그 클로저가 첫 상태 `v`를 붙잡았으므로,
  상태가 바뀐 뒤에도 첫 값이 해제되지 않았다. 첫 값이 큰 데이터라면 그만큼 새어 나간다.
- 해결: `v`를 한 칸짜리 채널 `first`에 넣어 건네고, 반복문이 시작하며 한 번 꺼낸다(`_start(ch, first) = _serve(ch, recv(first)!)`). 클로저는 이제 빈 채널 둘만 쥔다.
- 탐침 테스트 `the_first_state_is_not_kept_by_the_loop`가 지킨다.

**(4) 두 번의 네이티브 호출 사이에 확인과 행동이 엇갈렸다.**
- `deref`는 처음에 `in_agent(a)`로 "안인가"를 묻고, 참이면 `agent_state(a)`로 상태를 읽었다. 두 번의 호출이다.
- 그 사이에 차례가 넘어갈 수 있다(3a의 `YIELD_EVERY`, 함수 호출 1만 번마다). 넘어간 사이에 에이전트가 `f`를 끝내고 표시를 지우면, 둘째 호출은 표시가 없어 내부 에러 E0801을 냈다.
  `f` 안에서 띄운 태스크가 `deref`를 많이 부를 때 생겼다.
- 이런 버그를 **확인 후 행동**(check-then-act) 경쟁이라고 한다. 확인한 사실이 행동할 때는 이미 거짓일 수 있다.
- 해결: 확인과 읽기를 한 번의 호출 `agent_peek(a)`로 합쳤다. 한 네이티브 호출 안에서는 차례가 넘어가지 않는다. `in_agent`·`agent_state`는 지웠다.
- 다른 곳도 살폈다. `swap`의 `check_swap` → `agent_ask`는 안전하다. 태스크의 꼬리표 목록은 그 태스크가 도는 동안 늘지 않으므로, "밖"이라는 답이 나중에 "안"으로 바뀌지 않는다.
- 테스트는 래퍼 깊이를 0부터 6까지 바꿔 차례가 넘어가는 자리를 옮기며 돌린다. 고치기 전에는 깊이 2에서 E0801이 났다.

**(5) `f` 안의 `exit()`이 에이전트를 죽였다.**
- 처음 `try_call`은 `exit`를 잡지 않고 그대로 흘려보냈다. 그러면 에이전트 태스크 자체가 끝났다. 뒤에 `at_exit` 핸들러가 그 에이전트에 `deref`하면 답이 오지 않아 E0702가 났다.
  atom이었다면 핸들러는 값을 읽었다.
- 해결: `Caught`를 `Error`·`Exit` 두 갈래로 나누고 `try_call`이 `exit`도 잡는다. 부른 쪽에서 `raise`가 `exit(n)`으로 다시 내고, 에이전트는 상태를 그대로 두고 계속 일한다.

**(6) Go가 `extras/*.fung`를 통째로 넣어서 Go의 `import agent` 에러가 바뀌었다.**
- 처음에는 파일을 `extras/agent.fung`에 두었다. Go는 `//go:embed *.fung`로 `extras/`의 fung 파일을 모두 바이너리에 넣는다.
  그러자 Go에서 `import agent`가 "모듈을 찾을 수 없음"(E0301) 대신 Go에 없는 `_native.conc` 멤버 13개의 E0303이 되었다. Go의 동작을 바꾸지 않는다는 제약에 어긋난다.
- 해결: `extras/rust/agent.fung`로 옮겼다. Go의 `embed` 패턴은 하위 디렉터리로 내려가지 않는다. Go `fmt --check extras`는 내려가므로 포맷 검사는 그대로 받는다.

### 알고 남긴 동작

모두 open-questions "Rust 이전"의 3b 목록에 적었다.
- **꼬리 위치의 `swap`.** fung으로 쓴 모든 prelude 함수처럼 `swap`도 꼬리 위치에서는 부른 쪽 프레임을 대신한다. 그래서 `f`의 에러가 `swap(`이 아니라 바깥 호출에서 난다.
  꼬리 위치의 E0704도 같다(`swap(a, x => swap(a, y => y))`는 안쪽이 아니라 바깥 `swap(`). Go도 자기 fung prelude 함수에서 똑같이 동작한다. atom은 네이티브라 프레임이 남았던 것이다.
  안쪽 위치를 얻으려면 꼬리 호출마다 호출 자리를 프레임에 적어야 해서 VM을 바꾸지 않았다.
- **에이전트끼리의 `deref`.** 에이전트 b의 `f` 안에서 `deref(a)`를 하는데 a가 b를 기다리고 있으면 진짜 교착이다. E0702로 보고된다.
- **막히지 않는 배경 태스크.** 계속 도는 배경 태스크가 있으면 다른 태스크들 사이의 진짜 교착이 보고되지 않는다. 계속 도는 보통 태스크도 이미 그렇다.
- **끝나지 않는 에이전트.** 상태가 자기 핸들을 품었거나, `f`가 바쁜 도중 끊긴 에이전트는 프로그램이 끝날 때까지 남는다.
- **E0705가 보지 않는 곳.** 두 채널 사이의 순환, 모듈·전역, 태스크 핸들. `send` 비용은 값의 크기에 비례한다.
- **출력.** 에이전트는 값이 아니라 `<agent>`로 출력된다. 값을 보이려면 에이전트에 물어야 해서 출력이 막히는 연산이 되기 때문이다.
