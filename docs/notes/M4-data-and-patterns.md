# M4. 자료구조와 패턴 — 무엇을 만들었고 왜 그렇게 했나

M4는 값과 패턴이다. 리스트·맵·튜플·태그·범위, 인덱스와 슬라이스, `match`와 guard, 구조 분해 대입,
결과값 연산자 `!` `?` `??`, 파이프 `|>`와 부분 적용 `_`, `for`, `in`, `type` 별칭, 가변 인자 `...rest`.
언어 핵심(core form)은 거의 늘지 않았다. 새로 생긴 명령은 컬렉션 생성·접근 명령과 **`MATCH` 한 개**가 중심이다.

## 1. 한눈에

```
fn sign(v) = match v:
  0 => "zero"
  n when n < 0 => "neg"
  _ => "pos"
;;
```

`fung dump bytecode`의 `sign` 부분:
```
== sign ==
0000  LOADLOCAL    0          ; v
0001  STORELOCAL   1          ; $m0 = v  (대상을 한 번만 계산해 숨은 변수에)
0002  LOADLOCAL    1
0003  MATCH        0    ; 0   ; 패턴 0번(리터럴 0)과 맞춰 보고 bool을 남긴다
0004  JUMPIFFALSE  7          ; 안 맞으면 다음 절로
0005  CONST        0    ; "zero"
0006  JUMP         23         ; 절 끝 → match 끝
0007  LOADLOCAL    1
0008  MATCH        1    ; $2  ; 패턴 1번: 이름 n → 2번 슬롯에 쓴다
0009  JUMPIFFALSE  16
0010  LOADLOCAL    2          ; guard: n < 0
0011  CONST        1    ; 0
0012  LT
0013  JUMPIFFALSE  16         ; guard가 거짓이면 다음 절로
0014  CONST        2    ; "neg"
0015  JUMP         23
0016  LOADLOCAL    1
0017  MATCH        2    ; _
0018  JUMPIFFALSE  21
0019  CONST        3    ; "pos"
0020  JUMP         23
0021  LOADLOCAL    1
0022  NOMATCH                 ; 어느 절도 안 맞음 → E0601
0023  RETURN
```

`match`는 **절마다 "대상 로드 → `MATCH` → 거짓이면 다음 절 → (guard) → 본문 → 끝으로 점프"**의 반복이다.
`if`/`else` 사슬과 구조가 같고, 차이는 조건 자리에 `MATCH`가 있다는 것뿐이다. 패턴 자체는 명령에 들어 있지 않고
Proto의 **패턴 상수표**(`Patterns`)에 트리로 저장된다. `MATCH 1 ; $2`의 `$2`는 "슬롯 2에 묶는 이름 패턴"이라는 뜻이다.

## 2. 값 표현

새 값 다섯 가지는 모두 `internal/value`의 Go 구조체다 (02).

| fung | Go | 비고 |
|------|----|------|
| `[1, 2]` | `*List{Items}` | 불변. `+`는 새 리스트. |
| `(1, 2)` | `*Tuple{Items}` | 리스트와 **다른 타입**: `[1] == (1,)`는 false. |
| `{a: 1}` | `*Map{keys, vals}` | 삽입 순서 유지 + 해시 색인. 출력 순서가 입력 순서다. `==`는 순서를 무시한다. |
| `Circle(3)` | `*Tag{Name, Args}` | `TypeName()`이 태그 이름을 돌려주므로 `type_of(Circle(3)) == 'Circle`, 타입 표기 `s: Circle`이 그대로 맞는다. |
| `0..3` | `Range{Start, End, Inclusive}` | **게으르다**: 원소를 만들지 않고 `Len`·`Contains`만 계산. `map`·`for`가 필요할 때 `Items()`로 펼친다. |

"불변·단순 복사"가 핵심이다. 리스트를 담은 변수를 다른 변수에 대입하면 같은 Go 포인터를 가리키지만, 바꿀 수 있는
연산이 없으므로 공유가 보이지 않는다. 슬라이스는 항상 **복사본**을 만든다(`append([]Value(nil), …)`). 원본의 뒷부분을
참조하는 Go 슬라이스를 그대로 돌려주면 나중에 가변 연산이 생겼을 때 함정이 된다.

괄호 없는 `Red`는 태그가 아니라 **심볼** `'Red`다. 태그는 `이름(…)` 꼴일 때만 만들어진다 (02).

## 3. 패턴 엔진

패턴은 파서가 `pbind` `plit` `ptag` `ptuple` `plist` `pmap` `palt` `pwild` 노드로 읽고, resolve가 이름을 슬롯·전역으로
바꾸고(`(pbind (local 2))`), 컴파일러가 `bytecode.Pattern` 트리(상수)로 바꾼다. 실행은 `vm/match.go`의
`matchPattern` **함수 하나**다. 패턴 종류가 여덟이지만 각각 몇 줄이다: 리터럴은 `value.Equal`, 태그는 이름과 인자 수가
같고 인자가 각각 맞을 것, 리스트는 길이(또는 rest가 있으면 "최소 길이")와 원소, 맵은 **적힌 키만** 있고 맞을 것(다른 키는
무시), `|`는 차례로 시도.

**실패한 절의 슬롯 재사용이 안전한 이유.** `(a, b) when a > 100 => …; (c, _) => c` 에서 첫 절은 `a`, `b`를 슬롯에
쓰고 나서 guard에서 실패한다. 두 번째 절의 `c`는 `a`와 같은 슬롯을 쓸 수도 있다. 그래도 안전한 것은, 절의 이름은 그
절의 본문·guard에서만 보이므로(resolve가 절마다 블록 스코프를 연다) 실패한 절이 써 둔 값을 **읽는 코드가 없기**
때문이다. 쓰기만 있고 읽기가 없는 값은 쓰레기라도 문제가 없다. 그래서 `MATCH`는 되돌리기(롤백)를 하지 않는다.

**`|` 대안의 이름 검사(E0216).** `Ok(x) | Err(y) => …`를 허용하면 본문에서 `x`가 묶였는지 알 수 없다. 모든 대안이
같은 이름 집합을 묶어야 한다고 resolve가 확인한다. 실행 시점이 아니라 **컴파일 시점** 에러인 이유는, 이 문제가 값과
무관하게 코드 모양만으로 결정되기 때문이다.

**괄호 없는 태그의 함정.** `match v: Ok => 1` 의 `Ok`는 심볼 `'Ok`를 뜻하지 "`Ok(…)` 아무거나"가 아니다.
`Ok(_)`라고 써야 한다. 02의 규칙("태그는 괄호가 있을 때만")을 패턴에도 똑같이 적용한 결과다. 예외를 두면
"식에서는 심볼, 패턴에서는 태그"라는 조항이 생긴다 (원칙 7).

## 4. 구조 분해는 대입, `match` 절은 가리기

같은 패턴 문법이 두 곳에 쓰이지만 **이름을 묶는 규칙이 다르다.**

- `(a, b) = f()`는 **대입**이다. 03의 대입 규칙 그대로: 같은 스코프에서 재대입 OK, 바깥 블록의 이름이면 E0205.
  `(a, b) = (b, a)`로 맞바꾸기가 되는 것은 이 때문이다. 바이트코드는 `값; MATCHORFAIL p` 한 쌍이고, 안 맞으면 E0602.
- `match` 절의 이름과 `for`의 변수는 **새 이름**이다(가리기). 절은 그 자체로 작은 블록이고, 바깥 `n`이 있어도
  `n => …`은 새 `n`을 만든다. 절마다 스코프를 열고 닫으므로 절 이름이 밖으로 새지 않는다.

왜 둘을 다르게 두는가. `match`의 이름이 대입이라면 `x = 10; match v: x => …`가 바깥 `x`를 덮어쓰거나(놀람)
에러가 나야(불편) 한다. 반대로 구조 분해가 가리기라면 `(a, b) = (b, a)`가 새 이름을 만들어 맞바꾸기가 안 된다.
각각 그 자리에서 사람이 기대하는 쪽을 택했고, 03에 한 줄로 적었다.

## 5. 숨은 변수와 desugar

desugar는 새 문법을 **이미 있는 핵심 형태로** 바꾼다. 컴파일러와 VM은 파이프·부분 적용·`for`를 모른다.

| 표면 | 핵심 형태 |
|------|------|
| `xs \|> map(f)` | `(call map xs f)` — 왼쪽 값을 첫 인자로 끼워 넣는다 |
| `add(1, _)` | `(do (let $p0 add) (let $p1 1) (fn (h0) (call $p0 $p1 h0)))` |
| `for x in xs: body ;;` | `(call map xs (fn ($f0) (do (let x $f0) body)))` |
| `match e: …` | `(do (let $m0 e) (match $m0 …))` |

`$p0` `$f0` `$m0`은 **숨은 변수**다. `$`는 사용자 식별자에 쓸 수 없으므로 충돌하지 않고, resolve는 보통 변수처럼
슬롯을 준다. 부분 적용에서 `add`와 `1`을 먼저 `let`으로 받아 두는 이유는 **고정 인자를 한 번만 계산하기** 위해서다.
`g = f(side(), _)`에서 `side()`는 `g`를 만들 때 한 번 실행되고, `g(1)` `g(2)`에서는 실행되지 않는다. 람다가
`$p0` `$p1`을 **복사**(모델 C)하므로 그 값이 람다 안에 고정된다.

`for`가 `map` 호출로 풀리므로 `for` 본문의 `return`은 바깥 함수가 아니라 람다에서 돌아가게 된다. 그래서 resolve가
`for` 본문의 `return`을 E0213으로 막고 `find`/`all`/`any`/`fold`를 권한다 (M5).

## 6. `!` `?` `??`

세 연산자는 02의 표 한 장으로 정해지고, 명령은 세 개다.

- `x!` → `UNWRAPABORT`: `Ok(v)`면 `v`, `Err(e)`면 E0603(`message` 키가 있는 맵이면 그 문장), nil이면 E0604, 그 외 E0605.
- `x ?? b` → `x; COALESCE L1; JUMP L2; L1: b; L2:`. `Ok(v)`는 `v`로 풀고, nil·Err면 버리고 `b`로 간다. 그 외 값은 그대로.
- `x?` → `x; UNWRAPTEST L1; JUMP L2; L1: [CHECKRETURN] RETURN; L2:`. `Ok(v)`면 `v`로 바꾸고 계속, `Err`면 **그 Err를
  스택에 둔 채** L1로 뛰어 `RETURN`한다. 즉 `?`는 **현재 함수의 반환 경로를 공유**한다. 반환 타입 표기가 있으면
  `CHECKRETURN`도 같이 나가므로 `-> int`인 함수에서 `?`가 `Err`를 돌려주면 E0404가 된다. `?`는 nil을 **그냥 통과**시킨다
  (02: nil은 실패가 아니라 "없음"). 최상위에서 `?`를 쓰면 돌아갈 함수가 없으므로 E0214, `for` 본문 안에서는
  람다에서 돌아가 `Err`가 리스트 원소가 되므로 E0220 (E0213과 같은 이유).

## 7. 인덱스·슬라이스의 엄격함

`xs[i]`는 `INDEX`, `xs[a..b]`는 `SLICE flags`(bit0 = 시작 있음, bit1 = 끝 있음, bit2 = `..=`), `m.k`는 `FIELD`(키를 상수로).
대괄호 안은 보통 식이고, 그 결과가 범위 식이면 슬라이스다: `xs[i ?? 0]`는 인덱스, `xs[1..=2]`는 슬라이스.
범위를 벗어나면 **에러**다(E0507). Python처럼 조용히 잘라 주지 않는다 — "값이 없는데 있는 척"은 엄격함 원칙에
어긋난다. 안전하게 자르고 싶으면 M5의 `take`/`drop`을 쓴다. 문자열 인덱스·슬라이스·`len`은 **룬(문자) 단위**다:
`"참치회"[1]`은 `"치"`. 바이트 단위면 한글이 깨진다. 튜플은 인덱스를 지원하지 않는다(E0509): 튜플은 "자리가 정해진
묶음"이라 패턴으로 꺼내는 것이 맞고, 인덱스를 허용하면 리스트와의 차이가 흐려진다.

## 8. `in`의 네 대상

`a in b`는 `IN` 한 명령, `value.Contains`가 `b`의 타입으로 분기한다: 리스트는 원소(`Equal`), 문자열은 부분 문자열,
맵은 **키**, 범위는 정수 포함. `not in`은 파서가 `not (a in b)`로 풀므로 명령이 없다. 다른 타입은 E0512.

## 9. 타입 별칭

`type shape = Circle | Rect`는 **컴파일 시점에만** 존재한다. resolve가 파일의 별칭을 먼저 모두 모으고(끌어올림: 정의보다
앞에서 써도 된다), 타입 표기 안의 이름을 재귀적으로 펼친다. 중복 정의 E0217, `type a = a` 같은 순환 E0218, 함수 안
정의 E0219. 펼친 뒤에는 M3의 `CHECKTYPE`이 그대로 동작하므로 VM은 별칭을 모른다.

## 10. 가변 인자

`fn f(a, ...rest)`의 `rest`는 Proto의 마지막 `Param`에 `Rest` 표시가 붙은 보통 슬롯이다. `bindArgs`가 고정 인자 수를
넘는 위치 인자를 **리스트로 묶어** 그 슬롯에 넣고, 없으면 빈 리스트를 넣는다. 이름 인자로 `rest`를 지정하는 것은
E0406. M3의 E0805("rest 미지원")는 번호만 남기고 더 이상 나지 않는다.

## 11. 테스트와 다음

단위 테스트는 층마다(value, parser, desugar, resolve, compiler, vm, native), 골든은 값·흐름 10 + 에러 20, 전체 84개.
마무리 리뷰에서 고친 것: `xs[1..=3]`과 `xs[i ?? 0]`(대괄호 안을 보통 식으로), `for` 본문의 `?`(E0220), `for (a, b)`의
가리기, `Err()!`와 `Ok(a: 1)`의 내부 에러, 패턴 파서의 깊이 한도.
M4 중 설계와 계획이 어긋난 곳은 계획 쪽을 고쳤다: `?`는 nil을 통과시킨다(02 표), guard 안에서 `name =>`는 람다가
아니라 절의 화살표다(파서 플래그), 서로 다른 타입의 비교는 guard 안에서도 에러다(골든의 절 순서를 바꿨다).

다음은 M5 모듈과 실사용: `import`, 내장 stdlib, `fs` `path` `exec` `sh` `env` `args`, `find`/`all`/`any`/`fold`/`take`/`drop`.
