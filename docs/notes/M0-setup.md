# M0. 준비 — 무엇을 만들었고 왜 그렇게 했나

M0는 언어 기능이 하나도 없는 단계다. 그 대신 앞으로 모든 마일스톤이 올라탈 바닥을 깐다.
Go 모듈, 실행 파일의 뼈대, 그리고 "언어가 맞게 동작하는지"를 자동으로 확인하는 장치다.

## 1. Go 모듈 (`go.mod`)

```
module github.com/tunarider/fung
go 1.27
```

- Go에서 "모듈"은 하나의 저장소 단위다. 모듈 경로(`github.com/tunarider/fung`)는 패키지를 import할 때
  쓰는 이름의 앞부분이 된다. 예: `import "github.com/tunarider/fung/internal/diag"`.
- 아직 원격 저장소는 없지만 경로를 이렇게 정해 두면 나중에 올릴 때 바꿀 것이 없다.
- 의존성 줄(`require`)이 하나도 없다. 설계 원칙대로 Go 표준 라이브러리만 쓴다. 그래서 `go.sum`도 생기지 않는다.
- `internal/` 디렉터리는 Go가 특별 취급한다. 이 모듈 바깥에서는 import할 수 없다.
  언어 내부 구조(렉서, VM 등)를 외부에 API로 약속하지 않겠다는 뜻이다.

## 2. 실행 파일 뼈대 (`cmd/fung/main.go`)

### 하위 명령 분기

`fung version`, `fung help`는 동작하고, 나머지(`run`, `-e`, `check`, `fmt`, `test`, `dump`, REPL)는
"not implemented yet"을 내고 끝난다. 미리 분기를 다 만들어 두는 이유는 M1부터는 **분기 구조를 건드리지 않고
빈 칸만 채우면** 되게 하기 위해서다.

### `main`과 `run`을 나눈 이유

```go
func main() { os.Exit(run(os.Args[1:], os.Stdin, os.Stdout, os.Stderr)) }
func run(args []string, stdin io.Reader, stdout, stderr io.Writer) int
```

`main`은 프로세스 전체에 묶여 있어 테스트하기 어렵다 (`os.Exit`를 부르면 테스트도 같이 죽는다).
그래서 실제 일은 `run`이 하고, 입력·출력·인자를 전부 **매개변수로** 받는다.
테스트에서는 진짜 터미널 대신 메모리 버퍼를 넘겨 "무엇을 출력했고 몇 번으로 끝났는지"를 검사한다.
이 패턴은 CLI 도구를 만들 때 거의 항상 쓰는 기본 구조다.

### 종료 코드

프로그램이 끝날 때 운영체제에 돌려주는 정수다. 쉘의 `set -e`, `a && b`, CI 등이 전부 이 값을 본다.
fung은 네 가지로 고정했다 (08 문서에 추가함).

| 코드 | 의미 | 누가 보나 |
|------|------|----------|
| 0 | 정상 | 모두 |
| 1 | 실행 중 실패 | 쉘 스크립트: "돌다가 죽었다" |
| 2 | 컴파일 실패 | 편집기·CI: "코드가 틀렸다" |
| 3 | `fung` 명령 사용 오류 | 테스트 실행기: "테스트 설정이 잘못됐다" |

1과 2를 구분하는 이유: 골든 테스트에서 "컴파일 에러를 기대했는데 런타임까지 갔다"를 잡을 수 있고,
사용자도 `$?`만 보고 어느 단계가 문제인지 안다. 3을 따로 둔 이유는 아래 테스트 실행기에서 설명한다.

상수는 `internal/diag`에 둔다. 08 문서에서 `diag/`는 "에러 번호, 카탈로그, 출력 형식"을 맡는 패키지이고,
종료 코드도 진단의 일부이므로 여기가 자연스럽다. CLI와 테스트 실행기가 같은 상수를 쓰므로 어긋날 수 없다.

### 스크립트와 하위 명령 구분

`fung script.fung`은 실행, `fung check`는 하위 명령이다. 그런데 `fung frobnicate`는 뭘까?
파일일 수도, 오타일 수도 있다. 규칙을 정했다: **`.fung`으로 끝나거나 경로 구분자(`/`, `\`)가 있으면 스크립트**,
아니면 하위 명령. 확장자 없는 스크립트를 shebang으로 실행하면 커널이 전체 경로를 넘기므로(`fung /path/to/tool`)
구분자가 반드시 들어온다. 애매하면 `fung run <파일>`을 쓰면 된다.

## 3. 골든 테스트 실행기

### 골든 테스트란

"이 입력을 주면 이 출력이 나와야 한다"를 파일로 적어 두고 자동으로 비교하는 방식이다.
언어 구현에서는 가장 중요한 테스트다. 렉서를 바꾸든 VM을 바꾸든, 사용자가 보는 결과가 같은지를 한 번에 검사하기 때문이다.

```
print(1 + 2)
# expect: 3

print(fiels)
# expect-error: E0204
```

기대값을 **같은 파일의 주석**에 적는다. 별도 `.out` 파일 방식보다 읽기 쉽고, 테스트 하나가 파일 하나로 끝난다.

### 두 층으로 나눈 구조

- `internal/golden`: 주석에서 기대값을 뽑는 `Parse`, 실제 결과와 비교하는 `Check`. **순수 함수**라 단위 테스트가 쉽다
  (17개 테스트). 프로세스를 띄우지 않는다.
- `tests/golden_test.go`: `TestMain`에서 `fung` 바이너리를 **한 번** 빌드하고, `tests/` 아래 `*.fung`을 찾아
  각각 서브프로세스로 실행한 뒤 `Parse`/`Check`에 넘긴다. 파일마다 서브테스트가 생기므로 `go test -run 'TestGolden/lang/pipe'`처럼 하나만 돌릴 수 있다.

서브프로세스 방식을 고른 이유(사용자 결정 2-A): 사용자가 겪는 것과 정확히 같은 경로(인자 파싱, 종료 코드, stdout/stderr 분리)를 검사한다.
비용은 파일당 몇 ms다.

### 종료 코드 3을 따로 둔 이유

실행기는 종료 코드 3을 보면 **무조건 실패**로 처리한다. 기대 에러가 있어도 마찬가지다.
3은 "fung이 시작조차 못 했다"는 뜻이므로, 언어의 동작이 아니라 테스트 환경의 문제다.
이 구분이 없으면 "`run`이 아직 없어서 실패"한 것이 "에러를 기대했으니 통과"로 잘못 읽힐 수 있다.
실제로 M0에서 임시 골든 파일을 넣었을 때 실행기는 다음과 같이 보고했다.

```
fung could not start (exit 3)
stderr:
error: `run` is not implemented yet
```

### 기대 에러 검사 범위

`# expect-error: E0204`가 있으면 종료 코드가 1 또는 2이고 표준 에러에 `error[E0204]`가 포함되는지만 본다.
메시지 전문을 비교하지 않는 이유는 08 문서의 에러 형식(소스 발췌, 힌트)이 M2에서 다듬어질 것이고,
그때마다 모든 골든 파일을 고치고 싶지 않아서다. 에러 **번호**가 계약이다.

## 4. 작업 방식

- 모든 코드는 테스트를 먼저 쓰고(RED), 실패를 눈으로 확인하고, 통과할 만큼만 구현했다(GREEN).
  M0에서는 `run`이 없어 컴파일조차 안 되는 것이 첫 RED였다.
- 커밋 전 확인: `gofmt -l .` (출력 없음), `go vet ./...`, `go test ./...`.
