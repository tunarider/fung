# R4d 소켓·TLS·fung으로 쓴 HTTP: 무엇을 옮겼고 왜 그렇게 했나

2026-10-16. 계획 `docs/plans/2026-10-16-rust-net-http-4d.md`, 스펙 `docs/superpowers/specs/2026-10-16-rust-net-http-4d-design.md`
(끝의 "2026-10-16 구현 중 결정"이 사용자 결정), 결정과 남은 차이는 `docs/design/open-questions.md`의 "Rust 이전". 커밋 `6bdcab6..4660516`.

4단계(네이티브 원시 기능)의 마지막 조각이다. Go 구현은 `http`를 Go `net/http`에 통째로 맡겼다. Rust에서는 나눴다.
- Rust는 **소켓과 TLS 원시 기능만** 준다(`_native.net`).
- **HTTP/1.1 프로토콜은 fung으로** 썼다(`extras/rust/http.fung`). URL 해석, 요청 조립, 응답 해석, 조각 전송, 리다이렉트, 프록시, 서버 루프가 모두 여기 있다.

이것은 open-questions "라이브러리 구조"의 결정("런타임은 TCP 소켓·TLS 같은 원시 기능만, HTTP 프로토콜은 fung 라이브러리로")을 처음 실제로 해 본 것이다.
그린 스레드는 이 단계에서 하지 않았다(7절).

## 1. 무엇을 만들었나

사용자에게 보이는 것:
- `import http`가 Rust에서도 된다. `get`·`post`·`request`·`serve` 넷 모두, 매개변수 표는 `spec/builtins.txt`와 같다.
- 06에 **"fung HTTP 약속"**을 적었다. 그 안에서는 Go와 같고, 약속 밖(연결 재사용, HTTP/2, 압축 등)은 "0.2.0에서 바뀌는 것"이다.
- 응답 본문 상한 64 MiB(사용자 결정). Go에는 없는 동작이다. 넘으면 `Err`.
- 이제 Rust가 못 돌리는 표준 모듈이 없다. 그래서 "지원 안 함" 에러(E0805)를 내던 장치와 실행 비교의 제외 목록(`run_parity_skip.txt`)을 **지웠다**.
  E0805 번호는 카탈로그에 그대로 둔다(번호는 바꾸지 않고 Go에는 아직 있다). 구현마다 갈라지는 파일은 이제 `# only:` 표시 하나로만 다룬다.

내부:
- `crates/fung-vm/src/native/net.rs`(+ `sock.rs`): `_native.net` 19개. `connect` `listen` `local_addr` `accept` `read_line` `read_bytes` `read_all` `write` `close`
  `set_deadline` `byte_len`에 더해, 작업 중에 필요해서 더한 것이 여덟이다.
  - `read_bytes_into`·`take_body`: 본문을 바이트로 모았다가 한 번에 글자로 바꾼다(2절 끝).
  - `utf8_bytes`·`utf8_string`: 글자 ↔ 바이트. fung 문자열은 글자로만 보여서, URL의 `%XX`를 만들고 풀 방법이 없었다.
  - `need_str_map`: Go와 같은 E0403 "map of strings" 에러. fung 코드는 원하는 에러 번호를 낼 수 없다.
  - `start_tls`: 이미 열린 연결 위에서 TLS를 시작한다(프록시 터널, 5절).
  - `hold`·`close_on_cancel`: 서버의 끝(6절).
- `_native.conc`에 둘: `set_asker`(핸들러를 서버 태스크 아래에서 돌림), `describe`(잡은 에러의 번호와 문구).
- 값 종류 둘: `Value::Conn`, `Value::Listener`. 파일 핸들(4a)과 같은 방식이다. 출력은 `<conn>`·`<listener>`이고, 같음은 동일성으로 본다. 마지막 사본이 사라지면 닫힌다.
- `crates/fung-vm/src/vm/watch.rs`: 실행권 밖에서 **취소할 수 있게** 기다리는 장치(2절).
- `crates/fung-vm/src/native/tls.rs`: rustls 클라이언트를 비차단 소켓 위에서 돌리는 층(3절).
- `extras/rust/http.fung`(약 2,000줄): Rust 부팅만 읽는다(`agent.fung`과 같은 자리).
- 크레이트: `rustls` 0.23.45(암호는 `ring`), `rustls-native-certs` 0.8.4와 그것들이 끌고 오는 것. 표는 open-questions "Rust 이전".
- 테스트 인증서: `scripts/gen-test-certs.sh` → `crates/fung-cli/tests/data/tls/`(100년짜리 localhost, 이름이 틀린 것, 만료된 것, 아무것도 서명하지 않은 CA).

비교로 확인한 것:
- 실행 비교 189건(`tests/lang` 143개 중 표시 없는 133개, 벤치마크, `-e`)과 Rust 골든 139개(`http_serve_rust` 포함)가 통과했다. 실행 비교에서 빼는 파일은 이제 하나도 없다.
- `crates/fung-cli/tests/http_parity.rs`: 테스트 14개, 그중 하나는 릴리스 전용. 같은 가짜 서버에 Go fung과 Rust fung 클라이언트를 붙인다.
  출력, 표준 에러, 종료 코드에 더해 **가짜 서버가 받은 요청 원문**까지 비교한다.
  - 클라이언트 프로그램 61개, 연결 없는 경우 30개, 인자 에러 13개, 리다이렉트·프록시 사례, `NO_PROXY` 표 23줄.
  - 서버는 Go 서버와 Rust 서버에 같은 원시 요청 88개를 보낸다. `Date` 값만 가리고 응답을 바이트 단위로 비교한다.
  - 그 밖에 헤더 10초 한도, 바인드 실패, 예제(`static.fung`·`checkurls.fung`).
  - 한 번 도는 데 프로필마다 약 45초 걸린다.
- `crates/fung-cli/tests/tls.rs`: Go TLS 서버 하나에 Go fung과 Rust fung을 붙여 인증서 에러 문구를 비교한다. macOS에서도 돈다(3절).
- 단위 테스트는 `net_tests.rs` 46개, `tls_tests.rs` 18개, `watch.rs` 5개다. 프로그램마다 끝난 뒤 열린 소켓, 깨우개 파이프, 이름 조회 스레드가 모두 0인지 본다.

## 2. 소켓과 막히는 입출력, 실행권 밖에서 기다리기, 취소로 깨우기

**소켓이 막힌다는 것.** `accept`는 누가 연결해 올 때까지, `read`는 상대가 무엇을 보낼 때까지 돌아오지 않는다. 그동안 그 스레드는 커널 안에서 잠든다.
fung의 태스크는 운영체제 스레드 하나씩이고(3a), fung 코드는 **실행권**을 쥔 스레드만 돌린다. 그래서 막히는 호출은 실행권을 놓고 한다(`outside`, 파일 입출력과 같은 장치).
실행권 밖으로는 Rust 값(바이트, 소켓)만 가지고 나간다. fung 값(`Rc`)은 실행권 안에서만 만진다.

**문제는 취소다.** `cancel(t)`나 다른 태스크의 `exit`가 오면 `accept`에서 잠든 태스크도 곧 E0701로 끝나야 한다. 커널 안에서 자는 스레드를 깨우는 방법이 필요하다.
- 처음 계획은 소켓 `shutdown`이었다. 그런데 macOS에서는 `shutdown`이 `accept`도, 진행 중인 `connect`도 깨우지 않는다. 게다가 연결을 함께 쓰는 다른 태스크에게서도 연결을 죽인다.
- 짧은 간격으로 깨어나 플래그를 보는 방법(폴링 루프)은 늦게 깨고, 할 일이 없어도 계속 깨어난다.

**그래서 고른 것: 비차단 소켓 + `poll` + 깨우개 파이프.**
1. 소켓은 모두 비차단(non-blocking)으로 연다. 읽을 것이 없으면 커널이 기다리지 않고 "지금은 없음"(`WouldBlock`)을 돌려준다.
2. 그러면 `poll`로 **두 개를 함께** 기다린다. 하나는 소켓, 다른 하나는 이 기다림 전용 파이프의 읽는 쪽이다. 둘 중 하나라도 준비되면 깬다.
3. 파이프의 쓰는 쪽은 태스크의 취소 노드에 거는 **갈고리**(hook, `CancelNode::on_cancel`)에 넘긴다.
   취소하는 쪽은 그 갈고리를 불러 파이프에 1바이트를 쓴다. `poll`이 깨고, 기다림은 "취소됨"을 보고하고, 실행권을 되찾은 뒤 E0701로 풀린다.

`cancel`, 어디서든 `exit`, 교착 보고, 띄운 쪽의 끝 모두 같은 길로 깨운다. 경쟁 조건은 이렇게 닫았다(`vm/watch.rs` 주석).
- **갈고리를 걸기 전에 취소가 오는 경우.** 취소 쪽은 플래그를 먼저 세운 뒤 노드를 잠그고, 거는 쪽은 잠근 채 플래그를 본다.
  거는 쪽이 이기면 취소 쪽이 갈고리를 찾아 부르고, 지면 거는 쪽이 플래그를 보고 바로 "취소됨"이다.
- **걸고 나서 `poll` 전에 취소가 오는 경우.** 바이트가 파이프에 남아 있으므로 `poll`이 바로 돌아온다.
- **기다림이 끝나는 순간 취소가 겹치는 경우.** 기다림이 정리될 때(`Drop`) 먼저 노드 잠금 아래에서 갈고리를 떼므로, 그 뒤로는 갈고리가 돌지 않는다.
- 소켓이 준비된 순간과 취소가 겹치면 취소가 이긴다(`block`과 같은 규칙).

쓰레기가 남지 않는지도 셌다. 기다림마다 스레드를 만들지 않는다. 막힐 때만 파이프 하나(디스크립터 2개)를 만들고 호출이 끝나면 닫는다.
예외가 하나 있다. 이름 조회(`getaddrinfo`)는 중간에 끊을 수 없어서 스레드에서 돌린다. 취소되거나 시간이 다 된 `connect`는 바로 돌아오지만, 그 조회 스레드는 해석기가 답할 때까지 남는다.
해석기 시간 제한이 있어 시간으로는 묶여 있지만, 개수로는 묶여 있지 않다(open-questions R7 항목).

**한 연결에 읽는 쪽 하나, 쓰는 쪽 하나.** 리뷰에서 나온 문제다. 두 태스크가 한 연결을 동시에 읽으면, 두 번째는 연결의 읽기 잠금에서 기다리고 그 잠금 기다림은 취소할 수 없다.
- 취소할 수 있는 잠금을 만드는 대신 **규칙으로 정했다**(컨트롤러 판정). HTTP는 연결마다 읽는 쪽 하나와 쓰는 쪽 하나만 필요하기 때문이다.
- `net.rs` 머리 주석에 적었고, `a_second_reader_waits_for_the_first`가 그 동작을 고정한다.
- 틀렸을 때의 대가: 나중에 연결 하나를 여러 태스크가 나눠 쓰는 fung 라이브러리를 만들면 취소에서 멈출 수 있다.

**기한.** `set_deadline(c, d)`는 Go `SetDeadline`처럼 이후의 모든 읽기·쓰기에 "지금 + d"라는 절대 시각을 건다. 넘으면 Go 문구 `read tcp L->R: i/o timeout`이다.
다만 이미 `poll`에 들어가 막힌 호출은 시작할 때의 기한을 그대로 들고 있다. 새 기한은 다음 기다림부터 적용된다(알려진 차이).

**글자 하나가 두 번의 읽기에 걸친다.** 리뷰가 찾은 것이다. `read_bytes`는 읽을 때마다 UTF-8로 풀었다.
- 조각 전송(chunked)에서 "한"(3바이트)의 1바이트가 앞 조각, 2바이트가 뒤 조각에 오면, 두 조각 모두 깨진 바이트로 보여 U+FFFD 두 개가 된다.
- Go는 본문 전체를 바이트로 모은 뒤에 한 번만 푼다.
- 해결: 연결마다 **바이트 그대로 쌓는 버퍼**를 두었다. `read_bytes_into(c, n, cap)`가 n바이트를 풀지 않고 쌓고, `take_body(c)`가 다 쌓인 것을 한 번에 풀어 돌려준다.
- `cap`은 버퍼 전체의 상한이다. 넘을 것 같으면 아무것도 읽지 않고 `'limit` 에러를 낸다. 그래서 클라이언트의 64 MiB, 서버의 16 MiB(413) 한도가 같은 장치로 지켜진다.
- 프로토콜은 fung에 두고 바이트 모으기만 Rust에 둔 것이다(컨트롤러 판정). 대가는 조각 해석을 fung으로 하는 만큼의 속도다.

## 3. TLS와 인증서 신뢰

**TLS가 하는 일.** TCP 위에 암호화된 통로를 만든다. 처음 주고받는 **핸드셰이크**에서 서버가 인증서를 보이고, 클라이언트가 그것을 검증하고, 둘이 키를 정한다.
그 뒤의 데이터는 **레코드**라는 단위로 오간다. 레코드마다 5바이트 머리(종류·버전·길이)와 암호화된 내용이 있다.

**poll 루프 위의 TLS.** rustls는 소켓을 직접 만지지 않는 "상태 기계"다.
- 사용자가 소켓에서 읽은 바이트를 넣어 주면(`read_tls`) 풀어서 평문을 내놓고(`process_new_packets`), 보낼 바이트를 꺼내 가라고 한다(`write_tls`).
- 그래서 2절의 비차단 소켓과 `poll`, 취소 깨우개를 그대로 쓸 수 있었다. 핸드셰이크도 같은 `Watch`에서 기다리므로 핸드셰이크 중에도 취소된다.
- 연결마다 `Mutex<Session>`이 하나 더 있다. 이 잠금은 기다리지 않는 짧은 단계에서만 쥐고, `poll` 동안에는 쥐지 않는다.
  그래서 2절의 "읽는 쪽 하나, 쓰는 쪽 하나"가 TLS에서도 같은 뜻이다. 읽는 쪽이 기다리는 동안 3 MB를 쓰는 테스트가 있다.
- 세션 재개(resumption)는 껐다(Go 클라이언트도 기본으로 세션 캐시가 없다). ALPN도 보내지 않는다.

**close_notify와 EOF.** TLS에서는 "다 보냈다"를 알리는 경고 메시지(close_notify)가 따로 있다. 공격자가 TCP 연결만 끊으면 본문이 잘린 것을 끝으로 착각할 수 있어서다.
- Go의 규칙: close_notify 없이 TCP가 끝나도 **레코드 사이**면 끝으로 받아들이고, **레코드 중간**이면 `unexpected EOF`다.
- 이것을 맞추려고 `Records`가 읽은 바이트의 레코드 경계를 따로 센다(rustls는 이 구분을 주지 않는다).
- `close`는 close_notify를 보내고 소켓을 닫는다. 마지막 사본이 사라질 때는 close_notify 없이 닫는다(Go의 finalizer와 같다).

**인증서 신뢰.** 서버 인증서는 내가 믿는 **루트 인증서**에서 시작하는 서명 사슬로 검증한다. 그 루트 목록을 어디서 얻을지가 문제다.
- `rustls-native-certs`가 운영체제의 루트를 읽는다. macOS는 키체인이고, Linux는 `/etc/ssl/certs` 등이다. 환경 변수 `SSL_CERT_FILE`·`SSL_CERT_DIR`이 있으면 그것을 쓴다.
- 루트 목록은 프로세스마다 처음 TLS 연결 때 한 번 읽는다(`OnceLock`).
- **Go 1.27은 macOS에서도 `SSL_CERT_FILE`을 따른다.** 계획은 "macOS의 Go는 운영체제 검증기를 쓰니 Go 대조는 Linux에서만"이었다. 그런데 Go 1.27부터는 변수가 있으면 macOS에서도
  Go 자신의 검증기와 그 파일을 쓴다(옛 동작은 GODEBUG `x509sslcertoverrideplatform=0`). 그래서 `tests/tls.rs`가 macOS에서도 돌고, 스펙과 계획을 고쳤다.
- 에러 문구는 Go를 따랐다(`x509: certificate signed by unknown authority`, `certificate is valid for X, not Y`, 만료 문구의 시각 형식).
  Go는 날짜, 이름, 사슬 순서로 검사하므로 그 순서로 보고하는 검증기(`GoOrder`)를 rustls의 공개 부품으로 직접 조립했다.
- 변수 없이 macOS의 Go는 Apple 검증기를 써서 문구가 다르다. 예를 들어 100년짜리 인증서는 "not standards compliant"다. 이 경우는 맞추지 않는다.

## 4. HTTP/1.1 메시지 구조와 본문 길이 세 가지

HTTP/1.1 메시지는 글자로 된 머리와 바이트로 된 본문이다.

```
GET /path?x=1 HTTP/1.1          ← 시작 줄(요청 줄): 메서드, 대상, 버전
Host: example.com               ← 헤더: "이름: 값", 줄 끝은 CRLF
User-Agent: Go-http-client/1.1
                                ← 빈 줄: 머리의 끝
(본문)
```

응답의 시작 줄은 `HTTP/1.1 200 OK`(버전, 상태 코드, 이유 문구)다. 헤더 이름은 대소문자를 가리지 않는다.
fung은 응답 헤더 키를 소문자로 주고, 같은 이름이 여럿이면 `", "`로 잇는다.

**본문이 어디서 끝나는지가 핵심이다.** TCP는 바이트의 흐름일 뿐이라 메시지의 경계가 없다. 그래서 HTTP는 세 가지 방법 중 하나로 본문 길이를 알린다.
1. **`Content-Length: n`**: 정확히 n바이트. 가장 단순하다. 바이트 수라서 한글 한 글자는 3이다(`byte_len("한a") == 4`).
2. **`Transfer-Encoding: chunked`**: 길이를 모르는 채로 보낼 때 쓴다. "16진 크기 CRLF, 그만큼의 데이터, CRLF"를 되풀이하고, 크기 0인 조각과 선택적인 트레일러 헤더로 끝난다.
3. **연결이 닫힐 때까지**: 둘 다 없으면 상대가 연결을 닫을 때까지가 본문이다.

본문이 아예 없는 경우도 있다. `HEAD` 응답, 1xx, 204, 304는 헤더에 길이가 적혀 있어도 본문이 없다.
어느 길로 읽을지 정하는 규칙(Go `fixLength`·`parseTransferEncoding`)은 생각보다 까다롭다. `Content-Length`가 둘이고 값이 같으면 하나로 치고 다르면 에러다.
조각 전송이면 `Content-Length`를 버린다. `gzip` 같은 다른 전송 인코딩은 거부한다. 이런 규칙과 에러 문구를 Go 코드를 옆에 두고 그대로 옮겼다.

**망가진 상대에 대비한 한도.** 악의적이거나 고장 난 상대가 끝없는 헤더나 본문을 보내도 메모리가 끝없이 늘면 안 된다.
- `read_line(c, limit)`은 줄이 `limit`을 넘는 순간 `'limit` 에러를 낸다. 그때까지 `limit + 2`바이트 넘게 쌓지 않는다.
- 클라이언트의 헤더 예산은 Go와 같은 10 MiB, 조각 크기 줄은 4096바이트, 본문은 64 MiB다.
- 서버는 머리 1 MB + 4 KB에 값 500개(넘으면 431), 본문 16 MiB(넘으면 413), 머리를 10초 안에 다 보내지 않으면 끊는다.

**압축을 하지 않는 이유.** Go는 몰래 `Accept-Encoding: gzip`을 보내고 받은 것을 풀어서 준다. 사용자에게는 푼 본문만 보인다.
Rust는 아예 요청하지 않으므로 서버가 압축하지 않은 본문을 보내고, 결과는 같다. 비교 테스트는 Go가 보낸 요청에서 그 한 줄만 지우고 나머지를 바이트 단위로 비교한다.

## 5. 리다이렉트·프록시·터널

**리다이렉트**는 서버가 "다른 곳으로 가라"(3xx + `Location` 헤더)라고 답하는 것이다. Go `Client`의 규칙을 그대로 따랐다.
- 301·302·303이면 `GET`으로 바꾸고 본문을 버린다(원래 `HEAD`면 `HEAD`). 307·308이면 메서드와 본문을 그대로 둔다. 다른 3xx와 `Location`이 없는 3xx는 그대로 돌려준다.
- 요청 10번을 보냈는데 10번째 답이 또 리다이렉트면 `stopped after 10 redirects`다.
- `Location`이 상대 경로면 지금 URL을 기준으로 푼다(Go `URL.Parse` + `ResolveReference`).
- 첫 요청과 다른 호스트로 넘어가면(같은 호스트나 그 하위 도메인이 아니면) `Authorization`·`Cookie` 같은 민감한 헤더를 그 뒤로 계속 버린다. 남의 서버에 비밀번호를 넘기지 않으려는 것이다.
- `Referer`를 붙인다. https에서 http로 갈 때는 붙이지 않는다.
- `timeout`은 리다이렉트를 모두 포함한 요청 전체의 예산이다.

리다이렉트에서 함정 둘이 있었다(8절 (9)).
- **본문 버리기.** Go는 리다이렉트 응답의 본문을 **2 KB까지 읽고 버린 뒤** 다음으로 간다. 연결을 재사용하려는 것이다.
  그래서 본문을 보내다 멈춘 서버를 만나면 Go는 거기서 기다리다 시간 초과가 난다. Rust는 처음에 바로 다음으로 갔다.
  재사용을 하지 않는 Rust에는 필요 없는 일이지만 Go와 같게 했다(컨트롤러 판정: Go가 정답지이고 몇 줄이다). 이것은 과도기 잔가지다.
- **순서.** Go는 `Location`을 먼저 해석하고, 그다음 본문을 버리고, 그다음 횟수를 본다. `Location`이 망가졌고 본문이 멈춘 경우, Go는 바로 `failed to parse Location header`를 내는데 Rust는 시간 초과를 냈다.

**프록시**는 요청을 대신 보내 주는 중간 서버다. Go `ProxyFromEnvironment` 규칙을 따랐다.
- `HTTP_PROXY`/`http_proxy`는 http에만, `HTTPS_PROXY`/`https_proxy`는 https에만 쓴다. 대문자가 먼저지만 빈 값이면 없는 것으로 친다.
- 정확히 `localhost`와 루프백 주소는 프록시를 거치지 않는다. 쓴 그대로 비교하므로 `LOCALHOST`는 거친다.
- `NO_PROXY`는 쉼표로 나눈 목록이다.
  - `*`는 모두를 뜻한다. `example.com`은 그 자신과 하위 도메인, `.example.com`은 하위 도메인만이다.
  - 포트를 붙이면 포트까지 같아야 한다. IP와 CIDR도 쓸 수 있다.
  - 도메인 패턴은 IP에, IP 패턴은 이름에 맞지 않는다.
  - Go의 IPv4/IPv6 CIDR 구분 같은 세부까지 23줄짜리 표로 Go와 대조했다.
- CGI 안전장치: `REQUEST_METHOD`가 있으면 `HTTP_PROXY`를 쓰는 요청을 거부한다(`golang.org/s/cgihttpproxy`). 요청 헤더 `Proxy:`가 환경 변수 `HTTP_PROXY`로 둔갑하는 공격을 막는 Go의 장치다.

**http와 https는 프록시를 쓰는 방법이 다르다.**
- http는 요청 줄에 절대 URL을 쓴다(`GET http://host/path HTTP/1.1`). 프록시가 내용을 다 보고 대신 보낸다.
- https는 프록시가 내용을 보면 안 된다. 그래서 먼저 `CONNECT host:443 HTTP/1.1`로 프록시에게 "저 서버까지 TCP 통로(터널)를 뚫어 달라"고 한다.
  200을 받으면 그 연결은 이제 목적지 서버와 이어진 관이다. 그 위에서 목적지 이름으로 TLS를 시작한다.
- 이미 열린 연결 위에서 TLS를 시작하는 원시 기능이 없어서 `start_tls(c, host, timeout)`을 더했다. 새 소켓을 열지 않고 `c`의 소켓을 넘겨받는다(`Conn::take_over`).
  - 넘겨준 옛 값은 닫힌 것으로 읽힌다.
  - 미리 읽어 둔 바이트는 버린다(Go도 버퍼를 버린다).
  - 다른 태스크가 그 연결을 읽거나 쓰는 중이면 바로 `tls: the connection is in use`로 실패한다.
- SOCKS 프록시와 https 프록시 너머의 https(TLS 안의 TLS)는 하지 않았다. Rust만의 문구로 실패한다(알려진 차이).

## 6. 서버, 그리고 fung으로 프로토콜을 쓴 경험

**서버의 모양**(`extras/rust/http.fung`의 "The server" 절).

```
serve(사용자 태스크 S): 검사 → listen → close_on_cancel → ready(주소) → 접수 루프를 S 아래에서 → hold(l, 2s)
접수 루프: accept 반복. 리스너가 닫히면 끝, 다른 에러는 5 ms에서 1 s까지 늘려 가며 다시(Go)
연결마다 배경 태스크 하나: 기한 10초 → 요청 읽기 → 핸들러(try_call, S 아래) → 응답 → 닫기
```

- **요청마다 태스크.** 연결마다 새 태스크가 요청 하나를 읽고, 핸들러를 부르고, `Connection: close`로 답하고 닫는다. 느린 핸들러 하나가 다른 요청을 막지 않는다.
- **연결 태스크는 배경 태스크다.** 서버를 취소해도 503을 쓰는 코드나 처리 중인 응답은 끝까지 가야 한다. Go에서는 그 코드가 fung 태스크가 아니다.
  배경 태스크는 프로그램을 붙잡지 않는다. 붙잡는 것은 서버 태스크 S다.
- **그래도 핸들러는 서버와 함께 취소된다.** `set_asker`로 S의 취소 노드를 표시해 두면 `try_call`이 핸들러를 S와 연결 태스크 **양쪽 아래**에서 돌린다.
  그래서 `cancel(server)`, 어디서든 `exit`, 교착 보고가 핸들러를 끊고 503(보고 없음)이 나간다.
- **핸들러가 띄운 태스크.** 핸들러 아래에 걸려 핸들러와 함께, 서버와 함께 취소된다. 다만 배경 종류를 물려받는다.
  그래서 프로그램을 붙잡지 않고, 교착 집계에 따로 들고, 꺼내지 않은 실패는 보고된다.
- **끝내기(Go `Shutdown`).** 취소되면 리스너를 닫고, 처리 중인 연결을 최대 2초 기다린 뒤 E0701이다. "취소 뒤에도 정해진 시간만큼 기다리기"는 fung으로 쓸 수 없어서 `hold`가 맡는다.

**취소 경쟁(리뷰가 찾음).** 처음에는 S가 `hold`에서 기다리다 취소되면 리스너를 닫았다. 그런데 `ready` 뒤, `hold`에 들어가기 전의 한 틱에 취소가 오면 문제가 생겼다.
`await(server)`가 끝났는데도 리스너가 잠깐 열려 있어 연결이 들어왔다(k=9988번째 틱에서 재현).
- 고친 것 (a): `close_on_cancel(l)`. listen 직후 S의 취소 노드에 "리스너를 닫는" 갈고리를 건다. `cancel` 호출 **안에서** 리스너가 닫히므로, `await`가 돌아오기 전에 이미 닫혀 있다.
- 고친 것 (b): 접수 루프도 S 아래에서 돌린다.
- (b)만으로는 부족했다. 리스너는 결국 닫히지만 `await`보다 늦을 수 있었다.
- 회귀 테스트는 틱 9900~10000(릴리스에서는 차례 넘기기 한 주기 전체)마다 취소해 보고, 그 뒤 포트가 HTTP로 답하지 않는지 본다.

**서버 자신의 실패를 보고하기(리뷰가 찾음).** 배경 태스크의 실패는 보고되지 않는다. 그래서 핸들러가 아니라 서버의 fung 코드에 버그가 있으면 연결이 조용히 끊길 뿐이었다.
- 지금은 연결마다 `try_call`로 감싼다. 끝내기(exit·E0701·E0702)가 아닌 실패는 `http: internal error: <제목>` 한 줄을 찍는다(Go의 `http: panic serving …`과 같은 자리).
- 접수 루프가 실패하면 그 에러를 `serve`에 넘겨 다시 낸다. 라이브러리의 버그이지 네트워크 결과가 아니므로 `Err` 값이 아니라 실패다.

**fung으로 프로토콜을 쓴 경험: 편했던 것.**
- `Ok`/`Err`에 `match`, 그리고 `?`로 위로 넘기기. 단계마다 실패 길이 한 줄이었다.
- 꼬리 재귀가 곧 루프였다. 조각마다, 헤더 줄마다, 바이트마다, `accept`마다 돌아도 스택이 자라지 않는다.
- 맵·리스트가 넣은 순서를 지키고 `sort`가 튜플을 정렬하므로 Go의 정렬된 헤더 출력이 쉬웠다.
- 공개 함수의 매개변수에 타입 표기(`url: str`, `timeout: dur`)를 달았더니 Go와 똑같은 E0403 문구와 위치가 공짜로 나왔다.
- 클라이언트의 부품(헤더 해석, 길이 규칙, 조각 읽기)이 서버에 거의 그대로 쓰였다. Go `serveOne`은 작은 `match` 함수들로 풀렸다.
  `try_call` + `describe`로 "핸들러 실패를 잡아 분류하기"가 두 줄이었다.
- 가짜 서버 대조 테스트가 진짜 설계서였다. Go 출력이 명세가 되었고, Go 소스를 옆에 두고 읽으며 옮겼다.

**모자랐던 것.**
- **바이트가 없다.** `ord`·`chr`·바이트 리스트가 없어 `utf8_bytes`·`utf8_string` 네이티브와 글자 표(`_printable`, 제어 문자 목록)가 필요했다.
- **문자열 도구.** `index_of`·`cut`·한쪽만 `strip`이 없어 `split`과 `len`으로 짰다. 한쪽 trim은 보초 글자를 붙여 `trim`으로 했다.
- **튜플 인덱스가 안 된다.** `_cut(..)[0]`이 실패해서 `_before`를 따로 만들었다. 서버 첫 실행에서는 이것이 배경 태스크 안에서 조용히 죽었다.
- **최상위 함수가 모듈 상수를 못 본다**(모델 C). 상수를 인자 없는 함수(`_body_cap()`)로 만들었다. 테스트 핸들러도 채널을 만든 뒤 대입한 람다로 써야 했다.
- **모듈 안에서 자기 `get`이 prelude `get`을 가린다.** 실행해 보고서야 알았다.
- **원하는 에러 번호를 낼 수 없다.** fung 코드는 `fail`(E0803)뿐이라 E0403 "map of strings"는 네이티브(`need_str_map`)로 냈다. "fn이나 nil" 검사는 타입 표기를 단 도우미(`_ready_check`)로 했다.
- **`read_line`이 줄 끝이 CRLF였는지 LF였는지 숨긴다.** 조각 크기 줄은 바이트 하나씩 네이티브를 불러 읽는다. 부를 때마다 실행권을 놓지만 프로토콜 규모에서는 괜찮았다.
- **줄 잇기.** `+`로 시작하는 줄은 앞줄에 이어지지 않는다. 앞줄에 이어지는 것은 `|> . ?? and or then else`뿐이다.
- **문자열 `+` 누적은 제곱 시간이다.** 그래서 리스트에 모아 한 번에 잇는다. 접힌 헤더 처리가 처음에 제곱이었다(8절 (6)).
- **맵 키가 문자열뿐이다.** 상태 문구 표를 `"200"` 키로 만들었다가 정수 `match`로 바꿨다.
- **배경 태스크의 에러가 보이지 않는다.** 디버깅할 때 `spawn_background`를 잠깐 `spawn`으로 바꿔 실패 보고를 봤다.
- 끝내기 의미(취소할 수 없는 쓰기, 취소 뒤 정해진 시간 기다리기)는 fung으로 아예 표현할 수 없어 `hold`·배경 태스크·`set_asker`가 필요했다.

정리하면, **프로토콜 논리는 fung으로 충분했고, 모자란 것은 "바이트"와 "시간·취소의 바깥 의미"였다.** 더한 네이티브 여덟 개가 모두 그 둘 중 하나다. 어느 것도 프로토콜 일은 하지 않는다.

## 7. 그린 스레드를 미룬 이유

3a는 "태스크마다 운영체제 스레드 + 실행권 잠금"으로 시작했다. 그린 스레드(VM이 직접 태스크를 주차·재개하고 이벤트 루프가 입출력을 기다림)는 "4단계 이벤트 루프와 함께 재검토"였다.
4d 스펙에서 **6단계(Go 삭제) 뒤의 별도 단계 "R7 스케줄러"**로 미뤘다. 이유는 셋이다.
- **언어 의미를 바꾸지 않는 내부 교체다.** 막히는 곳은 이미 `block()` 한 곳으로 모여 있다. 이번 단계의 소켓 기다림도 같은 `Watch`를 지난다.
  그래서 나중에 그 자리만 갈아끼우면 된다. 사용자 코드도 골든 테스트도 바뀌지 않는다.
- **이 단계는 이미 컸다.** 소켓, TLS, 크레이트, HTTP 전체를 fung으로 짜기까지 했다. 여기에 스케줄러 교체를 더하면 실패했을 때 원인을 나눌 수 없다.
- **스크립트 규모에서는 지금 모델로 충분하다.** URL 몇십 개를 동시에 확인하거나 내부용 서버를 띄우는 정도는 태스크당 약 55 µs가 보이지 않는다(R3a 9절).

미룬 대가는 open-questions의 "R7 스케줄러" 항목에 모았다. 이번 단계에서 새로 생긴 것은 다음과 같다.
- 본문 중간에 멈춘 HTTP 클라이언트 하나가 그 연결 태스크의 스레드 하나를 닫을 때까지 붙잡는다. Go도 `ReadTimeout`이 없어 연결을 붙잡지만, Go는 고루틴이라 싸다.
- 막히는 기다림마다 파이프 하나.
- 이름 조회 스레드(시간으로는 묶이고 개수로는 묶이지 않음).
- `mio`는 들이지 않았다. 이벤트 루프 크레이트는 R7에서 판단한다.

## 8. 실제로 부딪힌 함정

진행 기록(`.superpowers/sdd/2026-10-16-rust-net-http-4d/progress.md`)과 작업 보고서, 리뷰에 적힌 것만 적는다.

**(1) `shutdown`으로는 깨울 수 없었다.** macOS에서 `accept`와 진행 중인 `connect`가 깨지 않는다(2절). 계획의 첫 후보였다.

**(2) 글자 하나가 두 읽기에 걸쳤다.** 읽을 때마다 UTF-8로 풀면 조각 경계에서 한글이 U+FFFD 둘이 된다. 바이트 버퍼(`read_bytes_into`·`take_body`)로 풀었다(2절).

**(3) 두 번째 읽는 쪽은 취소되지 않았다.** 잠금 기다림은 끊을 수 없다. "한 연결에 읽는 쪽 하나, 쓰는 쪽 하나"를 규칙으로 정했다(2절).

**(4) 테스트가 멈췄는데 원인은 테스트였다.** 첫 실행에서 테스트 하나가 끝나지 않았다. fung 프로그램의 최상위 `fn`이 뒤에 나오는 전역을 볼 수 없어서(모델 C) 컴파일이 실패했다.
그런데 Rust 쪽 상대가 `accept`에서 영원히 기다렸다. 그 뒤로 상대 도우미는 20초 뒤 실패하고, 자식 프로세스는 30초(`CHILD_LIMIT`)에 죽인다.
또 하나: 갈고리 호출을 `drop(hook)`으로 바꿔도 테스트가 통과했다. 쓰는 쪽이 닫혀도 `poll`이 깨기 때문이다. 이 사실은 주석에 적었다.

**(5) 읽지 않은 세션 티켓이 RST가 되었다.** TLS 테스트가 가끔 `UnexpectedEof` 대신 `ConnectionReset`을 봤다.
테스트 서버가 TLS 1.3 세션 티켓을 보냈는데 클라이언트가 읽지 않았다. 읽지 않은 데이터가 남은 소켓을 닫으면 커널이 RST를 보낸다(Go에서도 같은 실제 동작이다). 테스트 서버가 티켓을 보내지 않게 했다.

**(6) 접힌 헤더가 제곱 시간이었다.** 이어지는 줄을 `+`로 붙여서, 40만 줄이 7.8초 걸렸다. 조각 리스트로 모아 한 번에 잇자 0.94초가 되었다. 릴리스 전용 테스트가 4초로 지킨다.

**(7) 너무 많이 지우는 비교 필터.** 처음 대조는 Rust 호출 경로의 `extras/http.fung` 줄을 지우고 비교했다. 리뷰는 그것이 다른 차이(꼬리 호출 위치)까지 가린다고 지적했다.
지금은 Go와 Rust의 표준 에러를 각자 정확히 적고, 차이는 "알려진 차이"로 단언한다. 교훈: 비교에서 무엇을 지우는 장치는 그 자체가 차이를 숨길 수 있다.

**(8) 보이지 않던 Go 기본 동작.** URL의 사용자 정보(`user:pass@`)를 Go는 `Authorization: Basic`으로 바꿔 보낸다. 리뷰가 찾았다.
서버 쪽에서는 `OPTIONS *`를 Go 서버가 핸들러 없이 스스로 답한다. 둘 다 "Go 기본" 안이라 따라 했다.

**(9) 리다이렉트 본문과 순서.** Go는 리다이렉트 본문을 2 KB까지 읽고 버리고, 멈춘 본문에서는 기다린다. 그리고 그보다 `Location` 해석이 먼저다. 두 번의 리뷰에 걸쳐 맞췄다(5절).

**(10) 짐작한 기대값이 또 틀렸다.** `NO_PROXY`의 `::ffff:192.0.2.0/120`이 `192.0.2.5`에 맞는다는 것을 몰랐다(Go가 `To4`로 줄인다). 4b·4c와 같은 교훈이다. 기대값은 Go를 돌려 얻는다.

**(11) 2주 규칙과 보안 공지가 부딪혔다.** rustls 0.23.45를 고정한 이틀 뒤 공지 4건이 0.23.46의 수정과 함께 나왔다. 0.23.46은 2주가 안 되었다.
사용자 결정으로 정책을 세웠다. 공지가 우리 설정에 **닿지 않으면** 2주 규칙을 지키고, 이유를 적어 무시하고, 해제 날짜를 추적한다. **닿으면** 바로 올린다.
네 건 모두 닿지 않는다(세션 재개 끔, ECH·brotli 없음, ring에 MLKEM 없음). 그래서 2026-10-28 이후 0.23.46으로 올리고 무시 항목을 지운다.

**(12) 서버 취소 경쟁과 테스트의 포트 재사용.** 6절의 한 틱 창이다.
회귀 테스트는 처음에 "취소 뒤 포트가 거부되는지"를 봤다. 그런데 같은 시각에 다른 테스트가 `127.0.0.1:0`에 바인드하면서 풀린 포트 번호를 받아 가는 일이 있었다. 1만 틱 훑기마다 3~5번 연결이 잘못 성공했다.
그래서 "그 포트에서 HTTP로 답하는 것이 없는지"를 보게 바꿨다.

**(13) 배경 태스크의 조용한 실패.** 6절. 디버깅은 `spawn`으로 바꿔 보는 것밖에 없었고, 리뷰 뒤 내부 에러 보고를 넣었다.

**(14) `HEAD`의 `Content-Length`.** 서버가 `HEAD /echo`에 107을 냈고 Go는 109였다. 클라이언트의 `_length`를 요청 메서드로 불러서 생긴 실수였다.

**(15) Go 포매터의 결함.** `fn f(h: fn, x = 1):` 뒤의 블록 몸통을 Go `fung fmt`가 내어쓴다. 매개변수 타입의 `fn`을 람다로 읽기 때문이다.
Go가 정답지라 고치지 않고 `serve = _serve(...)`라는 한 줄 감싸개로 피했다. 그 대가로 `ready` 인자 에러의 호출 경로에 `_serve (1 tail calls elided)` 프레임이 하나 더 보인다.
open-questions에 M9 결함으로 적었다.

**(16) `gofmt -l .`과 cargo가 겹쳤다.** 동시에 돌리면 `target/` 아래 cargo의 임시 파일을 `gofmt`가 보려다 부딪힐 수 있다. 검사는 차례로 돌린다.

**(17) 컨트롤러의 `commit -a`.** 작업을 나눠 주는 쪽(컨트롤러)이 스펙 결정을 커밋하면서 `git commit -qam`을 썼다. 그때 다른 작업자가 아직 커밋하지 않은 Task 4 파일까지 쓸려 들어갔다.
푸시 전이라 문서만의 커밋과 Task 4 커밋으로 다시 나눴다(트리는 같음). 교훈: 여럿이 한 작업 트리를 쓰는 동안에는 `-a`·`-A`를 쓰지 않고 경로를 하나씩 적는다.

### 알고 남긴 동작

모두 open-questions "Rust 이전"의 "4d단계(http)에서 알고 남긴 차이"와 "0.2.0에서 바뀌는 것"에 적었다. 큰 것만 꼽으면 이렇다.
- 약속 밖: 연결 재사용, HTTP/2, 압축, 바이너리 본문(U+FFFD), SOCKS 프록시, https 프록시 너머의 https.
- 서버는 HTTP/1.1에서 늘 `Connection: close`이고 2 KB 넘는 본문도 `Content-Length`로 보낸다(Go는 조각 전송). 끝내는 중에 읽은 요청에는 503으로 답한다(Go는 답 없이 닫음).
- 인자 에러의 호출 경로에 `extras/rust/http.fung` 프레임이 보인다. 꼬리 위치에서 부르면 부른 함수의 프레임이 사라진다(fung으로 쓴 모든 라이브러리 함수와 같음).
