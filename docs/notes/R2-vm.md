# R2 Rust 값과 VM: 무엇을 옮겼고 왜 그렇게 했나

2026-10-15. 계획 `docs/plans/2026-10-15-rust-vm.md`, 결정과 남은 차이는 `docs/design/open-questions.md`의 "Rust 이전".

Rust 이식의 두 번째 단계가 끝났다. 1단계(`docs/notes/R1-front-end.md`)는 소스를 바이트코드까지 만드는 앞단을 옮겼다.
이번 단계는 그 바이트코드를 **실제로 실행하는** 부분, 곧 값과 VM을 옮겼다. 이제 Rust 버전의 `fung run`과 `fung -e`가 돈다.
이 노트는 두 가지를 다룬다.
- 무엇을 옮겼고 어떻게 Go와 같은지 확인했나.
- 이 과정에서 Rust의 어떤 개념을 썼나. 특히 Go에서는 가비지 컬렉터가 대신 해 주던 일을 Rust에서 어떻게 직접 하나.

## 1. 무엇을 옮겼나

새 크레이트 `crates/fung-vm`이 생겼다. 외부 크레이트 의존성은 앞단처럼 0개다.
- `value`: 값 표현. 정수·실수·문자열·기간·심볼과 리스트·맵·튜플·태그·범위·함수·모듈. 영속 벡터(`pvec`)와 HAMT(`hamt`), 순서 있는 맵(`omap`), 인덱스·슬라이스, 산술·비교·출력 형식.
- `vm`: 명령 실행 루프, 프레임, 호출 규약, 꼬리 호출, 패턴 매칭, `assert`·`test`, 모듈 실행, 런타임 에러와 호출 경로.
- `prelude`: Go 코어 내장 함수 42개(`print`·`map`·`fold`·`put`·`split`·`int`…)와 `args`.
- `native/process.rs`: `_native.process`(`exec`·`sh`·`env`).
- `conc.rs`: 동시성 내장 함수 자리. 부르면 `E0805 not supported yet: <이름>`.
- `boot.rs`: 바이너리에 들어 있는 `extras/prelude.fung`를 컴파일하고 실행해 fung으로 쓴 prelude 함수(`take`·`sum`·`retry`…)를 붙인다.

`crates/fung-cli`에는 `run.rs`가 생겼다. `fung run <파일>`, `fung <파일>`, `fung -e '<코드>'`가 Go `execute`와 같은 순서로 동작한다.
컴파일 에러는 종료 코드 2, 런타임 에러는 1, `exit(n)`은 n의 아래 8비트, `at_exit` 핸들러는 거꾸로 돈다.

옮기지 않은 것:
- 동시성 실행(`spawn`·채널·`atom`). 3단계에서 런타임을 새로 설계하며 만든다.
- 네이티브 다리 모듈 `fs`·`path`·`json`·`time`·`regex`·`http`. 4단계다. 순수 fung 모듈인 `cli`는 돈다.
- REPL·`check`·`test`·`fmt`. 5단계다.

### 어떻게 같은지 확인했나

1단계와 같은 방법을 실행까지 넓혔다. **Go 바이너리를 정답지로 두고 같은 입력을 두 바이너리에 넣어 바이트 단위로 비교한다.**
- `crates/fung-cli/tests/run_parity.rs`: 152건. 골든 테스트 `tests/lang` 136개 중 118개, `bench/` 4개, `-e` 프로그램 23개(인자와 표준 입력을 줌), 실행 방식 7가지(경로 없음, 없는 파일, 디렉터리, 모르는 명령 등). 표준 출력, 표준 에러, 종료 코드를 모두 본다.
- 제외 18개는 `run_parity_skip.txt`에 이유와 함께 적었다. 동시성 9개, 네이티브 모듈 9개. 테스트가 제외 목록 자체도 검사한다. 이유가 "동시성"이면 파일에 실제로 `spawn(` 같은 호출이 있어야 하고, "네이티브 모듈"이면 `import json` 같은 줄이 있어야 한다.
- `crates/fung-vm/src/prelude/go_cases.rs`: 내장 함수마다 성공과 에러 경로를 찌르는 프로그램 281개를 Go 바이너리와 실행 시점에 비교한다.
- 1단계의 dump 비교(561건 이상)도 그대로 돈다.
- `crates/fung-cli/tests/perf.rs`(이번에 추가): 릴리스 빌드에서만 도는 성능 테스트. 9절.

`FUNG_REQUIRE_PARITY=1`이면 Go가 없을 때 건너뛰지 않고 실패한다. CI는 이 값을 켜고 `cargo test`와 `cargo test --release`를 둘 다 돈다.

## 2. VM 실행 루프와 프레임

fung의 VM은 **스택 기계**다. 명령은 값 스택에서 피연산자를 꺼내고 결과를 다시 쌓는다. `1 + 2`는 `CONST 1`, `CONST 2`, `ADD`다.

실행 단위는 `Task`다 (`crates/fung-vm/src/vm.rs`).

```rust
pub struct Task<'rt> {
    rt: &'rt mut Runtime,
    stack: Vec<Option<Value>>,
    frames: Vec<Frame>,
    native: Option<&'static Native>,
}
```

- `stack`: 모든 함수의 지역 변수와 계산 중인 값이 한 줄로 쌓인다.
- `frames`: 지금 실행 중인 함수들. 프레임 하나가 함수 호출 하나다.
- `'rt`는 **수명**(lifetime) 표기다. "이 `Task`는 빌려 온 `Runtime`보다 오래 살 수 없다"는 약속을 컴파일러가 검사한다. Go라면 포인터 하나로 끝났을 관계를 Rust는 타입에 적는다.

프레임 (`vm/frame.rs`):

```rust
pub(super) struct Frame {
    pub proto: Rc<RtProto>,
    pub ip: usize,
    pub base: usize,
    pub closure: Option<Rc<Closure>>,
    pub globals: Globals,
    pub tail_calls: u64,
}
```

- `proto`: 실행할 함수의 명령 열과 상수.
- `ip`: 다음에 실행할 명령의 번호.
- `base`: 이 함수의 지역 변수가 `stack`의 몇 번째 칸부터 시작하나. 지역 변수 3번은 `stack[base + 3]`이다.
- `tail_calls`: 꼬리 호출로 이 프레임을 몇 번 재사용했나. 에러의 호출 경로에 "(N tail calls elided)"로 보인다.

실행 루프 `exec`는 매 명령마다 맨 위 프레임에서 명령을 하나 읽고, `match`로 갈래를 탄다.

```rust
loop {
    let fi = self.frames.len() - 1;
    let f = &mut self.frames[fi];
    let ip = f.ip;
    let instr = f.proto.code[ip];
    f.ip = ip + 1;
    match instr.op() {
        Op::Add => self.binary(pos, i64::checked_add, value::add)?,
        Op::Jump => self.frames[fi].ip = arg,
        Op::Call | Op::TailCall => { ... }
        ...
    }
}
```

프레임을 변수에 붙잡아 두지 않고 **매번 번호로 다시 찾는** 이유는 빌림 검사기다. `f`가 `self.frames`를 빌리고 있는 동안에는 `self.push(...)`처럼 `self` 전체를 고치는 호출을 할 수 없다. 번호(`fi`)는 빌림이 아니라 그냥 정수라서 이 문제가 없다.
`match`가 모든 `Op`를 다뤘는지 컴파일러가 검사한다. Task 7에서 마지막 명령(`IMPORT`)을 넣자 "모르는 명령" 갈래가 도달 불가능 경고가 되어 지웠다.

정수 덧셈에는 빠른 길이 있다. 두 값이 모두 정수면 `i64::checked_add`로 바로 더하고, 넘치면(`None`) 값 층의 `value::add`로 넘겨 E0503 보고를 만든다.

호출은 `vm/call.rs`가 맡는다.
- fung 함수를 매개변수 개수 그대로 부르면, 스택에 이미 쌓인 인자가 **그 자리에서** 새 프레임의 첫 지역 변수가 된다. 인자 배열을 따로 만들지 않는다.
- 이름 인자, 기본값, `...rest`가 있으면 Go `bindArgs`와 같은 일반 길로 간다.
- 꼬리 호출은 새 프레임을 쌓지 않고 지금 프레임을 비우고 재사용한다. 그래서 꼬리 재귀는 몇 번을 돌아도 프레임이 늘지 않는다.
- 꼬리가 아닌 호출은 프레임이 10만 개를 넘으면 `E0804`다. Go와 같은 한도다.

## 3. `Rc`와 참조 계수

Go는 가비지 컬렉터가 "아무도 가리키지 않는 값"을 찾아 치운다. Rust에는 가비지 컬렉터가 없다. 그래서 VM은 **참조 계수**로 값을 관리한다.

`Rc<T>`(reference counted)는 힙에 값을 두고, 그 값을 가리키는 손잡이가 몇 개인지 센다.
- `Rc::clone(&x)`는 값을 복사하지 않는다. 계수만 1 올리고 같은 값을 가리키는 손잡이를 하나 더 준다.
- 손잡이가 사라지면(`drop`) 계수가 1 내려간다. 0이 되는 순간 값이 바로 해제된다.
- `Rc`는 스레드 사이에 넘길 수 없다. 원자적 연산을 쓰지 않아 빠른 대신이다. 스레드 사이 공유용은 `Arc`다. open-questions의 결정(태스크마다 힙을 따로 두고 경계에서만 복사)이 `Rc`를 쓸 수 있게 해 준다.

값의 모양 (`value.rs`):

```rust
pub enum Value {
    Int(i64),
    Float(f64),
    Bool(bool),
    Nil,
    Str(Rc<String>),
    Sym(Sym),
    Dur(i64),
    List(Rc<List>),
    Map(Rc<Map>),
    Tuple(Rc<Tuple>),
    Tag(Rc<Tag>),
    Range(Rc<Range>),
    Closure(Rc<Closure>),
    Native(&'static Native),
    Module(Rc<Module>),
}
```

- 크기는 16바이트다. 종류 표시 8바이트 + 칸 8바이트. 테스트가 이 크기를 고정한다.
- 정수·실수·불·기간은 칸에 바로 들어간다. 상자도 계수도 없다. Go의 인터페이스 값은 정수를 상자에 넣는 경우가 있는데, 이 점은 Rust가 유리하다.
- 큰 값은 `Rc`로 가리킨다. 그래서 `Value`를 복제(`clone`)해도 큰 리스트가 복사되지 않는다. 계수만 오른다.
- `Native(&'static Native)`: 내장 함수는 프로그램이 끝날 때까지 살아 있으므로 계수 없이 `'static` 참조로 가리킨다.

불변 값이라는 fung의 성질이 여기서 효과를 낸다. 값을 고치지 않으므로 여러 곳이 같은 값을 공유해도 안전하다. 그리고 태스크 안에서는 순환 참조가 생기지 않으므로(값이 만들어질 때 이미 있는 값만 가리킬 수 있다) 참조 계수만으로 회수가 완전하다.

예외가 하나 있다. 전역 변수에 저장한 함수는 그 전역 표를 붙잡고, 전역 표는 그 함수를 붙잡는다. 이것은 순환이다. 그래서 `Runtime`이 끝날 때(`Drop for Runtime`) 전역 표를 비워 고리를 끊는다.

## 4. `Rc::make_mut`와 제자리 수정

참조 계수의 덤이 있다. **손잡이가 하나뿐이면, 그 값을 고쳐도 아무도 눈치채지 못한다.** 이것이 제자리 수정이다.

`Rc::make_mut(&mut rc)`가 이 판단을 해 준다.
- 계수가 1이면: 그 값을 그대로 고칠 수 있는 `&mut`를 준다. 복사 없음.
- 계수가 2 이상이면: 값을 복제해 새 `Rc`에 넣고, 이 손잡이를 새 것으로 바꾼 뒤 `&mut`를 준다. 다른 손잡이들은 원래 값을 그대로 본다.

`put` 내장 함수가 그 예다 (`prelude/collections.rs`).

```rust
fn put_fn(_: &mut Task<'_>, mut a: Vec<Value>) -> Result<Value, Stop> {
    ...
    let mut m = take_map(&mut a, 0);
    Rc::make_mut(&mut m).put(k, v);
    Ok(Value::Map(m))
}
```

`take_map`은 인자 배열에서 맵을 **꺼내 온다**(move). 복제하지 않는다. 그래야 다른 손잡이가 없을 때 계수가 1이 되어 제자리 수정이 가능하다.

### VM이 값을 옮기는 규칙

제자리 수정이 실제로 일어나려면 VM이 쓸데없이 계수를 올리지 않아야 한다. 규칙은 이렇다.
- 연산자의 피연산자는 스택에서 **꺼내서(move)** 쓴다. 복제하지 않는다.
- 호출 인자는 스택에서 꺼내 새 프레임의 지역 변수로 옮기거나, 내장 함수의 인자 배열로 옮긴다(`drain`).
- `fold`는 누적값을 인자 버퍼로 옮기고, 람다의 결과를 다시 꺼내 온다. 원소마다 복제하지 않는다.
- 다만 지역 변수를 **읽는** `LOADLOCAL`은 복제한다. 변수는 그 뒤에도 읽힐 수 있기 때문이다.

마지막 규칙 때문에 `fold(0..n, {}, (acc, i) => put(acc, ...))`의 람다 안에서는 `acc`의 손잡이가 둘이다(지역 변수 칸 하나, `put`의 인자 하나). 그래서 `make_mut`는 맵의 **겉껍데기**를 복제한다.
그래도 느려지지 않는 이유가 5절이다. 겉껍데기 복제는 `Rc` 몇 개의 계수를 올리는 일이고, 안쪽은 바뀌는 경로만 복사한다.
변수의 마지막 사용을 컴파일러가 알려 주면 이 복제도 없앨 수 있다. 10절에 적었다.

Review Focus 중 하나가 "공유된 컬렉션에 덧붙이거나 `put`해도 원본이 바뀌지 않아야 한다"였다. `make_mut`는 공유 중이면 반드시 복사하므로 원본은 안전하다. 테스트(`put_on_a_shared_map_keeps_the_original`, `shared_list_is_never_changed` 등)가 이를 고정한다.

## 5. 영속 자료구조를 Rust 소유권 아래서

M10(`docs/notes/M10-persistent-collections.md`)에서 Go 버전은 리스트를 32개 넘으면 **영속 벡터**로, 맵을 16개 넘으면 **항목 벡터 + HAMT 색인**으로 바꿨다. 새 버전을 만들 때 바뀌는 경로의 노드만 복사하고 나머지는 옛 버전과 공유한다(경로 복사).

Rust에서도 구조는 같다. 다른 것은 "경로 복사"를 쓰는 방법이다.
- Go: 경로의 노드를 **항상** 새로 만든다. 옛 노드는 GC가 나중에 치운다.
- Rust: 경로의 노드마다 `Rc::make_mut`를 부른다. 그 노드를 아무도 공유하지 않으면 제자리에서 고치고, 공유 중이면 복사한다 (`value/pvec.rs`).

```rust
let mut n = Rc::make_mut(&mut self.root);
for level in ... {
    n = Rc::make_mut(&mut n.kids_mut()[(i >> level) & MASK]);
}
```

이렇게 하면 같은 코드가 두 경우를 다 처리한다.
- 아무도 옛 버전을 들고 있지 않으면(빌더, 혼자 쓰는 누적값): 복사 없이 제자리.
- 누가 옛 버전을 들고 있으면: Go처럼 경로만 복사. 옛 버전은 그대로.

리스트의 꼬리(tail, 마지막 32개 이하)는 `Rc::get_mut`를 쓴다. 이 함수는 계수가 1일 때만 `&mut`를 주고, 아니면 `None`이다. `None`이면 32칸짜리 새 잎을 만든다.

작은 컬렉션은 다르게 다룬다.
- 32개 이하 리스트는 그냥 `Vec<Value>`다. 복제는 원소 32개 이하의 계수 올리기다.
- 16개 이하 맵은 `Vec<(Rc<String>, Value)>`다. Go는 Go 맵 + 키 순서 슬라이스를 쓰지만, 16개를 처음부터 훑는 것이 Rust에서는 더 싸고 순서도 공짜로 지켜진다.

해시 값은 프로세스마다 무작위 시드(`RandomState`)로 만든다. 맵을 출력하는 순서는 항상 넣은 순서(항목 벡터)라서, 해시가 바뀌어도 출력은 같다. 1단계에서 정한 "출력 순서가 드러나는 곳에서 `HashMap`을 순회하지 않는다"는 규칙이 여기서도 이어진다.

## 6. `Drop`과 연쇄 해제

Rust는 값이 사라질 때 `Drop`을 부른다. 기본 동작은 **필드를 하나씩 해제**하는 것이다. 리스트 안에 리스트 안에 리스트가 백만 단 들어 있으면, 마지막 손잡이가 사라질 때 해제가 백만 단 재귀한다. 스택이 넘친다.
Go에서는 GC가 반복으로 훑으므로 이런 문제가 없다. Rust에서는 직접 막아야 한다.

해결은 `value/release.rs` 한 곳에 모았다.
- 값을 담는 모든 그릇(리스트, 맵, 튜플, 태그, 함수, 모듈)이 자기 `Drop`에서 자식들을 **꺼내** 명시적 스택(`Vec<Value>`)에 넣는다.
- 그중 "깊어질 수 있는 것", 곧 계수가 1인 그릇만 남긴다. 계수가 2 이상이면 계수만 내려가고 해제가 일어나지 않으니 깊어지지 않는다.
- `release`가 스택에서 하나씩 꺼내 `Rc::try_unwrap`으로 연다. 열리면(계수가 1이었으면) 그 자식들도 같은 스택에 넣는다. 빈 껍데기는 재귀 없이 사라진다.

```rust
fn nests(v: &Value) -> bool {
    match v {
        Value::List(rc) => Rc::strong_count(rc) == 1,
        Value::Map(rc) => Rc::strong_count(rc) == 1,
        ...
        _ => false,
    }
}
```

왜 맨 위에서 한 번만이 아니라 **그릇마다** `Drop`을 두나. 값이 해제되는 곳이 많기 때문이다. 맵 항목을 덮어쓸 때, 공유 노드가 사라질 때, VM이 지역 변수 칸을 덮어쓸 때. 어디서 해제되든 결국 어떤 그릇의 `Drop`을 지나므로, 재귀가 모든 곳에서 끊긴다.

`impl Drop for Value`는 기각했다. `Value`에 `Drop`이 있으면 VM의 모든 `match`에서 값을 꺼내 옮길(move) 수 없게 된다. Rust는 `Drop`이 있는 타입을 부분적으로 옮기지 못하게 하기 때문이다.

테스트는 1 MiB 스택 스레드에서 백만 단 리스트, 튜플 사슬, 맵 사슬, 함수 사슬, 모듈 사슬을 만들고 버린다. 해당 그릇의 `Drop`을 끄면 각 테스트가 스택 넘침으로 죽는 것을 확인했다. 테스트가 실제로 무언가를 지킨다는 뜻이다.

## 7. 내장 함수가 VM을 다시 부르는 구조

`map(xs, f)`나 `fold(xs, init, f)`는 Rust로 쓴 내장 함수인데, 원소마다 fung 람다 `f`를 불러야 한다. 내장 함수가 VM을 **다시** 부른다.

방법은 `Task::call`과 `Task::call_buf`다.
- 내장 함수는 `&mut Task`를 받는다. 그 `Task`에 `call(f, args)`를 하면 VM이 `f`의 프레임을 쌓고, `f`가 돌아올 때까지 실행 루프를 한 번 더 돈다.
- 이때 Rust 함수 호출이 쌓인다. 실행 루프 → `fold` → `call` → 실행 루프 → ... 람다가 다시 `fold`를 부르면 Rust 스택이 한 단 더 깊어진다.
- `call_buf`는 인자 버퍼를 재사용한다. 원소마다 새 `Vec`을 만들지 않는다. Go 성능 2단계의 "태스크별 인자 버퍼"를 옮긴 것이다. 단 내장 함수를 원소마다 부를 때(`map(xs, str)`)는 여전히 인자 배열을 새로 만든다. 9절의 `str` 결과와 이어진다.

람다 안의 에러는 Go와 같은 호출 경로로 보고되어야 한다(Review Focus 3).
- 에러가 나면 그 순간의 프레임 목록으로 호출 경로를 한 번 기록한다. 바깥으로 전파되는 동안에는 이미 있는 경로를 지킨다(`with_call_path`).
- prelude.fung 안의 함수(`take`, `sum` 등)에서 난 에러는 위치를 사용자의 호출 자리로 옮긴다. Go `attach`와 같다. 사용자에게 "내 코드의 어디가 문제인가"를 보여 주기 위해서다.

## 8. 실제로 부딪힌 함정

이번 단계에서 실제로 겪고 진행 기록·보고서에 적힌 것만 적는다. 1단계와 마찬가지로 대부분 "Go가 해 주던 일을 Rust에서는 직접 해야 한다"는 형태였다.

**(1) 튜플의 타입을 바꿔야 했다.**
- 계획은 튜플을 `Rc<Vec<Value>>`로 적었다. 그런데 `Vec<Value>`는 남의 타입이라 여기에 우리 `Drop`을 붙일 수 없다. 그러면 튜플만으로 된 깊은 사슬이 재귀로 해제된다.
- 해결: `pub struct Tuple(Vec<Value>)`로 감싸고 `Value::Tuple(Rc<Tuple>)`로 바꿨다. `Deref`를 구현해 `.len()`, `[i]`는 전처럼 쓴다. 값 크기는 여전히 16바이트.
- 대가: 뒤 작업의 계획서가 `Rc<Vec<Value>>`라고 적은 곳을 모두 `Value::tuple(items)`로 읽어야 했다. `Tag`도 `Drop`이 생겨서 필드를 옮겨 꺼내려면 `std::mem::take`를 써야 한다.

**(2) 내장 함수가 람다를 부르면 Rust 스택을 쓴다.**
- `fn r(n) = ... fold([n], 0, (a, x) => r(x - 1))`처럼 `fold`를 통해 6만 단 재귀하는 프로그램을 Go는 문제없이 돈다. 고루틴 스택은 자라기 때문이다.
- Rust에서는 7절의 구조 때문에 한 단마다 Rust 함수 몇 개가 쌓인다. 6만 단에 릴리스 빌드로 128~256 MiB의 스택이 필요했다. 메인 스레드(보통 8 MiB)에서는 스택 넘침으로 프로세스가 죽는다.
- 해결: CLI가 VM을 1단계에서 만든 4 GiB 스택 스레드에서 돌린다. 런타임과 모든 값도 그 스레드 안에서 해제한다.
- 이것은 임시방편이다. 3단계에서 태스크를 주차·재개하는 런타임을 만들 때 이 구조를 다시 본다(open-questions의 "C 경계를 넘는 yield").

**(3) 아주 큰 범위가 E0801 대신 프로세스를 죽였다.**
- `sort(0..10^17)`처럼 2^44개를 넘는 범위를 리스트로 펼치려 하면 Go는 `make`가 패닉하고, 그 패닉이 `E0801 internal error: runtime error: makeslice: cap out of range`로 보고된다.
- Rust는 그만큼 메모리를 잡으려다 할당 실패로 **중단(abort)**됐다. Rust의 할당 실패는 패닉이 아니라 중단이라 VM의 패닉 울타리(`catch_unwind`)가 잡지 못한다.
- 해결: `nat::check_items`가 Go가 펼치는 곳마다 같은 순서로 크기를 먼저 검사하고, Go와 같은 E0801 문구를 낸다. 16개 내장 함수 × 두 크기 = 32개 프로그램을 Go와 비교한다.
- 교훈: "Go에서 패닉"이 "Rust에서도 패닉"이라는 보장은 없다. 정답지가 내는 출력을 그대로 만들어야 한다.

**(4) 얼린 정답 대신 실행 시점 비교.**
- 내장 함수 비교 테스트는 처음에 Go의 출력을 파일에 **얼려** 두었다. 리뷰에서 문제가 됐다. Go가 바뀌면 얼린 정답이 낡아도 아무도 모른다.
- 해결: 프로그램 목록만 두고, 테스트가 Go 바이너리를 빌드해 그 자리에서 비교한다. `parity.rs`의 관례(`FUNG_REQUIRE_PARITY`)를 따른다. 틀린 대소문자 변환을 일부러 심어 비교가 실제로 잡는지 확인했다.
- 교훈: 정답지가 살아 있으면 정답을 저장하지 않는다. 저장한 정답은 정답지와 어긋날 수 있다.

**(5) 닫힌 파이프.**
- `fung -e 'each(0..1000000, print)' | head -1`처럼 읽는 쪽이 먼저 닫히면, Go는 SIGPIPE 신호로 조용히 죽는다. 셸은 141을 본다.
- Rust 표준 라이브러리는 시작할 때 SIGPIPE를 **무시**하도록 설정한다. 그래서 쓰기가 에러(`BrokenPipe`)로 돌아오고, 처음 버전은 이를 `E0801 internal error: Broken pipe`로 보고하고 종료 코드 1로 끝나며 `at_exit` 핸들러까지 돌렸다.
- SIGPIPE를 다시 기본값으로 돌리면 될 것 같지만 안 된다. 자식 프로세스의 표준 입력에 쓸 때(`exec(..., stdin: ...)`)는 끊긴 파이프가 에러 값이어야 하는데, 그때도 fung이 죽어 버린다.
- 해결: 표준 출력·에러에 쓰는 곳만 감싸서(`ProcessOut`), `BrokenPipe`를 만나면 바로 `exit(141)`. 셸에서는 같은 141이다. 신호로 진짜 죽는 것은 `libc`가 필요해 3단계로 미뤘다.

**(6) 빈 칸은 `nil`이 아니다.**
- Go VM에서 아직 값이 들어가지 않은 지역 변수·전역 변수 칸은 Go의 `nil`이다. fung의 `nil` 값과는 다르다. `JUMPIFSET`(기본값 매개변수에서 "인자가 들어왔나"를 묻는 명령)이 이 둘을 구분한다.
- 해결: 칸을 `Option<Value>`로 두었다. `None`이 빈 칸, `Some(Value::Nil)`이 fung의 `nil`이다.
- `Option<Value>`도 16바이트다. Rust가 `Value`의 종류 표시에서 쓰지 않는 값을 `None`에 써서 크기를 늘리지 않는다(niche 최적화). 테스트가 이 크기를 고정한다.

**(7) prelude를 부팅하면 파일 번호가 밀린다.**
- 에러 위치는 (파일 번호, 줄, 열)이다. 파일 번호는 컴파일할 때 로더가 붙인다.
- 사용자 프로그램과 `extras/prelude.fung`를 따로 컴파일하니 둘 다 0번부터 번호를 붙였다. prelude 안 함수가 호출 경로에 나오면 사용자 파일 이름이 찍힐 뻔했다.
- 해결: 프로그램을 먼저 컴파일해 `Runtime`을 만들고, 부팅 때 prelude의 파일을 뒤에 덧붙이며(`add_sources`) prelude 쪽 위치의 파일 번호를 그만큼 민다. Go는 부팅을 먼저 하지만, 부팅은 실패할 수 없어서 출력은 같다.
- 미는 코드를 일부러 끄면 부팅 테스트 셋이 실패한다.

**(8) 정수의 가장자리.**
- `Dur - MIN`: Go는 기간 뺄셈을 "음수로 바꾼 뒤 더하기"로 하므로, 오른쪽이 i64의 최솟값이면 부호를 바꿀 수 없어 E0503이다. 정수 뺄셈은 그렇게 하지 않는다. Rust도 기간에서만 같은 검사를 한다(`-1 - MIN`은 정수로는 `MAX`).
- 꼬리 호출 횟수를 처음에 `u32`로 세었다. 2^32번 넘게 꼬리 호출하면 디버그 빌드에서 패닉, 릴리스에서 0으로 되돌아간다. Go의 `int`는 64비트라 `u64`로 바꿨다.
- `exit(n)`의 n도 `i64`로 들고 다닌다. 아래 8비트로 줄이는 것은 프로세스가 끝나는 순간 한 번뿐이다(`exit(300)`은 44, `exit(-1)`은 255). Go와 같다.

## 9. 벤치마크와 성능 테스트

### Go와 비교

`bench/`의 네 스크립트를 Go 바이너리(`go build -o /tmp/fung-go ./cmd/fung`)와 Rust 릴리스 빌드(`cargo build --release`)로 각 5번 돌리고 가장 빠른 값을 적었다. 프로세스 시작부터 끝까지의 시간이다.

기계: Apple M2 Max(`arm64`), macOS 27.0.1, Go 1.27.2, Rust 1.94.1. 2026-10-15.

| 스크립트 | 재는 것 | Go | Rust | Go/Rust |
|---|---|---|---|---|
| `fib.fung` | `fib(30)` 재귀: 함수 호출 | 0.202초 | 0.203초 | 1.00 |
| `loop.fung` | 300만 번 `fold`: 산술과 반복 | 0.240초 | 0.212초 | 1.13 |
| `str.fung` | 숫자 50만 개를 문자열로 잇기 | 0.053초 | 0.072초 | 0.73 |
| `map.fung` | 키 20만 개 맵 만들고 조회 | 0.450초 | 0.359초 | 1.26 |

네 스크립트 모두 출력은 Go와 같다. 빈 프로그램(`-e 'print(1)'`)은 Go 0.006초, Rust 0.004초다.

읽는 법:
- 함수 호출(`fib`)은 같다. 둘 다 같은 바이트코드를 같은 방식으로 실행하므로 놀랍지 않다.
- 맵(`map`)은 Rust가 빠르다. 16개 이하 맵을 `Vec`으로 두고, GC가 없어 해제가 그 자리에서 끝나는 덕으로 보인다.
- **문자열(`str`)은 Rust가 느리다.** 나눠 재 보면 원인이 좁혀진다.
  - `map(0..500000, (i) => i)`: Go 0.026초, Rust 0.020초. 람다 호출은 느리지 않다.
  - `map(0..500000, (i) => str(i))`: Go 0.060초, Rust 0.103초. 람다 안에서 **내장 함수 `str`을 부르는 길**이 느리다.
  - 진행 기록에 "내장 함수 호출은 인자 배열을 두 번 만든다(위치 인자 배열 + 매개변수 칸 배열). Go는 한 번"이라는 보류 항목이 있다. 가장 그럴듯한 원인이지만 이번 작업은 고치지 않았다. 성능 테스트가 통과하는 한 최적화는 범위 밖이다.

### 성능 테스트

`crates/fung-cli/tests/perf.rs`는 Go `tests/perf_test.go`의 다섯 모양을 같은 소스·2만 개로 옮겼다. M10에서 "복사하면 제곱 시간이 되는" 모양들이다. 각 모양을 한 번 데운 뒤 재서 0.3초 안이어야 한다. 디버그 빌드는 느려서 아무것도 말해 주지 못하므로 `#![cfg(not(debug_assertions))]`로 릴리스 빌드에서만 돈다(`cargo test --release`).

같은 기계에서 잰 값:

| 모양 | 시간 |
|---|---|
| 맵 `put` 누적 | 31ms |
| 기존 키 갱신 | 23ms |
| 리스트 덧붙이기 `acc + [i]` | 9ms |
| `[_, ...rest]` 재귀 | 6ms |
| `ys[1..]` 재귀 | 8ms |

모두 한도의 10분의 1 아래다. 고칠 것이 없었다. 원소 수를 20만으로 10배 늘리면 리스트 덧붙이기는 0.05초, 맵 누적은 0.30초로, 제곱(100배)이 아니라 대략 선형으로 늘어난다.

## 10. 다음: 3단계

3단계는 런타임이다. open-questions "Rust 이전"의 결정을 따른다.
- 태스크마다 힙을 따로 두고 경계(`spawn`이 붙잡은 값, 채널로 보낸 값, `await` 결과)에서만 복사한다. 태스크 안은 지금처럼 `Rc`.
- VM이 직접 하는 스케줄러: 명령 사이에서 태스크를 주차·재개하고, 일정 명령 수마다 차례를 넘긴다.
- 채널, `spawn`·`await`·`cancel`, 교착 감시. `atom`은 만들지 않는다.
- 그러면 실행 비교 제외 목록의 동시성 9개가 비교에 들어간다.

3단계 이후로 미룬 것:
- 내장 함수가 람다를 부를 때 Rust 스택을 쓰는 구조(8절 (2)). 태스크를 주차하려면 Rust 스택 위에 VM이 겹쳐 있으면 안 되므로 3단계 설계에서 함께 다룬다.
- 닫힌 파이프에서 진짜 SIGPIPE로 죽기(`libc` 허용 뒤).
- 성능: 내장 함수 호출의 인자 배열 두 번 만들기(9절의 `str`), 지역 변수의 마지막 사용을 이동으로 바꿔 `make_mut`가 겉껍데기도 복사하지 않게 하기(4절).
- 유니코드 글자·숫자 판정을 Go 표와 맞추기는 바로 다음 작업(Task 12)에서 한다.

이 단계에서 배운 것을 한 줄로 줄이면, **가비지 컬렉터가 하던 일(해제 순서, 깊은 해제, 공유 판단)을 참조 계수로 옮기면 그 일이 코드에 드러나고, 드러난 곳마다 테스트로 고정할 수 있다.**
