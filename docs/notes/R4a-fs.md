# R4a `fs`·`path`: 무엇을 옮겼고 왜 그렇게 했나

2026-10-15~16. 계획 `docs/plans/2026-10-15-rust-fs-4a.md`, 스펙 `docs/superpowers/specs/2026-10-15-rust-fs-4a-design.md`,
결정과 남은 차이는 `docs/design/open-questions.md`의 "Rust 이전".

Rust 이식 4단계는 네이티브 원시 기능(운영체제·외부 세계에 닿는 것)을 옮긴다. 넷으로 나눴고(4a `fs`·`path`, 4b `time`·`json`, 4c `regex`, 4d `http`),
이 노트는 첫 조각 4a다. 3b까지는 VM 안의 일이었다면, 4a는 처음으로 **운영체제가 돌려주는 것**(에러, 디렉터리 순서, 파일 디스크립터)을 Go와 똑같이 보여야 했다.

## 1. 무엇을 옮겼나

사용자에게 보이는 것: `import fs`·`import path`가 Rust에서도 된다(3b까지는 E0805 "지원 안 함"). `extras/fs.fung`·`path.fung`과 prelude의 `with_open`·`read_line`·`read_lines`는
Go와 같은 fung 파일을 그대로 쓴다. 골든 테스트 `fs_and_path`가 Go 대조와 Rust 골든 실행기 양쪽에 들어갔다.

내부(`crates/fung-vm/src/native/`):
- `path.rs`: `_native.path` 6개(`join` `base` `dir` `ext` `stem` `abs`)와 Go `filepath.Clean`을 바이트 단위로 옮긴 `clean`.
- `fs.rs`: `_native.fs` 17개. 파일·디렉터리 함수 11개(`read` `write` `append` `exists` `stat` `mkdir` `remove` `remove_all` `move` `copy` `temp_dir`),
  목록 3개(`list` `glob` `walk`), 핸들 3개(`open` `close` `write_line`).
- `oserr.rs`: 운영체제 에러를 Go 문구로(2절).
- `glob.rs`: Go `filepath.Match`·`Glob`(5절).
- `file.rs`: 파일 핸들(`Value::File`)과 Go `bufio`를 흉내 내는 `GoWriter`(3·4절).
- 덤으로 3b에서 남긴 취소 노드 누수를 고쳤다(`vm/task.rs`, 6절).

크레이트는 쓰지 않았다. 전부 Rust 표준 라이브러리(`std::fs`, `std::io`)다.

비교로 확인한 것: 경로 입력 38개와 에러 11개가 Go와 같다. errno 표 161개가 Go와 같다(2절). 무작위 `Match` 30만 쌍이 Go와 같다.
핸들 프로그램 14개, 준비한 디렉터리 트리 위의 `list`·`walk`·`glob` 프로그램들이 Go 바이너리와 바이트 단위로 같다.
`tests/lang`의 실행 비교는 131개(네이티브 모듈 8개와 `# only: go` 3개 제외), Rust 골든 실행기도 131개.

## 2. 운영체제 에러를 값으로: errno → Go 문구

fung에서 파일 함수는 실패를 예외가 아니라 값으로 돌려준다. `fs.read("x")`는 `Err({kind: 'not_found, message: "cannot read `x`: no such file or directory"})`다.
`kind`는 프로그램이 분기할 때 쓰고, `message`는 사람이 읽는다. 골든 테스트는 이 `message`까지 글자 단위로 비교한다.

운영체제는 실패를 **errno**라는 작은 정수로 알린다(없는 파일은 2번 `ENOENT`, 권한 없음은 13번 `EACCES`). 이 번호를 문장으로 바꾸는 방법이 언어마다 다르다.
- Go는 자기 표를 들고 있다(`syscall` 패키지의 `zerrors_<os>_<arch>.go`). 2번은 `no such file or directory`.
- Rust의 `io::Error`를 그냥 출력하면 C 라이브러리의 `strerror` 문구에 번호가 붙는다. `No such file or directory (os error 2)`. 대문자로 시작하고 꼬리가 붙는다.

그래서 Rust 쪽은 `io::Error`를 출력하지 않고 errno 번호만 꺼내(`raw_os_error()`) **Go의 표**에서 문구를 찾는다(`oserr::reason`).
표는 Go 소스에서 그대로 베꼈다. errno 번호는 macOS와 Linux가 다르므로(예: `ENOTEMPTY`는 macOS 66, Linux 39) 표가 둘이고, arm64에서 한 줄씩 더 있다.

베낀 표가 맞는지는 테스트가 **살아 있는 Go로** 확인한다. `errno_table_matches_go`는 임시 디렉터리에 작은 Go 프로그램을 써서 `go run`으로
`syscall.Errno(n).Error()`를 0부터 160까지 찍고, 한 줄씩 Rust 표와 비교한다. 이 기계(macOS arm64)에서 통과했고, Linux 표는 Linux CI에서 같은 테스트가 확인한다.

errno 하나로는 끝나지 않는 곳도 있었다. Go의 `os.MkdirAll`·`os.Remove`·`os.RemoveAll`·`os.Rename`·`os.MkdirTemp`는 시스템 호출을 여러 번 하고,
**어느 호출의 errno를 보고하는지**가 함수마다 정해져 있다. 예를 들어 Go `os.Remove`는 `unlink`를 해 보고, 실패하면 `rmdir`를 해 본 뒤 `rmdir`의 에러를 보고한다
(그 에러가 "디렉터리가 아님"이면 `unlink`의 것을). Rust `std::fs::remove_file`은 `unlink` 하나뿐이라 디렉터리에서 다른 errno가 나온다.
그래서 이 함수들은 Go의 단계를 그대로 옮겼다(`fs.rs`의 `mkdir_all`·`remove`·`remove_all`·`rename`·`make_temp_dir`).
경로에 NUL 바이트가 있으면 Go는 시스템 호출 전에 `EINVAL`(invalid argument)을 내는데, Rust는 errno 없는 자기 에러를 만든다. 이것도 먼저 검사해서 `EINVAL`로 맞췄다.

이 모든 것이 Go의 우연을 따라 하는 코드라서 open-questions "과도기 잔가지"에 적었다. Go를 지운 뒤에는 "에러 문구를 무엇으로 할지"를 언어 규칙으로 따로 정한다.

## 3. 파일 핸들의 수명과 참조 계수

`fs.open(path, mode: 'write)`는 **파일 핸들**을 준다. 열린 파일(운영체제의 파일 디스크립터 하나)을 품은 값이다. `write_line`으로 쓰고 `close`로 닫는다.
디스크립터는 한 프로세스가 동시에 열 수 있는 수가 정해져 있으므로(`ulimit -n`), 닫지 않은 핸들이 쌓이면 언젠가 `too many open files`가 난다.

**닫지 않고 버린 핸들은 언제 닫히나?** 여기서 두 구현의 메모리 모델 차이가 드러난다.
- Go는 가비지 컬렉터(GC)가 "이제 아무도 이 값을 가리키지 않는다"를 **나중에, 주기적으로** 알아낸다. 그때 파일의 finalizer(GC가 값을 거둘 때 부르는 함수)가 디스크립터를 닫는다.
  GC가 돌기 전까지는 열려 있다.
- Rust는 참조 계수(`Rc`: 값을 가리키는 곳의 수를 세다가 0이 되면 해제)다. 핸들의 **마지막 사본이 사라지는 순간** `Drop`(Rust에서 값이 사라질 때 자동으로 도는 정리 코드)이
  돌고, 안에 든 `std::fs::File`의 `Drop`이 `close(2)`를 부른다.

그래서 Rust 쪽은 핸들 수천 개를 열고 버려도 디스크립터가 새지 않는다. 테스트(`dropped_handles_free_their_descriptors`)가 5,000개씩 열고 버린 뒤에도 열기가 되는지 본다(7절 (4)).

정확해서 생기는 선택도 있었다. **버리는 핸들의 쓰기 버퍼를 비울까?** 핸들은 쓴 줄을 4 KiB 버퍼에 모았다가 한 번에 파일에 쓴다(4절). 버릴 때 비우면 친절하지만,
Go의 finalizer는 디스크립터만 닫고 버퍼는 비우지 않는다. 이식 중에는 Go와 같게 두기로 했다(Task 4 판단). 그래서 `close` 없이 버린 핸들에 쓴 마지막 4 KiB 미만은 사라진다.
`with_open`을 쓰면 반드시 `close`하므로 해당 없다. Go를 지운 뒤 언어 규칙으로 다시 정한다(open-questions "4a단계(fs)에서 알고 남긴 차이").

**실행권 규칙과 `Drop`.** Rust 런타임에서 fung 값(`Rc`를 품은 것)은 실행권(한 번에 한 태스크만 쥐는 잠금, R3a)을 쥔 스레드만 만지고 해제한다.
`Rc`의 계수는 원자적이지 않아서, 두 스레드가 동시에 바꾸면 계수가 틀어지기 때문이다. 핸들 자체(`File`)는 경로 문자열과 `Mutex`로 감싼 표준 파일뿐이고 fung 값을 품지 않는다.
그래서 실행권 밖에서 핸들을 쓸 때는 `Rc<File>`이 아니라 그 안의 `&File`(빌린 참조)만 넘긴다. 계수는 실행권 안에서만 움직인다.

## 4. 실행권 밖의 입출력과 핸들 잠금

큰 파일을 읽는 동안 다른 태스크가 멈추면 안 된다. 그래서 모든 파일 입출력은 `outside`(R3a: 실행권을 내려놓고 일을 한 뒤 다시 잡는 도우미) 안에서 한다.
규칙은 하나다. `outside`에 넘기는 클로저에는 fung 값을 넣지 않는다. 경로는 `String`으로, 읽은 내용은 `Vec<u8>`로 꺼내고, fung 값은 실행권을 되찾은 뒤에 만든다.

실행권이 보호하지 않으니 **핸들에는 자기 잠금이 따로 있다**(`File { path, state: Mutex<Option<Io>> }`, `None`이면 닫힘). Go의 핸들 뮤텍스와 같다.
`write_line` 하나, 한 줄 읽기 하나, `close` 하나가 각자 잠금을 처음부터 끝까지 쥔다. 그래서 여러 태스크가 한 핸들에 동시에 줄을 써도 줄이 섞이지 않는다.
테스트(`concurrent_write_lines_stay_whole`)는 태스크 8개가 약 320바이트짜리 줄을 200개씩 써서 1,600줄이 모두 온전한지 본다.
`write_line`을 잠금 두 번으로 쪼개면 이 테스트가 실패하는 것도 확인했다(테스트가 정말 무언가를 잡는지 보는 것을 "이빨이 있다"고 한다).

**쓰기 버퍼는 Go의 `bufio`를 그대로 흉내 낸다(`GoWriter`).** 버퍼링은 작은 쓰기를 모아 시스템 호출 수를 줄이는 기법이다. 문제는 "언제 파일에 실제로 쓰이나"가
구현마다 다르다는 것이다. `close` 전에 같은 파일을 `fs.read`로 읽는 프로그램은 그 시점까지 파일에 닿은 바이트만 본다. 그래서 그 시점이 출력이 된다.
- Go `bufio.Writer`(4096바이트): 들어온 글이 남은 칸보다 크면, 버퍼가 비어 있을 때는 파일에 바로 쓰고, 아니면 **버퍼를 꽉 채운 뒤** 비우고 나머지를 이어 간다. 첫 쓰기 에러는 계속 남는다.
- Rust 표준 `BufWriter`는 같은 경우 버퍼에 든 것만 먼저 비우고 새 글을 따로 다룬다. 같은 줄들을 써도 파일에 닿는 바이트 수가 순간순간 다르다.

그래서 `GoWriter`는 Go의 `WriteString`·`Flush`를 단계 그대로 옮겼다. 4094·1·5000·9000·10000바이트 줄을 쓰고 매번 파일 크기를 재는 프로그램과 덧붙이기 모드로 Go와 대조했다.
이것도 과도기 잔가지다. 버퍼 크기와 비우는 시점은 Go를 지운 뒤 정한다.

핸들의 표시 `<file "...">`는 fung 문자열 표기가 아니라 Go `strconv.Quote` 형식이다(제어 문자가 `\x01`, ` `처럼 보임). 1단계 앞단에 이미 같은 함수가 있어서(`fung_front::diag::quote`) 그것을 쓴다.

## 5. `glob`과 경로 규칙을 직접 구현한 이유

Rust 표준 라이브러리에도 `std::path::Path`가 있다. 그런데 **규칙이 Go `filepath`와 다르다.**
- Go `filepath.Ext(".hidden")`은 `.hidden`, Rust `Path::extension`은 없음(`None`, 점으로 시작하는 이름은 확장자가 아니라고 본다).
- Go `filepath.Clean("a//b/../c/")`는 `a/c`. Rust의 `components()`는 겹친 `/`와 `.`은 정리하지만 `..`는 지우지 않는다(심볼릭 링크가 있으면 `..`의 뜻이 바뀌기 때문에 일부러 그렇다).
- `glob`은 Rust 표준에 아예 없다. 크레이트를 쓰지 않는 원칙이라 직접 짜야 했다.

그래서 Go의 `Clean`·`Join`·`Base`·`Dir`·`Ext`, `Match`·`Glob`, `WalkDir`을 바이트 단위로 옮겼다. 경로를 `String`이 아니라 바이트(`&[u8]`)로 다룬 이유는
파일 이름이 UTF-8이 아닐 수 있기 때문이다(Linux에서는 아무 바이트나 된다). 출력할 때만 fung 문자열로 바꾼다(잘못된 바이트는 U+FFFD).

Go `Match`에는 언어 규칙이라기보다 **구현의 우연**인 동작이 여럿 있고, 이것도 그대로 따라 했다.
- 잘못된 패턴은 매칭이 그 조각에 닿을 때만 드러난다. `a*[`는 `a`로 시작하는 이름이 있어야 에러이고, 없으면 그냥 빈 결과다.
- `[!a]`의 `!`는 부정이 아니라 글자 `!`다(부정은 `^`).
- 읽지 못하는 디렉터리는 조용히 건너뛴다. 디렉터리 부분의 재귀 한도는 10,000.

순서도 맞췄다. `std::fs::read_dir`는 운영체제가 주는 순서(정렬 안 됨)로 돌려준다. Go `os.ReadDir`는 이름의 **바이트 순서**로 정렬한다.
그래서 `10.txt`가 `9.txt`보다, `B.md`가 `a b.txt`보다 앞이다(사람의 사전순이 아님). `glob`은 디렉터리마다 정렬한 결과를 마지막에 한 번 더 통째로 정렬하므로
디렉터리별 순서와 다를 수 있다(`a.b/x`가 `a/x`보다 앞). `walk`는 깊이 우선이고, 읽지 못하는 첫 디렉터리에서 끝나며 에러에는 그 디렉터리가 아니라 **시작 경로**가 찍힌다. 모두 Go 그대로다.

검증은 Go의 `matchTests` 표(55건)를 그대로 옮기고, 무작위 패턴·이름 30만 쌍을 Go와 비교하고, 숨김 파일·빈 디렉터리·링크·잠긴 디렉터리가 섞인 트리에서 Go 바이너리와 대조했다.

## 6. 3b 누수 수정: 부모가 둘인 취소 노드

3b에서 에이전트의 `f`는 **부모가 둘인 취소 노드** 아래에서 돈다. 에이전트 태스크 아래(주 부모)와, 부탁한 태스크 아래(연결 부모, `also_under`)에 함께 걸려
어느 쪽이 취소돼도 `f`가 멈춘다(R3b 9절 (7)). 이 노드는 "`f`가 끝나고 `f`가 띄운 태스크도 다 끝나면 스스로 끝난다"(`end_when_empty`)는 표시를 단다.

3b 리뷰가 찾은 누수는 이렇다. `swap(a, x => x + swap(b, fn(y): spawn(() => 1); y + 1 ;;))`처럼 겹친 `swap`에서
- 바깥 `f`(a의 것)는 노드 Ra 아래에서 돈다. 그 안의 `swap(b, …)`가 만든 노드 Rb는 b의 태스크 아래(주 부모)와 **Ra 아래(연결 부모)** 에 걸린다.
- 안쪽 `f`(b의 것)가 띄운 태스크 때문에 Rb는 안쪽 `f`가 돌아온 뒤에도 잠깐 살아 있다. 그사이 바깥 `f`가 끝나면 Ra는 "자식이 다 떠나면 끝남" 상태로 기다린다. 남은 자식은 Rb뿐이다.
- Rb가 끝나며 부모 목록에서 빠질 때, **주 부모** 쪽은 "마지막 자식이 떠났으니 끝나라"를 검사했지만 **연결 부모** 쪽은 목록에서 빼기만 했다.
- 그래서 Ra는 영영 끝나지 않고 a의 노드 아래에 남았다. 반복할 때마다 쌓였다(몇 개가 남는지는 시점에 달렸다).

고친 것은 한 줄짜리 대칭이다. `CancelNode::leave`가 연결 부모에도 주 부모와 같은 검사(`remove(..).is_some() && end_when_empty && children.is_empty()`)를 하고,
잠금을 놓은 뒤 `cancel()`을 부른다. 노드 잠금은 한 번에 하나만 쥔다(둘을 쥐면 순서에 따라 교착이 생길 수 있다).
테스트는 둘이다. 노드 셋으로 만든 결정적인 단위 테스트, 그리고 위 프로그램을 2,000번 돌린 뒤 뿌리 아래 노드 수가 50개 미만인지 세는 테스트(`descendant_count` 탐침).
고치기 전에는 82개가 남았다.

교훈: 3b에서 "부모가 둘"이라는 예외를 하나 들였더니, 부모를 다루는 모든 곳에 대칭이 필요해졌다. 배경 문서의 원칙 7(예외 조항 최소화)이 코드에서도 그대로다.

## 7. 실제로 부딪힌 함정

진행 기록(`.superpowers/sdd/2026-10-15-rust-fs-4a/progress.md`)과 작업 보고서에 적힌 것만 적는다.

**(1) Rust `io::Error`의 문구가 새어 나올 뻔했다.**
- `io::Error`를 `to_string()`하면 `No such file or directory (os error 2)`다. 손쉬운 길이라 그대로 쓰면 메시지가 Go와 달라진다(스펙의 리뷰 1순위였다).
- 해결: errno 번호만 꺼내 Go 표로 바꾼다(2절). 그리고 표를 손으로 믿지 않고 테스트가 매번 `go run`으로 Go에게 직접 묻는다.
  번호가 없는 `io::Error`(표준 라이브러리가 스스로 만든 것)가 나오는 길은 NUL 경로였고, 먼저 `EINVAL`로 바꿔 막았다.
- 남은 차이: Go `RemoveAll`은 깊은 곳의 여러 실패 중 자기 순서대로 첫 errno를 보고한다. Rust는 디렉터리 안쪽을 `std::fs::remove_dir_all`에 맡겨서, 아래쪽에 권한 에러가 여럿 섞이면
  첫 errno가 다를 수 있다. `close(2)`의 에러도 보고하지 않는다(표준 `File`의 `Drop`이 버린다). 둘 다 open-questions에 적었다.

**(2) 표준 `BufWriter`로는 파일에 닿는 시점이 달랐다.**
- 4절. 줄을 몇 개 쓰고 `close` 전에 파일 크기를 보는 프로그램에서, 같은 바이트를 써도 그 순간의 크기가 Go와 다를 수 있다.
- 해결: `GoWriter`로 Go `bufio`의 단계를 옮기고, 줄 크기별로 Go와 크기를 대조했다. 기록하는 가짜 writer로 비우는 시점과 남는 에러도 단위 테스트한다.

**(3) FIFO 테스트가 8번에 1번 실패했다: `'write`는 읽기·쓰기로 연다.**
- "입출력이 실행권 밖에서 돈다"를 시간 없이 확인하려고 FIFO(이름 있는 파이프, `mkfifo`)를 썼다. FIFO는 한쪽을 열면 **반대쪽이 열릴 때까지** 열기가 막힌다.
  두 태스크가 양 끝을 열어 서로를 기다리므로, 막힌 입출력이 실행권을 쥐고 있었다면 영영 끝나지 않는다.
- 그런데 쓰는 쪽을 `'write`로 열었더니 가끔 데이터가 사라졌다. `'write`는 Go `os.Create`를 따라 `O_RDWR`(읽기·쓰기)로 연다.
  FIFO를 읽기·쓰기로 열면 자기 자신이 읽는 쪽도 되므로 **기다리지 않고** 열린다. 그러면 읽는 쪽이 열기 전에 쓰고 닫아서 데이터가 사라질 수 있다. Go도 똑같이 경쟁한다.
- 해결: 쓰는 쪽을 `'append`(쓰기 전용, `O_WRONLY`)로 열었다. 병렬 8번 실행이 모두 통과한다.
- 교훈: 테스트를 시간이 아니라 상태로 맞추려 해도, 그 "상태"가 운영체제의 정확한 동작(열기 모드)에 기대고 있으면 거기서 경쟁이 난다.

**(4) 디스크립터 누수 테스트는 `ulimit -n 128`이 필요했다.**
- "핸들 5,000개를 열고 버려도 새지 않는다"를 보려 했는데, 이 세션의 디스크립터 한도가 약 100만(1,048,576)이었다. 5,000개가 다 새도 한도에 닿지 않아 테스트가 아무것도 잡지 못한다.
- 해결: 테스트가 자기 실행 파일을 `sh -c 'ulimit -n 128; …'`로 다시 띄운다. 자식은 먼저 핸들 5,000개를 **붙잡아** `too many open files`가 나는 것을 확인하고(한도가 정말 걸렸다는 증거),
  그다음 5,000개씩 열고 버린 뒤 열기가 되는지 본다. 열 때마다 `Rc` 하나를 일부러 새게 하면 실패하는 것도 확인했다.
- 교훈: 자원 누수 테스트는 **한도를 테스트가 직접 낮춰야** 한다. 기계마다 한도가 다르면 같은 테스트가 어떤 기계에서는 아무것도 지키지 않는다.

**(5) 부모가 둘인 취소 노드가 남았다.** 6절. 연결 부모 쪽에서 "끝나라" 검사를 빠뜨려 겹친 `swap`마다 노드가 쌓였다.

### 알고 남긴 동작

모두 open-questions "Rust 이전"의 "4a단계(fs)에서 알고 남긴 차이"에 적었다.
- 닫지 않은 핸들은 마지막 사본이 사라질 때 닫히지만 버퍼(마지막 4 KiB 미만)는 비우지 않는다(Go와 같음, 3절).
- 마지막 사본이 사라질 때의 `close(2)`는 실행권을 쥔 채 돈다. 로컬 파일은 순식간이지만 NFS 같은 네트워크 파일 시스템에서는 그동안 다른 태스크가 멈출 수 있다.
  고친다면 닫을 파일을 배경 스레드(닫기 전용)에 넘기는 방법이 있다.
- `close(2)`의 에러를 보고하지 않는다(핸들, `write`·`append`·`copy`). `remove_all`은 첫 errno만, 그것도 깊은 실패에서는 Go와 다를 수 있다.
- 잘못된 UTF-8 경로: Go는 핸들 표시에 `\xff`로 보이고, Rust는 U+FFFD가 보인다(2단계의 U+FFFD 차이와 같은 뿌리).
