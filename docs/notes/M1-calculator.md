# M1. 계산기 — 무엇을 만들었고 왜 그렇게 했나

M1의 목표는 `fung -e 'print(1 + 2 * 3)'`이 `7`을 출력하는 것이다. 숫자와 연산자뿐이지만,
렉서 → 파서 → 균일 트리 → desugar → resolve → 컴파일러 → VM이라는 **전체 배관이 처음으로 한 줄로 이어진다.**
M2부터는 이 배관에 기능을 하나씩 얹는다.

## 1. 파이프라인 한눈에

`print(1 + 2 * 3)` 한 줄이 각 단계에서 어떤 모양이 되는지. 모두 `fung dump`로 직접 볼 수 있다.

**토큰** (렉서): `Name(print) ( Int(1) + Int(2) * Int(3) ) EOF`. 각 토큰은 파일·줄·칸 위치를 가진다.

**겉 문법 트리** (`fung dump ast`):
```
(program (call print (binary + 1 (binary * 2 3))))
```
`*`가 `+`보다 안쪽에 있다. 우선순위가 트리 모양으로 굳었다.

**코어 트리** (`fung dump core`, desugar와 resolve를 거친 뒤):
```
(do (call (prelude print) (op + 1 (op * 2 3))))
```
`program`이 `do`로, `binary`가 `op`로, 이름 `print`가 "prelude의 print"로 바뀌었다. 컴파일러는 이 형태만 안다.

**바이트코드** (`fung dump bytecode`):
```
== <main> ==
0000  1:1   CONST        0    ; <fn print>
0001  1:7   CONST        1    ; 1
0002  1:11  CONST        2    ; 2
0003  1:15  CONST        3    ; 3
0004  1:13  MUL
0005  1:9   ADD
0006  1:6   CALL         1
0007  1:1   RETURN
```
둘째 칸이 각 명령의 소스 위치(줄:칸)다. `MUL`은 `*`가 있던 1:13을 가리킨다. 이것이 08의 "모든 명령은 소스 위치를 가진다"의 실체이며, 아래 에러 메시지가 정확한 위치를 찍는 비결이다.

**실행** (VM): 스택에 `print`, 1, 2, 3을 쌓고, `MUL`이 2와 3을 꺼내 6을 넣고, `ADD`가 1과 6을 꺼내 7을 넣고, `CALL 1`이 함수와 인자 하나를 꺼내 `print`를 부른다. 출력 `7`.

## 2. 렉서 — 글자를 토큰으로

렉서(`internal/lexer`)는 01의 글자 수준 규칙을 **전부** 구현했다. M2·M4에서 문자열과 기간을 쓸 때 렉서를 다시 열지 않기 위해서다. 설계하면서 부딪힌 문제 셋:

**가장 긴 매칭.** `;;`는 `;` 둘이 아니라 토큰 하나이고, `..=`는 `..` + `=`가 아니다. 렉서는 세 글자 표(`..=` `...`), 두 글자 표(`==` `;;` `|>` …), 한 글자 표 순서로 시도한다(`punct3/2/1`). 그래서 `;;;`는 `;;` + `;`가 된다. 01에 적은 "렉서가 항상 가장 길게 자른다"가 코드로는 이 순서다.

**숫자 바로 뒤의 글자.** `30s`는 기간, `30abc`는 오류, `30 s`는 숫자와 이름이다. 숫자를 읽은 직후 글자가 붙어 있으면 기간으로 해석을 시도하고, 첫 단위가 `ms` `s` `m` `h`가 아니면 "잘못된 숫자"(E0102)다. `1h30m`처럼 복합 기간은 단위가 **내림차순**이어야 한다(`30m1h`는 E0105). 지수가 있는 숫자(`1e5s`)에는 단위를 붙일 수 없다.

**문자열 보간 안의 따옴표.** `"${m["k"]}"`에서 안쪽 `"`가 바깥 문자열을 끝내면 안 된다. 렉서는 `${`를 만나면 중괄호 깊이를 세면서 코드 부분을 건너뛰고, 그 안에서 `"`를 만나면 중첩 문자열 하나를 통째로 건너뛴다(`skipInterpolation`과 `skipQuoted`가 서로 부른다). 코드 부분은 파싱하지 않고 **글자 그대로 + 위치**만 보관한다. M2에서 파서가 그 조각을 다시 파싱한다.

그 밖의 결정:
- 주석은 토큰 흐름에서 빼되 위치와 함께 **별도 목록(trivia)**에 둔다. 포맷터(알파 이후)가 원래 자리에 되돌려 놓기 위해서다.
- 줄바꿈은 `Newline` 토큰으로 내보낸다. 어느 줄바꿈이 문장 끝인지는 **파서가** 문맥으로 정한다(01). `\r\n`은 `\r` 자리의 줄바꿈 토큰 하나다.
- 열(칸) 번호는 바이트가 아니라 **글자(룬)** 단위다. `참치 x`에서 `x`는 4번째 칸이다.
- 식별자의 첫 글자가 유니코드 대문자면 태그, 아니면 이름. 한글은 대소문자가 없으므로 항상 이름이다.

## 3. Pratt 파서 — 우선순위를 숫자 하나로

파서(`internal/parser`)의 식 부분은 **Pratt 파서**다. 연산자마다 "결합력(binding power)" 숫자를 주고, 왼쪽 피연산자를 읽은 뒤 "다음 연산자가 내 최소 결합력 이상이면 계속 먹는다"는 루프 하나로 모든 이항·단항·후위 연산을 처리한다. 07의 우선순위 표를 10배 해서 썼다(`then` 10, `or` 20, …, `**` 120, 호출 130).

- `1 + 2 * 3`: `+`(90)를 읽은 뒤 오른쪽을 "91 이상만"으로 파싱한다. `*`(100)가 91 이상이라 `2 * 3`이 먼저 묶인다.
- `1 - 2 - 3`: 오른쪽을 91 이상으로 파싱하면 두 번째 `-`(90)는 못 들어오므로 `(1 - 2) - 3`. 왼쪽 결합은 "오른쪽 결합력 = 왼쪽 + 1"로 나온다.
- `2 ** 3 ** 2`: `**`는 오른쪽 결합력을 왼쪽과 **같게**(120) 두어 `2 ** (3 ** 2)`.
- `-2 ** 2`: 단항 `-`는 피연산자를 110 이상으로 파싱한다. `**`(120)가 들어와 `-(2 ** 2) = -4`. 07의 결정 그대로.

비교 연쇄 금지는 변수 하나로 잡았다. 방금 묶은 연산자가 비교였는데 다음도 비교면 E0111. `a < b < c`는 "`and`로 나누세요" 힌트와 함께 거절된다.

줄 이어짐은 두 군데서 처리한다. 연산자를 먹은 직후에는 줄바꿈을 건너뛴다(줄 끝 연산자). 다음 연산자를 엿볼 때 줄바꿈 뒤에 `and` `or` `|>` 같은 이어짐 전용 토큰이 오면 그 줄바꿈을 건너뛴다(줄 앞 연산자). 괄호 안에서는 `peek`이 아예 줄바꿈을 보지 않는다. 호출 괄호 `(`는 같은 줄에서만 후위로 인정하므로 `f\n(1)`은 문장 둘이다.

## 4. 균일 트리와 desugar — "속은 Lisp"

트리 노드(`internal/tree`)는 종류가 하나뿐이다: `{머리, 위치, 리터럴, 자식들}`. 노드 종류마다 Go 구조체를 만들지 않았다. 얻는 것은 `dump`가 한 함수로 끝나고, desugar가 "트리를 받아 같은 형태의 트리를 돌려주는" 단순한 변환이 된다는 점이다. 잃는 것은 Go 컴파일러가 "`if` 노드는 자식이 셋"을 검사해 주지 않는다는 점인데, 그 검사는 desugar가 맡는다.

desugar(`internal/desugar`)는 겉 문법을 09의 코어 언어로 줄인다. M1에서 실제로 하는 일은 하나뿐이지만 중요하다. `a and b`는 코어에 없고 `if`로 풀린다:
```
a and b   →  (if a (op bool b) false)
a or b    →  (if a true (op bool b))
```
`if`가 조건에 따라 한쪽만 실행하므로 **단락 평가가 공짜**로 나온다. `false and (1 / 0 == 1)`이 에러 없이 `false`인 이유다. `(op bool b)`는 "b가 bool이 아니면 에러"라는 검사다. 07의 "조건 자리에는 true/false만"을 지키려면 `if`의 조건(`a`)은 VM의 점프 명령이 검사하지만, 실행된 쪽의 값(`b`)은 따로 검사해야 하기 때문이다. `true and 1`은 그래서 E0505다.

## 5. resolve — 실행 중에 이름을 찾지 않는다

resolve(`internal/resolve`)는 코어 트리를 한 번 훑어 모든 이름을 "어디서 온 것"으로 바꾼다. M1에서는 prelude(`print`)뿐이라 `name` 잎이 `(prelude print)`로 바뀌거나 E0204가 된다. 핵심은 **에러를 하나 찾아도 멈추지 않고 끝까지 모은다**는 것(08의 "의미 에러는 모두")과, 컴파일러와 VM은 이름 문자열을 다시 들여다보지 않는다는 것이다. M2에서 지역 변수의 **슬롯 번호**가 바로 이 단계에서 정해진다.

## 6. 값과 산술 — 조용히 넘어가지 않기

값(`internal/value`)은 Go 인터페이스 `Value` 하나와 `Int(int64)`, `Float`, `Bool`, `Nil{}`, `*Native`다. fung의 `nil`(`Nil{}`)과 Go의 nil 인터페이스를 구분한 것이 중요하다. Go의 nil은 "슬롯이 아직 비었다"는 뜻으로 남겨 두어, M2의 "정의 전 사용" 검사와 M3의 기본값 처리가 공짜가 된다.

02·07의 엄격함은 산술 함수마다 검사로 들어갔다:
- **정수 오버플로**: 덧셈은 "양수를 더했는데 작아졌는가"로, 곱셈은 "결과를 다시 나누면 원래 값인가"로 잡는다. `9223372036854775807 + 1`은 E0503.
- **내림 나눗셈과 나머지의 짝**: Go의 `/`는 0 쪽으로 자르므로 부호가 다르면 1을 뺀다. `-7 // 2 == -4`, `-7 % 2 == 1`이고, 실수에도 같은 규칙(`-7.5 % 2 == 0.5`).
- **`Inf`·`NaN` 추방**: 실수 결과를 만들 때마다 `finite`가 검사한다. `1e308 * 10`은 E0504, `1 / 0`은 E0502. `NaN`이 있으면 `x == x`가 거짓이 되어 02의 비교 표가 깨진다.
- **`**`**: 정수^음이 아닌 정수는 제곱 반복(exponentiation by squaring)으로 정수를 유지하며 매 곱셈에서 오버플로를 검사한다. 지수가 음수거나 실수가 섞이면 실수.

출력 형식은 08의 "리터럴 형태" 원칙을 따른다. `5.0`은 `5.0`으로 나와야 다시 읽었을 때 실수다. Go의 기본 `%g`는 `1000000.0`을 `1e+06`으로 바꾸므로 쓰지 않고, JavaScript처럼 지수가 21 이상이거나 -4 미만일 때만 지수 표기(`1e21`, `1e-07`)를 쓴다. `0.1 + 0.2`는 `0.30000000000000004`로, 가장 짧은 왕복 표현을 그대로 보여 준다.

(테스트에서 배운 것 하나: Go에서 `Float(0.1 + 0.2)`는 상수 계산이라 정확히 0.3이 된다. 실행 시점 계산을 테스트하려면 변수에 담아야 했다.)

## 7. 바이트코드와 VM — 스택 머신

명령(`internal/bytecode`)은 32비트 한 단어다: 위 8비트가 명령, 아래 24비트가 피연산자. 디코딩이 비트 연산 둘이고 점프 대상이 명령 번호 그대로라 역어셈블러가 단순하다. `Proto`는 코드, 상수 풀, 그리고 **명령마다 하나씩의 위치**를 가진다. 같은 상수는 풀에서 재사용한다(`1`이 두 번 나와도 한 칸).

VM(`internal/vm`)은 스택 머신이다. `1 + 2 * 3`의 스택:

| 명령 | 실행 후 스택 |
|------|------|
| CONST 1 | `[1]` |
| CONST 2 | `[1 2]` |
| CONST 3 | `[1 2 3]` |
| MUL | `[1 6]` |
| ADD | `[7]` |

`if`는 점프 둘로 컴파일된다. 조건을 평가하고 `JUMPIFFALSE`로 else로 뛰고, then 끝에서 `JUMP`로 끝으로 뛴다. 컴파일할 때는 뛸 곳을 아직 모르므로 0으로 두었다가 나중에 `Patch`로 채운다. `true and false`의 바이트코드를 `dump bytecode`로 보면 `JUMPIFFALSE 5`와 `JUMP 6`이 보인다.

에러 위치는 이렇게 나온다. `value.Div`는 자기가 어디서 불렸는지 모르므로 위치 없는 에러를 돌려주고, VM이 방금 실행한 명령의 위치(`proto.Pos[ip]`)를 `WithPos`로 채운다. 그래서 두 줄짜리 `print(1 +\n 2 / 0)`의 에러가 `2:4`, 즉 둘째 줄의 `/`를 정확히 가리킨다.

Go 패닉 울타리: `Run`은 `recover`로 모든 Go 패닉을 잡아 E0801 "internal error"로 바꾼다. 원칙 00 "Go 스택 추적은 사용자에게 보이지 않는다"의 구현이다. 테스트에서 일부러 패닉하는 네이티브 함수를 불러 확인했다.

M7을 위한 준비도 들어 있다. 스택과 프레임은 `Task` 구조체 안에 있고 전역 변수가 없다. 태스크를 하나 더 만들면 VM이 하나 더 생긴다. 네이티브 함수는 `value.Context` 인터페이스(지금은 `Stdout()`뿐)로 VM과 대화하므로 `native` 패키지가 `vm`을 import하지 않는다(순환 import 방지).

## 8. 종료 코드와 테스트

`cmd/fung`의 `execute`가 단계를 잇는다. 렉서·파서·resolve 에러는 **컴파일 에러**로 종료 코드 2, VM 에러는 1. `print(1)\nprint(1 / 0)`은 `1`을 출력한 뒤 에러를 내고 1로 끝난다.

골든 파일 13개(`tests/lang/`): 산술, 비교·논리, 리터럴, 줄 이어짐 4개와 에러 번호별 9개. 각 에러 파일은 에러 하나만 담아 "그 번호가 정확히 그 상황에서 나는가"를 고정한다. 에러 번호는 이제 계약이다. 바꾸면 골든 테스트가 깨진다.

M1에서 할당한 번호: E0101~E0105 (렉서), E0110·E0111 (파서), E0204 (미정의 이름), E0401 (호출 불가), E0501~E0506 (연산), E0801 (내부 에러), E0802 (식 중첩 깊이 초과). 전부 08의 분류 안에 있다.

검토에서 잡힌 것들: 소스 안의 NUL 글자가 파일 끝으로 읽혀 뒤를 조용히 버리던 문제(EOF 표지를 룬 범위 밖 값으로), 앞머리 BOM 거부, 기간 리터럴의 실수 곱셈 오차와 오버플로(`4.35h`가 1ns 모자라던 것, `9999999999h`가 플랫폼마다 다른 값이 되던 것), 컴파일러가 모르는 연산자를 `CONST 0`으로 조용히 내보내던 것, 괄호 2만 겹에서 Go 스택 추적이 새던 것(파서 깊이 한도 10,000 → E0802).

## 다음: M2 변수와 흐름

대입(`x = 1`)이 들어오면 resolve가 **슬롯 번호**를 정하고 VM에 `LOAD_SLOT`/`STORE_SLOT`이 생긴다. 블록(`if … ;;`)과 블록 스코프, `then … else`, 문자열과 보간(렉서가 보관해 둔 코드 조각을 파서가 다시 파싱), 심볼, 기간이 값으로 들어온다. 그리고 에러 출력에 소스 발췌(`12 |   for f in fiels:` 줄과 `^^^^^` 표시)가 붙는다.
