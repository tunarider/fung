# L4. 문자열과 바이트

0.5.0 큰 문제 L4(`docs/plans/0.5.0/04-strings-and-bytes.md`)를 고치며 배운 것. 질문은 하나였다:
**바깥에서 들어온 바이트가 UTF-8이 아니면 문자열은 무엇을 담는가.**

## 1. 무엇이 문제였나

fung 문자열은 Rust의 `String`, 곧 "언제나 유효한 UTF-8"이었다. 그래서 바깥에서 들어오는 바이트(파일 내용, 명령 출력, 환경 변수, 인자, 표준 입력, 소켓, 파일 이름)를
문자열로 만들 때마다 풀어야 했고, 잘못된 부분은 U+FFFD(`�`) 하나로 바꿨다. 원래 바이트는 사라졌다. 그래서 fung으로 파일을 읽어 그대로 쓰기만 해도 파일이 달라졌다
(`a\xffb` 3바이트 → `a\xef\xbf\xbdb` 5바이트). 에러도 경고도 없었으니 원칙 1(조용히 넘어가는 동작은 에러로)에 어긋났다.

## 2. 세 가지 길

언어들은 이 문제를 셋 중 하나로 푼다.

| 길 | 언어 | 문자열이 담는 것 | 대가 |
|---|---|---|---|
| 글과 바이트를 타입으로 나눔 | Python 3(`str`·`bytes`), Rust(`String`·`Vec<u8>`) | 글은 늘 유효 | 바깥을 읽는 함수가 두 벌. 파일 이름·환경 변수는 세 번째 타입(`OsString`)이나 꼼수(PEP 383 surrogateescape)가 필요 |
| 문자열 = 바이트, 글자 연산이 UTF-8로 읽음 | Go, Lua, Perl | 아무 바이트 | 글자 연산이 잘못된 바이트를 어떻게 셀지 정해야 함 |
| 유효한 UTF-8을 지키고 잘못된 바이트를 다른 글자로 옮겨 둠 | Python의 surrogateescape | 겉보기에 유효 | 내보낼 때 늦게 터진다(`surrogates not allowed`). Rust `String`은 홀로 선 서로게이트를 못 담아 자체 표현이 필요 |

fung은 **둘째 길(Go 방식)**을 골랐다. 쉘을 대신하는 언어라 명령 출력·파일·파일 이름을 그대로 넘기는 일이 핵심이고, 값 종류와 API를 늘리지 않으며(원칙 6), 규칙이 하나다:
**문자열은 바이트이고, 글자 연산은 그것을 UTF-8로 읽는다.**

## 3. 잘못된 바이트는 몇 글자인가

UTF-8은 첫 바이트가 길이를 알려 준다(`0xxxxxxx` 1바이트, `110xxxxx` 2바이트, `1110xxxx` 3바이트, `11110xxx` 4바이트, 뒤따르는 바이트는 `10xxxxxx`).
잘못된 곳은 여러 모양이다: 뒤가 모자라는 시작 바이트(`\xe2\x82` 다음에 `c`), 홀로 선 뒤따름 바이트(`\x80`), 같은 글자를 더 길게 쓴 것(overlong, `\xc0\x80`),
서로게이트 영역(`\xed\xa0\x80`), U+10FFFF를 넘는 것.

규칙: **어떤 자리에서 유효한 글자가 시작하면 그 글자, 아니면 그 바이트 하나가 한 글자**다. Go의 `utf8.DecodeRune`이 이렇게 한다.
그러면 `"a\xffb\xe2\x82c"`는 `a`, `\xff`, `b`, `\xe2`, `\x82`, `c`의 여섯 글자다. 좋은 점은 **자르고 다시 이어도 바이트가 보존된다**는 것이다.
"잘못된 부분마다 U+FFFD 하나"(유니코드 권고, 전의 `from_utf8_lossy`)로 세면 `\xe2\x82`가 한 글자라 바이트 수와 글자의 관계가 흐려진다.

세기는 빠르게 할 수 있다: Rust 표준 라이브러리의 `<[u8]>::utf8_chunks()`가 "유효한 조각 + 잘못된 조각"을 번갈아 주는데, 잘못된 조각 안에서는 뒤따름 바이트만 나오므로
(유효한 글자는 뒤따름 바이트에서 시작할 수 없다) 잘못된 조각의 바이트 수가 곧 글자 수다(`fung_front::text::char_count`).

## 4. 표현: 만들 때 한 번 잰다

값은 `Value::Str(Rc<Text>)`이고 `Text`는 유효한 UTF-8이면 `String`, 아니면 `Vec<u8>`을 들고, ASCII인지를 함께 기억한다(`value/text.rs`).
문자열을 만들 때 한 번 재 두면 `len`과 `s[i]`의 ASCII 빠른 길, "글이 필요한 곳"의 검사가 모두 O(1)이다. `String`에서 만들면 재지도 않는다(이미 유효). 아래 9절의 이야기다.

비교·해시·맵 키는 바이트로 한다. UTF-8은 바이트 순서가 코드 포인트 순서와 같게 설계되었으므로(첫 바이트가 클수록 큰 글자) 유효한 글에서는 결과가 전과 같다.

## 5. 어디서 바이트를 그대로 두고, 어디서 멈추나

처음 계획은 "유니코드 뜻이 필요한 연산(`upper`·`lower` 등)은 잘못된 바이트에 에러"였다. 다시 보니 `upper`가 잘못된 바이트를 **그대로 두는 것은 조용히 바꾸는 것이 아니다**.
바이트는 글자가 아니니 바꿀 대소문자도 없고, 잃는 것도 없다. 반대로 에러로 하면 바이트 하나 깨진 로그 줄 때문에 스크립트가 멈춘다. 그래서 선을 이렇게 그었다:

- **그대로 둔다**: `+`, 비교, `split`, `replace`, `trim`, `upper`·`lower`(유효한 조각만 바꾸고 잘못된 바이트는 사이에 그대로), 정규식, `print`.
- **멈춘다(E0518)**: 출력 **형식 자체가 글을 요구하는** 곳. `json.stringify`(JSON 텍스트는 UTF-8), 정규식 패턴, 시간 형식, 호스트 이름·주소.
- **`Err`**: 바깥 값을 읽는 함수(`json.parse`, `parse_int`, `time.parse` …). 잘못된 바이트는 "읽을 수 없는 입력"이고, 이 함수들은 원래 그런 입력에 `Err`를 준다.

HTTP는 계획과 달리 멈추지 않는다. URL 경로의 바이트는 원래 퍼센트 인코딩(`%FF`)으로 보내는 것이 맞고, 헤더 값은 HTTP/1.1이 0x80 이상 바이트(obs-text)를 허용한다.

## 6. 보이기: 다시 읽히는 모양

`print`와 보간은 바이트를 그대로 쓴다(`cat`처럼). 값의 리터럴 모양(`str`이 아닌 표시: 리스트 안, REPL, `dbg`, 에러 메시지)은 터미널을 망치지 않도록
잘못된 바이트를 `\xff`로 쓴다. 그 모양이 **리터럴로 다시 읽혀야** 하므로 문자열 리터럴에 `\xHH`를 더했다. 여기서 한 가지를 정해야 했다:
Python·JavaScript의 `"\xe9"`는 글자 U+00E9(`é`)다. fung의 `\xHH`는 **바이트 하나**다(Go·Rust의 바이트 문자열과 같다). 그래야 `"\xff"`로 보인 값이 같은 바이트로 다시 읽힌다.
그 대가로 `"\xe9"`는 `é`가 아니다(`é`는 `"\u{e9}"` 또는 `"\xc3\xa9"`).

앞단에서는 리터럴의 값을 글자가 아니라 바이트로 모으고, UTF-8이 아니면 트리의 `Lit::Bytes`, 상수의 `Const::Bytes`로 나른다. 이름·연산자·모듈 경로처럼
글이어야 하는 리터럴은 그대로 `Lit::Str`이라 바뀐 곳이 적다.

## 7. 소스는 UTF-8

소스 파일의 잘못된 바이트도 전에는 U+FFFD가 되었다. 프로그램에 아무도 쓰지 않은 글자가 들어가는 셈이라, 이제 실행·검사·가져오기가 읽기를 거절한다
(``not valid UTF-8 at line 3, column 7``, 가져온 모듈은 E0312). 포매터는 원래 바이트를 그대로 되쓰도록 짜여 있어 그런 파일도 받는다.

## 8. 정규식: 바이트 위의 매칭과 빈 매치

정규식은 같은 크레이트의 `regex::bytes`로 옮겼다. 패턴을 먼저 검사하는 `regex_syntax`도 UTF-8 모드를 꺼야 한다(`ParserBuilder::utf8(false)`). 켜 두면
`(?-u:\xff)`처럼 UTF-8이 아닌 바이트에 맞을 수 있는 패턴을 `pattern can match invalid UTF-8`로 거절한다. 유니코드 모드에서는 `.`과 `\w` 같은 클래스가 **유효한 UTF-8에만** 맞는다. 잘못된 바이트는 `.`에도 맞지 않으므로
"바이트 하나 = 한 글자"의 예외다(`(?-u:\xff)`로 찾는다).

하나 걸린 것: 바이트 정규식은 **빈 매치를 UTF-8 글자 한가운데에서도** 찾는다. `replace("가나", "x*", "-")`가 `"-\xea-\xb0-\x80-…"`처럼 글자를 쪼갰다.
그래서 빈 매치는 글자 경계(바이트가 뒤따름 바이트가 아니거나, 앞의 글자에 속하지 않는 홀로 선 바이트)에서만 받는다(`native/regex.rs`의 `at_boundary`).

## 9. 성능

부분 열 찾기(`split`, `replace`, `in`)는 `&str`의 메서드를 못 쓰게 되어 `memchr::memmem`을 직접 들였다(이미 `regex`가 끌고 오던 크레이트).
`bench/compare/`의 13개 작업을 바꾸기 전 바이너리와 견주면 흔들림을 빼고 모두 ±5% 안이다(`docs/notes/bench-languages.md` 4.2절).

처음 판에서 배운 것 둘. 첫째, "유효한가"를 표시로만 기억하고 바이트를 `Vec<u8>`로 들면, 글이 필요할 때마다 `str::from_utf8`로 **다시 검사**해야 한다(검사하지 않는
`from_utf8_unchecked`는 `unsafe`다). 유효한 글은 아예 `String`으로 들고 있게(`enum Repr { Utf8(String), Bytes(Vec<u8>) }`) 바꾸자 검사가 사라지고, `str`의 빠른 길
(`chars().count()`, `char_indices`)을 그대로 쓴다. 긴 문자열 인덱스가 0.44초에서 0.037초가 되었다. 둘째, 정규식의 빈 매치를 거르려고 `is_match`를 `find_iter`로 바꾸면
느려진다(매치의 끝까지 찾아야 하므로). 패턴의 최소 길이가 0보다 크면 빈 매치가 없으니 거르지 않는다.

## 10. 남긴 것

글로만 다루는 세 자리는 아직 U+FFFD로 읽는다: REPL에 직접 친 줄, UTF-8이 아닌 디렉터리 아래의 모듈 경로(모듈 키와 위치가 글이다), 시간대 이름(`TZ`, 표준상 ASCII).
셋 다 값이 되는 바깥 데이터가 아니라 open-questions "알려진 한계"에 적었다.

## 11. 시험

골든 파일(`tests/lang/bytes.fung`)은 UTF-8 글이라 잘못된 바이트를 `\xHH`로만 쓴다. 프로세스 경계(인자·환경 변수·표준 입력·파일·명령 출력·바이트 그대로의 `print`, UTF-8이 아닌 소스)는
`crates/fung-cli/tests/bytes.rs`가 바이트로 넣고 바이트로 견준다. 비UTF-8 파일 이름은 macOS(APFS)가 만들지 못하므로(`Illegal byte sequence`) 그 시험은 Linux에서만 돈다
(Docker `rust:1.94-slim`에서 확인).
