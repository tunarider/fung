# L13. HTTP의 세부

0.5.0 큰 문제 L13(`docs/plans/0.5.0/13-http.md`)을 고치며 배운 것. HTTP는 "말이 되는 바이트를 보내는가"의 문제가 대부분이었다.

## 1. 틀(framing)은 서버의 일이다

HTTP/1.1에서 본문이 어디서 끝나는지는 머리의 `Content-Length`나 `Transfer-Encoding: chunked`가 정한다. 핸들러가 `Content-Length: 3`과 본문 `hello`(5바이트)를 주면,
클라이언트는 3바이트만 본문으로 읽고 나머지 `lo`를 **다음 응답의 시작**으로 읽는다. 연결을 다시 쓰는 서버라면 이것은 응답 밀반입(response smuggling)이다.
`Transfer-Encoding: chunked`와 `Content-Length`를 함께 보내는 것은 RFC 9112 6.1이 금지한다.

그래서 틀을 정하는 헤더는 서버만 쓴다. 핸들러가 넣으면 조용히 고치지 않고 **잘못된 답**(500 + 이유 한 줄)으로 한다. 정당한 쓰임 하나는 남겼다: 본문이 없는 답(`HEAD`·304)의
`Content-Length`는 "GET이었다면 이만큼"이라는 뜻이라 받는다. 대소문자만 다른 이름 둘(`X-A`, `x-a`)도 같은 이유로 거절한다. 맵 리터럴의 중복 키처럼 실수이고, 한쪽이 말없이 사라지기 때문이다.

## 2. 서버가 스스로 하는 답도 틀이 있어야 한다

400·431 같은 답에 `Content-Length`가 없으면 클라이언트는 연결이 닫혀야 끝을 안다. 431 뒤에는 서버가 남은 요청을 읽어 버리느라(닫으면 연결이 리셋되어 클라이언트가 답을 잃을 수 있다)
500 ms 동안 닫지 않았으므로, 클라이언트는 그만큼 기다렸다. 답에 길이를 붙이고, **쓰기 쪽만 닫는다**(`shutdown(SHUT_WR)`, 새 원시 기능 `close_write`).
클라이언트는 답의 끝을 곧 보고, 서버는 그 뒤에도 읽어 버릴 수 있다. TCP의 "반쯤 닫기"가 쓰이는 전형적인 자리다.

## 3. 클라이언트: 받을 수 있는 답은 받는다

서버는 요청을 다 받기 전에 답하고 닫을 수 있다(RFC 9112 9.6, 큰 업로드에 이른 413). 그러면 클라이언트의 쓰기가 실패한다. 전에는 그 쓰기 에러를 그대로 보고했지만,
답은 이미 와 있을 수 있다. 이제 쓰기가 실패하면 답을 한 번 읽어 보고, 왔으면 그것을 준다(curl도 이렇게 한다).

## 4. 호스트는 ASCII로 나간다

`Host` 헤더와 DNS 이름은 ASCII다. 비ASCII 도메인(`例え.jp`)은 IDNA로 퓨니코드(`xn--r8jz45g.jp`)로 바꿔 보내야 한다. 전에는 UTF-8 바이트를 그대로 보냈고, 직접 연결이면
그 바이트가 `getaddrinfo`로 가서 운영체제마다 다르게 실패했다. IDNA는 유니코드 매핑 표가 필요한 기능이라 0.5.0 밖이고, 대신 **틀린 바이트를 보내지 않게** 거절하고 길을 알려 준다
(``write it in punycode, `xn--…` ``). 괄호 안의 IPv6 주소도 이름 조회로 넘기지 않고 먼저 검사한다.

## 5. 머리를 네이티브로: 원칙과 비용 사이

06은 "HTTP는 fung으로 쓴다"고 정했다. 그런데 머리 한 줄마다 fung 함수 수백 번(글자마다 `_is_tchar`, 이름 대소문자 바꾸기)이 돌아서, 값 500개인 1 MB 요청 머리 하나에 서버가 0.55초를 썼다.
실행 스레드가 하나라 그동안 다른 요청은 모두 멈춘다. 서비스 거부가 쉬운 모양이다.

나눈 선: **바이트를 줄로 자르고 줄을 필드로 만드는 일**(줄 나누기, 접힌 줄 잇기, 이름과 값의 글자 검사, 이름의 대소문자)은 `_net.read_fields`가 하고,
**뜻을 따지는 일**(`Host`가 하나인지, `Content-Length`가 맞는지, 전송 코딩, 리다이렉트)은 fung에 남겼다. 규칙은 그대로라 기대 출력이 한 바이트도 바뀌지 않았다.
값 500개 요청 4개가 2.27초에서 0.09초가 되었다.

## 6. 벤치가 잡은 내 실수

H2(중복 이름)를 처음 고칠 때 "이름마다 앞의 이름들에 있는지"를 봤다: `find(0..n, i => names[i] in take(names, i))`. 이름이 n개면 n²/2번 견준다.
보통 답의 헤더는 열 개 안팎이라 시험은 모두 통과했지만, 헤더 2만 줄 벤치에서 몇 초가 걸렸다. 맵에 넣은 뒤 크기가 줄었는지로 판정하게 고쳤다(겹친 이름이 있으면 맵이 작다).
"작은 입력에서만 시험하면 복잡도 실수가 숨는다"는 것을 다시 배웠다. 측정용 입력을 벤치(`bench/heads.fung`)로 남긴 이유다.
