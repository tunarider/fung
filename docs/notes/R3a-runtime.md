# R3a Rust 동시성 런타임: 무엇을 옮겼고 왜 그렇게 했나

2026-10-15. 계획 `docs/plans/2026-10-15-rust-runtime-3a.md`, 스펙 `docs/superpowers/specs/2026-10-15-rust-runtime-3a-design.md`,
결정과 남은 차이는 `docs/design/open-questions.md`의 "Rust 이전".

Rust 이식 3단계의 앞 절반(3a)이 끝났다. 2단계(`docs/notes/R2-vm.md`)는 태스크 하나로 도는 값과 VM을 옮겼다.
이번 단계는 fung의 **동시성**을 옮겼다. 이제 Rust 버전의 `fung run`이 `spawn`·채널·`atom`·취소·교착 감지를 쓰는 프로그램을 Go와 같은 출력으로 돈다.

3단계는 둘로 나눴다.
- **3a(이번)**: Go와 같은 의미. `atom`까지 Go 그대로 옮기고, Go 바이너리를 정답지로 런타임 전체를 검증한다.
- **3b(다음)**: Go와 일부러 달라지는 언어 변경. `atom` 제거, 채널에 자기 자신 보내기 에러 등.

이 노트는 세 가지를 다룬다.
- 무엇을 만들었고 어떻게 Go와 같은지 확인했나.
- 운영체제 스레드, 잠금, 조건 변수, `unsafe` 같은 동시성의 기본 개념을 Rust에서 어떻게 썼나.
- 실제로 부딪힌 함정과, 태스크가 많을 때 치르는 비용.

## 1. 무엇을 만들었나

`crates/fung-vm/src/vm/`에 파일이 늘었다. 외부 크레이트는 여전히 0개다. 표준 라이브러리의 `Mutex`·`thread`·원자적 변수만 쓴다.
- `world.rs`: 태스크들이 함께 쓰는 부분(`World`)과 그것을 지키는 **실행권**(run token). 3절.
- `token.rs`: 디버그 빌드에서 "이 스레드가 지금 실행권을 쥐었나"를 기록하고 단언한다. 3절.
- `task.rs`: `spawn`·`await`·`cancel`, 태스크 핸들, 취소 트리(`CancelNode`). 5절.
- `block.rs`: 태스크가 기다리는 **단 하나의 함수** `block`과 운영체제를 기다리는 `outside`, 차례 넘기기. 4절.
- `channel.rs`: 채널. Go 런타임의 `hchan`처럼 기다리는 쪽의 줄(queue)을 직접 둔다.
- `atom.rs`: `atom`·`swap`·`deref`. 3b에서 통째로 지울 수 있게 한 파일에 모았다.
- `deadlock.rs`: 교착 감지. 6절.
- `failure.rs`: 아무도 꺼내지 않은 태스크 실패 보고. 7절.
- `stdin.rs`: 여러 태스크가 나눠 읽는 표준 입력.

`crates/fung-cli/src/run.rs`는 Go `execute`와 같은 순서로 끝을 정리한다.
1. 진입 파일을 돌린다. 성공하면 남은 태스크를 기다리고, 에러면 남은 태스크를 취소한 뒤 기다린다.
2. `exit(n)`이 있었으면 그 값을 종료 코드로 삼는다.
3. `at_exit` 핸들러를 거꾸로 돌린다. 핸들러의 E0701(취소)·E0702(교착)는 다시 출력하지 않는다.
4. 다시 기다리고, 아무도 꺼내지 않은 실패를 보고한다. 보고가 있었고 종료 코드가 정해지지 않았으면 1.

### 어떻게 같은지 확인했나

2단계와 같은 방법이다. **Go 바이너리를 정답지로 두고 같은 입력을 두 바이너리에 넣어 바이트 단위로 비교한다.** 동시성에는 하나가 더 붙는다. 같은 프로그램을 여러 번 돌려도 결과가 흔들리지 않아야 한다.
- `crates/fung-cli/tests/run_parity.rs`: 187건. 골든 테스트 `tests/lang` 136개 중 127개(제외는 4단계의 네이티브 모듈 9개뿐), `bench/` 6개, `-e` 프로그램 47개(그중 동시성 23개), 실행 방식 7가지. 2단계의 152건에서 늘었다.
- 같은 파일의 `concurrent_runs_are_stable`(릴리스 빌드만): 동시성을 쓰는 골든 파일 8개와 동시성 `-e` 23개, 모두 31건을 Rust로 50번, Go로 50번 돌려 모두 Go의 첫 결과와 같아야 한다. Go 쪽도 돌리는 이유는 **Go 자신이 흔들리는 프로그램**을 찾기 위해서다. 실제로 하나 찾았다(8절의 차이 목록).
- Go 단위 테스트(`conc_test.go`·`unretrieved_test.go` 등)를 `task_tests.rs`·`channel_tests.rs`·`atom_tests.rs`·`failure_tests.rs`·`exit_tests.rs`로 옮겼다. `fung-vm`의 단위 테스트는 268개다.
- `prelude/go_cases.rs`에 태스크·채널·atom 사례를 더해 실행 시점에 Go와 비교한다.
- **흔들림 검사**: Rust에는 Go `-race` 같은 표준 도구가 없다. 대신 디버그 테스트 바이너리를 8~12개 동시에 여러 번 돌려 멈추거나 결과가 바뀌는지 봤다(마지막 상태: 실패 0).

## 2. 운영체제 스레드와 그린 스레드

"동시에 여러 일을 한다"를 만드는 방법은 크게 둘이다.
- **운영체제 스레드**: 운영체제가 스레드마다 스택을 주고, 언제 어느 스레드를 돌릴지 정한다. 스레드를 바꾸려면 커널에 들어간다(문맥 전환, 수 마이크로초).
- **그린 스레드**: 언어 런타임이 직접 만든 가벼운 실행 단위. 스택이 작고(Go 고루틴은 2 KiB에서 시작해 자란다), 바꾸는 일이 커널 없이 런타임 안에서 끝난다(수십~수백 나노초). Go 고루틴, Erlang 프로세스가 그렇다.

Go 버전의 fung 태스크는 고루틴이다. 그래서 태스크를 수만 개 띄워도 가볍다.

3a는 **태스크마다 운영체제 스레드 하나**를 쓰고, fung 코드는 한 번에 한 스레드만 돌린다(3절의 실행권). Python의 GIL, OCaml 4의 런타임 잠금과 같은 모델이다. 왜 그린 스레드가 아닌가.
- **내장 함수가 람다를 부르는 구조.** `each(xs, x => send(ch, x))`에서 `send`가 막히면, Rust 스택 위에 `each` → VM → `send`가 겹쳐 있다(R2 7절). 그린 스레드로 태스크를 주차하려면 이 Rust 스택까지 통째로 치워 둬야 하는데, Rust는 이것을 표준 기능으로 주지 않는다. 운영체제 스레드는 스택을 통째로 들고 잠들 수 있어서 이 문제가 없다.
- **표준 입력·외부 프로세스.** 운영체제 호출에서 막히는 일은 어차피 다른 스레드가 필요하다. 그린 스레드를 해도 이 부분은 따로 만들어야 한다.
- **비용은 측정해서 판단한다.** 태스크가 몇 개~몇백 개인 스크립트에서는 차이가 작다. 태스크 수천 개, 채널 주고받기가 많은 프로그램에서 비싸다. 9절에 숫자가 있다.

대신 갈아끼울 자리를 남겼다. 태스크가 기다리는 곳은 모두 `block` 함수 하나를 지난다(4절). 그린 스레드로 바꿀 때 이 함수가 "스레드를 재운다"에서 "태스크를 주차하고 스케줄러로 돌아간다"로 바뀐다. 다만 바뀌는 곳이 이 함수 하나는 아니다. 스레드가 잠들거나 시작하는 곳이 모두 바뀐다: `world.rs`의 `Token::sleep`·`yield_turn`·`Gate`, `block.rs`의 `Waiter` 재우기·깨우기(park/unpark), `task.rs`의 `Task::spawn`, `stdin.rs`의 `Reader::wait`.

스택 크기:
- 진입 파일은 2단계처럼 4 GiB 스택 스레드에서 돈다.
- `spawn`한 태스크의 스레드는 1 GiB(`TASK_STACK`). Go 고루틴이 자랄 수 있는 최대 크기와 같다. 그래서 고루틴에서 되는 프로그램은 태스크에서도 된다. 처음에는 256 MiB였는데, `map`이 fung 함수를 99,000단계 겹쳐 부르는 프로그램이 태스크 안에서만 스택을 넘쳐 프로세스가 중단됐다(종료 코드 134, `at_exit`도 돌지 않음). Go와 진입 스레드는 같은 프로그램을 끝까지 돌린다. 릴리스 전용 테스트 `crates/fung-cli/tests/task_stack.rs`가 지킨다.
- 이것은 **가상 주소 예약**일 뿐이다. 운영체제는 실제로 쓴 페이지만 메모리를 준다. 그래서 태스크 2,000개(주소 2 TB)가 문제없이 돈다(`two_thousand_tasks_run`). 256 MiB 때와 시간이 같다(9절).
- 운영체제가 예약을 거부하면(스레드 수 한도, 엄격한 overcommit, `ulimit -v`) `spawn`은 프로세스를 죽이지 않고 `E0801 internal error: cannot start a task: ...` 에러를 낸다. `at_exit`도 돈다. macOS의 프로세스당 스레드 한도(8,192)를 넘겨 확인했다.
- Linux: Rust 표준 라이브러리는 `pthread_attr_setstacksize`만 부르고, glibc가 스택을 `MAP_NORESERVE` 없이 `PROT_NONE`으로 `mmap`한 뒤 가드 페이지를 뺀 부분을 `mprotect`로 쓰기 가능하게 바꾼다. 이때 1 GiB가 커밋 양(Committed_AS)에 잡힌다. 하지만 기본값인 휴리스틱 overcommit(`vm.overcommit_memory=0`)은 요청 **하나**가 램+스왑보다 큰지만 보고 합계는 보지 않으므로 2,000개도 통과한다. 엄격 모드(`=2`)에서는 합계가 한도를 넘는 순간 위의 에러가 난다.

## 3. 실행권 잠금과 `unsafe`의 근거

### 문제: `Rc`는 스레드 사이에 넘길 수 없다

2단계의 값은 `Rc`로 공유한다(R2 3절). `Rc`의 참조 계수는 **원자적이지 않은** 보통 정수다. 두 스레드가 같은 값의 계수를 동시에 올리고 내리면 계수가 틀려지고, 아직 쓰는 값이 해제되거나 영원히 해제되지 않는다.

Rust는 이것을 타입으로 막는다.
- **`Send`**: "이 타입의 값은 다른 스레드로 옮겨도 안전하다"는 표시(trait). 컴파일러가 필드를 보고 자동으로 붙인다. `Rc`는 `Send`가 아니다.
- **`Sync`**: "이 타입을 여러 스레드가 동시에 빌려 봐도(`&T`) 안전하다"는 표시.
- `thread::spawn`에 넘기는 것은 `Send`여야 한다. 그래서 `Rc`가 든 값을 다른 스레드로 넘기는 코드는 **컴파일이 안 된다.**

스레드 사이에서 쓰는 도구는 따로 있다.
- **`Arc`**: 원자적 계수를 쓰는 `Rc`. 조금 느리지만 스레드 사이에 공유할 수 있다.
- **`Mutex`**(상호 배제 잠금): 한 번에 한 스레드만 안의 값에 닿게 한다. `lock()`이 돌려주는 **guard**가 살아 있는 동안만 값에 닿을 수 있고, guard가 사라지면 잠금이 풀린다.

### 해법: 실행권 하나

모든 값을 `Arc`로 바꾸면 계수 연산마다 원자적 연산이 붙어 태스크 하나일 때도 느려진다. 대신 규칙 하나를 세웠다.

> **fung 값(`Rc`를 품은 모든 것)을 만들고, 읽고, 복제하고, 해제하는 일은 실행권을 쥔 스레드만 한다.**

실행권은 잠금 하나다. 태스크 스레드는 fung 코드를 돌리기 전에 실행권을 얻고, 기다릴 때(4절) 내려놓는다. 한 순간에 값을 만지는 스레드가 하나뿐이므로 `Rc`의 계수가 틀려질 수 없다.

그런데 컴파일러는 이 규칙을 모른다. `World`(공유 부분)에는 `Rc`가 들어 있어 `Send`가 아니고, 그러면 `Mutex<World>`를 스레드 사이에 공유할 수 없다. 그래서 컴파일러에게 "내가 보증한다"고 말해야 한다.

```rust
// SAFETY: ... every fung value that shares an `Rc` with a value
// reachable from the world is created, cloned and dropped only by the
// thread that holds `Shared::world`'s mutex (the run token). ...
unsafe impl Send for World {}
```

**`unsafe`**는 "컴파일러가 검사하지 못하는 약속을 프로그래머가 대신 진다"는 표시다. `unsafe`가 붙은 곳이 틀리면 메모리 안전이 깨진다. 그래서 규칙을 정했다.
- `unsafe impl Send`는 실행권 규칙에 기대는 감싸개에만 쓴다. 지금 두 곳이다. `World`(`world.rs`)와 `Handoff`(`task.rs`, `spawn`이 함수와 결과 칸을 새 스레드에 건네는 상자).
- 쓰는 곳마다 `// SAFETY:` 주석에 근거를 적는다.

### 근거는 모든 길에서 지켜져야 한다

`unsafe`의 근거는 "보통 그렇다"가 아니라 "**어떤 공개 함수를 어떤 순서로 불러도** 그렇다"여야 한다. 이 차이를 실제로 겪었다(8절 (1)). 처음 근거는 `World` 안쪽만 봤는데, `Runtime`의 공개 함수들이 `Rc`가 든 값을 바깥으로 돌려주고 있었다. 그 값은 실행권 없이 아무 스레드에서나 해제될 수 있었다.

그래서 `Runtime`의 공개 API를 다시 짰다.
- **값이 경계를 넘지 않는다.** 공개 함수는 fung 값을 받지도 돌려주지도 않는다. 앞단의 결과물(바이트코드)이 들어가고, `()`·문자열·정수·에러 보고(`Diag`)만 나온다. prelude 부팅, 진입 파일 링크, 실행은 모두 런타임 안에서 실행권을 쥐고 한다(`boot` → `load` → `run`).
- **`Runtime`은 `Send`지만 `Sync`가 아니다.** 명령이 런타임을 다른 스레드로 넘길 수는 있지만, 두 스레드가 동시에 같은 런타임을 부르지는 못한다. `PhantomData<Cell<()>>` 필드가 이것을 만든다. `PhantomData`는 "크기 0이지만 타입 검사에서는 이 타입을 가진 것처럼 친다"는 표시이고, `Cell`은 `Send`지만 `Sync`가 아니므로 `Runtime`도 그렇게 된다. 크레이트 없이 컴파일 시점에 `!Sync`를 고정하는 검사도 넣었다.

### 지키는 법: 디버그 단언

근거를 사람이 읽고 믿는 것만으로는 부족하다. 디버그 빌드는 스레드 지역 변수(`thread_local!`의 `Cell<bool>`) 하나로 "이 스레드가 지금 실행권을 쥐었다"를 기록한다(`token.rs`).
- 잠금을 얻은 직후 표시하고, 내려놓기 직전에 지운다.
- 값의 경계마다 단언한다. 태스크 시작과 끝, `block`에 들어갈 때·깬 뒤·나올 때, 차례 넘기기와 `outside` 앞뒤, `Handoff`를 열 때와 버릴 때, 태스크 핸들·채널·atom의 `Drop`, 런타임의 `Drop`.
- 같은 스레드가 실행권을 두 번 얻으려 하면 교착 대신 "run token taken twice on one thread"로 패닉한다.
- 릴리스 빌드에서는 모두 사라진다. 비용 0.

이 단언이 실제로 버그를 잡았다. `outside` 안에서 패닉이 나자 되감기(unwind) 도중 태스크 핸들이 실행권 없이 해제되어 단언이 터졌다(8절 (9)).

### 실행권의 모양: 줄 서는 문 + 잠금

처음에는 실행권이 그냥 `Mutex<World>`였다. 태스크가 여럿이 되자 부족했다. 표준 `Mutex`는 **공정하지 않다**. 잠금을 풀고 곧바로 다시 잡는 스레드가 기다리던 스레드보다 거의 항상 이긴다(8절 (2)).

그래서 실행권은 두 부분이 되었다(`world.rs`).
- **`Gate`**: 기다리는 스레드의 FIFO 줄. 실행권을 내놓는 쪽이 줄 맨 앞 스레드에게 직접 넘긴다(`park`/`unpark`, 4절).
- **world 잠금**: `Gate`를 통과한 스레드만 잠근다.

**차례 넘기기**: 막히지 않고 계산만 하는 태스크가 다른 태스크를 굶기지 않도록, 함수 호출을 1만 번(`YIELD_EVERY`) 할 때마다 줄에 누가 있는지 본다. 있으면 맨 앞에게 넘기고 자기는 줄 끝에 선다. 없으면 원자적 변수 하나를 읽는 것으로 끝난다. 그래서 태스크가 하나뿐인 프로그램에는 비용이 거의 없다(9절).

1만이라는 값은 쟀다. 넘기기 한 번이 약 3.5 µs라서, 값이 작으면 계산하는 태스크 둘의 처리량이 떨어지고(200이면 +37%), 크면 잠에서 깬 태스크가 차례를 오래 기다린다(20만이면 1.9초). 1만에서 처리량 손해 약 1%, 기다림 약 0.5 ms다.

## 4. 조건 변수와 막히는 지점 하나

### 조건 변수

태스크가 "채널에 값이 올 때까지" 기다리는 모습을 생각해 보자.
1. 실행권을 쥐고 채널을 본다. 비어 있다.
2. 실행권을 내려놓고 잠든다.
3. 다른 태스크가 값을 넣고 깨워 준다.

1과 2 사이에 틈이 있으면 문제다. 1에서 "비었다"를 본 뒤, 2에서 잠들기 전에 다른 태스크가 값을 넣고 깨우면, 그 깨움은 아무도 듣지 못하고 사라진다. 그리고 이 태스크는 영원히 잔다. 이것을 **잃어버린 깨움**(lost wakeup)이라고 한다.

**조건 변수**(`Condvar`)는 이 틈을 없애는 표준 도구다. "잠금을 내려놓는 일과 잠드는 일"을 한 번에 한다. 그리고 깨어나면 반드시 조건을 다시 확인한다. 깨움이 거짓일 수 있기 때문이다(spurious wakeup).

### 처음 설계와 바꾼 설계

처음(Task 3)에는 조건 변수 하나에 모든 태스크가 잤다. 무슨 일이든 생기면(값이 오거나, 태스크가 끝나거나, 취소되면) 전부 깨우고, 각자 자기 조건을 다시 확인했다. 단순하지만 막힌 태스크 수만큼 비용이 들었다. 잠든 태스크 2,000개에서 커널 시간이 9초를 넘었다(8절 (3)).

지금은 **기다리는 태스크마다 깨움 표시**를 따로 둔다(`block.rs`의 `Waiter`).
- `Waiter`는 스레드 손잡이(`Thread`)와 원자적 불(`woken`)이다.
- `thread::park()`는 이 스레드를 재우고, 다른 스레드의 `unpark()`가 깨운다. 조건 변수보다 낮은 층의 도구다. `unpark`가 `park`보다 먼저 와도 표시가 남아 있어서 사라지지 않는다.
- 기다리는 것(채널의 줄, 태스크의 결과 칸, 취소 노드)마다 그것을 기다리는 `Waiter` 목록이 있다. 바뀐 것에 등록된 태스크만 깨운다.

잃어버린 깨움이 없는 이유는 조건 변수의 원리를 손으로 쓴 것이다.
1. 태스크는 실행권을 쥔 채로 깨움 표시를 지우고, 기다릴 것에 자기를 등록하고, 조건을 확인한다.
2. 조건을 바꾸려면 실행권이 필요하다. 그러므로 바꾸는 쪽은 1이 끝난 뒤에 오고, 등록된 태스크를 반드시 본다.
3. 바꾸는 쪽은 상태를 먼저 고치고 깨움 표시를 세운 뒤 `unpark`한다. 잠드는 쪽은 `park` 전마다 표시를 확인한다.

### 막히는 지점 하나: `block`

`await`·`sleep`·`send`·`recv`·`swap`은 모두 `block(t, ready, timeout)`을 지난다.
- `ready`는 "기다리던 일이 됐나"를 묻는 함수다. 됐으면 결과를, 아니면 `None`을 주며 자기를 등록한다.
- `block`은 `ready`를 묻고, 아니면 실행권을 내려놓고 잠들고, 깨면 실행권을 다시 얻어(줄 서서) 묻기를 되풀이한다.
- 시간이 다 되면 `None`(타임아웃), 취소되면 E0701.
- 교착 감지용 집계(6절)도 여기서만 바뀐다.

한 곳에 모은 덕분에 취소·타임아웃·교착 집계·디버그 단언을 한 번만 쓰면 된다. 그린 스레드로 바꿀 때는 이 함수가 중심이지만, 2절 끝에 적은 대로 스레드를 재우고 깨우고 시작하는 다른 자리들(`Token::sleep`·`yield_turn`·`Gate`, `Waiter`, `Task::spawn`, `Reader::wait`)도 함께 바뀐다.

운영체제를 기다리는 일(표준 입력, 자식 프로세스)은 `outside(t, f)`를 지난다. 실행권을 내려놓고 `f`를 부르고 다시 얻는다.
- `f`는 `Send`여야 한다. 그래서 fung 값이 `f` 안으로 들어갈 수 없다. 컴파일러가 실행권 규칙의 일부를 검사해 주는 셈이다.
- 표준 입력은 읽기 전용 스레드 하나가 Go `bufio`처럼 4 KiB씩, **누가 줄을 원할 때만** 읽는다(8절 (8)). 태스크는 그 줄을 기다리며, 취소되면 기다림을 그만둔다.
- `outside`에 있는 태스크는 살아 있지만 막힌 것으로 세지 않는다. 언제 입력이 올지 fung은 알 수 없기 때문이다(05와 같다).

## 5. 취소 트리

`cancel(t)`은 그 태스크와 그 태스크가 띄운 자식, 손자까지 모두 취소한다. Go는 `context`로 이것을 한다. Rust 버전은 같은 모양의 `CancelNode` 트리를 직접 만들었다(`task.rs`).
- 노드마다 취소 표시(`AtomicBool`)가 있다. VM은 함수 호출마다, 그리고 `block`에서 이 표시를 본다. 취소됐으면 내부 에러 E0701로 되감는다. 이 E0701은 출력되지 않고 핸들이 `Err({kind: 'cancelled})`로 바꾼다.
- `cancel`은 표시를 세우고 자식들을 차례로 취소한다. 재귀가 아니라 반복이라 트리가 깊어도 스택이 넘치지 않는다.
- 노드에는 그 아래에서 막힌 태스크의 `Waiter`도 등록된다. 그래서 `sleep(10s)`나 `recv`에서 자고 있던 태스크가 취소 즉시 깬다.

뿌리는 둘이다.
- `root`: 진입 파일과 그 자손 전부. `exit(n)`과 교착 판정이 이것을 취소한다.
- `handlers`: `at_exit` 핸들러들. 핸들러마다 그 아래 새 노드에서 돌고, 핸들러가 끝나면 그 노드를 취소한다.

### 강한 연결과 스스로 떨어지기

Rust에서 트리를 만들 때 늘 나오는 질문이 "부모가 자식을 어떻게 가리키나"다.
- **강한 참조**(`Arc`): 가리키는 동안 상대가 해제되지 않는다.
- **약한 참조**(`Weak`): 상대를 살려 두지 않는다. 쓸 때 `upgrade()`로 "아직 살아 있나"를 확인한다. 부모↔자식처럼 서로 가리키는 구조에서 고리(순환)를 피하려고 흔히 쓴다.

처음에는 부모가 자식을 `Weak`로 들었다. 그러자 중간 노드가 사라지면 그 아래 손자들이 뿌리에서 닿지 않는 고아가 되었다. 그 손자는 취소를 받지 못하고, 그 태스크를 기다리는 프로그램은 끝나지 않았다(8절 (4)).

지금은 Go `context`와 같다.
- 부모가 자식을 **강하게** 든다(`HashMap<usize, Arc<CancelNode>>`). 자식은 부모를 `Weak`로 가리킨다.
- 자식은 취소될 때 **스스로** 부모의 목록에서 빠진다.
- 태스크가 끝나면 그 노드를 취소하고(Go의 `defer cancel()`), 테스트 블록·핸들러·`run_task`의 노드도 끝날 때 취소한다. 그래서 노드가 쌓이지 않는다.

이렇게 하면 살아 있는 노드 아래의 어떤 노드도 뿌리에서 떨어질 수 없다. 뿌리를 취소하면 반드시 모두에게 닿는다.

## 6. 교착 감지: Go의 50 ms와 무엇이 다른가

**교착**(deadlock)은 모든 태스크가 서로를 기다려 아무도 진행할 수 없는 상태다. `recv(channel())`처럼 아무도 보내지 않는 채널을 기다리는 프로그램이 가장 단순한 예다. fung은 이것을 알아채 E0702를 출력하고 종료 코드 1로 끝낸다(05).

판정 조건은 세 개의 수로 쓴다.
- `live`: fung 코드를 돌리는 태스크 수. 진입 파일, 테스트 블록, 핸들러, `spawn`한 태스크. `spawn`한 태스크는 스레드가 생기기도 전에 부모가 센다.
- `blocked`: 그중 `block`에서 자고 있는 수.
- `waking`: 그중 타이머가 깨워 줄 수(`sleep`, 타임아웃 있는 `recv`).

`live > 0`이고 `blocked == live`이고 `waking == 0`이면, 아무도 다시 돌 수 없다. 교착이다.

### Go는 왜 50 ms를 기다리나

Go 버전은 "모두 막힘"이 50 ms 동안 바뀌지 않아야 교착으로 판정한다. 이유는 집계가 정확하지 않아서다. Go에서 태스크를 깨우면 그 고루틴이 실제로 스케줄되어 자기 수를 고칠 때까지 잠깐 "막힘"으로 남는다. 그 순간에 판정하면 거짓 양성(실제로는 교착이 아닌데 교착이라고 함)이 나온다. 50 ms는 그 틈을 덮는 여유다.

### Rust는 왜 바로 판정할 수 있나

**깨우는 쪽이** 실행권을 쥔 채로, 실행권을 넘기기 전에, 깨운 태스크를 `blocked`에서 뺀다(`Waiter::wake`).
- 그래서 실행권이 넘어가는 모든 순간에 `blocked`는 "누군가 깨워 주지 않으면 돌 수 없는 태스크 수"와 정확히 같다.
- 실행권을 기다리는 줄에 선 태스크, `outside`에 있는 태스크, 아직 시작하지 않은 태스크는 살아 있고 막히지 않은 것으로 센다.
- 조건이 참이 될 수 있는 순간은 둘뿐이다. 살아 있는 태스크가 막힘으로 세어질 때, 살아 있는 태스크가 끝날 때. 판정은 정확히 이 두 곳에서 한다. 깨우기나 타이머는 조건에서 멀어지는 쪽으로만 수를 바꾼다.

그래서 유예 없이 즉시 판정한다. 출력은 Go와 같다. 깨우는 쪽에서 빼는 줄을 지우면 `a_woken_task_that_has_not_run_is_not_blocked` 테스트가 거짓 E0702를 내는 것을 확인했다.

판정 뒤에는 Go와 같은 일을 한다. E0702를 출력하고, 종료 코드 1을 기록하고, `root`를 취소한다. 막혔던 태스크들은 E0702로 되감고, 핸들러는 그대로 돈다.

즉시 판정에는 대가가 있었다. Go의 50 ms는 집계 오차만 덮은 게 아니라 **순서 문제**도 덮고 있었다. 진입 파일이 에러로 죽을 때 판정이 `cancel_all`보다 먼저 돌아 거짓 E0702가 나왔다(8절 (7)).

## 7. 참조 계수로 꺼내지 않은 실패 보고하기

05의 규칙: `spawn`한 태스크가 실패했는데 아무도 `await`로 꺼내지 않으면 그 실패를 버리지 않고 `task failed: ...`로 보고하고 종료 코드를 1로 한다. 문제는 "아무도 꺼내지 않을 것"을 **언제** 아느냐다.
- Go는 가비지 컬렉터에 기댄다. 핸들이 버려지면 GC가 그것을 찾을 때(수 초~2분 뒤) 보고한다. 프로그램이 끝날 때 남은 것은 한꺼번에 보고한다.
- Rust는 참조 계수다. **마지막 핸들이 사라지는 순간**을 정확히 안다. `TaskHandle`의 `Drop`이 그 순간이다.

`failure.rs`의 규칙:
- 태스크가 실패하면(취소·교착·`exit`는 실패가 아니다) 보고문을 그 자리에서 만든다. 소스 발췌와 호출 경로까지 Go `reportFailure`와 같은 글자다.
- 핸들이 이미 사라졌으면 바로 보고한다. 아직 있으면 기록만 해 둔다.
- 핸들의 `Drop`이 기록된 실패를 보고한다. fung 값의 모든 복사본은 같은 `Rc<TaskHandle>`을 가리키므로, `Drop`이 불리면 그것이 마지막 핸들이다.
- `await`가 결과를 실제로 돌려주면 기록을 지운다. 타임아웃으로 끝난 `await`는 꺼낸 것이 아니다.
- `pmap`·`fan_in`처럼 스스로 기다리는 도우미가 쓰는 `spawn_awaited`는 처음부터 꺼낸 것으로 친다.
- 프로그램 끝에서 남은 기록을 실패한 순서대로 보고한다.

모든 단계가 실행권 아래에서 일어나므로 같은 실패가 두 번 보고되거나, 꺼낸 뒤에 보고되는 일이 없다. 핸들의 `Drop`은 `World`에 닿지 못하므로 표준 에러를 따로 공유한다(`Arc`로 감싼, 쓸 때마다 잠그는 스트림).

`Value::Task`도 2단계의 깊은 해제(R2 6절)에 넣었다. 태스크 결과가 다른 태스크 핸들이고 그 결과가 또 핸들인 사슬이 20만 단이어도 재귀 없이 풀린다.

Go와 달라지는 점: 보고가 Go보다 이르다. 표준 출력과 에러가 한 터미널에 섞이면 `task failed:` 줄이 Go보다 앞에 보일 수 있다. 출력을 나눠 보면 내용과 종료 코드는 같다. 여러 실패가 끝에 보고될 때의 순서도 다를 수 있다(8절 뒤의 차이 목록).

이번 단계에서 실제로 겪고 진행 기록(`.superpowers/sdd/2026-10-15-rust-runtime-3a/progress.md`)과 작업 보고서에 적힌 것만 적는다.

**(1) `unsafe`의 첫 근거는 공개 API에서 거짓이었다.**
- Task 2에서 `unsafe impl Send for World`의 근거를 "모든 접근이 잠금을 지난다"로 적었다. 리뷰에서 반례가 나왔다. `run`은 결과 값을, `import_module`은 `Rc<Module>`을, `tests`는 테스트 함수 목록을, `boot`는 prelude를 **바깥으로 돌려줬다.** 그 `Rc`들은 실행권 없이 명령의 스레드에서 해제되었다. 태스크가 하나일 때는 아무 일도 없지만, 다른 스레드에서 태스크가 돌기 시작하면 계수가 깨질 수 있었다.
- 또 `Runtime`이 `Arc<Shared>` 때문에 의도치 않게 `Sync`였다.
- 해결: 3절처럼 API를 다시 짰다. 어떤 `Rc`도 실행권의 경계를 넘지 않고, `Runtime`은 `!Sync`다.
- 교훈: `unsafe`는 "내가 아는 사용법에서는 안전하다"가 아니라 "**모든 공개 경로에서** 안전하다"는 약속이다. 근거를 적을 때 공개 함수 하나하나를 반례로 찾아봐야 한다.

**(2) 표준 `Mutex`는 공정하지 않다.**
- 처음 설계는 `Mutex` + `Condvar`였다. 계산만 하는 태스크가 차례를 넘기려고 잠금을 풀었다가 다시 잡으면, 거의 항상 자기가 다시 잡았다.
- 더 나빴던 것: 조건 변수에서 깬 태스크는 그 `Mutex`를 다시 잡아야 하는데, 계산하는 태스크가 잠금을 계속 쥐고 있어서 깬 태스크가 줄에 설 자리조차 없었다. `a_busy_task_hands_the_token_back` 테스트가 멈췄다.
- 해결: 3절의 FIFO `Gate`. 넘기는 쪽이 줄 맨 앞에게 직접 넘긴다.

**(3) 사건마다 막힌 태스크 전부를 깨우면 비싸다.**
- 조건 변수 하나에 모두가 자던 설계에서, 2,000개 태스크가 각자 다른 시간만큼 `sleep`하는 프로그램이 커널 시간(sys)을 9초 넘게 썼다(9.16~9.45초). Go는 0.1초 아래였다. 태스크 하나가 끝날 때마다 2,000개가 모두 깨서 조건을 확인하고 다시 잤기 때문이다(사건당 O(막힌 태스크 수)).
- 해결: 4절의 태스크별 `Waiter`. 커널 시간이 0.14~0.18초로 줄었다.

**(4) 약한 자식 연결이 취소 트리에 고아를 만들었다.**
- 부모가 자식을 `Weak`로 들자, 중간 태스크(또는 그 핸들)가 사라진 뒤 그 아래 손자가 뿌리에서 닿지 않았다. 또 `at_exit` 핸들러의 노드는 취소되지 않아서, 핸들러가 띄운 태스크를 프로그램이 끝없이 기다렸다.
- 해결: 5절의 강한 연결 + 스스로 떨어지기(Go `context`와 같은 방식). 핸들러의 노드도 끝날 때 취소한다.

**(5) 취소된 채널 대기자의 칸이 짝지어질 수 있었다.**
- `cancel(t)`은 막힌 태스크를 깨우지만, 그 태스크가 실행권을 얻어 줄에서 빠지기 전까지 그 칸(slot)은 채널의 줄에 남아 있었다. 그 사이 다른 태스크가 `send`하면 **죽은 칸에 값을 넣었다.** 값이 사라지거나, 엉뚱한 받는 쪽이 받거나, 취소된 보내는 쪽의 값이 전달됐다.
- 해결: 짝짓는 순간에 "이미 취소됐거나 시간이 지난 칸"을 건너뛴다. 짝짓기는 실행권 아래에서 일어나고 취소 표시와 시계는 한 방향으로만 움직이므로, 이 순간이 결과를 정하는 **선형화 지점**(linearisation point: 동시에 일어나는 일들이 "이 순간에 일어났다"고 말할 수 있는 한 점)이 된다. 이미 짝지어진 뒤 취소된 칸은 "값을 옮긴 쪽이 이긴다"는 Go 규칙대로 성공으로 끝난다.
- 같은 방식을 `atom`의 대기 줄에도 썼다.

**(6) "부하에서 멈춤"은 잃어버린 깨움이 아니라 테스트의 시간 가정이었다.**
- 채널 테스트 하나가 테스트 바이너리 12개를 동시에 돌리면 60번 중 6번 멈췄다. 처음에는 잃어버린 깨움을 의심했다.
- 원인은 테스트였다. `sleep(5ms)` 뒤에는 보내는 태스크가 이미 시작해 막혀 있으리라 가정했는데, 부하가 크면 그 스레드가 아직 시작도 안 했다. 그러면 `cancel`이 보내기 전에 태스크를 끝내 버려, 마지막 `recv`를 아무도 채우지 않았다.
- 해결: 시간 대신 **상태로 순서를 정한다.** 테스트 전용 내장 함수(`queued(ch)`, `held(a)`, `waiters(a)`)로 "보내는 쪽이 줄에 섰다"를 확인할 때까지 기다린다. 같은 가정을 한 Task 3·5의 테스트도 모두 바꿨다. 실패가 60번 중 6번에서 0번이 되었다.
- 동시에 실제 잃어버린 깨움이 없음을 따로 확인했다. CPU를 잡아먹는 프로세스 12개 옆에서 주고받기+취소를 2만 번 넘게 돌려 한 번도 멈추지 않았다.

**(7) 진입 파일의 에러가 거짓 교착(E0702)이 됐다.**
- 다른 태스크가 막혀 있을 때 진입 파일이 에러로 죽으면, 진입 태스크가 끝나는 순간의 판정이 명령의 `cancel_all`보다 먼저 돌았다. 남은 태스크가 모두 막혀 있으니 교착으로 판정했고, 진짜 에러 대신 E0702가 나왔다.
- Go에서는 50 ms 유예 동안 `cancel_all`이 먼저 일어나서 이 순서 문제가 **가려져** 있었다.
- 해결: 진입 파일이 에러로 끝나면, 진입 태스크가 아직 실행권을 쥔 채로 `root`를 취소한다. 그러면 막혔던 태스크들이 깨어 판정에서 빠진다.

**(8) 미리 읽는 표준 입력이 다음 명령의 입력을 훔쳤다.**
- 처음 표준 입력 스레드는 효율을 위해 64 KiB를 미리 읽었다. `fung -e 'print(read_line())'; cat` 같은 셸 파이프라인에서, fung이 한 줄만 쓰고 끝나도 뒤의 줄들이 fung 안으로 사라져 `cat`이 받지 못했다.
- 해결: 누가 줄을 원할 때만, Go `bufio`의 기본 크기인 4 KiB씩 읽는다. 명령도 `std::io::stdin()`(자체 8 KiB 버퍼)을 거치지 않고 표준 입력의 복사본을 직접 읽는다. 이제 파일에서 한 줄 읽은 뒤의 위치가 Go처럼 4096이다.

**(9) `outside`가 되감기에 안전하지 않았다.**
- Rust의 패닉은 기본적으로 스택을 **되감으며**(unwind) 지나가는 값들을 해제한다. `catch_unwind`가 그 되감기를 잡는다. VM은 이것으로 내장 함수의 버그를 E0801로 바꾼다.
- `outside`는 실행권을 내려놓고 `f`를 부른다. `f` 안에서 패닉이 나면, 되감기가 실행권 없이 `f`의 인자(태스크 핸들)를 해제했다. 3절의 디버그 단언이 이것을 잡았다. 단언 자체가 되감기 중의 패닉이 되어 프로세스가 중단됐다.
- 해결: `outside`가 `f`를 `catch_unwind`로 감싸고, 실행권을 다시 얻은 **뒤에** `resume_unwind`로 되감기를 이어 간다.
- 교훈: "실행권 없는 구간"에는 패닉으로 빠져나가는 길도 포함된다.

### Go와 다르게 남은 것

open-questions "Rust 이전"의 3a 항목에 모두 적었다. 요약하면:
- 기다리는 `swap`은 즉시 취소된다(Go는 쥔 쪽이 놓을 때까지 기다림). 최종 결과는 같고 시간만 다르다. atom을 쥔 태스크의 `exit` 사례는 Go 자신이 흔들려 실행 비교에서 뺐다.
- 다른 태스크가 표준 입력을 기다리는 중의 `exit`는 곧 끝난다(Go는 줄이나 EOF를 기다림).
- `exit`이나 교착 뒤 `at_exit` 핸들러 안의 교착은 그 핸들러의 E0702가 된다(Go는 런타임이 종료 코드 2로 죽음).
- 꺼내지 않은 실패는 핸들이 사라질 때 보고되고, 여러 보고는 띄운 순서·실패 순서로 나온다(Go는 GC 때, 흔히 띄운 역순).
- 띄운 태스크는 띄운 쪽이 차례를 넘기거나 막히기 전에는 돌 수 없다. 그래서 곧바로 끝나는 태스크의 자식은 항상 취소된다(Go는 가끔 돈다).
- 자기 자신을 `cancel`하면 다음 호출에서 바로 끝난다(Go는 플래그가 늦게 서서 대개 이어서 돈다).
- 형제 태스크의 시작 순서는 Rust에서 대개 띄운 순서, Go에서 흔히 역순이다. 어느 쪽도 보장이 아니어서 순서에 기대는 `test` 블록은 두 구현에서 다르게 나올 수 있다.
- 4 KiB 넘게 읽은 뒤의 표준 입력 위치가 Go와 몇 바이트 다르다(Go `bufio` 내부 동작, 따라 하지 않음).
- 자기 자신을 품은 채널·atom은 3b까지 `Rc` 순환으로 새어 나간다.

## 9. 벤치마크

### Go와 비교

`bench/`의 여섯 스크립트를 Go 바이너리(`go build -o /tmp/fung-go ./cmd/fung`)와 Rust 릴리스 빌드로 각 5번 돌리고 가장 빠른 값을 적었다. 프로세스 시작부터 끝까지의 시간이다. 새로 더한 둘:
- `chan.fung`: 버퍼 없는 채널로 값 10만 개를 주고받는다. 값마다 한 번씩 태스크가 바뀐다.
- `spawn.fung`: 태스크 2,000개를 한꺼번에 띄우고 모두 기다린다.

기계: Apple M2 Max(`arm64`, 12코어), macOS 27.0.1, Go 1.27.2, Rust 1.94.1. 2026-10-15.

| 스크립트 | 재는 것 | Go | Rust | Go/Rust |
|---|---|---|---|---|
| `fib.fung` | `fib(30)` 재귀: 함수 호출 | 0.206초 | 0.196초 | 1.05 |
| `loop.fung` | 300만 번 `fold`: 산술과 반복 | 0.240초 | 0.213초 | 1.13 |
| `str.fung` | 숫자 50만 개를 문자열로 잇기 | 0.053초 | 0.072초 | 0.74 |
| `map.fung` | 키 20만 개 맵 만들고 조회 | 0.441초 | 0.353초 | 1.25 |
| `chan.fung` | 채널로 값 10만 개 | 0.089초 | 0.254초 | 0.35 |
| `spawn.fung` | 태스크 2,000개 | 0.010초 | 0.116초 | 0.09 |

**태스크 하나일 때의 비용.** 기존 네 개는 2단계 노트(R2 9절)의 Rust 값(0.203·0.212·0.072·0.359초)과 같다. 실행권 잠금과 차례 넘기기는 태스크가 하나면 원자적 변수 읽기 하나라서 보이지 않는다.

다만 한 번 5%를 넘었다. 이번 측정에서 `loop`가 0.226초(+7%)로 나왔다. 옛 커밋들을 따로 빌드해 번갈아 재 보니, 공개 API를 다시 짠 커밋(8절 (1)의 해결)부터 느려졌다. 그 커밋은 실행 루프를 건드리지 않았다. 프로파일러(`sample`)로 보니 `Task::run`이 따로 된 함수로 나타났다. 전에는 컴파일러가 `call_buf` 안으로 **인라인**(함수 몸통을 부르는 자리에 그대로 펼쳐 넣기)하던 함수다. 관계없는 코드가 바뀌자 컴파일러의 인라인 판단이 바뀐 것이다. `#[inline(always)]`를 붙여 0.213초로 돌아왔다(`perf(rust):` 커밋). 동작은 같고 기계어만 다르므로 단위 테스트로 고정할 수는 없었다. 벤치마크 비교가 그 검사다.

**태스크가 많을 때의 비용.**
- `chan`: 값 하나에 Rust 약 2.5 µs, Go 약 0.9 µs. Rust의 사용자 시간(user)은 Go보다 오히려 적고(0.09초 대 0.13초), 차이는 커널 시간(sys 0.16초 대 0.04초)이다. 주고받을 때마다 운영체제 스레드를 재우고 깨우기 때문이다.
- `spawn`: 태스크 하나에 Rust 약 55 µs, Go 약 2 µs. 운영체제 스레드를 만들고(주소 예약 포함) 거두는 비용이다. 예약을 256 MiB에서 1 GiB로 늘려도 같았다(0.11초 → 0.12초, sys 0.05 → 0.06초; 잠든 태스크 2,000개는 2.11~2.14초 → 2.11~2.15초, 최대 RSS 약 40 MB로 같음). 주소 예약은 크기와 상관없이 `mmap` 한 번이기 때문이다.

앞 작업들에서 잰 값도 같은 이야기를 한다(진행 기록과 보고서).

| 측정 | Go | Rust |
|---|---|---|
| `spawn`+`await`를 차례로 20만 번 | 0.57초 | 3.8초 (메모리는 일정) |
| 두 태스크가 핑퐁 10만 번(맞교환 20만 번) | 0.19초 | 0.68초 (user 같음, sys 0.09 대 0.42초) |
| `sleep`하는 태스크 2,000개, 태스크별 깨움 전 | 2.01초 (sys 0.07) | 2.42초 (sys 9.16초) |
| 같은 프로그램, 태스크별 깨움 뒤 | 2.01초 (sys 0.07) | 2.12~2.15초 (sys 0.14~0.18) |

### 그린 스레드 판단에 주는 의미

- **스크립트에는 충분하다.** 태스크 수십~수백 개로 파일을 나눠 처리하거나 URL 몇십 개를 동시에 확인하는 프로그램(`examples/checkurls.fung` 같은)은 태스크당 55 µs, 주고받기당 2.5 µs가 전체 시간에 비해 무시할 만하다. 계산 위주의 프로그램은 Go와 같거나 빠르다.
- **잘게 나눈 동시성에는 3~10배 느리다.** 태스크를 수만 개 띄우거나 채널로 값을 잘게 흘려보내는 파이프라인은 운영체제 스레드 전환이 지배한다. 사용자 시간은 같고 차이가 커널 시간이라는 점이 원인을 분명히 보여 준다. 이 차이는 스레드 수를 줄이거나 잠금을 다듬어서는 줄지 않는다. 바꾸는 단위가 커널 스레드인 한 남는다.
- **그래서 4단계에서 다시 본다.** HTTP 서버(`http.serve`는 요청마다 태스크)가 들어오는 4단계에는 이벤트 루프가 생긴다. 그때 그린 스레드(`block`이 태스크를 주차하고 스케줄러로 돌아가기)를 함께 판단한다. 숫자는 이 표가 기준이다.

## 10. 다음: 3b와 그 뒤

3b는 Go와 일부러 달라지는 언어 변경이다(open-questions "Rust 이전"의 결정).
- `atom`을 없애고, 상태를 쥔 태스크에 채널로 편지를 보내는 fung 라이브러리로 대신한다. `atom.rs`와 `Value::Atom` 갈래를 지운다.
- 채널에 그 채널 자신을 보내면 에러. 자기 자신을 품은 채널·atom의 `Rc` 순환(지금은 새어 나감)을 막는다.
- 보낼 쪽이 모두 사라진 채널은 자동으로 닫힌다.
- 구현마다 결과가 갈라지는 골든 테스트를 정리하고, 바뀐 점을 CHANGELOG에 적는다.

그 뒤로 미룬 것:
- 그린 스레드와 이벤트 루프(4단계, 9절).
- 태스크별 힙과 경계 복사, 여러 코어. 실행권 아래에서는 값 공유가 안전하고, 불변 값이라 프로그램은 차이를 볼 수 없다. 여러 코어로 갈 때 한다.
- 닫힌 파이프에서 진짜 SIGPIPE로 죽기(`libc`, 4단계).
- Go 동등을 위해 붙인 잔가지(open-questions의 "과도기 잔가지")는 Go를 지운 뒤 걷어낸다.

이 단계에서 배운 것을 한 줄로 줄이면, **동시성 코드의 정확성은 "보통 이렇게 돈다"가 아니라 "어떤 순서로 돌아도 이렇다"로 따져야 하고, 그 따짐을 한 함수(`block`), 한 규칙(실행권), 디버그 단언으로 좁혀야 지킬 수 있다.**
