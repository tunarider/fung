# 05. 동시성 모델

## 원칙

- 언어/런타임은 **최소한의 원시 연산만** 제공한다.
- 병렬 map, 워커 풀, 채널 합치기, 액터 같은 고수준 패턴은 **fung 코드로 작성**한다 (표준 라이브러리도 가능한 한 fung으로).
- async/await 없음. 파일·네트워크 I/O는 평범한 함수 호출이고, 기다리는 동안 다른 태스크가 실행된다 (막힌 태스크는 실행권을 놓는다, 아래 "구현").
- 값은 불변이라 태스크 사이에서 그냥 공유해도 안전하다. 바뀌는 상태는 `atom`이 가리키는 값 하나로 두고, `swap`으로 비교 후 교체한다(아래 "공유 상태: atom").

## 원시 연산

| 영역 | 연산 | 설명 |
|------|------|------|
| 범위 | `scope(f)` | 범위를 열고 `f(s)`를 부른다. 본문과 범위의 태스크가 모두 끝나야 돌아온다. 아래 "범위" |
| | `supervise(f, on_fail)` | 자식의 실패를 격리하는 범위. 실패는 `on_fail(e)`로 간다 |
| 태스크 | `spawn(s, f)` | 범위 `s` 안에서 f를 새 태스크로 실행, 태스크 핸들 반환 |
| | `await(t)` | 결과 대기. 아래 "결과" 참고 |
| | `cancel(t)` | 태스크나 범위 취소. 자식 태스크에도 전파 |
| 채널 | `channel(n = 0)` | 통로를 만들고 두 끝 `(tx, rx)`를 준다 (n은 버퍼 크기. 0이면 받는 쪽이 있을 때까지 `send`가 막힌다. 버퍼는 미리 잡지 않으므로 n에 상한이 없다). 아래 "채널의 두 끝" |
| | `send(tx, v)` | `Ok(nil)`, 닫혔거나 받는 끝이 모두 사라졌으면 `Err({kind: 'closed})` |
| | `recv(rx)` | `Ok(v)`, 닫혔고 버퍼가 비었으면 `Err({kind: 'closed})` |
| | `close(tx)` | 닫기 (그 끝의 사본이 더 있어도 지금 닫는다) |
| 공유 상태 | `atom(v)` | 값 `v`를 가리키는 칸 (아래 "공유 상태: atom") |
| | `swap(a, f)` / `reset(a, v)` / `deref(a)` | `f`로 비교 후 교체 / 그냥 바꾸기 / 지금 값 읽기(기다리지 않음) |
| 시간 | `sleep(d)` | 대기 |

- `for x in rx: ... ;;`는 `Ok`를 풀어서 주고, 채널이 닫히면 끝난다. 받는 끝은 **순회 대상**이다(02): `each`·`map`·`filter`·`fold`처럼
  순회하는 모든 함수가 받는 끝을 받으면 닫힐 때까지 받아서 처리한다. 보내는 끝은 순회 대상이 아니다(E0506). 규칙은 하나다.
  - **값이 올 때마다** 함수를 부른다(6c-1, 2026-10-17). 그래서 `for x in rx:`는 일꾼이 보낸 값을 바로 처리한다.
    인자 검사(순회할 수 있는지, 함수인지)가 받기보다 먼저다.
  - 일찍 멈추는 함수(`find`·`any`·`all`·`take`·`first`)와 함수가 실패한 순회는 거기서 멈추고, 받지 않은 값은 채널에 남는다.
  - 전체가 있어야 하는 함수(`sort`·`sort_by`·`reverse`·`last`·`drop`·`zip`·`min`·`max`)는 닫힐 때까지 받은 뒤 일한다.
  - 순회하는 채널에 함수가 다시 보내도 된다(보내는 끝을 쥐고 있으면). 그 값도 차례가 되면 받으므로, 채널이 닫힐 때까지 순회가 이어진다.
- 닫힌 채널에 보내는 것이 Go처럼 패닉이 아니라 `Err`인 이유: 채널을 닫는 것은 다른 태스크가 하는 일, 즉 외부 요인이다 (06의 에러 규칙).
- `swap(a, f)`의 `f`는 여러 번 돌 수 있으므로 **순수 계산만** 한다. 효과 있는 연산을 부르면 E0707(아래).
- 원시 연산 이름은 Go 용어(`go`, `chan`, `select`, `context`)를 쓰지 않는다.

## 채널의 두 끝 (L4, 2026-10-18)

- `channel(n)`은 보내는 끝과 받는 끝의 튜플 `(tx, rx)`를 준다. `type_of`는 `'sender`·`'receiver`, 출력은 `<sender>`·`<receiver>`,
  타입 표기는 `sender`·`receiver`다. 타입 이름 `channel`은 없다. `==`는 같은 채널의 같은 쪽 끝인지 본다.
- 끝을 잘못 주면 인자 타입 에러(E0403)다: `send(rx, v)`, `recv(tx)`, `close(rx)`. 받는 쪽은 닫지 않고 버린다.
- 끝은 복사할 수 있다. 여러 생산자가 같은 `tx`로 보내고, 여러 일꾼이 같은 `rx`에서 받는다.
- **자동 닫힘**: 끝의 사본이 어디에 있든(변수, 클로저가 붙잡은 값, 컬렉션, 다른 채널의 버퍼) 마지막 사본이 사라지는 때를 런타임이 안다.
  - 보내는 끝의 마지막 사본이 사라지면 닫힌다. 받는 쪽은 남은 버퍼를 다 받은 뒤 `Err({kind: 'closed})`를 받는다.
  - 받는 끝의 마지막 사본이 사라지면 닫히고 버퍼의 값을 버린다. 그 뒤의 `send`와 막혀 있던 `send`는 `Err({kind: 'closed})`다.
- 사본이 사라지는 때는 값의 수명 규칙 그대로다. 지역 변수는 함수가 돌아올 때, 태스크가 붙잡은 값은 태스크가 끝날 때, 최상위 변수는 프로그램이 끝날 때다.
  - 그래서 채널을 만든 함수가 받는 끝만 돌려주고 생산 태스크에 보내는 끝을 넘기면, 생산 태스크가 끝날 때 채널이 닫힌다.
  - 최상위에 둔 보내는 끝은 프로그램 끝까지 산다. 그 채널을 끝까지 도는 `for`는 교착(E0702)으로 끝난다. 멈추지 않고 보고된다.
  - 그래서 `close(tx)`를 남긴다. 다른 사본이 있어도 지금 닫고 싶을 때 쓴다.

## 정지 요청과 신호 (L6, 2026-10-18)

- **취소와 정지 요청은 다르다.** 취소는 "지금 멈춰라"이고 모든 자손에게 간다. 정지 요청은 "하던 일을 마치고 끝내라"이고, 받는 쪽이 스스로 정리한다(Go `Server.Shutdown`, Trio의 관례).
- `stop_signal()`은 정지 요청을 받는 끝(`receiver`)을 준다. 정지 요청이 오면 닫히므로 `recv`하면 `Err({kind: 'closed})`, 순회는 끝난다. 이미 왔으면 닫힌 끝을 준다.
  - **보는 쪽**은 그 끝의 사본이 하나라도 살아 있는 상태다(L4의 참조 수). 런타임은 보내는 끝을 쥐고 받는 끝은 약한 참조로만 기억한다.
  - 정지 신호에서만 기다리는 것은 교착이 아니다(신호가 깨운다).
- 정지 요청을 보내는 것: 첫 SIGINT·SIGTERM, 또는 `request_stop()`(사용자 결정: 공개. 첫 신호와 똑같이 동작한다).
  - 보는 쪽이 있으면 끝들을 닫기만 한다. 프로그램은 보는 쪽이 일을 마치고 진입 파일이 끝날 때 끝나고, **종료 코드는 0**이다(사용자 결정, 2026-10-18).
  - 보는 쪽이 없으면 `exit`처럼 루트를 취소한다(`release`는 돈다). 종료 코드는 신호면 128 + n(SIGINT 130, SIGTERM 143), `request_stop()`이면 0.
    그래서 정지 요청을 모르는 스크립트의 Ctrl-C는 지금처럼 곧바로 멈춘다.
  - **두 번째 신호**는 정리를 기다리지 않고 곧바로 끝낸다(128 + n).
  - REPL에서는 평가 중의 Ctrl-C가 그 평가를 취소하고 세션이 이어진다. SIGTERM은 곧바로 끝낸다.
  - `fung test`는 테스트 블록마다 정지 상태를 새로 둔다. 신호가 오면 그 파일에 정지 요청을 보내고, 다음 파일은 돌리지 않으며, 명령은 128 + n으로 끝난다.
- 구현: 명령이 시작하자마자 두 신호를 모든 스레드에서 막고, 전용 스레드가 `sigwait`로 받는다(`fung-vm/src/signals.rs`). 신호 처리기가 아무 데서나 끼어들지 않으므로
  잠금과 실행권을 기다리는 보통 코드로 처리한다. 외부 프로세스는 마스크를 비우고 띄운다. 정지 상태는 `vm/stop.rs`.
- `http.serve(…, drain = 10s, reuse_port = false)`는 정지 요청을 본다. 오면 리스너를 닫아 새 연결을 그만 받고, 처리 중인 요청을 `drain`까지 마친 뒤
  남은 것은 취소하고(503으로 답함) `nil`을 돌려준다. 서버가 취소되면 기다리지 않는다(06).

## 여러 채널 기다리기: `select` 없음

- Go `select`에 해당하는 원시 연산은 두지 않는다. 문법·VM 모두에 큰 추가다.
- 스크립트에서 필요한 것은 거의 "타임아웃 있는 받기"와 "여럿 중 먼저 온 것"이다.
  - 전자는 `timeout(d, () => recv(rx))`.
  - 후자는 `conc` 모듈의 `fan_in(s, rxs)` (fung 코드: 범위 `s` 안에서 받는 끝마다 전달 태스크를 띄워 하나로 모으고, 모은 받는 끝을 돌려준다). 맵 `merge`와 이름이 겹치지 않게 했다.

## fung으로 작성하는 것들 (예)

- `pmap(list, f, limit: n)`: 병렬 map (자기 범위 안에서; 결과는 같고, 여러 코어를 쓰는지는 구현이 정한다. open-questions "R7 스케줄러")
- `fan_in(s, rxs)`: 채널 합치기
- 워커 풀, 파이프라인, 액터식 상태 태스크

## 범위 (구조적 동시성, 2026-10-18)

태스크는 **범위 안에서만** 띄운다(동시성 v2, 스펙 `docs/superpowers/specs/2026-10-18-concurrency-v2-r7-design.md` 3절).
범위를 벗어나 사는 태스크가 없으므로 실패는 언제나 그것을 기다리는 코드로 가고, "아무도 확인하지 않은 실패"나 고아 태스크가 생기지 않는다.

```
fn load(id) = scope(fn(s):
  user = spawn(s, () => fetch_user(id))
  orders = spawn(s, () => fetch_orders(id))
  {user: await(user), orders: await(orders)}
;;)
```

- `scope(f)`는 범위를 열고 `f(s)`를 부른다(`s`는 범위 핸들). 본문과 `spawn(s, g)`로 띄운 태스크가 **모두** 끝나야 돌아오고,
  결과는 본문의 반환값이다. 본문이 끝난 뒤 자식을 기다리는 동안에도 자식은 같은 범위에 `spawn`할 수 있다.
  `scope(`가 돌아온 뒤의 범위에 `spawn`하면 E0706.
- **실패**: 자식이 런타임 에러로 죽으면 범위가 실패한다. 다른 자식과 본문을 취소하고, 모두 끝나기를 기다린 뒤, 그 에러(자식의 위치와
  호출 경로 그대로)를 `scope(`에서 다시 낸다. 보고에는 `note: scope opened at <파일:줄>`이 붙고, 동시에 난 다른 실패는
  `note: also failed: …`로 덧붙는다(버리지 않는다). 함수가 `Err` 값을 돌려준 것은 실패가 아니다.
- **취소는 그것이 겨눈 범위가 받는다** (Trio의 cancel scope와 같음). `cancel(s)`로 취소된 범위는 `scope(`에서 `Err({kind: 'cancelled})`를
  돌려주고 호출한 쪽은 이어 간다. 바깥에서 온 취소(바깥 범위, 태스크 취소, `exit`, 교착 보고)는 범위를 지나 계속 되감는다.
  범위가 자식을 기다리는 동안 바깥에서 취소가 와도 자식이 다 끝난 뒤에야 되감는다.
  본문이 이미 값을 돌려준 뒤(자식을 기다리는 동안)에 `cancel(s)`돼도 결과는 `Err({kind: 'cancelled})`다. 범위가 취소됐다는 사실을 언제나 보이게 한다(2026-10-18 결정).
- 본문 자신의 런타임 에러나 `exit`은 그대로 올라간다(자식을 취소하고 기다린 뒤).
- `supervise(f, on_fail)`: 자식의 런타임 에러가 형제·주인에게 번지지 않고 `on_fail(e)`로 간다(`e = {kind: 'error, message}`).
  `await(t)`도 `Err(e)`를 준다. `on_fail`은 실패 순서대로 하나씩 돈다: 처리하는 쪽이 없을 때 실패한 자식의 태스크가 처리기가 되어
  대기열이 빌 때까지 `on_fail`을 부르고, 그동안 범위의 살아 있는 자식으로 남는다. `on_fail`이 런타임 에러를 내면 그 범위가 실패한다.
  범위가 취소되어 처리하지 못한 실패는 표준 에러에 `task failed:`로 보고하고 종료 코드를 1로 한다.
- 오래 사는 배경 작업은 그보다 오래 사는 범위를 인자로 넘겨받아 그 안에서 띄운다(숨은 태스크 종류는 없다).
- 기각: 자유로운 `spawn(f)`과 핸들이 사라질 때의 실패 보고(2026-10-14 규칙). 서버처럼 핸들을 들고만 있는 프로그램은 끝날 때까지
  실패가 보고되지 않았고, "진입 파일이 남은 태스크를 기다린다"·`spawn_awaited` 같은 예외가 따라 붙었다.

## 태스크의 결과와 에러

- `await(t)`는 다음 중 하나를 돌려준다.
  - 정상 종료: 함수의 반환값 그대로 (함수가 `Ok`/`Err`를 돌려줬다면 그것이 결과)
  - 런타임 에러로 죽음(`supervise` 안이나 범위 밖에서 핸들을 기다릴 때): `Err({kind: 'error', message: …})`.
    `scope` 안에서는 범위가 실패해 기다리던 쪽이 취소되므로 이 값을 볼 일이 없다.
  - 취소됨: `Err({kind: 'cancelled})`
  - 시간 초과: `Err({kind: 'timeout})`
- `await(t)!`, `await(t)?`, `await(t) ?? v` 사용 가능.
- `await`를 두 번 하면 같은 결과를 돌려준다 (결과는 저장된다). 닫힌 범위의 태스크를 `await`해도 저장된 결과를 준다.
- **취소된 태스크는 실패가 아니다.** 출력 없이 끝나고 종료 코드에 영향이 없다. `await`하면 `Err({kind: 'cancelled})`.
  - 기각: 즉시 중단 (Go 고루틴 패닉) → 서버에서 요청 하나가 모든 요청을 죽인다. 종료 코드 0 → 실패가 조용히 묻힌다.

## 종료

- 진입 파일이 끝나면 프로그램이 끝난다. 범위 밖에 남은 태스크는 있을 수 없다(서버는 범위 안에서 돈다).
- 즉시 끝내려면 `exit()`. **어느 태스크에서 불려도** 프로그램을 끝낸다: 루트를 취소하고, 모든 태스크가 되감기며 지나는 `with`의
  `release`가 돈 뒤 프로세스가 끝난다 (03). `at_exit`는 없다(L3에서 지움).
- 진입 파일이 **런타임 에러**로 죽으면 남은 태스크를 기다리지 않는다: 취소하고 `release`들이 돈 뒤 종료 코드 1 (03: 에러는 중단).
- 모든 태스크가 서로 기다려 멈추면 "deadlock: all tasks are waiting"(E0702, 종료 코드 1, 되감기의 `release`는 돈다). 런타임이 **직접** 센다:
  살아 있는 태스크 수와 fung 원시 연산(`await` `recv` `send` `swap` `sleep`)에서 막힌 태스크 수, 그중 타이머가 깨울 수를 세고,
  "전부 막혔고 깨어날 것이 없는" 순간 바로 판정한다. 셈은 실행권을 쥔 채로만 바뀌고, 깨운 쪽이 깨우는 순간 막힌 수에서 빼므로
  "이미 깨어날 수 있는데 아직 돌지 못한 태스크"를 막힌 것으로 세는 일이 없다(유예 시간이 필요 없다).
  표준 입력·자식 프로세스 기다림(실행권 밖)은 막힌 것으로 세지 않는다(교착으로 몰지 않는 안전한 쪽). 정지 신호(`stop_signal()`)를 기다리는
  것도 그렇다(신호가 깨운다).
  "살아 있는 태스크"는 fung 코드를 도는 모든 것이다: 진입 파일, `spawn`된 태스크, `fung test`의 테스트 본문, 모듈 초기화. 마지막 실행 태스크가 끝날 때도 다시 판정한다(보낸 쪽이 보내지 않고 끝난 경우가 가장 흔한 교착이다).
- 취소된 태스크가 기다리던 외부 프로세스(`exec`·`sh`)는 끝낸다(L6). 취소(기한, `exit` 포함)가 오면 SIGTERM, 2초 뒤에도 남아 있으면 SIGKILL을 보낸다.
  그동안 온 취소는 출력보다 이긴다. 명령이 끝났어도 그것이 남긴 것(`sleep 30 &`)이 출력을 쥐고 있으면 그것까지 끝낸다.
  - **프로세스 그룹** (사용자 결정, 2026-10-18): 터미널이 없으면(서비스·컨테이너·CI·cron) 명령은 자기 그룹으로 돌고 신호는 그룹 전체에 가서
    `sh -c`가 띄운 손자까지 끝난다. 터미널 앞(fung이 전경 그룹)이면 fung과 같은 그룹이다. 다른 그룹은 터미널을 읽는 순간(sudo·ssh 비밀번호)
    SIGTTIN으로 멈추기 때문이다. 이때 Ctrl-C는 셸처럼 명령에도 바로 가고, 취소의 신호는 명령 하나에만 간다.
- `with`의 `release`는 차단 노드에서 돌아 취소가 닿지 않는다. 그래서 교착 판정은 `release`가 도는 동안이면 앞서 `exit`이나 교착이
  있었어도 다시 판정하고, 멈춘 `release`의 차단 노드를 취소해 끊는다(`vm/deadlock.rs`). 정리 중에 멈춘 프로그램이 영원히 남지 않는다.
- `conc` 모듈의 `pmap`은 자기 범위를 열어 태스크를 띄우므로 `f`의 런타임 에러는 `pmap`의 실패가 된다. `fan_in(s, chs)`는 범위 `s`에 전달 태스크를 띄운다.

## 타임아웃·취소

- **기한은 범위 하나로 준다** (2026-10-18, 동시성 v2 L2): `timeout(d, f)`는 `f()`를 돌려 그 값을 주고, `d`가 지나면 `f` 안의 모든 것(그 안에서 연
  범위의 자식 태스크 포함)을 취소한 뒤 `Err({kind: 'timeout})`을 준다. `await`·`recv`에는 `timeout:`이 없다: `timeout(1s, () => recv(rx))`.
  - 기한은 안쪽으로 물려진다. 실제 기한은 바깥과 안쪽 중 이른 쪽이고, 바깥 기한이 먼저 지나 안쪽이 취소되면 바깥 `timeout`이 `Err`를 준다.
  - `d <= 0`이면 이미 지난 기한이다: `f`는 첫 호출에서 되감기고 결과는 언제나 `Err({kind: 'timeout})`(Trio의 `move_on_after(0)`).
    기다리지 않고 한 번 보는 연산은 없다(open-questions).
  - 본문이 되감기기 전에 값을 돌려줬으면 그 값이다. 본문 자신의 런타임 에러와 `exit`은 그대로 올라간다.
  - 연산마다의 기한을 지운 이유: 함수 안에서 여러 연산을 거치는 "이 요청 전체를 2초 안에"를 표현할 수 없고, 겹치지도 않는다.
  - 구현: 기한은 취소 노드에 실린다(`vm/deadline.rs`). 막힌 태스크는 기한까지만 자고(채널·`sleep`·`await`·소켓·표준 입력),
    계산하는 태스크는 차례를 넘길 때 시계를 본다. 처음 본 쪽이 기한의 주인 노드를 만료시킨다. 기한이 있는 기다림은 교착 집계에서 타이머가
    깨울 것으로 센다. 타이머 스레드는 없다.
  - **알려진 한계**: 실행권 밖에서 운영체제를 기다리는 일 중 소켓·표준 입력·외부 명령이 아닌 것(파일, 정규식 컴파일)은 기한에 끊기지 않고
    끝날 때까지 기한이 밀린다. 돌아오는 즉시 끊기므로 그 뒤의 일은 돌지 않는다(스레드 풀은 R단계). 외부 명령은 L6부터 끝낸다(아래).
- `cancel(t)`·`cancel(s)` 지원.
- **취소는 자식 태스크에 전파된다** (Go `context` 트리와 같음). 범위의 노드는 연 태스크의 노드 아래에, 자식의 노드는 범위의 노드 아래에 달린다.
- 취소는 협조적이다: VM이 함수 호출·반복 지점과 막히는 연산(`sleep`, `recv`, `send`, `await`, I/O)에서 확인하고,
  그 태스크를 런타임 에러처럼 끝낸다. 감싸는 함수의 정리는 실행되지 않는다 (03의 한계와 같음).
- 내부적으로 취소 노드 트리(`CancelNode`)를 쓴다. 막힌 소켓 기다림은 노드의 깨우개 파이프로 풀린다(`vm/watch.rs`).

## 기간(duration) 리터럴

```
sleep(500ms)
timeout(30s, () => await(t))
ttl = 1h30m
```

- 단위: `ms`, `s`, `m`, `h`. 글자 수준 규칙은 01, 값으로서의 성질은 02.

## 에러 번호

E0701 `task cancelled` (취소된 태스크의 내부 되감기용, 사용자에게 보이지 않음), E0702 `deadlock: all tasks are waiting`,
E0705 `channel sent into itself`, E0706 `spawn into a closed scope`, E0707 `` `…` has an effect, which a swap's function must not have ``,
E0708 `an atom cannot hold …`. (E0703·E0704는 0.1의 atom·3b의 에이전트 재진입 에러라 쓰지 않는다.)

## fung으로 쓰는 것의 자리

`conc` 모듈(`extras/conc.fung`, `import conc`; 06): `fan_in(s, chs)`, `pmap(xs, f, limit = 0)`(0은 제한 없음), `retry(f, times = 3, delay = 0ms)`(`f`가 `Err`를 돌려주면
`delay`만큼 쉬고 다시, 마지막 `Err` 반환).

## 출력과 공유 상태

- `print` 한 번은 한 번의 write이고 출력 writer는 뮤텍스로 감싼다: 태스크 둘이 동시에 찍어도 줄이 섞이지 않는다.
- 모듈 초기화는 모듈당 뮤텍스로 **한 번만** 일어난다 (두 태스크가 같은 모듈을 처음 import해도 안전).
- REPL에서 태스크가 도는 중에 전역을 재정의하는 것은 정의하지 않는다 (08).

## 구현 메모

- VM 상태(스택, 호출 프레임)는 태스크별로 분리한다. 모듈·상수는 불변이라 공유한다.
- Rust로 만든 내장 함수(`map` 등)가 사용자 람다를 다시 부를 때는 같은 태스크의 VM을 쓴다.
- GUI를 위해 운영체제 메인 스레드를 비워둔다. fung 코드는 처음부터 별도 스레드(큰 스택, `fung_vm::stack`)에서 실행한다.
- 웹서버는 요청마다 런타임이 태스크를 띄운다. 핸들러는 평범한 함수.
- 범위는 `crates/fung-vm/src/vm/scope.rs`: 범위마다 취소 노드 하나, 살아 있는 자식 수, 첫 실패와 덧붙일 실패. 자식 핸들은 쥐지 않으므로 자식이 범위 핸들을 붙잡아도 `Rc` 순환이 아니다. 본문이 끝난 뒤의 기다림은 새 루트 노드 아래에서 해서 바깥 취소로 끊기지 않는다(교착 집계에는 든다). 노트 `docs/notes/R7-language.md`.

## 공유 상태: atom (2026-10-18, 동시성 v2 L5)

- `atom(v)`은 불변 값 하나를 가리키는 칸이다. `deref(a)`는 기다리지 않고 지금 값을 준다(값이 불변이라 읽는 쪽은 언제나 온전한 스냅숏을 본다).
  `reset(a, v)`은 그냥 바꾸고 새 값을 준다. 출력은 `<atom>`, `type_of`는 `'atom`, 타입 표기는 `atom`, `==`는 같은 칸인지.
- `swap(a, f)`는 **비교 후 교체**다: 옛 값과 판 번호를 읽고 `f(옛 값)`을 계산한 뒤, 판이 그대로면 바꾸고 아니면 새 값으로 `f`를 다시 돌린다.
  `f` 도중에 차례가 넘어가 다른 태스크가 바꿔도 갱신이 사라지지 않고, 여러 코어로 가도 의미가 같다. `f`가 실패하면 상태는 그대로다.
- **`f`는 순수 계산만 한다** (런타임이 강제): `f`를 도는 동안 효과 있는 내장 함수를 부르면 E0707. 효과 표는 `vm/atom.rs` 한 곳에 있다:
  출력(`print`·`eprint`·`dbg`), 표준 입력, `exit`, 동시성(`spawn`·`await`·`cancel`·`send`·`recv`·`close`·`sleep`), 다른 atom의 `swap`·`reset`,
  `_native.fs`·`_native.net`·`_native.conc` 전부, 외부 프로세스(`exec`·`sh`). 채널을 `for`·`map`·`fold` 등으로 도는 것도 받기라 E0707(`recv`)이다.
  읽기(`deref`, 시간, 환경 변수)와 순수 계산은 된다.
  기준은 "`f`가 여러 번 돌아도 바깥에서 보이는 차이는 걸린 시간뿐"이다. 0.1과 3b의 재진입 에러(E0703·E0704)는 이 규칙에 들어간다.
- **atom 안에는 변하는 것을 넣지 못한다** (E0708): atom, 채널, 태스크·범위 핸들, 파일, 소켓, 그리고 이것들을 품은 리스트·맵·튜플·태그·클로저.
  그래서 atom을 거치는 `Rc` 순환이 원리상 생기지 않는다. 검사는 O(1)이다: 영속 벡터의 노드가 "변하는 것을 품었는지"를 기억해서, 바뀐 뒤에는
  복사된 경로만 다시 본다(`value/pvec.rs`). 모듈 최상위의 atom은 된다(모듈 참조는 표시를 전파하지 않는다. 모듈은 프로그램 끝까지 살아 순환이 누수를 키우지 않는다).
- 입출력이 필요한 갱신(토큰 갱신)은 갱신 태스크 하나가 `reset`하고 나머지는 `deref`하는 모양으로 쓴다. 구독자 채널 목록처럼 변하는 것을 모아 둬야 하면
  그 목록을 쥔 태스크와 채널(액터 패턴)로 짠다.
- 기각(3b, 2026-10-15): 상태를 쥔 배경 태스크에 편지를 보내는 `agent`. 읽기 한 번이 편지 왕복이고, 배경 태스크 종류·E0704·`swap` 안의 `deref` 같은 특례가 따랐다.
  0.1의 atom을 그때 지운 이유(순환, 재진입)는 위의 두 규칙으로 막는다. 경위는 `docs/notes/R7-language.md` L5.
- **배경 태스크는 없다** (L6에서 지움). `http.serve`도 자기 범위 안에서 돈다(아래 "정지 요청"). 모든 태스크는 범위에 속하고, 프로그램이 끝날 때 남는 태스크는 없다.
- **채널에 그 채널의 끝을 보내면 E0705 (3b, L4).** 어느 끝이든, 리스트·클로저 같은 값 안에 있어도 해당한다. 참조 계수로 메모리를 회수하는 구현에서 순환을 막기 위해서다.
  버퍼가 자기 보내는 끝을 쥐면 영원히 닫히지 않고, 자기 받는 끝을 쥐면 영원히 버려지지 않는다. 다른 채널의 끝을 보내는 것(응답 채널)은 된다.
  `send`는 변하는 것을 품지 않은 값을 훑지 않는다(큰 리스트·맵은 아래 atom 절의 O(1) 기억, 작은 것은 공유된 부분을 한 번씩). 품은 값만 그 크기에 비례해 훑는다.
  다른 채널의 버퍼·모듈·태스크 결과를 거치는 순환은 잡지 않는다.
  설명은 `docs/notes/R3b-agent.md`, 남은 한계는 open-questions "Rust 구현: 정한 것과 남은 일"의 알려진 한계.
- **런타임 (2026-10-15)**: 태스크마다 운영체제 스레드 하나, fung 코드는 실행권 잠금을 쥔 스레드만 돌린다(Python GIL·OCaml 4 모델).
  막히는 곳은 `crates/fung-vm/src/vm/block.rs`의 `block` 하나로 모았다. 설명은 `docs/notes/R3a-runtime.md`.
- 목표는 Erlang VM식 런타임이다: 그린 스레드, 태스크마다 힙을 따로 두고 경계에서만 값을 복사(불변 값이라 프로그램은 차이를 볼 수 없다).
  open-questions "Rust 구현: 정한 것과 남은 일"의 R7 스케줄러.
