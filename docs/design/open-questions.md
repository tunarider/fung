# 미결 사항

구현 중 반드시 부딪히지만 아직 정하지 않은 세부 사항을 여기에 적는다.
구현하다가 해당 지점에 닿으면 **추천안과 함께 사용자에게 묻고** 결정 후 해당 섹션 문서를 갱신한다.

2026-10-12~13의 전체 재점검으로 이전 목록은 모두 해당 섹션에 확정되었다.
(람다 표기·`_` 범위·숫자·문자열·식별자 → 01, 맵 사본·튜플 인덱스·`?`와 nil·`Err` 내용·순회 대상·함수 `==` → 02,
`defer` → 03, 여러 채널 기다리기 → 05, `print`·`args`·`exit`·표준 입력 → 06, 0으로 나누기 → 07.)

## 알파 이후

- [x] 프로젝트 extras에서 `_native.*` import 허용 여부 → **허용하지 않는다** (06, 2026-10-14). 측정해 보니 네이티브 원시 기능 대부분이
  공개 모듈에 같은 함수 값으로 이미 나와 있어(비용 없음) 열어도 얻는 성능이 없고, 숨김 층을 바꿀 자유만 잃는다(Node의
  `process.binding` 폐기 사례). 사용자가 네이티브 코드를 붙이는 확장도 열지 않는다. 필요한 원시 기능은 fung 본체에 추가한다.
- [x] 불변 컬렉션의 누적 비용 (2026-10-14 측정): `fold`로 `put(acc, k, v)`를 쌓으면 맵 전체를 매번 복사해 n²이다(2만 개에 18.5초).
  `acc + [x]`(2만 개 0.85초), `acc + s`(0.31초)도 같은 성질. 후보: 영속 자료구조(맵 HAMT·리스트 벡터 트라이), 소유자 확인 후 제자리
  덧붙이기, 일괄 구성 원시(`from_pairs`). → **영속 자료구조로 해결** (M10, 2026-10-14). 맵·리스트 누적과 꼬리 재귀는
  선형(2만 개 13~61ms). 문자열 `acc + s`는 그대로 n²이고, 리스트에 모아 `join`하라고 매뉴얼에 안내한다.

## 태스크 실패 후속 (2026-10-14 보류 → 2026-10-18 닫음)

동시성 v2 L1(구조적 동시성)으로 세 항목 모두 닫았다. 태스크는 범위 안에서만 띄우고, 실패는 범위를 연 코드로 가거나(`scope`)

- [x] 전역 처리기 `on_task_failure` → 필요 없음(꺼내지 않은 실패 보고 자체를 지움).

## 성능 (2026-10-14 측정)

같은 기계에서 4가지 작업(`fib(30)`, 300만 번 산술 반복, 문자열 50만 개 잇기, 맵 20만 개)을 10개 언어로 쟀다. fung 0.1은
기하평균으로 8위(컴파일 언어 셋·Node·Perl·Python·Ruby 다음, Tcl·awk 앞), 호출·산술은 Python의 2~4배 느리고 문자열은
Python과 같으며 시작 시간(6ms)은 Python(22ms)보다 빠르다. fung 쪽 벤치마크는 `bench/`에 둔다.

- [x] 1단계: 산술 디스패치의 맵 조회(모든 명령에서 먼저 수행), 호출마다 다시 만드는 매개변수 표, `fold`·`map` 등이 범위를 리스트로 펼치는 것. → 완료 (2026-10-14)
- [x] 2단계: fung 함수 호출의 할당 0 빠른 길(위치 인자·개수 일치 시 인자를 VM 스택의 프레임으로 바로), 내장 함수가 람다를 부를 때 인자 버퍼 재사용. → 완료 (2026-10-14)
  - 결과(`bench/`, 5회 중 최고): fib 0.513→0.205초(2.5배), loop 0.563→0.241초(2.3배, Python 0.276초보다 빠름), str 0.065→0.053초,
    map 0.492→0.458초(맵은 영속 구조 비용이라 거의 그대로). 남은 시간은 명령 해석 루프 자체(3단계).
- [x] 3단계: 값 표현 변경(정수를 상자에 담지 않기), 정수 전용 명령, 묶음 명령. → 값 표현은 `enum`(정수·실수를 상자 없이 칸에)으로 해결(아래 "Rust 구현"),

## Rust 구현: 정한 것과 남은 일

fung은 Rust로 구현한다. 문법과 사용자에게 보이는 동작이 핵심이고 내부는 바뀌어도 된다. C 구현은 기각: GC·동시성·TLS를 직접 만들어야 하고,
`http.serve`처럼 외부 입력을 파싱하는 코드에서 메모리 안전을 잃는다. 구현 독립으로 이어지는 것: 설계 문서, 에러 번호, 매뉴얼, `extras/`의 fung 코드,
골든 테스트(`tests/lang`), 기대 출력 파일, `bench/`, 릴리스 흐름.
이식의 기록(단계별 결정, 비교, 해결된 항목)은 `docs/notes/R-port-record.md`, 단계별 설명은 `docs/notes/R<n>-*.md`.

### 정한 것

- [x] 동시성과 메모리 모델 → **태스크마다 운영체제 스레드 하나 + 실행권 잠금, 값은 참조 계수.** (3a, 2026-10-15; 노트 `docs/notes/R3a-runtime.md`)
  - fung 코드는 실행권을 쥔 스레드만 돌린다(Python GIL·OCaml 4 모델). 막히는 곳은 `crates/fung-vm/src/vm/block.rs`의 `block`과 소켓의 `vm/watch.rs`(`Watch`)로 모아,
    그린 스레드(R7)로 갈아끼울 자리를 남겼다. 비용: 태스크 생성 약 55 µs, 채널 주고받기 약 2.5 µs(태스크 하나일 때는 비용 없음; 측정은 R3a 노트 9절).
  - 값은 `enum`(종류 태그 + 값 칸, 16바이트). 정수·실수는 상자 없이 칸에 바로 들어간다. 긴 구조의 연쇄 해제는 재귀가 아니라 반복으로 한다.
    태스크 안은 원자적 연산 없는 `Rc`이고, 참조가 하나면 제자리 수정(Roc식, `Rc::make_mut`)도 가능하다.
  - 불변 값이라 태스크 사이의 "공유"와 "복사"를 프로그램이 구분할 수 없다. 여러 코어로 갈 때는 태스크마다 힙을 따로 두고 경계(`spawn`이 붙잡은 값,
    채널로 보낸 값, `await` 결과)에서만 복사한다(Erlang식; 큰 문자열만 공유하는 refc binary). 실행권 아래에서는 값 공유가 안전하므로 그때까지 미룬다.
  - 런타임은 `World`(공유, 실행권 아래)와 `Task`(태스크별)로 나뉘고, 내장 함수의 기본값은 `Lit`, 내장 함수 표는 프로세스에 하나(`OnceLock`)다.
- [x] `atom` → **없다. 공유되는 변경 칸 대신 `agent`** (3b, 2026-10-15; 노트 `docs/notes/R3b-agent.md`). **동시성 v2 L5(2026-10-18)에서 되돌렸다**: 엄격한 `atom`(05 "공유 상태: atom"). 아래는 3b 당시의 기록이다. 원칙 5·6에 맞추고 순환의 주된 원인을 없앤다.
  상태는 그 상태를 쥔 태스크가 들고 다른 태스크는 편지를 보낸다(Erlang·Elixir `Agent`). `agent(v)`·`swap(a, f)`·`deref(a)`, fung 코드 `extras/agent.fung`.
  - 에이전트는 배경 태스크다(프로그램 끝을 막지 않고 교착 집계에 따로 들며 되감기가 끝난 뒤에 취소). 핸들은 닫개: 마지막 사본이 사라지면 요청 채널을 닫아 에이전트가 끝난다.
  - `f`는 에이전트의 태스크에서 받은 순서대로 하나씩 돈다. 실패하면 상태는 그대로 두고 같은 에러를 부른 쪽 `swap(`에서 낸다. 자기 `f` 안의 같은 에이전트 `swap`은 E0704.
    `f`는 부른 태스크를 따른다: 부른 태스크가 취소되면 그 `f`도 취소되고 갱신은 반영되지 않는다(`CancelNode::also_under`).
  - 대가: 읽기·쓰기가 편지 왕복이라 자물쇠보다 느리다(`swap` 한 번 약 7 µs). 출력은 `<agent>`(값을 보이려면 에이전트에 물어야 해서).
- [x] 채널의 순환 → **유지하고, 채널에 그 채널 자신을 보내면 E0705** `channel sent into itself`(3b). `send(ch, v)`가 `v`를 재귀 없이 깊이 훑는다(공유된 부분은 한 번만, 에이전트 내부 요청은 검사 안 함).
  일반 채널은 보내는 쪽과 받는 쪽이 같은 값이라 자동으로 닫지 않는다(`close`로 닫음). 훑지 않는 곳과 비용은 아래 "알려진 한계".
- [x] 라이브러리 구조 → **언어 핵심은 최소, 공식 라이브러리는 패키지 구조로 만들되 패키지 관리자가 생길 때까지 바이너리에 함께 넣는다.**
  런타임은 파일·프로세스·TCP 소켓·TLS·시간·정규식 같은 네이티브 원시 기능만 주고, HTTP 프로토콜·JSON·`cli` 등은 fung 라이브러리로 쓴다.
  - 내장 함수 배치 → **prelude에는 확실한 것만** (2026-10-17). 나중에 prelude에 더하는 것은 W0103 경고뿐이라 안전하고 빼는 것은 호환성 깨짐이다.
    정책(동시 실행 수, 재시도 횟수·간격)을 품은 `fan_in`·`pmap`·`retry`는 `conc` 모듈. `until`·`iterate`(`while`이 없는 언어의 반복), `exec`·`sh`(셸을 대신하는 언어의 핵심)는 prelude.

  - 구현 언어 지침(2026-10-15): "빠지면 다른 것을 만들기 힘들어지는 것"이 핵심이다. fung으로 쓸 수 없는 것(OS·외부 세계) → Rust.

    이어 가기 프레임으로 부른다(R2, 2026-10-18: 람다를 직접 부르지 않고 VM에 부탁하므로 태스크를 멈출 수 있고 Rust 스택을 쓰지 않는다. `docs/notes/R7-scheduler.md`). 핵심이 아닌 조합·프로토콜(`take`·`retry`·`pmap`·HTTP) → fung.

- [x] **언어·VM 검토 (2026-10-20)**: 고칠 수 있는 문제를 `docs/plans/2026-10-20-language-vm-review.md`에 모았고 모두 처리했다(2026-10-20).
  결정 항목 L1~L11·T1~T4·V8·V10은 사용자 결정(뒤의 것들은 "추천대로" 지시), 앞단 F1~F12·VM V1~V9·동시성 C1~C7·성능 P1~P7·문서 D1~D9.
  P2(앞에 붙이기)와 P7의 맵·튜플은 아래 "알려진 한계". 남긴 의심은 그 문서의 12절.
- [ ] **아무도 `await`하지 않은 태스크의 `Err` 결과 (L1에서 보류, 사용자 결정 2026-10-20)**: `scope(s => spawn(s, fn(): Err("x") ;;))`는 조용히 지나간다.
  버려지는 Err(02)와 같은 "버림"이지만 "아무도 기다리지 않았다"를 범위가 끝날 때 판단해야 하고, `http.serve`처럼 핸들러 결과를 원래 버리는 구조가 있어 따로 설계한다.
- [ ] **정지 신호를 기다리기만 하는 코드 (L1 뒤, 사용자 결정 2026-10-20: 써 보며 판단)**: 정지 요청은 끝을 닫아 알리므로 `recv(stop)`은 늘 `Err({kind: 'closed})`이고,
  문장으로 쓰면 E0606이라 `_ = recv(stop)`으로 쓴다. 어색함이 쌓이면 기다리기 전용 내장 함수(예: `wait_stop()`)를 검토한다.
- [ ] **블록 본문 함수의 마지막 `if` (L3 뒤의 한계)**: `fn f(x): if x: 1 ;; ;;`는 값 자리가 아니라 E0223이 아니다. 그 함수를 값 자리에서 부르면
  (`y = f(false)`) 여전히 조용히 `nil`이다. 부수효과 함수가 `if`로 끝나는 것이 흔해 뺐다(사용자 결정 2026-10-20). 쓰는 패턴이 드러나면 다시 본다.

### 알려진 한계

고치기로 정하지 않은 동작상 한계. 고치면 해당 설계 문서의 규칙과 이 목록을 함께 고친다. 배경은 단계 노트(`docs/notes/R<n>-*.md`)와 `docs/notes/R-port-record.md`.

- 컬렉션 (2026-10-20 검토 P2·P7): 앞에 붙이기 `[x] + acc`는 매번 전체를 복사해 누적하면 n²다(매뉴얼의 안내대로 뒤에 붙이고 `reverse`). 고치려면 영속 벡터에 앞쪽 버퍼를 두거나 RRB 트리로 바꿔야 한다.
  상수 접기(P7)는 리스트 리터럴만 한다. 맵·튜플은 상수 종류가 새로 필요하고, 빈 리스트를 품은 리스트는 빈 리스트 상수가 `args`로 읽혀 접지 않는다.
- 태스크 (05; R3a·R3b 노트)
  - (닫힘, R1b 2026-10-19) 태스크마다 운영체제 스레드 하나라 스레드 한도가 천장이던 것: 이제 실행 스레드 하나가 모든 태스크를 돈다. 기다리는 태스크 2만 개가 돈다(`bench/wait.fung`).
    파일·이름 조회·정규식 컴파일은 풀(최대 64)에서, 소켓·TLS는 이벤트 루프에서 기다린다(R4a, 스레드 없음). 외부 명령도 루프에서 기다린다(R4b).
    끝나지 않는 파일 읽기(FIFO 등)는 기한에 버려져도 풀 스레드 하나를 붙잡고, 그런 것이 64개면 다른 파일 일은 줄에서 기다린다(기한·취소에는 끊긴다).
  - 형제 태스크가 시작하는 순서는 보장되지 않는다(실행 스레드 하나가 대기열 순서로 돌지만, 띄운 쪽이 차례를 넘기는 시점과 깨어나는 순서에 달림). 끝에 남은 꺼내지 않은 실패도 실패한 순서로 보고된다.
    순서에 기대는 프로그램과 `test` 블록은 경쟁 상태다.
  - 띄운 태스크는 띄운 쪽이 차례를 넘기거나(호출 1,000번, R1b) 주차하기 전에는 돌지 못한다. 곧바로 끝나는 태스크가 띄운 자식은 한 번도 돌지 못하고 부모와 함께 취소된다.
  - (닫힘, L6) 자식 프로세스 기다림: 취소되면 SIGTERM, 2초 뒤 SIGKILL(터미널이 없으면 프로세스 그룹 전체에).
  - Rust로 쓴 내장 함수 하나(큰 `json.parse`, 콜백 없는 큰 정렬)는 중간에 차례를 넘기지 않는다. 약 6 MB JSON 파싱 옆의 가벼운 HTTP 요청은 파싱 시간(약 72 ms)만큼 늦다(R6 측정, 스펙 10.4는 기록만).
  - 공정성(R6, 순서를 보장하지 않을 뿐 굶기지는 않음): 오래된 깨움이 태스크에 차례를 한 번 더 줄 수 있다. 연결의 차례 줄은 놓을 때 기다리는 쪽을 모두 깨워 다시 다투게 한다.
  - 명령 출력 읽기에 한 번 보기당 한도가 없다. 출력이 아주 빠른 명령 옆의 태스크가 늦을 수 있다(잰 바로는 R4a와 비슷하고, 큰 출력의 문자열 만들기가 더 큼).
  - pidfd가 없는 Linux(5.3 전)에서는 명령마다 풀 스레드 하나가 끝을 기다린다. 64개를 넘는 긴 명령은 다른 파일 일을 줄에 세운다.
  - REPL: 한 묶음에 Ctrl-C 둘이 오면 `release`가 시작하기도 전에 버린다(알림은 "정리가 끝나지 않음"). 버릴 때 태스크를 먼저 버리고 루프 등록을 뒤에 해제한다(닫힌 fd 번호에 해제를 부름; 해는 없음).
  - `fung test`에서 파일 N의 런타임(과 풀)은 파일 N+1이 신호 처리기를 바꿀 때 사라진다(쌓이지는 않음).
  - 시험 도우미: `release_fifo`의 막히는 열기는 줄에서 버려진 일이면 떨어진 시험 스레드를 남긴다.
  - 끝없이 도는 태스크(막히지 않는 것)는 다른 태스크들 사이의 진짜 교착을 가린다. 배경 태스크는 L6에서 없어졌다.
  - 회수되지 않는 순환(`Rc`): 자기 핸들을 결과로 담은 태스크, 서로의 끝을 버퍼에 담은 채 버려진 두 채널(그래서 둘 다 닫히지 않는다). atom을 거치는 순환은 E0708이 막는다(L5).
  - E0705가 훑지 않는 곳: 다른 채널의 버퍼(두 채널 순환), 모듈·클로저의 전역(런타임 끝에 `World::release_values`가 끊음), 태스크 핸들.
  - 변하는 것(채널 끝, 태스크 등)을 품은 값의 `send` 비용은 그 값의 크기에 비례한다. 품지 않은 값은 훑지 않는다: 큰 리스트·맵은 노드의 기억으로 O(1), 작은 것은 공유된 부분을 한 번씩 훑는다(L4). 같은 영속 벡터를 공유하는 여러 보기는 보기마다 다시 훑는다(일부러 만든 입력에서는 지수적).
  - 꼬리 위치 호출: fung으로 쓴 라이브러리 함수(`http.*`, `fs.with_open` 등)를 꼬리 위치에서 부르면 그 프레임이 사라져, 에러가 부른 쪽의 부른 쪽 위치를 가리키고
    경로에 `… (1 tail calls elided)`가 보인다. 꼬리 호출마다 호출 자리를 적어야 해서(모든 꼬리 호출에 저장 하나) 하지 않았다.
- 메모리·스택 (R1·R4b·R6a 노트)
  - 값 출력(`value/format.rs`, `print`·`str`)은 재귀라 큰 스택에 기댄다. 10,000겹 JSON 값과 백만 겹 리스트(진입 스레드)는 출력되지만 5백만 겹 리스트를 `str`하면 디버그 진입 스레드에서 스택이 넘쳐 죽는다(종료 코드 134).
  - 진입 스레드 4 GiB·태스크 1 GiB 스택 예약이 거부되는 호스트에서는 64 MiB까지 줄여 다시 시도하므로(`fung_vm::stack`), 아주 깊은 네이티브 재귀(`map`·`fold`의 깊은 중첩, 깊은 값 출력)의 한도가 낮다.
    디버그 빌드는 약 80만 단계 체인에서 넘친다(릴리스는 200만까지).
- 문자열과 바이트 (02·06; R2·R4a 노트)
  - 문자열은 UTF-8이라 바이트를 그대로 품지 않는다. 비UTF-8 프로세스 출력·환경 변수 값·파일 내용(`fs.read`·`read_lines`·`read_line`)·HTTP 바이너리 본문·경로·시간대 약어는
    잘못된 부분마다 U+FFFD 하나로 바뀐다(원래 바이트 보존 없음). 비UTF-8 디렉터리 아래 모듈 경로도 U+FFFD로 표시된다. 문자열을 바이트 기반으로 바꿀 때 다시 본다.
  - `exec`·`sh`의 `env`는 물려받은 환경에 더해지고, 자식이 보는 환경은 이름순으로 정렬된다. 이름에 `=`가 든 키(`{"HOME=z": …}`)를 주면 원래 `HOME`이 남는다.
- 파일 (06 `fs`; R4a 노트)
  - `close(2)`의 에러를 보고하지 않는다(`fs.close`·`write`·`append`·`copy`, 버린 핸들의 버퍼 비우기). NFS 같은 파일 시스템에서만 드러난다.
  - 마지막 사본이 사라질 때의 `close(2)`는 실행권을 쥔 채 돈다(`Drop`). NFS 같은 곳에서 멈추면 그동안 다른 태스크도 멈춘다. 고친다면 배경 닫기 스레드에 넘긴다.
- 시간 (06 `time`; R4b 노트)
  - `now()`에 단조 시계가 없다. 두 `now()` 사이에 시스템 시각이 바뀌면(NTP 보정 등) 경과 시간 재기가 틀린다.
- 정규식 (06; R4c 노트)
  - 컴파일된 크기가 128 MiB를 넘는 패턴(`[a-z]{1000}` 수천 번, `\pL`을 약 5,000번 넘게 반복)은 E0515 `pattern too large`이고, 실패까지 시간이 걸린다(`\pL` × 20,000이 릴리스 약 3초).
    컴파일은 실행권 밖에서 돌아 그동안 다른 태스크는 계속 돈다. 같은 패턴을 동시에 놓친 두 태스크는 각자 컴파일한다.
- 소켓·TLS (06; R4d 노트)
  - `set_deadline`은 이미 막힌 호출에 닿지 않는다(막힌 기다림은 시작할 때의 기한을 들고 있고, 새 기한은 다음 기다림부터).
  - 이름 붙은 포트(`:http`)를 찾지 않는다(``invalid port `http` ``). 주소 계열을 경주시키지 않는다(Happy Eyeballs 없음): 주소들을 한 기한 안에서 차례로 시도하고 첫 에러를 보고한다.
  - 한 연결에 읽는 쪽 하나, 쓰는 쪽 하나. 두 번째로 기다리는 쪽은 잠금에서 기다리며 취소되지 않는다.
  - 이름 조회(`getaddrinfo`)는 끊을 수 없어 풀(최대 64)에서 돈다. 취소되거나 시간이 다 된 `connect`는 바로 돌아오지만 그 풀 스레드는 해석기가 답할 때까지 붙잡힌다.
  - TLS: close_notify를 기다리지 않고 보낸다(소켓 버퍼가 차 있으면 버려짐). ALPN을 보내지 않는다. `SSL_CERT_FILE`·`SSL_CERT_DIR`이 하나라도 있으면 변수의 위치만 읽는다.
    정적 바이너리도 실행 중에 시스템 CA 파일을 읽으므로 CA 인증서가 없는 `scratch` 컨테이너에서는 https가 실패한다.
- HTTP (06 "HTTP"; R4d 노트)
  - 응답 본문 상한 64 MiB(넘으면 `Err 'network`; 요청별 `max_body` 같은 옵션은 나중). 연결 재사용(keep-alive)·파이프라이닝, HTTP/2, 압축 없음.
    서버는 연결마다 요청 하나라 HTTP/1.1 응답에 늘 `Connection: close`이고 HTTP/1.0 keep-alive에 `Connection: keep-alive`로 답하지 않는다. 101 응답은 본문 없음(연결을 넘겨주지 않음).
  - SOCKS 프록시(`socks5://`·`socks5h://`)와 `https://` 프록시 너머의 https는 지원하지 않는다. 알 수 없는 스킴의 프록시 URL에 포트가 없으면 80으로 연결하고,
    `NO_PROXY`의 공백 다듬기는 ASCII 공백(공백·탭·CR·LF)만 본다.
  - URL: IDN·퓨니코드 없음(`NO_PROXY`·같은 사이트 판정 포함), 호스트의 `%XX`(0x80 이상)를 풀지 않음, 괄호 IPv6는 "IPv4인가 아닌가"만 검사(잘못된 IPv6는 연결에서 다른 문구로 실패),
    에러 URL의 조각(fragment)은 다시 이스케이프하지 않음, 사용자 정보의 비ASCII는 가린 에러 URL에서 `%C3%A9`처럼 보임.
  - 서버가 일찍 닫아 쓰기가 실패하면 답을 읽을 수 있어도 쓰기 에러를 보고한다. `CONNECT` 답은 상태 줄과 헤더 줄만 검사하고, 프록시 요청의 `Host` 헤더 검사가 없다.
  - 인자 에러의 호출 경로에 `extras/http.fung` 프레임이 보인다(`serve`의 `ready` 에러에는 `_ready_check`·`serve` 두 프레임). 06은 extras 프레임을 보이게 둔다.
  - 비용: 헤더를 fung으로 해석하므로 접히거나 끝없는 머리 40만 줄(10 MiB 예산)에 클라이언트 릴리스 약 1초, 꽉 찬 요청 머리(1 MiB, 값 500개) 하나에 서버 요청마다 약 0.1~0.25초,
    1바이트 청크 10만 개에 약 0.6초.
  - 서버: 핸들러가 넣은 틀 헤더는 쓴 그대로(`Content-Length`는 자동 값을 끄지만 본문은 다 씀, `Transfer-Encoding`은 해석하지 않음, 101 전환의 `Connection: upgrade` 세부 없음).
    이름이 대소문자만 다른 응답 헤더는 뒤의 것. 431 뒤에는 반쯤 닫기 없이 읽기만 한다. `PRI * HTTP/2.0`, `CONNECT`의 2xx 답, 요청 컨텍스트를 취소하는 배경 읽기는 없다.
  - (닫힘, R4a 2026-10-19) 서버: 본문 중간에 멈춘 클라이언트가 소켓 기다림의 스레드 하나를 붙잡던 것. 이제 소켓은 이벤트 루프에서 기다린다. 연결 태스크는 더는 실패하지 않는다.
  - 서버: macOS는 받기 전 대기 줄(`kern.ipc.somaxconn`, 기본 128)이 차면 새 연결을 끊는다(`connection reset by peer`). 한꺼번에 128개 넘게 몰려오는 접속은 그만큼 실패한다. fung은 시스템이 허락하는 가장 긴 줄을 요청한다. Linux의 기본값은 4096.
- 도구 (08; R5 노트)
  - REPL 세션의 `SourceMap`은 입력마다 파일 하나씩 계속 커지고, 런타임이 입력마다 글을 한 벌 더 쥔다(`Runtime::add_session_files`; `Arc<str>`로 나누면 없어짐).
  - 표시 너비는 글자 단위 UAX #11이라 ZWJ로 이은 이모지(각 글자 2칸)와 VS16(U+FE0F, 0칸) 붙은 글자는 터미널과 다를 수 있다.
  - 프롬프트에서 밖으로부터 SIGTERM·SIGHUP을 받거나 출력이 EPIPE로 죽으면 터미널이 raw로 남는다(신호 처리기 없음; 고친다면 `tcsetattr`로 되돌리는 처리기 약 40줄).
  - 포매터: 함수 머리가 여러 줄이면(`fn f(h:` 다음 줄 `int):`) 몸통을 4칸, `;;`를 2칸에 둔다. 정렬(`align_runs`)이 묶음의 첫 줄마다 다시 시작해 긴 묶음에서 O(n²).
    제자리 `fmt`가 원자적이지 않다(임시 파일 + 이름 바꾸기가 아님, 쓰다 죽으면 파일이 잘림).
