### 문자열

- `"..."`: `${}` 보간, 이스케이프 지원. `` `...` ``: 원시 문자열. (01. 문법 참고)
- **문자열은 바이트 열이고, 글자 연산이 그것을 UTF-8로 읽는다**(L4, 2026-11-07). 바깥 값(파일·명령 출력·`env`·`args`·표준 입력·소켓·파일 이름)은
  UTF-8이 아니어도 바이트 그대로 들어오고 그대로 나간다. 그래서 읽고 쓰기만 하는 스크립트가 데이터를 바꾸지 않는다. 기각: 글과 바이트를 타입으로 나누기
  (바깥을 읽는 함수가 두 벌, 그래도 파일 이름·`env`·`args`는 답이 없다), 잘못된 바이트를 서로게이트로 옮겨 두기(Python surrogateescape, 실패를 뒤로 미룬다).
- 길이·인덱싱은 **글자(룬) 단위**. `len("참치") == 2`. UTF-8에 속하지 않는 바이트는 **그 바이트 하나가 한 글자**다(그 글자는 바이트 하나짜리 문자열).
  그래서 글자로 자르고 다시 이어도 바이트가 보존된다(`glob`도 같은 규칙).
- `s[0]`은 글자 하나짜리 **문자열**이다. 별도 문자 타입은 없다.
- 룬 단위라 비ASCII 문자열의 `s[i]`는 바이트 자리를 걸어서 찾는다(ASCII 문자열은 O(1): 만들 때 ASCII인지 재 둔다). 마지막으로 찾은 자리에서 앞뒤로, 끝이 가까우면 끝에서 걷고, 멀리 뒤로 가는 접근이 처음 오면 64글자마다의 바이트 자리 표를 한 번 만들어 그 뒤로는 64글자 안쪽만 걷는다(VA68, 2026-11-14). 처음 한 번 읽는 `s[i]`는 O(i)다. `len`은 처음 한 번 세고 문자열에 기억한다(2026-11-08). 글자를 훑을 때는 `chars(s)`로 리스트를 만든다. 유효한 UTF-8의 큰 자르기 `s[a..b]`는 원본 바이트 위의 보기로 O(1)이고, 64바이트 이하이거나 원본의 4분의 1보다 작은 조각은 복사해 원본을 붙잡지 않는다(VA69, 2026-11-14).
- 순서 비교와 `==`·해시는 바이트로 한다. 유효한 UTF-8에서는 코드 포인트 순과 같다. 한글 가나다순과 일치하므로 일상 용도엔 충분하고, 로케일 정렬은 추후 라이브러리.
- 표시: `str`·REPL·컬렉션 안에서 UTF-8이 아닌 바이트는 `\xff`로 보이고 그 모양이 리터럴로 다시 읽힌다. `print`와 보간은 바이트를 그대로 쓴다.
  표시 너비는 그런 바이트 하나가 한 칸이다(터미널이 보통 `�` 한 칸으로 그린다).
- 바이트를 그대로 둘 수 있는 연산은 그대로 둔다: `+`, `split`, `replace`, `trim`, `upper`·`lower`(글자가 아닌 바이트는 바꿀 대소문자가 없다), 정규식(`regex::bytes`).
  다만 정규식의 `.`·`\W`·`\D`·`[^…]` 같은 유니코드 클래스는 UTF-8이 아닌 바이트에 맞지 않는다(엔진의 유니코드 모드, SP20). 그런 바이트는 `(?-u:.)`·`(?-u:\xff)`로 잡는다.
  **형식 자체가 글을 요구하는 곳만** E0518로 멈춘다: `json.stringify`, 정규식 패턴, 시간 형식, 호스트 이름·주소, 모듈 멤버 이름(이것은 E0303).
  바깥 값을 읽는 `parse_int`·`parse_float`·`parse_dur`·`time.parse`·`json.parse`에는 읽을 수 없는 입력일 뿐이라 `Err`다.
- 바이트 함수: `byte_len(s)`, `bytes(s)`(0~255 정수 리스트), `from_bytes(xs)`(거꾸로), `is_utf8(s)`.

### 심볼

- 내용 없이 이름만 있는 값. 선언 없이 쓰는 열거형 값.
- 문자열과 다른 타입: `'ok == "ok"`는 `false`다(D91, 2026-11-13; 0.4.0부터 그날까지는 E0517).
- 내부적으로 정수로 바뀌어 비교가 빠르다.
- 이름 ↔ 글: `sym("ok")`는 문자열을 심볼로, `sym_name('ok)`는 심볼의 이름을 문자열 `"ok"`로(2026-11-10 SP26·D15). `str('ok)`는 보이는 모양 `"'ok"`라 이름으로 쓰지 않는다.

### nil

- 허용: `==` `!=`, `??`, `print`, 리스트 원소·맵 값·인자·반환값으로 담기.
- 그 외(산술, 순서 비교, 인덱스, 필드, 호출, `!`, `?`)는 즉시 런타임 에러. nil은 조용히 퍼지지 않는다. `nil?`도 `nil!`과 같이 E0604다(SP13, 결정 D3, 아래 "에러 처리와 축약 연산자").

## 자료구조

### 리스트

`[1, 2, 3]` — 같은 종류의 것이 몇 개든 모인 것. map/filter의 대상.

- 인덱스·슬라이스가 **범위를 벗어나면 런타임 에러.** 인덱스와 슬라이스의 끝은 0부터만 세고 음수는 범위 밖이다(2026-11-11 SP29·D37: 전에는 음수가 뒤에서부터라 `xs[i - 1]`의 하나 모자란 계산이 말없이 맨 끝 원소를 주었다. 마지막은 `last(xs)`·`xs[len(xs) - 1]`, 앞부분은 `xs[..len(xs) - 1]`, 새 함수는 더하지 않음). 에러(E0507)는 프로그램이 쓴 인덱스를 그대로 보인다(`..=`의 끝 + 1이 아니라; 2026-10-18), 슬라이스면 시작인지 끝인지 말한다(`slice end 5 is out of range (length 2)`, 2026-10-24).
  `xs[a..=b]`는 정확히 `xs[a..b+1]`이다(값도 에러도, 범위 값 `a..=b`로 하는 색인도; 2026-11-14 SP80·D117): `xs[0..=-1]`은 `[]`, 원소 셋에 `xs[..=3]`과 빈 리스트의 `xs[..=0]`은 끝이 `len`을 넘어 E0507이다.
  전에는(2026-11-08) "`..=`의 끝은 실제 원소의 인덱스여야" 해서 `xs[1..=0]`은 `[]`인데 `xs[0..=-1]`만 에러였고, 올바른 빈 범위 값 `0..=-1`이 어떤 리스트도 색인하지 못했다. 시작 0에서만 붙던 예외라 지웠다.
  슬라이스의 시작이 끝보다 뒤면 범위 밖이 아니라 E0516(`slice start 2 is after its end 1 (length 3)`, 두 끝을 쓴 대로)이다.
  열린 끝은 끝을 비워 쓴다(`xs[a..]`). 끝에 nil이 오면 nil 인덱스처럼 E0501이다(`find`가 못 찾은 nil이 조용히 끝까지 자르지 않게; 2026-10-20).
  느슨하게 잘라내려면 `take`/`drop`(범위를 넘어도 있는 만큼). 이들은 컬렉션 함수라 리스트·범위·받는 끝만 받고 문자열은 받지 않는다(2026-11-10 SP23·D14; 2026-10-24에 받게 했다가 되돌림). 문자열은 슬라이스와 `chars`로 자른다. Python식 슬라이스 클램핑은 "조용히 넘어가는 동작"이라 채택하지 않음.
- 비용의 약속: `xs[i]`는 O(log₃₂ n), `len`은 O(1), 자르기(`xs[a..b]`, `...rest`)는 O(log n)(트리의 사본을 잘라 자기 원소가 든 잎만 쥠, 잘려 나간 원소를 붙잡지 않음, VA59 2026-11-14)이거나 32개 이하면 결과 길이에 비례하는 복사이고, 하나씩 쌓는 누적은 **앞으로도 뒤로도** 선형이다
  (`acc + [x]`·`[x] + acc` 모두 상각 O(1); L5, 2026-11-08). 두 리스트를 이으면 짧은 쪽을 긴 쪽의 끝에 붙여 짧은 쪽의 길이에 비례한다.
  큰 리스트 둘의 이어 붙이기(`a + b`, 둘 다 길 때)를 O(log n)으로 하는 것(RRB 트리)은 하지 않는다(흔한 누적 모양이 아님, open-questions "알려진 한계").

### 맵

```
user = {name: "a", tags: [1, 2]}
user.name          # user["name"] 의 축약
get(user, "age", 0)
```

- **삽입 순서를 유지한다.** 순회·출력 순서는 넣은 순서와 같다. 단, `==`는 순서를 무시한다.
- 값의 출력·`==`·순서 비교·해시는 값이 아무리 깊어도 실패하지 않는다(메모리만 든다; L9). 백만 겹 리스트의 `str`도 선형 시간이다.
- 값이 같은 이름의 변수면 키만 쓴다 (2026-10-14): `{name, port}`는 `{name: name, port: port}`. 패턴도 같다: `{line, col} = e`는
  `line`·`col`을 묶는다. 예약어 키(`{type: t}`), 문자열 키, 대문자 키(`{HOME}`, E0225)는 축약할 수 없다 — 그 이름의 변수가 있을 수 없으므로.
- 맵 패턴의 키는 리터럴과 같다(SP3, 2026-11-08, 사용자 결정): 식별자 모양이거나 보간 없는 문자열(`{"content-type": t} = h`; 원시 문자열도 같다, D129). 패턴의 키는 글이어야 하고(UTF-8 아닌 바이트 키는 E0112),
  한 패턴에 같은 키를 두 번 쓰면 리터럴처럼 E0113이다(FE12).
- 키는 **항상 문자열**(L10, 2026-10-20 유지: 다른 값을 키로 쓰면 E0514이고 힌트가 `str(…)`을 권한다. `group_by(xs, x => str(x % 2))`). 맵을 키로 찾거나 고치는 모든 자리(`m[k]`, `k in m`, `get`·`put`·`remove`, `group_by`)가 같은 E0514이고, 심볼 키면 힌트가 `"a"`로 쓰라고 한다(SP21, 2026-11-10 사용자 결정 D13; 전에는 `group_by`만 E0514, 나머지는 E0501). `{name: ...}`은 `{"name": ...}`의 축약이고, 키 자리의 식별자는 NFC로 읽은 문자열이다(D130, 01). 따옴표로 쓴 키는 쓴 그대로다. 식별자 모양이면 대소문자와 무관하게 축약할 수 있다
  (`{DB_HOST: 1}`, `m.DB_HOST`, 패턴 `{DB_HOST: v}`); 키 자리에는 값이 오지 않으므로 태그와 헷갈릴 일이 없다.
- 리터럴 안에서 같은 키를 두 번 쓰면(`{a: 1, a: 2}`) 컴파일 에러. 조용히 하나를 버리지 않는다.
- 없는 키 접근은 에러. 기본값이 필요하면 `get(m, "k", 기본값)` 또는 `??`.
- 수정된 사본은 **함수로만** 만든다: `put(m, "k", v)`, `merge(m, other)`, `remove(m, "k")`.
  `user |> put("name", "a")`처럼 파이프와 이어진다.
  - 기각: `with` 키워드 (예약어 추가, 중첩 갱신이 지저분), 리터럴 펼치기 `{...m, k: v}` (`merge`와 방법이 둘).

### 튜플

길이가 고정된, 자리마다 의미가 있는 묶음.

```
fn divmod(a, b) = (a // b, a % b)
(q, r) = divmod(7, 2)

match point:
  (0, 0) => "원점"
  (x, 0) => "x축 위"
  _      => "그 외"
;;
```

- 원소 하나: `(a,)`, 빈 튜플: `()`
- 지원하는 연산은 `==`, 순서 비교, 패턴 매칭, `len`뿐. **인덱스 `t[0]`는 없다.** 꺼낼 때는 패턴으로 이름을 붙인다.
  번호로 접근하고 싶은 데이터는 리스트다.

### 순회 대상

- `for`, `map`, `filter`, `fold` 등이 받는 것은 **리스트, 범위, 채널의 받는 끝**뿐(받는 끝은 닫힐 때까지 받는다, 05).
- 채널의 받는 끝도 순회 대상이다: 닫힐 때까지 값이 올 때마다 차례로 준다 (05). 일찍 멈추면 나머지는 채널에 남는다.
- 문자열은 `chars(s)`, 맵은 `pairs(m)` · `keys(m)` · `values(m)`로 명시적으로 바꿔서 순회한다.
  맵을 바로 순회하면 "키인지 쌍인지", 문자열은 "글자인지 줄인지"를 언어가 추측해야 하므로 없앴다.
- `map`·`filter`의 결과는 입력이 범위여도 리스트다.

### 크기 한도 (6c-1, 2026-10-17)

- 결과가 입력의 모든 원소를 담는 함수(`map`·`sort`·`sort_by`·`flatten`·`group_by`, 그리고 이것들로 쓴 함수)는 원소가 1억 개(100,000,000)를 넘는 범위를
  일을 시작하기 전에 `E0806 too many elements (limit 100000000)`으로 거절한다. 1억 개면 값만 1.6 GB다.
- 문자열은 1억 글자까지다: 넘으면 `E0806 too many characters (limit 100000000)`. `replace`·`join`·`repeat`·`+`·보간은 만들기 전에 크기를 센다(2026-10-20).
  그 밖의 모든 내장 함수도 돌려주는 문자열(맨 값, 또는 태그가 담은 값 `Ok(text)`)을 잰다(VA9, 2026-11-08, 사용자 결정): `str`·`upper`처럼 만든 것도,
  바이트 길이가 한도 안이면 길이 비교 한 번이다.
  바깥에서 읽은 글(파일 `fs.read`, 한 줄씩 읽는 `read_line`·`read_lines`의 줄, 외부 명령의 `out`·`err`, 소켓)은 크기를 프로그램이 정하지 못하므로
  한도를 넘으면 E0806이 아니라 그 함수의 `Err({kind: 'io, message: "… is longer than the string limit (100000000 characters)"})`다(LB29, 2026-11-10, 사용자 결정 D22).
  외부 명령은 읽는 중에 한도를 넘으면 명령을 끝내므로 메모리가 한도 근처에서 멈춘다. 줄 읽기(표준 입력·파일 핸들·FIFO)와 FIFO의 `fs.read`도
  한도를 넘는 순간 멈추고 `Err`다(2026-11-11): 넘은 줄의 읽은 조각은 버리고, 그 줄의 나머지는 다음 읽기가 이어 읽는다. `fs.read`는 한도의 네 배(한 글자는 4바이트 이하)보다 큰 파일을 읽지 않고 거절한다.
  리스트·맵 안은 훑지 않는다(`put`처럼 큰 맵을 거듭 돌려주는 함수가 매번 O(n)이 된다). 기각: 나열한 연산만 재기(같은 값이 `str(x)`는 되고 `"${x}"`는 에러였다).
- 인자 검사가 한도보다 먼저다: `map(0..10**18, 1)`은 `f`의 타입 에러다. 원소를 하나씩 보고 일찍 멈출 수 있는 함수(`find`·`any`·`all`)와
  결과가 입력보다 작을 수 있는 함수(`filter`·`fold`·`each`)는 큰 범위도 받는다.
- **리스트(와 맵)의 1억 원소 한도는 리스트를 만드는 모든 길에 건다**(VA29, 2026-11-11, 사용자 결정 D63; 전에는 범위를 펼칠 때만이라 `s + s`를 거듭하면 수 GB가 되었다).
  `+`(두 길이의 합), `flatten`(리스트를 받으면 원소들의 길이를 먼저 더해 만들기 전에), `put`·`merge`(맵의 항목 수), 펼치기 `...xs`, 받는 끝이나 범위에서 쌓는
  `map`·`try_map`·`filter`·`group_by`·`sort` 등(원소를 하나 더할 때마다 길이 비교 하나), `bytes`(바이트 수). 바깥에서 읽은 줄의 리스트(`read_lines`)는 D22처럼 그 읽기의 `Err`다.
  문자열 한도와 대칭이다. **전체 메모리 한도는 없다**: 한도 안의 큰 값을 여럿 만들면 메모리가 그만큼 는다(값 하나가 말없이 수 GB가 되는 것만 막는다).

## 태그

- **대문자로 시작하는 이름은 태그 전용.** 변수·함수·모듈 이름은 소문자로 시작해야 한다. 변수를 묶는 자리의 대문자 이름은 E0225(01 "이름 표기").
  기각(L4): 전부 대문자인 이름(`HOME`)을 변수로 보기. "첫 글자가 대문자면 태그"라는 한 줄 규칙이 깨지고(`HTTP`·`IO`·`A`는?) 원하는 일은 `cfg.HOME`·`{HOME: home}`로 된다.
- 선언 없이 바로 쓴다 (오타 책임은 작성자에게).

```
Circle(3)      # 태그 Circle, 인자 [3]
Rect(2, 5)     # 태그 Rect, 인자 [2, 5]
Red            # 인자 없으면 심볼(출력은 'Red; 소스에 'Red는 E0128, D41)
```

- 빈 괄호 `Red()`는 컴파일 에러다(E0117, 식과 패턴 모두; 2026-10-26). 파이프가 채우는 `x |> Ok()`(= `Ok(x)`)는 된다. 인자 없는 태그는 심볼 하나뿐이다: 전에는 `Red()`가 `Red`처럼 보이지만 같지 않은(`Ok() == Ok`는 거짓) 둘째 값이었다.
- 태그 값은 **튜플이 아니라 자체 타입**이다. 내부적으로 "이름 + 인자 목록". 인자는 하나 이상이다.
- `type_of(Circle(3))`은 `'Circle` (타입 표기 `s: Circle`과 같은 이름). `type_of(Red)`는 `'sym`.
- 인자는 패턴으로만 꺼낸다. `.0` 같은 위치 접근은 없다.
- `Ok(x)` / `Err(e)`도 일반 태그. 특별 취급은 아래 축약 연산자에서만.

## 비교와 동일성

| 타입 | `==` | `<` 등 순서 비교 |
|------|------|------|
| int, float | 값. 섞이면 숫자로 (`1 == 1.0` 참). **정확 비교**: 2^53을 넘는 정수를 float64로 바꾸지 않고 판정한다 (Python과 같음. `9007199254740993 == 9007199254740992.0`은 거짓). M2에서 구현 | 값 (같은 규칙) |
| str | 바이트열 | 바이트 순 (UTF-8에서는 코드 포인트 순과 같다) |
| bool, nil, sym | 값 | 에러 |
| dur | 값 | 값 |
| time | 같은 순간이면 참 (시간대 무관) | 순간 기준 |
| list, tuple | 길이 같고 원소가 차례로 `==` | 앞 원소부터 차례로. 앞이 전부 같으면 짧은 쪽이 작음 |
| map | 키 집합이 같고 각 값이 `==`. 삽입 순서 무시 | 에러 |
| 태그 값 | 이름 같고 인자가 차례로 `==` | 에러 |
| range | 같은 정수 열이면 참(2026-11-10 VA21·D19): 둘 다 비면 같고, 아니면 첫 수와 마지막 수가 같다(`0..5 == 0..=4`). 출력은 쓴 모양 그대로 | 에러 |
| fn | **런타임 에러 E0501**(같음이 없다, 2026-11-11 VM20·D62). 두 쪽이 다 함수를 품은 값(리스트·맵·튜플·태그 어디에든)이어도 E0501(D116). 해시도 없어 `unique`에 넣어도 E0501 | 에러 |
| module, file, task, scope, sender, receiver, atom | **동일성** (같은 객체인가) | 에러 |
| 타입이 다를 때 | `false`(같지 않다; 숫자끼리는 수로 견준다. 아래, D91) | 에러 |

`unique`, `contains`, `in`은 이 표의 `==`를, `sort`·`min`·`max`는 `<`를 따른다.

- **타입이 다른 두 값은 같지 않다: `==`·`!=`·`in`은 에러 없이 `false`다**(D91, 2026-11-13, 사용자 결정). `'ok == "ok"`, `"8080" == 8080`, `Ok(1) == 1`, `[1] == (1,)`이 모두 `false`이고, 리스트·튜플·맵·태그 안에서도 같다. 숫자끼리는 수로 견준다(`1 == 1.0`).
  - 지나온 길: 0.4.0(L10, 2026-10-20)부터 심볼과 문자열의 비교만 E0517이었고, 2026-11-11 D40이 타입이 다른 모든 비교로 넓혔고, 2026-11-13 D87이 "값과 상관없이 끝까지 검사"로 넓혔다. D91이 셋을 모두 되돌렸다(E0517 은퇴).
  - 되돌린 이유: (1) **비용.** 실행 중 검사라 "검사가 닿은 쌍만 에러"가 되어 에러가 자료에 따라 숨었고(D87의 동기), 그것을 막으려 끝까지 훑자 일찍 끝나던 `==`·`in`이 선형이 되었다
    (릴리스, 200만 원소: 첫 원소가 다른 리스트의 `==` 0.03 → 12.7 ms, 첫 원소에서 찾는 `in` 0.0005 → 10 ms). 그것을 줄이려면 리스트가 원소의 타입을 기억하는 장치가 더 필요했다. 규칙 하나가 구현 세 겹을 끌었다.
    (2) **이득이 작다.** 잡는 실수는 사실상 "바깥에서 온 문자열을 다른 타입과 견줌" 하나이고, 조건이 늘 거짓인 것은 실행해 보면 쉽게 드러난다는 것이 사용자의 판단이다. D87이 저장소에서 잡은 유일한 실제 코드(`http`의 `p != ()`)는 버그가 아니라 올바른 코드였다.
    (3) **예외 조항.** 정수와 실수, `nil`, 태그는 한 타입, 튜플의 개수라는 네 조항이 `==`에 붙어 있었다. `false`로 가면 모두 사라진다. (4) 거의 모든 동적 언어가 이렇게 한다.
  - 잃는 것: `env("PORT") == 8080`, `back.kind == 'not_found`가 다시 조용히 거짓이다. 매뉴얼이 "조건이 한 번도 참이 되지 않으면 타입부터 본다"와 `int(s)`·`sym(s)`를 가르친다.
  - 함수는 같음이 없다(VM20·D62): `f == g`, `<`, 해시 모두 E0501. 그래서 캡처 없는 람다를 상수로 만들어도(W10) 보이는 차이가 없다. 같은 저장소를 쓰는 값끼리의 지름길도 함수를 품은 값에는 쓰지 않는다(VA43).
    **두 쪽이 다 함수를 품은 값의 `==`·`!=`·`in`은 자리와 상관없이 E0501이다**(D116, 2026-11-14, 사용자 결정). 한쪽에만 함수가 있으면 타입이 다른 것처럼 `false`다(`cb == nil`).
    전에는 `==`가 실제로 견주는 쌍에서만 났다: 첫 차이에서 멈추므로 `[1, f] == [2, f]`는 `false`, `[1, f] == [1, f]`는 E0501이었고, 넣은 순서만 다른 같은 맵에서도 갈렸다(SP81).
    에러가 다른 원소의 값과 맵의 넣은 순서에 달리는 것은 지침 4에 어긋난다. 두 값을 통째로 보아("함수를 품었는가", 큰 리스트·맵은 노드의 기억으로 O(1)) 정하므로 이제 모양에도 값에도 순서에도 달리지 않는다.
    점검 문서의 추천 (가)(맞붙는 쌍을 끝까지 보기)는 "맞붙음"이 길이·태그 이름에 달려 규칙이 길었다. 함수가 없는 값은 지금처럼 첫 차이에서 끝난다.
  - **순서는 다르다**(D87, 2026-11-13에서 남긴 부분): 문자열과 수 사이, 개수가 다른 두 튜플 사이에는 순서가 없으므로 `<`는 E0501이다. 이 검사는 값과 상관없이 끝까지 간다:
    `<`는 첫 차이로 답을 정한 뒤에도 견줄 수 없는 쌍을 찾고, `sort`·`sort_by`·`min`·`max`는 시작 전에 모든 원소(키)의 모양을 하나로 합친다(11-10 D16을 모든 원소로 넓힘).
    정렬이 시험 자료에서 되고 운영 자료(앞 칸이 같은 두 행)에서 죽는 일을 막는다. 순서가 없는 것을 `false`로 답할 수는 없으므로(무엇이 앞인가) 여기는 에러가 맞다.
    처음(2026-11-13)에는 모든 원소를 첫 원소와 견주었는데, "첫 원소와 견줄 수 있다"는 추이적이지 않아(길이가 다른 리스트는 앞부분만 견준다) `[[], [1, "a"], [2], [3, 0]]`이 순서에 따라 되다 말다 했다(2026-11-14 VA60).
    이제 모든 원소를 하나의 모양(수·문자열·기간·시각, 튜플은 개수와 자리별 모양, 리스트는 자리별 모양이고 긴 리스트가 자리를 늘림)에 접어 넣고 첫 충돌에서 E0501이다.
    두 값은 모양이 합쳐질 때 정확히 견줄 수 있으므로 "모든 쌍을 견줄 수 있다"와 같고, 원소의 순서와 값에 달리지 않는다. 모양의 마디는 바뀌지 않고 나눠 쓰므로, 부분을 여러 번 공유하는 값도 (마디, 부분)마다 한 번만 접는다.
    30만 튜플의 `sort`는 전과 같고(약 0.22초), `max`는 원소마다의 비교 하나가 빠져 24 ms → 16 ms.
  - 리터럴 패턴(`'not_found =>`, `1 =>`)은 타입까지 보는 시험이다. 타입이 다르면 맞지 않는다.

## nil·Err·런타임 에러를 고르는 기준 (SP15, 2026-11-10)

함수가 "보통의 답이 아닌 것"을 낼 때 셋 가운데 하나를 고른다. 사용자 결정 D11.

- **`nil`: 값이 없을 수 있는 정상 질문.** `first([])`·`max([])`·`find`·`get`의 없는 키·`env("X")`. 없음은 실패가 아니다.
  nil은 연산에 쓰면 곧 에러가 나고(원칙 1), `??`로 기본값을 준다.
- **`Err`: 바깥 때문에 실패할 수 있는 일.** 파일·네트워크·명령·바깥 글의 해석(`parse_*`, `json.parse`, `time.parse`). 코드가 옳아도 일어난다.
- **런타임 에러: 코드의 잘못.** 타입이 틀린 인자(E0403), 범위 밖 인덱스, 0으로 나누기, 거꾸로 된 범위(E0522), 그리고 **개수·한도·기간에 준 음수**.
  개수·한도는 음이 아닌 정수, 아니면 E0403(`must be a non-negative int`): `take`·`drop`·`repeat`·`pad_left`·`pad_right`·`iterate`·`channel`·`exit`·`json.stringify`의 `indent`·`http`의 `max_body`.
  기다리거나 허락하는 기간도 음수면 E0403(`must be a non-negative dur`): `sleep`·`timeout`·`http`의 `timeout`·`drain`과 기간을 받는 모든 인자. `0s`는 "곧바로"다.
  `take(xs, n - k)`의 음수는 계산 실수일 가능성이 높아 말없이 0으로 깎지 않는다. `take`·`drop`이 느슨한 것은 길이보다 **큰** n뿐이다.
  남은 시간을 계산해 음수가 될 수 있는 코드는 `max(d, 0s)`로 드러낸다.
- 빈 입력의 답은 연산의 항등원이 있으면 그것이다: `sum([]) == 0`(원소 타입을 모르니 정수 0; 기간이면 `fold(xs, 0s, …)`), `join([]) == ""`.
  항등원이 없으면(`min`·`max`·`first`·`last`) `nil`이다.

## 엄격함

- 암묵적 형변환 없음: `"5" + 3`은 에러, `int("5") + 3`으로 쓴다.
- 선언 안 한 변수는 컴파일 시점 에러.
- 처리 안 된 런타임 에러는 즉시 중단 + 호출 경로 출력 (08).

## 에러 처리와 축약 연산자

```
text = fs.read("a.json")!           # Err면 프로그램 중단 (스크립트용)
data = json.parse(text)?            # Err면 현재 함수에서 그 Err를 그대로 반환
port = env("PORT") ?? "8080"        # 왼쪽이 nil 또는 Err면 오른쪽 값
cfg = (fs.read(p) ?? "{}") |> json.parse   # Ok(text)는 text로 풀린다
```

| 왼쪽 값 | `x!` | `x?` | `x ?? b` |
|------|------|------|------|
| `Ok(v)` | `v` | `v` | `v` |
| `Err(e)` | 프로그램 중단 (종료 코드 1) | 현재 함수에서 `Err(e)` 반환 | `b` |
| `nil` | 런타임 에러 (E0604) | 런타임 에러 (E0604) | `b` |
| 그 외 값 | 런타임 에러 | 런타임 에러 | 그 값 그대로 |

- `!`·`?`를 결과값이 아닌 값에 쓰는 것은 거의 확실히 버그(결과값을 돌려주지 않는 함수에 붙임)라 에러로 한다.
  규칙은 하나다: **`!`·`?`는 결과값만 받는다.** `nil`도 예외가 아니다(SP13, 2026-11-10, 사용자 결정 D3: 전에는 `nil?`만 `nil`을 그대로 넘겼다).
  `env`·`find`·`get`처럼 `nil`을 돌려주는 함수에 `?`를 붙인 실수가 `nil`일 때만 조용히 호출자로 퍼지던 것을 막는다.
  "없으면 위로 넘긴다"가 필요하면 `match`나 `if x == nil: return nil ;;`로 드러내 쓴다. nil을 거르는 것은 `??`의 몫이다.
- **값을 담은 `Ok`·`Err`는 값을 정확히 하나 담는다**(SP12, 2026-11-10, 사용자 결정 D2): 식·패턴·파이프(`x |> Ok(2)`)에서 개수가 다르면 컴파일 에러 E0236이다. 맨 `Ok`·`Err`는 다른 대문자 이름처럼 심볼이다(D123, 2026-11-14).
  태그 인자에는 펼치기가 없고 심볼은 부를 수 없으므로, 다른 개수의 `Ok`·`Err`를 만들 길은 없다. 그래서 결과값의 판정은 이름 하나로 끝나고,
  `!`·`?`·`??`·`try_map`·`is_ok`·`is_err`·보간·`join`·버려지는 자리·패턴·타입 표기가 모두 같은 판정을 쓴다(VM `result_kind`).
  타입 표기 `Ok`·`Err`는 다른 태그 이름처럼 결과값과 같은 이름의 심볼을 받는다(D123; 전에는 심볼을 받지 않는 예외였다).
  전에는(VM4, 2026-11-08) `Ok(1, 2)`를 "같은 이름의 보통 태그"로 두어 연산마다 다르게 보았다. 이 특수한 값은 D2로 없어졌다.
- `??`는 **모든** `Err`를 받는다(권한 오류도 기본값이 된다). 사용자가 직접 쓰는 "실패하면 이 값"이라 조용한 처리가 아니다(L10, 2026-10-20 유지).
  종류를 가리려면 `match`(`Err({kind: 'not_found, ...}) => 기본값`). 기각: `??`는 nil만 받고 `Err`는 함수로.
- `Err`의 내용은 **아무 값이나** 된다. 표준 라이브러리는 `{kind: 심볼, message: 문자열, …}` 맵을 쓰고 (06),
  사용자 코드에도 권장하지만 강제하지 않는다 (`return Err("없음")` 가능).
  `!`로 중단될 때는 내용이 `message` 키를 가진 맵이면 그 문장을, 아니면 리터럴 형태를 보여 준다.

### 버려지는 Err (L1, 2026-10-20)

버려지는 자리(01 "식과 문장")의 값이 `Err`면 런타임 에러 E0606 `discarded Err: <내용>`이다. 내용은 E0603과 같이 보인다.

```
fs.write(p, text)          # 실패하면 E0606: 결과를 버리는 자리다
fs.write(p, text)!         # 실패하면 중단 (E0603)
_ = fs.remove(tmp)         # 실패해도 상관없다: 일부러 버린다
each(rxs, r => send(tx, r))   # f의 결과도 버려지는 자리: 닫힌 tx면 E0606
```

- 내장 함수가 결과를 버리는 콜백도 같다: `each`의 `f`, `with`의 `release`(03), `supervise`의 `on_fail`(05). 그 `Err`는 그 콜백의 런타임 에러가 된다
  (`release`면 "release의 런타임 에러" 순위, `on_fail`이면 범위의 실패). 결과를 쓰는 콜백(`map`의 `f`, `use`)은 해당하지 않는다.

- 이유: 원칙 1(조용히 넘어가는 동작은 에러, background). 셸 대용 언어에서 결과를 버리는 줄은 가장 흔한 실패 지점이고(`set -e`를 잊은 셸),
  fung은 동적 타입이라 어느 호출이 `Err`를 돌려줄지 컴파일 때 알 수 없다. 그래서 정적 경고가 아니라 버리는 순간의 검사다(비용은 태그 검사 하나).
- 기각: 경고(정적으로는 거의 잡지 못함), 매뉴얼 권장만(가장 흔한 실수를 기억력에 맡김), 따로 쓰는 `ignore(x)` 함수(`_ = 식`이 이미 있고 눈에 띈다).
- 에러는 보통의 런타임 에러다. 태스크 안이면 그 태스크의 실패가 되어 `scope`·`supervise`로 간다(05).
- 버려지는 값이 **리스트·맵·튜플·태그**면 그 안을 깊이와 상관없이 훑는다(L2 2026-10-27에 리스트 한 겹, SP49-2 2026-11-11 사용자 결정 D54로 모든 깊이: 한 겹의 선은 임의였다).
  `Err`가 있으면 차례로 처음 나온 것이 E0606이 되고, `note: element 2 of the discarded list (of 3)`, `note: key "db" of the discarded map, then the value of `Ok(…)``처럼 길을 덧붙인다.
  그래서 `for`로 끝나는 함수를 문장으로 부를 때(`main()`), `map(…)` 문장, `each`의 `f`가 돌려준 값, `{a: Err(e)}`·`(Err(e), 1)`·`Ok(Err(e))` 안의 `Err`를 모두 잡는다.
  범위(`1..10`)와 함수(붙잡은 값)는 데이터를 돌려주는 값이 아니므로 보지 않는다. 비용은 버리는 값이 컬렉션·태그일 때만 든다(다른 값에는 종류 검사 하나).
  훑기는 명시적 스택이고 `Rc`로 나눠 가진 부분은 한 번만 본다(깊이·공유와 상관없이 서로 다른 부분의 수에 선형). 길은 같은 방식의 한 번 더 걷기로 찾는다.
  긴 리스트(33개 이상)는 영속 벡터의 노드마다 답을 기억한다(`atom`이 변하는 값을 찾을 때와 같은 기억). 그래서 같은 리스트나 그 조각을 거듭 버려도
  (`atom`에 든 큐를 `swap`하는 문장) 처음 한 번만 다 보고, 그 뒤로는 바뀐 길과 잘린 잎만 본다.
- 태스크의 함수가 돌려준 `Err`를 아무도 `await`하지 않으면 E0607이다(05 "읽지 않은 `Err`", L1 2026-10-27). 같은 원칙이고, 판정하는 때만 다르다.
- 잡지 않는 것: 변수에 담고 보지 않는 값(`r = f()`; `r`을 아예 안 쓰면 E0239), 함수가 붙잡은 `Err`.

### 글 안의 결과값 (SP2, 2026-11-08; SP39, 2026-11-11)

- 문자열 보간 `"${x}"`과 `join`에 넣는 값이 결과값(`Ok`·`Err`), `nil`, 핸들(함수·모듈·태스크·범위·채널 끝·atom·파일·소켓)이면, 리스트·맵·튜플·태그 안 어느 깊이에 있어도 런타임 에러 E0519다
  (SP2는 맨 결과값만; SP39·사용자 결정 D46으로 넓힘). 결과를 풀지 않은 실수(`"http://${recv(rx)}/"`), 없는 값(`"http://${env("HOST")}/"`이 `http://nil/`)이
  URL·경로·명령 인자로 흘러가지 않게 한다. 버려지는 `Err`(E0606)와 같은 원칙이다.
- 값 그대로를 글로 쓰려면(로그) `str(x)`로 바꾼다. `print`와 `str`은 무엇이든 보인다(명시적 표시·변환이다).
- 훑기는 버려지는 `Err`와 같은 명시적 스택이고 나눠 가진 부분은 한 번만 본다.
- 기각: `nil`만 더하기, 그대로 두기(SP2 때 "로그에 `nil`을 찍는 용도"로 `nil`을 뺐지만, 그 용도는 `print`·`str`이 맡는다).
