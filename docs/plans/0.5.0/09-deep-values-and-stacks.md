# L9. 재귀인 값 출력과 깊은 네이티브 재귀의 스택 한도

상태: 열림 (2026-10-26). 0.5.0 전에 고친다. 목록: [README](README.md).

## 문제

값을 훑는 Rust 함수 몇 개가 값의 모양을 따라 Rust 스택으로 재귀한다. 그래서 만들 수 있는 값을 출력·비교하다 프로세스가 죽는다.
스택 넘침은 Rust에서 잡을 수 있는 에러가 아니라 강제 종료(`SIGABRT`, 종료 코드 134)라서, fung의 에러 보고(`error[E…]`, 호출 경로)도 `release`도 없다.
08의 원칙("실행 중의 한도는 E08xx 에러")과 09의 프레임 한도(100,000에서 E0804)가 지키려는 것이 바로 이것인데, 값 쪽에는 그런 경계가 없다.

재현(릴리스 빌드, 이 문서를 쓰며 잰 값). 2천만 겹 리스트 두 개의 `==`:

```
$ fung -e 'd = fold(1..=20000000, [], (acc, _) => [acc])
e = fold(1..=20000000, [], (acc, _) => [acc])
print(d == e)'
thread '<unknown>' (69435021) has overflowed its stack
fatal runtime error: stack overflow, aborting
$ echo $?
134
```

1천만 겹은 `true`로 끝났다. 같은 2천만 겹에서 `len(unique([d, e]))`(해시)와 `d < e`(순서 비교)도 같은 메시지로 죽었다(최대 상주 메모리 2~3 GB).
출력은 더 일찍 문제가 된다. 깊이에 대해 **이차 시간**이기 때문이다.

```
$ time fung -e 'd = fold(1..=1000000, [], (acc, _) => [acc])
print(len(str(d)))'
2000002
... 79.40s user 0.37s system 98% cpu 1:21.22 total
```

10,000겹 0.01초, 100,000겹 0.69초, 200,000겹 1.79초, 1,000,000겹 81초다. open-questions의 "5백만 겹 `str`이 디버그 진입 스레드에서 134"는
이 이차 비용 때문에 릴리스로는 30분 넘게 걸릴 것이라 다시 재지 않았다. 스택 넘침과 별개로, 백만 원소짜리 값을 `print`하는 데 1분이 넘는 것 자체가 결함이다.

앞단에도 같은 종류가 있다. 긴 평평한 사슬(`1 + 1 + …`)은 중첩 한도(E0115, `parser.rs`의 `MAX_DEPTH` 10,000)에 세지 않는데 뒤 단계가 고리마다 재귀한다(R1 노트 9절).
릴리스는 400만 고리도 통과했다(9.2초). 디버그 빌드(이 세션의 `target/debug/fung`)는 45만 고리는 통과하고 60만 고리에서 134로 죽었다(open-questions의 "약 80만"보다 낮다).

## 지금 동작과 원인

- `crates/fung-vm/src/value/format.rs`의 `format`(`print`·`str`·`${}`·REPL 출력·에러 문구의 값이 모두 이것): 리스트·맵·튜플·태그의 원소마다 `format`을 재귀로 부르고,
  자식의 `String`을 모아 `join`한 뒤 `format!`으로 감싼다. 깊이 d면 각 층이 자기 아래 문자열 전체를 다시 복사해 O(d²) 바이트를 옮긴다.
- `crates/fung-vm/src/value/compare.rs`: `equal`(→ `equal_items`), `sym_meets_str`(`eq`가 먼저 부르는 E0517 검사), `compare`(→ `compare_items`), `hash_value`(`unique`·`in` 등)가 모두 재귀다.
- 이미 반복인 것: JSON 파싱과 출력(`native/json.rs`, 빌더·반복자 스택, R4b 노트 6절), 값 해제(`value/release.rs`), `send`의 변하는 값 훑기(`value.rs`의 `holds_mutable`).
- fung 호출과 고차 함수: R2 이후 `map`·`fold` 등은 이어 가기 상자(`vm/cont.rs`, `NativeBody::Step`)로 람다를 부르므로 Rust 스택을 쓰지 않는다.
  `fn walk(x): map(x, walk) ;;`를 백만 겹 리스트에 주면 134가 아니라 E0804(`call depth exceeded 100000`)로 끝난다(재현함).
  그런데 open-questions "메모리·스택"의 "`map`·`fold`의 깊은 중첩", `crates/fung-cli/src/main.rs`의 `STACKS` 주석("natives that call fung functions (`fold`, `map`) recurse on the Rust stack"),
  `crates/fung-cli/tests/task_stack.rs` 머리 주석은 R2 이전 설명이다. `Plain` 네이티브 중 fung을 부르는 것이 없는지는 전부 확인하지 못했다(`NativeFn`의 서명이 VM을 받지 않는 것만 봤다).
- 스택: `crates/fung-vm/src/stack.rs`의 `ENTRY_STACKS`(4 GiB → 1 GiB → 256 MiB → 64 MiB)와 `spawn_sized`. `fung` 명령(`main.rs`의 `start`)이 쓰고, R1b 이후 모든 태스크가 그 스레드에서 돈다.
  예약을 거부하는 호스트(`ulimit -v`, 엄격한 overcommit)에서는 위의 한도가 크게 낮아진다. 이 세션에서는 작은 스택 호스트를 흉내 내 재지 않았다.

## 고려할 점

- 값의 깊이는 프로그램이 정하지 않는다. JSON(깊이 10,000 한도)·파일·네트워크 입력을 접어 만든 값, 연결 리스트처럼 쓰는 `[x, rest]`가 쉽게 깊어진다. 출력·비교·해시는 "실패하지 않아야 할" 연산이다.
- 다른 언어: CPython은 `repr`·`==`가 재귀이고 깊이 한도에서 `RecursionError`를 낸다(죽지는 않음). Go의 `fmt`는 자라는 고루틴 스택(1 GB)에 기대다 넘으면 죽는다.
  `serde_json`은 깊이 128에서 에러. 함수형 언어 런타임(OCaml, GHC)은 큰 스택이나 자라는 스택에 기댄다. fung은 자라는 스택을 표준만으로 만들 수 없고, `stacker` 같은 크레이트는 의존성 정책(`deny.toml`)에 없다.
- 반복으로 바꾸면 명시적 스택(`Vec`)이 힙에 있으므로 한도는 메모리뿐이고, 스택 크기 폴백(64 MiB 호스트)과 무관해진다. 출력은 한 버퍼에 이어 쓰면 O(n)이 된다.
- `equal`은 같은 객체(`same_object`)를 먼저 보는 지름길이 있다. 반복판도 이 지름길과 "짧게 끝내기"(첫 차이에서 멈춤)를 지켜야 한다. `compare`는 에러(E0501)를 돌려주는 자리가 원소 순서와 같아야 한다.
- 맵 출력·비교·해시는 순서 규칙(넣은 순서로 출력, 비교·해시는 순서 무관)을 지켜야 한다. 기대 출력·골든 테스트가 바이트 단위로 같아야 한다.
- 앞단 사슬은 값과 다른 문제다. 사슬도 한도에 세면 지금 통과하는 20만 고리 시험(R1 노트, 599건)이 깨진다. 반복으로 바꾸려면 변환·resolve·컴파일러·포매터·`Drop` 여러 곳을 고쳐야 한다.

## 선택지

(가) 값을 훑는 함수를 모두 명시적 스택의 반복으로 바꾼다(`format`·`equal`·`sym_meets_str`·`compare`·`hash_value`). `format`은 `&mut String` 하나에 이어 쓴다.
  장점: 깊이 한도가 메모리뿐, 출력이 O(n), 스택 크기 폴백과 무관. 단점: 코드가 길어지고(JSON 출력과 같은 방식), 함수마다 반복자 스택을 짜야 한다.
(나) 값 깊이에 한도를 두고 넘으면 E08xx 에러(예: 깊이 100,000, 프레임 한도와 같은 수). 장점: 짧고 죽지 않는다. 단점: 만들 수 있는 값을 출력·비교하지 못하는 언어가 된다. 이차 출력 비용은 따로 고쳐야 한다.
(다) 큰 스택에 계속 기대고 문서에만 적는다. 장점: 할 일 없음. 단점: 134 강제 종료와 이차 출력이 그대로이고, 작은 스택 호스트에서 한도가 예측되지 않는다.

추천: 값에는 (가). 출력·비교는 실패하면 안 되는 연산이고, JSON 쪽에서 이미 같은 방식을 썼으며, 이차 비용도 함께 없어진다.
앞단 사슬은 이 문서에서는 (다)로 두되 측정으로 한도를 확인한다(정할 것 3). 값 쪽이 반복이 되면 4 GiB 예약이 필요한 이유는 앞단만 남는다.

## 정할 것

1. 반복으로 바꾸는 범위: `format`·`equal`·`sym_meets_str`·`compare`·`hash_value` 다섯 개 전부인가? 추천: 전부. 하나라도 남으면 같은 134가 남는다.
2. 반복판에도 안전망으로 깊이 한도를 둘 것인가? 추천: 두지 않는다. 힙 스택은 메모리 한도(E0806 수준의 원소 수 한도가 이미 있음)에 걸린다.
3. 앞단의 긴 사슬: (ㄱ) 큰 스택 유지 + 디버그 한도를 문서에 적기, (ㄴ) 사슬 길이도 E0115에 세기(한도는 64 MiB 폴백에서 릴리스가 통과하는 값으로 측정), (ㄷ) 앞단 전 단계를 반복으로. 추천: (ㄱ)을 0.5.0에, (ㄷ)은 open-questions에 남김. 사슬 수십만 고리는 사람이 쓰지 않는다.
4. 값이 반복이 된 뒤 `ENTRY_STACKS`의 4 GiB를 줄일 것인가? 추천: 앞단 측정(정할 것 3) 뒤에 정한다. 줄이면 거부되는 호스트가 줄지만 앞단 한도가 내려간다.

## 할 일

1. 시험 먼저(TDD). `value/tests.rs` 등에 작은 스택(1 MiB) 스레드에서 도는 단위 시험을 쓴다(R4b의 JSON 시험과 같은 방식): 백만 겹 리스트·맵·튜플·태그의 `format`·`equal`·`eq`·`compare`·`hash_value`.
   실패 먼저 확인은 스택 넘침이라 시험 프로세스째 죽는다. 한 번 손으로 돌려 134를 확인하고 기록한다. 이차 비용은 릴리스 `perf` 시험으로 지킨다(예: 백만 겹 `str`이 1초 안).
2. 기존 동작을 지키는 시험: 같은 객체 지름길, 첫 차이에서 멈춤, E0501·E0517의 보고 위치와 문구, 맵의 순서 무관 비교·해시, 한 원소 튜플 `(x,)`, 따옴표 키.
3. `format.rs`를 `fn write(v, out: &mut String)` + 명시적 프레임 스택으로 바꾼다. `format`·`format_for_print`는 그 위의 얇은 겉.
4. `compare.rs`의 다섯 함수를 반복으로. 짝(왼쪽, 오른쪽) 반복자 스택을 둔다.
5. 낡은 설명 고치기: open-questions "메모리·스택"(값 출력 항목 지우기, `map`·`fold` 언급 고치기, 디버그 사슬 한도를 다시 잰 값으로), `main.rs`의 `STACKS` 주석, `task_stack.rs` 머리 주석, `stack.rs` 머리 주석.
6. 설계 문서: 02(값의 출력·비교가 깊이와 무관하다는 규칙 한 줄), 09(구조: "값을 훑는 Rust 코드는 재귀하지 않는다"를 원칙으로). 매뉴얼 `manual/vm/10-values-and-memory.md`에 반복 순회 설명, 다시 생성(`FUNG_UPDATE_MANUAL=1 cargo test -p fung-cli --test manual_build`).
7. CHANGELOG `[Unreleased]`에 고침: 아주 깊은 값의 출력·비교·해시가 죽지 않음, 깊은 값 출력이 선형 시간.
8. `scripts/bench.sh`로 출력·비교 중심 작업 전후를 잰다(얕은 값에서 느려지지 않았는지). `bench/compare/`의 기록은 방법이 바뀌지 않으면 fung만 다시 잰다.
9. 정할 것 3의 측정: 릴리스·디버그에서 사슬이 넘치는 길이, 64 MiB 스택에서의 길이를 open-questions에 적는다.

## 끝의 기준

- 1 MiB 스택 스레드에서 백만 겹 값의 `format`·`equal`·`eq`·`compare`·`hash_value` 시험이 통과한다.
- 릴리스 `fung`에서 2천만 겹 리스트의 `==`·`unique`·`<`·`str`이 134 없이 끝나고, 백만 겹 `str`이 1초 안에 끝난다(이 세션 기준 81초).
- `value/` 안에 값 모양을 따라 재귀하는 함수가 없다(리뷰로 확인, 남긴 것은 이유를 주석에).
- 기대 출력·골든·매뉴얼 시험이 바뀐 줄 없이 통과하고, 커밋 전 검사(`fmt`·`clippy`·`test` 디버그와 릴리스·`deny`·`audit`)가 통과한다.
- open-questions와 주석의 낡은 설명이 고쳐졌고, 앞단 사슬의 결정이 open-questions에 적혀 있다.
