# L7. 회수되지 않는 `Rc` 순환

상태: **닫힘 (2026-10-28)**. 선택지 (나), 정할 것 1~4 모두 추천대로(사용자 결정 2026-10-28). 목록: [README](README.md).

결과: `vm/channel.rs`의 `contains`를 `cycle_to(Place, v)`로 넓혔다(다른 채널의 버퍼·주차한 송신 값·끝난 태스크 결과를 따라감, `Cycle::{No, Itself, Through}`). `send`·`try_send`(`conc.rs` `refuse_cycle`)와 태스크 끝(`scope.rs`, 결과를 쓰기 전)에서 부른다. 새 번호 E0709.
구현 중 드러난 것: 그대로 따라가면 채널 사슬 시험(앞 채널의 받는 끝을 품은 채널 백만 개)이 `send`마다 사슬 전체를 훑어 끝나지 않았다(O(n²)). 그래서 끝·핸들에 "버퍼나 결과에 들어간 적 있음" 표시(`Channel::kept`·`TaskState::kept`, 보수적이고 내리지 않음)를 두고, 받는 곳의 표시가 설 때만 건너 따라간다.
또 정수 2만 개가 쌓인 채널의 끝을 5천 번 보내면 버퍼를 매번 훑어 17배 느렸다: 버퍼가 변하는 것을 품은 값의 수(`buf_mutable`)를 세어 0이면 건너뛴다. 끝 하나만 보내는 흔한 경우는 스택 없이 판정한다.
측정(릴리스, 기준판 대비, 11~15번 중앙값): 응답 채널 패턴 +1.0~2.2%, 채널 사슬 20만 +0.5%, 큰 버퍼 −0.1%, `bench/chan.fung` +0.4%. 고리 아닌 비슷한 모양 N=1만·10만 RSS 9.3 MB로 같음.

## 문제

fung 값은 참조 계수(`Rc`)로 회수하고 가비지 컬렉터가 없다. 불변 값끼리는 순환을 만들 수 없지만(만들 때 그 값은 아직 없다), 나중에 값을 받는 칸은 순환을 닫을 수 있다.
그런 칸은 채널의 버퍼와 태스크의 결과 칸 둘이다(atom은 E0708이 막는다). 지금 E0705는 "같은 채널의 끝"만 보므로 아래 둘은 잡지 않고 메모리가 샌다.

서로의 받는 끝을 버퍼에 담은 채 버려진 두 채널(`pair()`를 N번, 릴리스 빌드, `/usr/bin/time -l`의 최대 RSS):

```fung
fn pair():
  (ta, ra) = channel(1)
  (tb, rb) = channel(1)
  _ = send(ta, rb)
  _ = send(tb, ra)
  nil
;;
```

```
send(ta, 1)·send(tb, 2)  (순환 없음)   N=100,000:  9,240,576
send(ta, tb)·send(tb, ta) (보내는 끝)  N=100,000:  9,240,576
send(ta, rb)·send(tb, ra) (받는 끝)    N=100,000: 60,653,568
send(ta, (tb, rb))·send(tb, (ta, ra))  N=10,000: 16,646,144  N=100,000: 83,230,720
```

자기 핸들을 결과로 담은 태스크(`recv(rx)`가 `Ok(t)`를 돌려준다):

```fung
fn one():
  (tx, rx) = channel(1)
  scope(fn(s):
    t = spawn(s, () => recv(rx))
    _ = send(tx, t)
    _ = await(t)
  ;;)
;;
```

```
N=10,000: 17,039,360   N=100,000: 86,409,216
```

한 번에 약 0.8 KB씩 쌓인다. 짧은 스크립트에서는 드러나지 않지만 `http.serve`처럼 오래 도는 프로그램에서는 끝없이 자란다.
05는 "참조 계수로 메모리를 회수하는 구현에서 순환을 막기 위해" E0705를 두었고, 매뉴얼(`manual/vm/10-values-and-memory.md` 끝 절)은 "바뀌는 것이 고리를 만들 자리는 E0705·E0708이 막는다"고 쓴다. 지금 구현은 그 말을 지키지 못한다.

참고: 보내는 끝끼리만 엮인 순환은 새지 않는다. 마지막 받는 끝이 사라지면 채널이 버퍼를 버려(`abandon`) 고리가 끊기기 때문이다. 새는 것은 받는 끝(또는 태스크 핸들)이 고리 안에 있을 때다.
순환을 닫는 칸은 시간 순으로도 둘뿐이다: `send`가 값을 버퍼에 넣을 때, 태스크가 끝나 결과를 쓸 때. 클로저가 붙잡은 값은 만들 때 정해지고, 범위는 자식 핸들을 쥐지 않는다(05 "범위", `docs/notes/R7-language.md` L1).

## 지금 동작과 원인

- `crates/fung-vm/src/conc.rs`의 `send`가 `channel::contains(ch, v)`로 `v` 안에 **같은 채널** `ch`의 끝이 있는지만 본다(E0705).
- `crates/fung-vm/src/vm/channel.rs`의 `contains`·`visit`: 리스트·맵 값·튜플·태그 인자·클로저가 붙잡은 값을 명시적 스택으로 훑는다. 머리 주석이 일부러 훑지 않는 곳을 적어 둔다.
  - 다른 채널의 버퍼: 두 채널 순환을 잡지 않는다.
  - 클로저의 모듈 전역과 모듈 값: 모듈 전역 ↔ 클로저 순환은 채널 없이도 있고, 런타임 끝에 `World::release_values`(`vm/world.rs`)가 전역 표를 먼저 비워 끊는다.
  - 태스크 핸들: 도는 태스크의 결과는 아직 없어 보면 에러가 타이밍에 달린다는 이유.
- `vm/scope.rs`의 `TaskEnd::body_ended`가 `TaskState.result`(`vm/task.rs`)에 결과를 쓴다. 이때 아무 검사도 없다. 결과가 자기 핸들(`Value::Task(Rc<TaskHandle>)` → `state: Rc<TaskState>`)을 품으면 고리다.
- `vm/atom.rs`의 E0708은 `Value::holds_mutable`(atom·채널 끝·태스크·범위 핸들·파일·소켓)인 값을 atom에 넣지 못하게 해 atom 쪽 고리를 원리상 없앤다. `holds_mutable`은 영속 벡터 노드의 기억(`value/pvec.rs`)으로 큰 값도 O(1)이다.
- 해제는 `value/release.rs`의 명시적 스택(`release`·`spill_channel`·`drop_children`)이 맡는다. 고리를 끊는 장치는 `World::release_values` 하나뿐이고 런타임 끝에만 돈다.
- 동시성 v2 스펙(`docs/superpowers/specs/2026-10-18-concurrency-v2-r7-design.md`)은 "순환을 회수하는 GC"를 비목표에, "채널 버퍼를 거치는 순환"을 남은 일에 두었다.

## 고려할 점

- 채널이 닫히는 순간은 언어 의미다(05: 보내는 끝이 모두 사라지면 닫힌다, L4). 순환 수거기가 고리를 늦게 풀면 "닫히는 때"가 수거기가 도는 때가 된다. 파일·소켓도 마지막 사본이 사라질 때 닫힌다(`Drop`). 참조 계수의 결정적 해제를 지키려면 고리를 막는 쪽이 맞다.
- 다른 언어: Python·PHP는 참조 계수 + 순환 수거기(시험 삭제), Nim ORC·Swift는 순환 수거기 또는 약한 참조를 사용자에게 맡김, Erlang은 프로세스 힙과 메일박스라 채널 끝이 값이 아니어서 이 문제가 없다(fung의 메일박스는 0.5.0 뒤, README 3절).
- 고리를 닫는 순간이 둘뿐이라는 점이 막는 쪽을 싸게 만든다. 그 두 곳에서 "넣는 값에서 닿는 변하는 칸을 따라가 넣는 곳으로 돌아오는가"를 보면 모든 고리를 닫히는 그 자리에서 잡는다.
  - 따라갈 간선: 받는 끝·보내는 끝 → 그 채널의 버퍼(와 보내려고 주차한 값), 태스크 핸들 → 끝난 태스크의 결과. 도는 태스크의 결과는 없으므로 보지 않는다. 그 태스크가 끝날 때 그 자리의 검사가 본다. 그래서 고리는 항상 잡히고, 다만 어느 쪽(보낸 쪽 또는 끝난 태스크)에서 잡힐지는 순서에 달린다.
  - 가득 찬 채널에 주차한 `send`의 값은 아직 버퍼에 없다. 검사를 `send` 시작에만 두면 주차 중에 다른 `send`가 고리의 나머지 반을 닫을 수 있다. 주차한 값도 간선으로 따라가거나, 값이 버퍼에 들어가는 자리(`deliver`)에서 검사해야 한다. 구현 때 확인한다.
  - 비용: 변하는 것을 품지 않은 값은 지금처럼 O(1)로 건너뛴다. 품은 값만 닿는 버퍼들의 크기에 비례한다. 응답 채널 패턴(`send(req_tx, (x, reply_tx))`)의 응답 채널 버퍼는 보통 비어 있어 싸다. 큰 버퍼를 거치면 `send`마다 그 버퍼를 훑을 수 있어 측정이 필요하다.
- 모듈 전역을 거치는 고리는 자라지 않는다. 최상위 이름은 한 번만 대입되므로(0.4.0) 고리 수가 전역 수로 묶이고 런타임 끝에 `release_values`가 끊는다. REPL에서 같은 이름을 다시 정의할 때 쌓이는지는 확인하지 않았다.
- 태스크 결과에서 고리가 보이면 그 태스크를 실패시키는 것이 자연스럽다(결과 대신 에러가 범위로 간다). 에러 번호는 한 번 붙이면 바꾸지 않으므로 E0705의 문구를 넓힐지 새 번호를 줄지 정해야 한다.

## 선택지

(가) 지금처럼 두고 문서만 고친다. 오래 도는 서버에서 메모리가 자란다. 0.5.0 전에 문제를 모두 고친다는 목표와 맞지 않는다.

(나) 고리를 닫는 두 자리에서 막는다. `send`(값이 버퍼에 들어가는 자리)와 태스크 끝(결과를 쓰는 자리)에서, 넣는 값으로부터 채널 버퍼·주차한 값·끝난 태스크 결과를 따라가 넣는 곳(그 채널, 그 태스크)에 닿으면 에러.
장점: 모든 고리를 결정적으로 막고, 해제 시점이 지금처럼 결정적이며, E0705·E0708과 같은 철학이다. 단점: 전에 되던 프로그램 일부가 에러가 된다(정당한 응답 채널 패턴은 고리가 아니라 영향 없음). 검사 비용이 닿는 버퍼 크기에 비례한다.

(다) 순환 수거기(Bacon–Rajan 시험 삭제). 후보는 채널과 `TaskState`뿐이다(고리는 반드시 이것들을 지난다). 계수가 0이 아닌 값으로 줄어든 후보를 모았다가 가끔 훑는다.
장점: 새 에러가 없다. 단점: 모든 값 종류에 훑기 함수가 필요하고, 채널 닫힘·파일 닫힘 시점이 수거기의 시점이 되어 결정적 의미가 깨진다. 구현이 크고 스펙이 비목표로 둔 일이다.

(라) 약한 참조(버퍼나 결과가 끝을 약하게 쥠). 버퍼의 값은 받는 쪽이 꺼내 써야 하므로 약하게 쥘 수 없다. 기각.

(마) 메일박스 모델로 채널 끝을 값에서 없앤다. 순환이 원리상 사라지지만 자동 닫힘을 잃고 link·monitor 설계가 필요하다. README 3절의 0.5.0 뒤 과제다.

추천: (나). 고리를 닫는 순간이 두 곳뿐이라 그 자리의 검사로 빠짐없이 막을 수 있고, 참조 계수의 결정적 해제(채널·파일이 닫히는 때)를 그대로 지킨다.

## 정할 것

1. 에러 번호: E0705를 "채널·태스크 고리 전체"로 넓혀 문구를 바꾼다 vs 새 번호(예: 두 채널 고리는 E0705 그대로, 태스크 결과 고리는 새 E07xx). 추천: 새 번호 하나(`value would form a cycle through channels or tasks` 류)를 두고 E0705는 자기 채널 경우로 남긴다. 번호를 바꾸지 않는 규칙에 맞고, 문구가 원인을 정확히 말한다. 지금 E0709 이후가 비어 있는지는 카탈로그에서 다시 확인한다.
2. 태스크 결과에서 고리가 보이면: 태스크를 그 에러로 실패시킨다(범위로 전파, `await`은 실패 값) vs 결과에서 고리 부분만 버린다. 추천: 실패시킨다. 조용히 바꾸지 않는다는 원칙(1급 에러)에 맞다.
3. 검사 자리: `send` 시작 + 주차한 값까지 따라가기 vs 값이 버퍼에 실제로 들어갈 때. 추천: `send` 시작에서 주차한 값까지 따라간다. 에러가 `send`의 호출 자리에서 나고, 닫힌 채널·가득 찬 채널과 관계없이 같은 에러라는 지금 규칙(`conc.rs` 주석)을 지킨다. 구현 중 빈틈이 보이면 다시 묻는다.
4. 보내는 끝만으로 된 고리(새지 않음)도 막을까. 추천: 막는다. 05의 E0705가 이미 "어느 끝이든"이고, 고리 판정을 끝 종류에 따라 나누면 규칙이 복잡해진다.
