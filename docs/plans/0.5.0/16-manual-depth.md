# L16. 매뉴얼의 깊이: 검사되는 VM 부록, 레퍼런스 깊이의 언어 명세

상태: 열림 (2026-10-26). 0.5.0 전에 고친다. 목록: [README](README.md).

## 문제

두 가지다. 출처는 open-questions "매뉴얼"의 첫 항목.

**1. VM 부록의 손으로 적은 `dump` 출력이 낡았다.** `manual/vm/internals.md`(목차의 "18. 내부 구조")는 "이 쪽의 출력은 모두 실제 명령의 결과다"라고 쓰지만,
`fung dump` 출력 일곱 곳을 `plain`·`core` 펜스에 손으로 적었다(겉 트리, 코어 트리, `sq`의 바이트코드, `greet`, `adder`, `count`, `match`). 생성기는 이것을 검사하지 않는다.
2026-10-26 릴리스 바이너리(HEAD `e1cf47b` 무렵 빌드)로 같은 프로그램을 돌리면 이미 다르다.

```
== <main> ==                                  매뉴얼(손으로 적음)
0003  2:6   CONST        1    ; [1, 2, 3]     0003~0006: CONST 1·2·3 + LIST 3
...                                           (P7의 리스트 상수 접기 전 모양)
0012  3:1   POP                               없음 (마지막 식도 POP하고 nil을 돌려줌, E0606)
0013  3:1   CONST        4    ; nil
== sq ==
0001  1:16  MOVELOCAL    0                    LOADLOCAL 0 (P9의 MOVELOCAL 전 모양)
```

`greet`·`adder`·`count`도 마지막 읽기가 `MOVELOCAL`로 바뀌었고, `adder`의 위치는 한 줄짜리 예인데 `2:15`처럼 둘째 줄로 적혀 있다.
`match` 예는 `v`가 어디서 오는지 없는 조각이라 실제로 같은 번호를 만들 수 없다(함수 안에 넣어 돌리면 `STORELOCAL`로 시작하고 첫 절이 `TAILCALL`이다).
겉 트리·코어 트리는 실제로는 한 줄로 찍히는데 들여쓴 모양으로 적었다. 산문에도 낡은 문장이 있다: "여러 태스크가 서로 다른 운영체제 스레드에서 같은 바이트코드를
번갈아 실행한다"는 R1b의 M:1 스케줄러 전 설명이다(지금은 실행 스레드 하나). 원고 지침(`docs/plans/2026-10-20-manual-2-content.md` 73줄)이
이 파일을 "부록으로 남는다, 고치지 않는다"로 두어서 생긴 일이다. 설계(`docs/superpowers/specs/2026-10-20-manual-structure-design.md` 3.4절)는 "`fung dump` 출력은 실제 출력이고 테스트가 지킨다"를 규칙으로 정했다.

**2. 언어 명세가 얕다.** `manual/reference/language.md`는 593줄 한 페이지다. 표와 짧은 목록이 중심이고, 실행되는 예는 `fung run` 16개, 실행하지 않는 조각(`fung frag`) 8개다.
에러 번호는 27번 나온다. 함수 레퍼런스는 PHP식 형식(설명 → 매개변수 → 돌려주는 값 → 에러 → 예제 → 같이 보기, 지침 60줄)을 갖췄지만 언어 명세에는 같은 깊이의 틀이 없다.
규칙마다 경계 사례(예: `if` 값 자리의 E0223, 파이프의 `_` E0227, 줄 이어짐의 예외)와 그 자리에서 나는 에러, 실행된 출력을 함께 보여 주지 않는 절이 많다.

## 지금 동작과 원인

- 생성기: `crates/fung-cli/tests/manual_site/`. 펜스 종류는 `markup.rs` `fence()`: `fung run|check|frag`, `dump ast|core|bytecode`, `shell`, `plain`, `core`, `file NAME`, `expect`.
  `dump` 펜스는 속성을 받지 않고(`&[][..]`), `examples.rs`가 `fung dump <단계> example.fung`을 돌려 출력 **전체**를 `render.rs`가 `$ fung dump …` 머리와 함께 넣는다.
  `plain`·`core`는 원문을 그대로 찍는다. 그래서 손으로 적은 dump는 검사 밖이다.
- VM 책 1~17장은 이미 `dump` 펜스를 쓴다(5장 12개, 6장 6개, 9장 6개 등). 손으로 적은 dump가 남은 곳은 `internals.md`뿐이다(`== 이름 ==`·`0000  1:1` 모양을 훑어 확인).
- 언어 명세의 절과 앵커(`lexical`·`values`·`results`·`for` 등)는 매뉴얼 44개 파일에서 링크된다(가장 많은 `#values`·`#results`가 각 16번). 깨진 내부 링크는 생성기가 막는다.
- 명세의 근거는 `docs/design/01`~`08`이다. 원고는 설계 문서를 옮기되 결정의 기록은 담지 않는다.

## 고려할 점

- 검사되는 출력은 "주석을 달 수 없다"는 대가가 있다. 지금 손 dump는 줄 끝에 설명(`; 슬롯 1이 차 있으면 기본값 건너뛰기`)을 붙인다. 설명은 산문이나 표(8장의 명령별 표처럼)로 옮긴다.
- 출력 전체를 넣으면 `<main>`의 `CLOSURE`·`STOREGLOBAL`·`CONST nil`·`RETURN`이 매번 따라온다. 한 함수만 보이고 싶은 자리가 많다.
- 부록과 1~17장의 겹침: 부록은 한 페이지 요약이고 장들은 길다. 부록을 없애면 관리할 곳이 줄지만 `docs/internals.html`(옛 주소)과 0.4.0 얼린 판이 가리키는 곳이다.
- 언어 명세의 깊이: PHP 매뉴얼의 언어 레퍼런스는 주제마다 페이지(타입, 연산자 묶음, 제어 구조 하나씩)를 두고 규칙 → 예제와 출력 → 주의 → 바뀐 판을 적는다.
  Python의 Language Reference는 형식 문법 조각 + 의미를 문장으로, Go 명세는 한 페이지에 EBNF 조각과 짧은 예. fung은 "찾아보는 곳"이므로 규칙과 경계 사례가 먼저이고, 배우기 책의 설명을 되풀이하지 않는다.
- 페이지를 나누면 링크 44개 파일의 앵커를 옮겨야 한다(생성기가 깨진 링크를 잡아 주므로 빠뜨릴 걱정은 없다). `docs/latest`는 아직 릴리스 전이고 0.4.0 판은 얼어 있어 바깥 링크의 깊은 주소만 문제다.

## 선택지

VM 부록:
(가) 손 dump를 모두 `dump` 펜스로 바꾸고 출력 전체를 보인다. 생성기 변경 없음. `<main>`이 매번 붙고 긴 `match` 예가 화면을 채운다.
(나) `dump` 펜스에 속성 `fn=NAME`을 더해 그 함수의 `== NAME ==` 덩어리만 보인다(없으면 에러). 생성기 수십 줄과 `markup.rs`·`examples.rs` 시험. 설명은 펜스 아래 산문·표로.
(다) 손으로 적되 주석을 떼고 실제 출력과 비교하는 "주석 단 dump" 펜스. 주석이 살지만 비교 규칙(무엇이 주석인가)이 복잡하고 부분 발췌(`…`)까지 다루기 어렵다.
(라) 부록을 없애고 내용을 1~17장으로 흩는다. 관리 지점은 줄지만 한 페이지 요약을 잃고 옛 주소를 옮겨야 한다.
추천: (나). 검사되는 출력이라는 설계 규칙을 지키면서 보이고 싶은 함수만 보일 수 있다. 1~17장에서도 바로 쓸 수 있다. 덧붙여 `plain` 펜스에 dump 모양(`== 이름 ==` 줄 + `0000  줄:칸` 줄)이 있으면 생성기가 에러를 내게 해 다시 손으로 적지 못하게 한다.

언어 명세:
(가) 한 페이지를 유지하고 절마다 틀(규칙 → 실행 예와 출력 → 경계 사례 → 에러 번호와 `errors.html` 링크 → 같이 보기)을 채운다. 앵커가 그대로다. 페이지가 2~3배로 길어진다.
(나) `reference/language/*.md`로 나눈다(어휘, 블록과 줄 이어짐, 값과 타입, 연산자와 파이프, 스코프, 함수, 조건과 `for`, 패턴, 결과값, 모듈, 타입 표기, 테스트, 형식 문법). 각 페이지에 같은 틀. 링크 44개 파일을 옮긴다.
추천: (나). 찾아보는 곳은 주제 하나가 한 화면 단위여야 하고, 함수 레퍼런스가 이미 "모듈 하나 = 한 페이지"다. 앵커 옮기기는 생성기가 검사하므로 비용이 한 번뿐이다.

## 정할 것

1. VM 부록의 방법: (나) `fn=NAME` 속성(추천) / (가) 출력 전체 / (라) 부록 없애기.
2. 겉 트리·코어 트리의 한 줄 출력: 그대로 둔다(추천, 작은 예를 골라 읽을 만하게) / `fung dump`에 들여쓴 출력을 더한다(도구 동작이 바뀌고 dump 기대 출력 전부가 바뀜, 이 문서의 범위를 넘는다).
3. 언어 명세의 모양: (나) 주제별 페이지(추천) / (가) 한 페이지. 나눈다면 `reference/language.html`을 목차 페이지로 남겨 옛 앵커를 새 페이지로 안내할지(추천: 남긴다, 앵커마다 링크 한 줄).
4. `fung frag` 조각: 가능한 것은 `file` 준비물과 함께 `fung run`으로 바꾼다(추천). 네트워크·`fs` 부수효과가 꼭 필요한 조각만 `frag`로 남긴다.
5. 명세 페이지의 틀에 "바뀐 판"(PHP의 changelog 표)을 넣을지: 넣지 않는다(추천, 0.5.0 전에는 CHANGELOG가 그 역할이고 사용자가 없다).

## 할 일

1. 시험 먼저: `markup.rs` 단위 시험에 `dump bytecode fn=greet` 파싱, 없는 함수 이름의 에러, dump 모양을 품은 `plain` 펜스의 에러를 더하고 실패를 확인한다. `examples.rs`·`render.rs`의 발췌 시험도.
2. 생성기: `Kind::Dump`에 함수 이름 선택을 더한다(`== NAME ==`부터 다음 빈 줄 또는 다음 `==`까지). 펜스 형식 설명(`docs/plans/2026-10-20-manual-1-skeleton.md` "원고 형식")을 갱신한다.
3. `internals.md`: 일곱 손 dump를 `dump` 펜스로 바꾸고, 줄 끝 설명은 산문·표로 옮긴다. `match` 예는 실행 가능한 함수로 다시 쓴다. 낡은 산문(운영체제 스레드, 그 밖에 읽으며 찾는 것)을 지금 구현(`docs/notes/R7-scheduler.md`, P7·P9)에 맞춘다.
   `docs/plans/2026-10-20-manual-2-content.md`의 "고치지 않는다" 문구를 지운다.
4. 언어 명세: 정한 모양으로 다시 쓴다. 절마다 근거가 되는 `docs/design/0n` 절을 확인하고, 경계 사례의 에러는 실제로 돌려 `fung run`(`exit=N`) 펜스로 보인다. 링크하는 원고들을 고친다.
   설계 문서와 어긋나는 것을 찾으면 임의로 정하지 말고 사용자에게 묻는다.
5. `toc.txt`를 고치고 `FUNG_UPDATE_MANUAL=1 cargo test -p fung-cli --test manual_build`로 `docs/latest/`를 다시 만든 뒤 diff를 검토한다.
6. 설계 스펙(`docs/superpowers/specs/2026-10-20-manual-structure-design.md` 3.3절)에 명세 페이지의 틀을 적는다. open-questions "매뉴얼"의 첫 항목을 닫는다.
7. CHANGELOG `[Unreleased]`: 매뉴얼 구성 변경을 한 줄 적는다(언어 동작 변화는 없음).
8. 커밋 전 검사 전부(CLAUDE.md).

## 끝의 기준

- `manual/` 어디에도 손으로 적은 `fung dump` 출력이 없고, 생성기가 그런 `plain` 펜스를 거절한다(시험이 지킨다).
- `internals.md`의 모든 dump가 `dump` 펜스이고, 컴파일러를 바꾸면 매뉴얼 빌드가 다시 만들 출력을 보인다.
- 언어 명세의 모든 절(또는 페이지)이 같은 틀을 갖고, 규칙마다 실행된 예가 하나 이상, 그 절에서 나는 컴파일·런타임 에러가 번호와 함께 링크되어 있다.
- 매뉴얼 빌드·`manual.rs`·커밋 전 검사가 통과하고 깨진 링크가 없다.

확인하지 못한 것: 형식 문법 절의 EBNF가 파서와 같은지 지키는 시험은 찾지 못했다(문장으로만 "파서가 그대로 옮긴" 것). 명세를 다시 쓸 때 확인한다.
