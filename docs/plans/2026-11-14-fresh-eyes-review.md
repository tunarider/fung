## 4. 높음

### SP82. 채널이 닫히는지가 변수의 자리에 달려 있다 — 결정, 높음

**재현.** 같은 생산자·소비자 코드다. 채널을 만든 자리만 다르다.

```
# (가) 바깥 함수에서 만든 채널: 1, 2를 찍고 E0702
fn main():
  (tx, rx) = channel(1)
  scope(fn(s):
    spawn(s, () => each([1, 2], x => send(tx, x)!))
    for x in rx: print(x) ;;
  ;;)!
;;
main()
```

```
# (나) scope의 함수 안에서 만든 채널: 정상 종료 (매뉴얼 12장의 예)
done = scope(fn(s):
  (tx, rx) = channel()
  spawn(s, () => each([1, 2], x => send(tx, x)!))
  for r in rx: r ;;
;;)!
```

**확인.** (가)는 `1`, `2` 뒤에 `error[E0702]: deadlock: all tasks are waiting`. 채널을 최상위에서 만들어도 E0702. 생산을 `fn produce(s, tx)`로 뽑아 인자로 넘겨도 바깥 함수가 `tx`를 붙잡은 익명 `fn` 안에서 받으면 E0702. (나)는 끝난다.

**명세.** `scope.md` "값의 수명": 변수는 마지막 읽기 뒤에 값을 놓고, 그래서 "함수 안에서 만든 채널의 보내는 끝을 생산 태스크에 넘기면, 생산이 끝날 때 채널이 닫힌다". 놓는 시점의 규칙이 일곱 가지 적혀 있다. 최상위 변수는 끝까지 살고, 익명 `fn`이 붙잡은 값은 그 함수가 도는 동안 산다.

**어긋나는 지침.**
- 4: 결과가 구현의 속사정(수명 분석이 어디까지 보는가)에 달려 있다.
- 2: 같은 코드가 블록의 깊이와 파일의 역할(최상위냐 함수 안이냐)에 따라 다르게 동작한다.

**선택지.**
- (A) 채널은 `close(tx)`로만 닫힌다. 값의 수명은 관찰되지 않는 최적화가 되고, `scope.md`의 "값의 수명" 문단은 VM 책으로 간다.
- (B) 그대로 둔다.

**추천 A.**

**A가 깎는 편의.**

```
# 지금
spawn(s, () => each(1..=4, j => send(tx, j)!))
# A
spawn(s, fn():
  each(1..=4, j => send(tx, j)!)
  close(tx)
;;)
```

- `close`를 잊으면 지금의 (가)와 같은 E0702로 곧바로 드러난다. 조용히 틀린 값은 없다.
- 생산자가 여럿이면 "모두 끝난 뒤 닫기"를 안쪽 `scope`로 쓴다. 이 모양은 돌려 보지 못했다.
- 생산자가 `!`로 죽으면 범위가 나머지를 취소하므로 닫힘이 필요 없다. 생산자가 `?`로 일찍 돌아가는 길은 `close`를 지나지 않아 E0702가 된다(`with`로 감싸야 한다). 이 비용이 A의 가장 큰 흠이다.

**확신.** 중간. 여러 생산자와 일찍 돌아가는 생산자의 실제 모양을 코드로 써 본 뒤 정하는 것이 좋다.

**닿는 이전 결정.** 동시성 v2 L4(채널 두 끝과 자동 닫힘), 11-08 VM1·VM2(문장 뒤 놓기), 다섯 번째 점검 VA59.

**결정할 때 고친 것 (2026-11-14).**
- 지침 4는 약한 근거다. "마지막 읽기 뒤에 놓는다"는 소스만으로 정해지므로 구현의 속사정이 아니다. 어긋나는 것은 지침 2(자리에 따라 다름)와 지침 3(닫는 방법이 둘)이다.
- 받는 끝도 저절로 닫힌다: 받는 끝의 마지막 사본이 사라지면 `send`가 `Err({kind: 'closed})`다(확인).
- 걱정하던 모양을 지금 바이너리에서 `close`를 직접 써서 돌렸다. 여러 생산자(안쪽 `scope` 뒤 `close(tx)`)와 `?`로 일찍 돌아가는 생산자(`with(() => tx, use, t => close(t))`)는 동작한다. `close(rx)`는 지금 E0403이다.

**결정: D136(A, `close`로만 닫힌다), D137(`close`가 받는 끝도 받는다).** 뒤집는 결정과 그때의 까닭은 결정 문서에 적었다.

처리: 2026-11-15, D136·D137, 묶음 6. `vm/channel.rs`의 `Sender`·`Receiver` `Drop`(자동 닫힘)과 `value/release.rs`의 끝 놓기 때의 닫기·버리기를 지움. 끝이 모두 사라지면 채널 자체가 풀린다. `close`(`conc.rs`)가 받는 끝을 받아 `abandon`(닫고 버퍼를 버림). 런타임 안에서 사본을 놓아 닫던 정지 채널(`vm/stop.rs`)은 `close`로 닫는다. E0702의 도움말(`deadlock.rs`)을 "채널은 `close`로만 닫힌다"로 바꾸고 받는 쪽이 기다리면 늘 붙인다. E0709는 그대로(문장의 "닫히지 않는다"만 "해제되지 않는다"로). `extras/conc.fung`의 `fan_in`은 출력이 닫히면 아직 열린 입력을 `close`한다(입력을 넘겨받는 함수의 규칙으로 정함). 값을 놓는 시점을 채널로 보이던 `tests/lang/local_lifetime.fung`은 시험용 탐침(`token`·`alive`)을 쓰는 `vm/lifetime_tests.rs`로 옮김. 매뉴얼 12장(예제마다 `close`, "짚고 넘어가기"), 동시성 레퍼런스(`channel`·`send`·`wait_closed`·`close`), `scope.md`의 "값의 수명"은 VM 책 10장으로(채널 문장 지움), VM 10·12·14장·내부 구조, E0702, 설계 문서 05·03, 동시성 v2 스펙 6절과 `R7-language.md`에 뒤집었다고 적음.

### SP83. prelude 이름을 가릴 수 있는지가 깊이와 공개 여부에 달려 있다 — 결정, 높음

**재현과 확인.**

```
lines = split("a\nb", "\n")       # 최상위: 된다
print(lines)
```

```
fn f(s):
  lines = split(s, "\n")          # E0238: cannot bind `lines` again
  lines
;;
```

```
fn f(s, timeout = 1s) = (s, timeout)     # 된다 (공개 fn의 매개변수)
fn _g(s, timeout = 1s) = (s, timeout)    # E0238 (비공개 fn의 매개변수)
```

```
lines = [1]
print(lines("a\nb"))              # 실행 중 E0401: 최상위 이름이 파일 전체에서 prelude를 가린다
```

**명세.** `scope.md` 2번: "예외는 하나다: 파일의 인터페이스(공개 최상위 이름과, 호출이 이름으로 줄 수 있는 공개 `fn`의 매개변수)는 prelude 함수와 같은 이름일 수 있다." 나머지 매개변수(`...len`)와 패턴 매개변수는 다시 예외의 예외다.

**어긋나는 지침.** 2: 명세가 스스로 예외라고 적었고, 조건이 셋이다(공개인가, 최상위인가, 이름으로 줄 수 있는 매개변수인가). 흔한 변수 이름(`lines`, `first`, `last`, `keys`, `values`, `min`, `max`, `sum`, `args`, `env`, `timeout`)이 모두 prelude 함수라, 최상위에 쓴 스크립트를 함수로 옮기면 에러가 된다.

**선택지.**
- (A) 인터페이스도 prelude 이름을 쓸 수 없다. 예외가 없다.
- (B) 어떤 묶기든 prelude 이름을 가릴 수 있다. "보이는 이름은 다시 묶을 수 없다"에 예외가 하나 남지만 깊이·공개 여부와 무관하다.
- (C) 그대로 둔다.

**추천 A.** 지침 6대로 예외 없는 쪽이다.

**A의 비용.**
- 표준 모듈의 공개 이름 8개를 바꾼다: `http.get`, `path.join`, `regex.split`·`regex.find`·`regex.replace`, `fs.write`·`fs.remove`·`fs.read_lines`. 매개변수 3개도(`http`의 `timeout`, `fs`의 `lines`, `cli`의 `values`).
- 사용자의 모듈도 `get`·`find`·`join` 같은 이름의 함수를 둘 수 없다. 에러는 컴파일 때 난다.
- prelude에 함수를 더할 때마다 그 이름을 쓰던 프로그램이 깨진다. 이것이 A의 가장 큰 흠이다. 치르기 어렵다고 보면 B다.

**B의 비용.** 가린 뒤 prelude 함수를 부르면 E0401이다(곧바로 드러난다). 규칙 문장에 "prelude 함수는 가릴 수 있다"가 남는다.

**확신.** 낮음~중간. A와 B 사이는 사용자의 판단이 필요하다. C보다는 둘 다 낫다.

**닿는 이전 결정.** D88(이름은 한 번만 묶임), D86(공개 최상위 이름은 인터페이스), D122.

**결정: D138(B, 어디서나 가릴 수 있다), D139(가린 블록 전체에서 가려진다).** 추천을 A에서 B로 바꿨다. 까닭은 결정 문서에 적었다.

### SP85. E0234가 내장 함수에만 있다 — 결정, 중간

**재현과 확인.**

```
fn double(n) = n * 2
fn f(a):
  double(a)                       # 통과한다. 5를 찍는다
  a
;;
print(f(5))
```

```
xs = [3, 1]
map(xs, x => print(x))            # E0234: the result of `map(…)` is computed and discarded
```

문장 `sort(xs)`, `put(m, "b", 2)`는 E0234다(명세의 예).

**명세.** `blocks.md`: "효과가 없다고 알려진 내장 함수·표준 모듈 함수의 호출은 인자와 상관없이 E0234다." "`each`와 사용자 함수는 된다." 함수를 받는 내장 함수는 이름을 나열한다(`map`·`filter`·`fold`·…).

**어긋나는 지침.** 2: "내장 함수에만 있고 사용자 함수에는 없는 검사"이고, 특정 이름을 나열하는 규칙이다. 효과가 있는 `map(xs, x => print(x))`는 "아무 일도 하지 않는 식"이 아닌데 에러다.

**선택지.**
- (A) 호출 대상이 컴파일 때 정해지는 사용자 함수도 본문이 효과 없는 식뿐이면 같은 판정을 받는다. 함수를 받는 함수는 넘긴 함수가 효과 없을 때만 효과 없다.
- (B) 호출이 든 식은 내장이든 아니든 검사하지 않는다(이름·리터럴·연산자만 E0234).
- (C) 그대로 둔다.

**추천 A.** 예외 없는 둘 가운데 실수를 더 일찍 잡는다(지침 6).

**B의 비용.** `put(m, "b", 2)`가 조용히 통과한다. `m`이 바뀌지 않은 채 프로그램이 계속 돈다(조용한 틀린 값). 이것 때문에 B를 버린다.

**A의 비용.** `map(xs, x => print(x))`가 문장으로 통과한다(리스트를 만들고 버린다). 틀린 값은 없다.

**확신.** 중간. "효과 없는 본문"의 판정이 서로 부르는 함수에서 어떻게 되는지 구현해 보지 않았다.

**닿는 이전 결정.** D90(`map`·`filter` 등의 문장도 E0234), 다섯 번째 점검 FE77, 11-13 VA47(`pure` 표시).

**결정: D141(A, 본문을 읽어 정한다).** 표시의 방향과 할 일은 결정 문서에 적었다.

처리: 2026-11-15, D141, 묶음 5. 새 `resolve/effect.rs`: resolve가 함수마다 효과가 될 수 있는 일(대상을 아는 호출과 그 인자, 매개변수의 호출, 모르는 호출, `assert`, `!`)을 적고, 파일을 다 풀면 함수(키는 `fn` 노드의 자리)의 요약 "이 매개변수로 받은 함수가 효과 없으면 효과 없다"를 고정점까지 구한 뒤 E0234의 호출 자리(`pure_calls`)를 정한다. `Sig`에 `calls`(부르는 매개변수)와 `body`(이 파일의 fung 함수)를 더함; 다른 파일에는 계산한 `pure`·`calls`로 내보낸다. 밑바닥 함수는 매개변수 `f`·`pred`를 부른다고 본다(명세의 이름 관례; 명세 생성이 fung 함수의 계산 결과와 같은지 단언). D90의 `RUNS_A_FUNCTION`, VA47의 `PURE_FUNG`·`CALLING_FUNG`를 지움. 결정 문서에 없던 판단 둘: (1) 인자 검사 `_native.arg`·`_r.pad`는 "일부러 에러를 낸다"며 순수 표시에서 뺐었으나, `len`처럼 계산만 하고 에러를 낼 수 있는 것이라 `pure`로 두고 extras의 문장 호출을 `_ = _arg.count(…)`로 고쳤다(안 그러면 그것을 쓰는 `drop`·`pad_left`·`iterate` 등이 모두 효과 있는 함수가 되어 E0234를 놓친다). (2) `first`·`take`·`zip`은 본문이 받는 끝을 읽어(`_receive`) 효과가 있는 함수가 되었다(VA47이 손으로 `pure`라 했던 것). E0707(`swap` 안의 효과)은 `EFFECTS` 표를 따로 쓰므로 바뀌지 않는다. 바깥 매개변수를 붙잡은 람다 안의 호출은 모르는 호출로 본다(보수적). 브랜치 점검에서 고친 것: 고정점을 작업 목록으로(바뀐 함수를 읽는 함수만 다시 봄, 함수 2만 개 사슬 11.5초 → 0.18초, 릴리스 성능 시험), 같은 파일의 함수를 받는 함수의 E0234 도움말도 `each`를 알림(요약에서 정함), 인자 검사를 호출마다 한 번만. 시험 프로그램의 `spin(n)`·`fib(30)` 문장은 `_ = …`로, E0606을 보이던 순수 함수는 `assert true`로 효과를 주었다. `blocks.md`·E0234·배우기 9장·`results.md`, 설계 문서 01.

### SP86. 람다와 익명 `fn`이 같은 위험에서 다르게 다뤄진다 — 결정, 중간

**재현과 확인.**

```
fn bad(xs) = map(xs, s => parse_int(s)? * 2)             # E0237: `?` inside a lambda
```

```
fn a(xs) = map(xs, fn(s): parse_int(s)? * 2 ;;)
print(a(["1", "x"]))              # [2, Err({kind: 'parse, …})]
```

**명세.** `functions.md` "람다의 본문": `?`가 돌려준 `Err`가 리스트의 원소가 되거나 조건이 되어 "말없이 섞이기 때문"에 람다에서는 E0237이다. "일찍 돌아가야 하면 익명 함수로 쓴다."

**어긋나는 지침.** 2: "규칙의 까닭은 닿는데 가장 단순한 모양에서만 적용되는 것". 적힌 까닭은 익명 `fn`에도 똑같이 닿는다. 람다는 지침 3이 설탕으로 인정한 표기인데, 설탕과 풀어 쓴 꼴의 뜻이 다르다.

**선택지.**
- (A) 람다에도 `?`·`return`을 허용한다. 람다는 식 하나짜리 익명 `fn`이다.
- (B) 그대로 둔다.

**추천 A.**

**A의 비용.** `map(xs, s => parse_int(s)? * 2)`가 `Err`가 섞인 리스트를 준다. 그 값은 버리면 E0606, 보간하면 E0519, 계산하면 타입 에러로 드러난다. 지금도 익명 `fn`으로 쓰면 같은 일이 난다.

**함께 정할 것: `for` 본문.** 명세가 서로 다르게 말한다.
- `scope.md` 5번: "`if` 가지, `match` 절, `for`가 모두 블록이다."
- `for.md`: "본문이 사실은 람다이므로 `return`과 `?`는 E0237이다."

블록이라면 `if` 가지처럼 `return`이 감싸는 `fn`에서 돌아와야 한다. 람다라면 A를 따라 `return`이 본문에서만 돌아오는데, 그러면 `for x in xs: if x > 2: return x ;; ;;`가 조용히 다른 뜻이 된다. 선택지는 (1) `for`는 블록이고 `return`·`?`가 감싸는 `fn`에서 돌아온다, (2) `for` 본문만 E0237을 남긴다. 확신이 낮아 추천을 내지 않는다.

**닿는 이전 결정.** 세 번째 점검의 E0237(E0213·E0220·E0226을 합침).

**결정: D142(A, 람다에도 허용), D143(`for`는 편의용 설탕이고 본문의 `return`·`?`는 E0237로 남는다).**

처리: 2026-11-15, D142·D143, 묶음 4. resolve의 `early_return`이 `for` 본문에서만 E0237을 낸다(FnScope의 `lambda` 표시는 쓰는 곳이 없어 지움). 람다 본문은 파서가 이미 `fn f() = 식`처럼 `return`을 받아(E0132도 같음) 고칠 것이 없었다. 꼬리 호출은 람다도 익명 `fn`과 같은 컴파일러 길이다(`loop(100000)` 확인). E0131은 식 하나짜리 본문이라 해당하지 않고, 람다에는 반환 타입 표기가 없다. 카탈로그 E0237 도움말, `for.md`(설탕의 정의와 E0237의 까닭)·`functions.md` "람다의 본문"·`scope.md` 5번·`grammar.md`·E0237·E0226, 배우기 9장, `collections.md`, 설계 문서 03. `tests/lang`의 람다 E0237 다섯을 `lambda_early_return.fung` 하나로.

### SP90. 같은 일을 하는 함수가 둘이다 — 결정, 중간

## 7. 보았지만 제기하지 않는 것

- **`nil`과 `Err`, 두 가지 "없음".** `get`·`find`·`first`·`last`·`min`·`max`·`env`·`index_of`·`regex.find`는 `nil`을, `parse_*`·`fs.*`는 `Err`를 준다. `get({a: nil}, "a")`와 없는 키가 구별되지 않는다(확인: 둘 다 `nil`). `find([nil, 1], x => x == nil)`도 `nil`이다.
  실제 비용은 작다: 잘못 붙인 `?`는 E0604로 드러나고, `??`는 둘 다 받으며, 값이 `nil`인 키와 없는 키를 갈라야 하는 코드는 `k in m`으로 쓴다. 유지를 추천한다. 확신은 낮다.
- **`1 == 1.0`.** "타입이 다른 값은 같지 않다"의 예외다. 없애면 `/`가 늘 실수라 `x / 2 == 1`이 조용히 거짓이 된다. 치르지 못할 비용이라 유지한다.
- **범위와 문자열.** 범위는 함수의 입력으로만, 문자열은 연산자(`[]`, 슬라이스, `+`, `in`)와 `len`으로만 리스트 같다. 각각 한 문장 규칙이다("연산자는 리스트, 함수는 순회할 수 있는 것", "문자열은 글자의 리스트가 아니다"). 확인: `(0..3)[1]`은 E0509, `(0..3) + [9]`는 E0501, `reverse("abc")`·`map("abc", f)`는 E0506.
- **`in`이 그릇마다 다른 것.** `1 in "abc"`는 E0501, `1 in {a: 1}`은 E0514, `"1" in [1]`은 `false`. 각 그릇의 다른 연산(부분 문자열, 키 조회, `==`)과 같은 규칙이다.
- **맵의 순서.** `{a: 1, b: 2} == {b: 2, a: 1}`은 `true`이고 찍힌 모양과 `keys`는 다르다. 넣은 순서는 프로그램이 정한 것이라 지침 4의 "속사정"이 아니다.
- **크기에 따라 달라지는 에러.** `sort([true])`, `unique([f])`, `max([true])`는 원소가 하나여도 에러다(확인). 지침 4에 맞다.
- **정수가 필요한 자리의 실수.** `xs[1.0]`은 E0509, `repeat("a", 2.0)`·`take(xs, 2.0)`은 E0403, `0..3.0`은 E0501. 같음(`1 == 1.0`)과 타입(`int`)은 다른 규칙이고 서로 어긋나지 않는다.
