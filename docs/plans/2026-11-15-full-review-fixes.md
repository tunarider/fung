# 일곱 번째 점검의 결정과 작업 (2026-11-15)

점검 문서 `docs/plans/2026-11-15-full-review.md`(SP98~SP106, FE83~FE85, VM55~VM59, VA72~VA75)의 결정을 모은다. **이 문서의 표가 기준이다.**
결정 번호는 여섯 번째 점검과 매뉴얼 점검(D136~D161)에 이어 D162부터다.

**상태 (2026-11-15)**: 결정 항목 열한 개(VM56, SP98~SP105, VM59, VA74)를 사용자와 하나씩 모두 정했다(D162~D171, SP104는 D164에 듦). 점검 문서의 추천과 다른 곳은 없고, 추천이 없던 VM59는 (나)로 정했다. 고친 것은 표 아래의 **처리** 문단에 적는다.

## 1. 결정

| D162 | VM56 | 쥐기만 하는 변수는 꼬리 호출을 넘어 산다: 꼬리 호출로 자리를 넘겨줄 때 쥔 값을 프레임이 이어받고, 그 프레임이 실제로 돌아올 때 놓는다. 꼬리 호출 규칙에 조건이 붙지 않고, 부르는 함수가 Rust든 fung이든 같다. 구현이 무겁거나 꼬리 호출이 느려지면 (나)(쥐기만 하는 이름이 있는 길의 꼬리 호출은 `CALL` + `RETURN`)로 물러나고 사용자에게 알린다 | 없음(명세 "함수가 돌아올 때까지 산다"를 지킨다) |

**처리**: 수명 묶음(VM55, D162·D172, VM57), 이름 묶음(D163, D168), 컴파일 때 검사 묶음의 D164·FE83·D166과 D165(D173; prelude, 모듈의 `_native.*`, 함수 레퍼런스의 타입)와 `return`·효과 묶음(D167, D169), 값 묶음(D171, VA72, VA73, VA75)을 2026-11-15~16에 고쳤다(점검 문서의 `처리:` 줄). D171의 측정: 길이가 다른 줄들의 `sort`가 5~8% 느려졌고, 긴 리스트와 짧은 접두사의 `<`는 긴 쪽 길이에 비례하게 되었다. 나머지 묶음(FE84, FE85, VM58, D170, SP106)도 2026-11-16에 고쳐 스무 항목이 모두 끝났다. FE85의 넷째(E0301이 보이는 경로)만 그대로 두었다(점검 문서의 `처리:` 줄).

**브랜치 점검 (2026-11-16)**: 고친 것 전체를 따로 검토해(이전 커밋과의 바이트코드 dump 대조, 무작위 프로그램) 둘을 더 고쳤다. (1) 매개변수 기본값 안에서 묶은 `_이름`이 매개변수의 칸을 차지하던 것(D162의 "새 칸" 배정이 매개변수 칸을 아직 쓴 것으로 치지 않았다: `fn w(a, b = (match a: [_x, ...] => 1; _ => 2 ;;), c = 3)`이 E0801). `resolve/fn_.rs`가 기본값을 읽기 전에 `max_slot`을 매개변수 수로 올린다. (2) `5(..."a")`가 컴파일 때는 E0401, 실행 때는 E0506이던 것(D166의 "실행 때와 같은 에러"): 펼침이 먼저다. 매뉴얼은 VM 장 다섯 곳(내장 함수의 타입 표, 가려진 prelude 이름과 E0206, 효과 요약, 바이트 문자열의 보기와 `trim`, `return`의 수명 분석)과 `operators.md`·`results.md`의 `?? return`을 채웠다.
