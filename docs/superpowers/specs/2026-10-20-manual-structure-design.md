# 매뉴얼 재구성 설계

2026-10-20. 지금의 매뉴얼(`docs/index.html`·`syntax.html`·`builtins.html`·`internals.html`, 레퍼런스 형식 네 장)을
"언어 책 한 권을 대신하는" 매뉴얼로 다시 짓는다. 이 문서는 전체 구조와 뼈대를 정하고, 각 부분의 원고는 뒤의 작업 단위에서 쓴다.

상태: 1~5단계 끝(2026-10-20, 계획 `docs/plans/2026-10-20-manual-1-skeleton.md`, 작성 지침 `docs/plans/2026-10-20-manual-2-content.md`). 쓰며 찾은 문제는 `docs/plans/2026-10-20-manual-findings.md`.

## 1. 의도와 이유

- **가장 중요한 기준**: fung을 전혀 모르는 사람이 매뉴얼만 읽고 언어를 파악할 수 있어야 한다. 지금 매뉴얼은 이미 아는 사람이 찾아보는 레퍼런스라 이 기준을 채우지 못한다.
- **지향점**(꼭 지켜야 할 조건은 아님): fung이 **첫 프로그래밍 언어**인 사람도 따라올 수 있다. 그래서 "값", "변수", "함수가 값이다", "에러를 값으로 다룬다" 같은 일반 개념을 fung 문법보다 먼저 설명한다.
- **책 한 권을 대신한다**: 언어를 배울 때 사는 입문서를 이 매뉴얼이 대신한다. 고급 기술·최적화 팁 수준은 목표가 아니다.
- **PHP 매뉴얼에서 가져올 것**: 기본 설명, 함수마다 문장으로 쓴 설명(제약, 무엇을 할 수 있는지, 어떻게 하는 게 좋은지), 다양한 예시. PHP 매뉴얼의 전체 구성은 따르지 않는다.
- **VM 책은 사용자 본인이 첫 독자다**: 사용자는 언어 구현을 아직 공부하지 않았고, `docs/design`·`docs/notes`의 md 파일은 읽기 불편하다. VM 책은 "프로그래밍 언어 런타임 입문서"이고, fung은 그 개념을 실제로 보여 주는 예제다.

## 2. 목표, 비목표, 반목표

목표
- 네 부분(배우기·예제 모음·레퍼런스·VM, 3절)으로 나눈 정적 매뉴얼.
- 언어 명세(레퍼런스)와 fung VM(VM 책)을 분리한다.
- 모든 실행 가능한 예제가 실제로 돌고, 출력 칸은 실제 실행 결과이며, 테스트가 이를 지킨다.
- 버전별 디렉터리와 사이드바의 버전 드롭다운.

비목표
- 영어판. 매뉴얼은 한국어다(코드·코드 주석은 영어, 저장소 규칙대로).
- 고급 최적화 가이드.
- 0.3.0 이하 버전의 매뉴얼. 0.3.0까지는 별도 매뉴얼을 두지 않는다(4절).
- 첫 단계의 전문 검색. 지금 있는 내장 함수 필터는 유지한다. 검색은 뒤로 미룬다(open-questions에 적음).

반목표 (기술적으로 돌아가도 실패인 것)
- 예제 출력이 실제 동작과 어긋나는 매뉴얼.
- 처음 배우는 사람이 명세 규칙에 걸려 넘어지는 배우기 장. 정확한 규칙은 레퍼런스로 보내고 링크한다.
- 사이드바나 이전/다음 링크를 페이지마다 손으로 맞춰야 하는 구조.
- "미릴리스" 같은 표현. 릴리스 전 내용은 영어 **unreleased**로 표시한다(사용자 결정).

## 3. 구성: 네 부분

사이드바 맨 위에 버전 드롭다운, 그 아래 네 부분. 지금 보는 부분은 장 목록을 펼치고 나머지는 제목만 보인다(접고 펼치는 방식은 빌더 몫).
지금 장 아래에는 그 페이지의 절(`h2`) 목록을 보이고, **스크롤 위치에 따라 지금 읽는 절을 강조**한다(사용자 요청). 강조된 항목이 사이드바 밖으로 나가면 사이드바를 그만큼 스크롤한다. 페이지 맨 끝에서는 마지막 절이 강조된다. JS가 없으면 강조만 빠진다.

좁은 화면(860px 이하, 사용자 질문으로 정함): 사이드바 대신 페이지 위에 붙는 막대 하나를 둔다. 막대에는 부분의 표식, 지금 장 이름, 지금 읽는 절(스크롤에 따라 바뀜), 목차 단추가 보이고, 막대 어디를 눌러도 사이드바 전체(버전 선택 포함)가 왼쪽에서 서랍처럼 열린다. 서랍은 닫기 단추·바깥 누르기·Esc·링크 누르기로 닫히고, 열 때 지금 위치가 보이게 스크롤한다. 앵커로 이동하면 제목이 막대 밑에 가리지 않는다(`scroll-margin-top`). JS가 없으면 서랍 대신 사이드바 전체가 페이지 위에 펼쳐져 있다.

### 3.1 📘 fung 배우기 (처음부터 순서대로 읽는 책)

장 목록 초안(빌더가 조정 가능, 순서의 원리는 유지: 앞 장만 알면 읽힌다):
프로그래밍과 fung · 설치와 첫 프로그램(REPL 포함) · 값과 이름 · 조건과 반복 · 함수 · 문자열 다루기 · 리스트·맵·튜플 · 패턴과 match · 에러는 값이다 · 모듈로 나누기 · 파일·외부 명령·CLI · 동시에 여러 일 하기 · JSON과 HTTP · 테스트와 포맷터.

장의 형식(시안 `pages.html` 왼쪽):
1. **이 장에서 배울 것** 목록
2. 본문: 일반 개념을 먼저 설명하고 fung 문법으로 들어간다. 코드와 **실제 출력**을 한 쌍으로 보여 준다.
3. **"처음 배우는 분께"** 상자: 일반 개념. 이미 아는 사람은 건너뛸 수 있게 분리한다.
4. **"자주 하는 실수"** 상자: 에러 번호와 함께 그 규칙이 왜 있는지 설명한다.
5. **해 보기**: 작은 연습 문제와 접힌 풀이(`<details>`).
6. **정리**
7. **다리**: 같은 주제의 레퍼런스·함수·VM 페이지로 가는 링크.
8. 이전 장 / 다음 장.

### 3.2 🧰 예제 모음 (자주 하는 작업별 레시피)

사용자가 실제로 하는 작업에서 뽑았다: 반복문으로 여러 파일 다루기, 여러 서버에서 받아 하나로 모으기, curl로 받아 문자열 처리하기.

- *파일 다루기*: 파일 이름 일괄 변경 · 큰/오래된 파일 찾기 · 여러 로그에서 패턴 세고 요약 · 설정 파일 값 치환(sed 대신) · 표준 입력을 받아 파이프 중간에서 쓰기
- *여러 서버에서 모으기*: 여러 서버에 `ssh` 명령을 동시에 보내고 합치기 · 서버별 결과를 표 하나로 · 실패·무응답 서버만 알리기(시간 제한, 재시도)
- *HTTP와 문자열*: JSON API에서 필드 뽑기(curl + jq 대신) · URL 여러 개 상태 동시 확인 · 텍스트 응답을 정규식으로 쪼개기 · 페이지 넘기며 모두 받기 · CSV/JSON으로 저장
- *작은 도구 만들기*: 명령줄 옵션과 도움말 · 종료 코드와 stderr · 웹훅을 받는 작은 HTTP 서버

레시피의 형식: 문제 → **"쉘로는 보통 이렇게"**(bash 한두 줄) → fung 전체 코드 → 줄별 설명 → 응용 → 배우기·레퍼런스 링크.
서버 접속은 외부 명령으로 `ssh`를 부르는 방식으로 보여 준다(fung에 SSH 기능을 넣지 않음).
저장소의 `examples/`(`rename`·`bigfiles`·`logsum`·`checkurls`·`serve` 등)는 이 형식으로 다듬어 넣는다.
`examples/*.fung` 파일과 레시피 원고의 관계(원고가 파일을 불러올지, 원고 안에 코드를 둘지)는 빌더 몫이지만, 같은 코드를 두 곳에서 따로 관리하지는 않는다.

### 3.3 📖 레퍼런스 (찾아보는 곳 = 언어 명세)

- **언어 명세**: 어휘, 문장과 블록, 값과 타입, 연산자, 스코프, 함수, 패턴, 결과값, 모듈, 타입 표기, 테스트, 형식 문법. 지금 `syntax.html`의 내용이 바탕이다.
- **prelude**: 주제별(문자열, 리스트, 맵, 결과값, 동시성 …)로 묶는다.
- **표준 모듈**: `fs`·`path`·`cli`·`json`·`time`·`regex`·`http`·`conc`.
- **에러 카탈로그**: `spec/errors.txt`의 번호마다 뜻, 예시, 고치는 법.
- **명령줄 도구**: `run`·`-e`·`check`·`test`·`fmt`·`dump`·REPL·종료 코드.

함수 항목의 형식(시안 `pages.html` 오른쪽, PHP식): 한 줄 요약 → 시그니처 → 문장으로 쓴 설명 → 매개변수 표 → 돌려주는 값 → 에러 → 권장·주의 → 예제 여러 개(출력 포함) → 같이 보기.
페이지 단위는 **모듈 하나(prelude는 주제 하나) = 한 페이지, 함수마다 앵커**다(빌더 판단으로 정함. 함수마다 한 페이지씩 두면 수백 페이지가 된다).
`manual.rs`의 검사(모든 공개 이름이 한 번씩, 시그니처가 실제와 같음, "fung으로 작성" 표시)는 새 페이지들에 대해 그대로 유지한다.

### 3.4 ⚙️ fung VM (언어는 어떻게 만들어지나)

목차 초안(시안 `vm-page.html`):
- 1부 언어란 무엇인가: 프로그램이 실행되기까지 · 인터프리터, 컴파일러, VM
- 2부 앞단: 렉서 · 파서 · desugar와 코어 언어 · 이름 해석과 스코프 · 에러 메시지 만들기
- 3부 뒷단: 바이트코드와 스택 머신 · 함수와 클로저 · 값과 메모리(`Rc`, 영속 컬렉션) · 모듈 적재와 prelude
- 4부 런타임(두툼하게): 태스크와 스케줄러(M:1) · 이벤트 루프와 스레드 풀 · 취소와 정리
- 5부 도구: 포맷터 · REPL · 테스트 러너

규칙:
- **아무것도 모른다고 가정한다.** 토큰, 형식 문법, 재귀 하강 파서, 스코프와 환경, 스택, 클로저가 변수를 붙잡는 방법 같은 개념을 fung 코드보다 먼저 설명한다.
- 장의 흐름: **일반 개념 → 다른 언어는 어떻게 하나 → fung의 선택과 이유 → 실제 출력으로 따라가기 → 소스 위치 → 해 보기.**
- **같은 예제를 끝까지 따라간다**(예: `fn double(x) = x * 2` / `print(double(21))`). 맨 위의 단계 띠(소스 → 토큰 → 트리 → 코어 → 바이트코드 → 실행)로 지금 위치를 보인다.
- fung이 쓰지 않는 방식(가비지 컬렉터, 레지스터 머신, JIT, 1:1 스레드 등)도 비교용으로 짧게 다룬다. "이런 길도 있고, 이래서 fung은 가지 않았다" 정도까지만.
- "fung의 선택과 이유"는 지어내지 않고 `docs/design/*`(특히 `background.md`의 결정과 기각된 대안)와 `docs/notes/*`에서 가져온다. 근거가 없으면 사용자에게 묻는다.
- `fung dump ast|core|bytecode` 출력은 실제 출력이고 테스트가 지킨다.
- 한 장은 20~30분 안에 읽을 분량. VM 책은 배우기 책을 다 읽었다고 가정한다.
- 지금 `internals.html`의 내용이 출발점이다.

## 4. 버전 체계

- 지금은 `docs/latest/`만 둔다. 0.3.0까지는 따로 매뉴얼을 두지 않는다.
- `latest`는 **main의 현재 내용**을 가리킨다. 드롭다운 표기는 `latest (unreleased)`처럼 영어 **unreleased**를 쓴다. 0.4.0 이후에도 `latest`는 main이고, 페이지 맨 위에 "unreleased 버전의 문서" 띠를 둔다(설치한 바이너리보다 앞설 수 있으므로).
- 0.4.0을 릴리스할 때 `docs/0.4.0/`을 얼린다. 방법(설계자 판단): 단순 복사가 아니라 **생성기를 버전 인자와 함께 한 번 돌려** `docs/0.4.0/`에 만든다. 그래야 드롭다운 표기·unreleased 띠·경로가 그 버전에 맞게 나온다. 그래서 생성기는 첫 단계부터 "버전 이름, 출력 디렉터리"를 인자로 받는다. 테스트는 `docs/latest/`만 다시 생성해 비교하고, 얼린 디렉터리는 절대 다시 만들지 않는다.
- 자산(`style.css`·`site.js`·글꼴 링크)은 **버전 디렉터리마다 복사**한다. 공유하면 나중에 CSS·JS를 고칠 때 얼린 페이지가 몰래 바뀐다. 예외는 버전 목록을 읽는 드롭다운 JS로, 이것만 `docs/versions.js`(공유)에 둔다. 로고 이미지는 공유해도 된다.
- 드롭다운은 버전 목록(`docs/versions.json`, 또는 `file://`로도 열리게 `docs/versions.js`, 빌더 몫)을 작은 JS로 읽어서 채운다. 이렇게 하면 얼려 둔 옛 페이지에도 새 버전이 뜬다. JS가 없으면 드롭다운 자리에 현재 버전 이름만 보인다.
- 버전을 바꿀 때 같은 경로의 페이지가 있으면 그 페이지로, 없으면 그 버전의 첫 페이지로 간다.
- 기존 주소(`docs/index.html`·`syntax.html`·`builtins.html`·`internals.html`)는 `latest`의 해당 페이지로 넘겨 주는 짧은 페이지로 남긴다. GitHub Pages는 서버 쪽 리다이렉트가 없다. 루트 `docs/index.html`은 `latest/`로 넘긴다.
  `<meta http-equiv="refresh">`는 `#앵커`를 잃으므로, 넘기는 페이지는 작은 JS로 앵커를 붙여 넘기고(`builtins.html#fn-map` → 그 함수가 있는 새 페이지의 앵커, 옛 앵커 → 새 주소 표는 생성기가 만든다) JS가 없으면 meta refresh와 링크로 물러난다(설계자 판단).
- 릴리스 절차(`docs/notes/release.md`)와 `changelog.rs`의 "매뉴얼 버전 = CHANGELOG 절" 검사는 `versions.json` 기준으로 바꾼다. 0.4.0 전까지 `versions.json`에는 `latest`만 있으므로, 검사는 "가장 최근에 얼린 버전에 CHANGELOG 절이 있다"(없으면 통과)로 바꾸고, CLAUDE.md의 "매뉴얼 사이드바 버전을 함께 고친다"도 새 절차로 고친다.

## 5. 만드는 방식

### 5.1 원고와 생성기 (사용자 결정: 생성기 방식)

- 원고는 마크다운과 비슷한 간단한 형식으로 쓴다. 생성기는 **Rust 표준 라이브러리만으로** 직접 만든다(크레이트 추가 없음, 저장소 의존성 정책).
- 생성기가 HTML을 만들고, **만든 HTML도 커밋한다**(GitHub Pages가 "브랜치의 `/docs`를 그대로 배포"하므로 배포 때 빌드가 없다).
- 테스트가 "원고로 다시 생성한 결과 = 커밋된 `docs/latest/`"를 확인한다. 갱신은 `spec/*.txt`처럼 환경 변수로 한다(예: `FUNG_UPDATE_MANUAL=1 cargo test …`). 갱신 뒤에는 diff를 검토하고 커밋한다.
- 사이드바, 이전/다음 링크, "이 장에서 배울 것" 같은 반복 요소는 목차 파일 **하나**에서 생성한다.
- 원고 디렉터리 위치, 원고 문법의 세부 사항, 생성기가 사는 곳(테스트 파일 / 작업 공간의 별도 바이너리 / `fung-cli`의 숨은 명령)은 빌더 몫이다. 단, `cargo test`만으로 검사가 돌아야 한다(CI와 커밋 전 검사가 그대로 덮도록).
- 세부 디자인은 사용자가 확인한 시안(`.superpowers/proto/`, 원본은 `.superpowers/proto-src/`의 `build.py`·`manual.css`, 커밋 안 함)을 따른다: 버전 선택은 진짜 `<select>`를 그린 상자 위에 투명하게 겹친다(키보드·화면 낭독기·휴대폰 선택기가 그대로 동작). 상자에는 버전 이름과 `unreleased` 꼬리표가 보인다. 브레드크럼은 부분의 표식(L·R·§·VM)으로 시작한다. 이전/다음은 방향 힌트가 붙은 두 칸이다. 배우기·VM의 머리말은 브레드크럼으로 통일한다. 세부 다듬기는 사용자가 "적절히 예쁘게" 빌더에게 맡겼다.
- 디자인은 지금 `docs/assets/style.css`의 팔레트(청록=겉 언어, 자주=코어, 다크 모드)와 IBM Plex 글꼴, `site.js`의 구문 강조를 이어 쓴다. 상자 종류(처음 배우는 분께 / 자주 하는 실수 / 권장 / 다른 언어는 / fung의 선택)는 시안의 색 구분을 따른다.

### 5.2 코드 블록의 종류

원고의 코드 블록은 종류를 반드시 표시한다. 모르는 종류는 생성기가 에러를 낸다(지금 `excluded`가 모르는 class에 패닉하는 원칙과 같음).

| 종류 | 검사 | 출력 칸 |
|---|---|---|
| 실행 | `fung check`·`fmt --check`·실행 | 생성기가 실제 출력을 채운다 |
| 검사만 | `check`·`fmt --check` (네트워크·`ssh`·서버처럼 테스트에서 돌릴 수 없는 것) | 없음, 또는 원고에 적은 "예상 출력"(검사하지 않는다는 표시를 붙인다) |
| 조각 | 없음(문법 설명용 일부 코드) | 없음 |
| 쉘 | 없음(레시피의 bash 비교) | 없음 |
| dump | `fung dump <단계>` 실행 | 생성기가 실제 출력을 채운다 |
| 그림 | 없음 | 없음 |

- 실행 예제의 출력은 `TZ=UTC` 등 기대 출력 테스트와 같은 환경에서 만들고, 호스트마다 달라지는 값은 치환한다(`tests/common/expected.rs`의 규칙). Linux·macOS에서 같은 결과여야 한다.
- 에러로 끝나는 예제(에러 메시지를 보여 주려는 것)도 실행 종류로 두고, 에러 출력과 종료 코드를 출력 칸에 보인다.
- 연습 문제의 풀이도 실행 예제다.
- **파일을 다루는 예제도 실제로 돈다**(설계자 판단: 사용자의 주된 쓰임새가 파일 조작이라, 여기를 검사하지 않으면 반목표를 정면으로 어긴다). 그래서 원고 형식은 첫 단계부터 **준비물**을 적을 수 있어야 한다: 미리 만들어 둘 파일·디렉터리와 내용, 표준 입력, 명령줄 인자, 환경 변수. 생성기는 예제마다 빈 임시 디렉터리를 만들어 준비물을 깔고 그곳을 작업 디렉터리로 실행하며, 출력에 나온 임시 경로는 고정된 이름으로 치환한다. 준비물은 페이지에 접힌 상자로 보여 준다(독자가 따라 할 수 있게).
- 지금 `tools_expected.rs`의 `manual_examples`(`docs/*.html`의 `<pre>` 검사)는 이 체계로 옮긴다. 얼린 버전 디렉터리(`docs/<버전>/`)는 검사하지 않는다. 옛 언어로 쓴 예제라 지금 바이너리로는 실패할 수 있기 때문이다.

### 5.3 기존 테스트·문서에 미치는 영향

- `manual.rs`: `docs/builtins.html` 대신 새 레퍼런스 페이지를 읽는다.
- `tools_expected.rs`: 5.2.
- `changelog.rs`: 4절.
- `repo_rust_only.rs`: `docs/index.html`·`syntax.html` 문장을 허용 목록으로 갖고 있다. 새 위치·새 문장으로 고친다. 새 원고도 이 검사 대상이다(현재 문서).
- CLAUDE.md의 매뉴얼 항목, `docs/notes/release.md`의 릴리스 절차를 새 구조로 고친다.
- `.superpowers/`(브레인스토밍 시안)를 `.gitignore`에 넣는다.

## 6. 작업 순서

여러 작업이 묶여 있다. 하나씩 차례로 하며, 각 작업마다 계획을 따로 세운다.

1. **뼈대**: 생성기, 원고 형식(준비물 포함), 목차 파일, 버전 디렉터리·`versions.json`·드롭다운, 옛 주소 넘기기, 테스트 연결(5.2·5.3). 이 단계에서는 지금 매뉴얼 네 장의 내용을 새 구조로 **옮기기만** 해서 매뉴얼이 끊기지 않게 한다. 옮기는 자리(설계자 판단):
   - `index.html`(기조·빠른 시작·명령·에러) → `latest/index.html`, 매뉴얼의 첫 페이지(네 부분을 소개하는 표지 겸 개요). 배우기의 1·2장이 생기면 그쪽으로 내용을 나눈다.
   - `syntax.html` → 레퍼런스 › 언어 명세 한 페이지.
   - `builtins.html` → 레퍼런스 › 함수 한 페이지(필터 그대로). 모듈·주제별로 나누는 일과 `manual.rs`를 새 페이지들에 맞게 고치는 일은 2단계에서 한 번에 한다.
   - `internals.html` → VM 한 페이지.
   - 사이드바에는 **내용이 있는 부분만** 보인다. 배우기·예제 모음은 첫 장이 생길 때 나타난다.
   2단계에서 함수를 여러 페이지로 나누면, 지금의 필터는 "모든 함수 목록" 페이지 하나(이름과 한 줄 요약, 각 항목으로 링크)로 옮겨 계속 전체를 거른다. 전문 검색은 여전히 뒤로 미룬다.
2. **레퍼런스**: 함수 항목을 PHP식 형식으로 다시 쓰고, 언어 명세·에러 카탈로그·명령줄 도구 페이지를 만든다. 지금 매뉴얼을 대체해야 하므로 먼저 한다.
3. **배우기**
4. **예제 모음**
5. **VM 책**

각 단계가 끝날 때 `docs/notes/`의 학습용 설명은 따로 쓰지 않는다(이 작업 자체가 문서다). CHANGELOG `[Unreleased]`에 매뉴얼 개편을 적는다.
