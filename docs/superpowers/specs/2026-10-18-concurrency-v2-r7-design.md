# 동시성 v2와 R7 스케줄러 — 설계

2026-10-18. 지금의 동시성 규칙은 `docs/design/05-concurrency.md`, 런타임 설명은 `docs/notes/R3a-runtime.md`·`R3b-agent.md`,
R7 항목은 `docs/design/open-questions.md`의 "Rust 구현: 정한 것과 남은 일"이다. 이 문서가 그것들을 대신하는 방향을 정한다.
결정은 2026-10-18 사용자와의 대화에서 했다. 표시가 없는 결정은 사용자가 정한 것이고, **(설계자 판단)**이라고 붙은 것은
대화에서 정하지 않아 이 문서를 쓰며 정한 것이다(검토 대상).

## 0. 의도

**전제가 바뀌었다.** fung을 스크립트 언어가 아니라 **상용 웹서비스를 짜는 언어**로 본다. 우선순위는 다음과 같다.

1. 엄격함 (틀린 프로그램이 조용히 돌지 않는다)
2. 쓰기 쉬움
3. 예외 규칙이 적음
4. 그다음이 성능

작업 크기는 따지지 않는다. 기존 결정이라도 이 우선순위에 방해가 되면 바꾸거나 지운다.

**지금 모델에서 바꾸는 이유.** 스크립트에서는 괜찮던 것들이 서버에서는 예외 규칙의 원천이 된다.

- 태스크 수명이 아무것에도 묶여 있지 않다(`spawn(f)`). 그 때문에 다음 규칙들이 따라 붙었다. 오래 도는 서버는 실패가 끝날 때까지 보고되지 않는다.
  - 꺼내지 않은 실패를 핸들이 사라질 때 보고한다.
  - 진입 파일이 남은 태스크를 기다린다.
  - `pmap`·`fan_in`만 쓰는 내부 함수 `spawn_awaited`가 있다.
- 에이전트에 특례가 몰려 있다. 배경 태스크 종류, E0704, `swap` 안의 `deref`, 핸들의 자동 닫힘이 그렇다. 읽기 한 번이 편지 왕복이다.
- 기다리는 연산마다 `timeout:`이 따로 있어서, 여러 연산을 거치는 "요청 전체의 기한"을 표현할 수 없다.
- 런타임 에러나 취소로 태스크가 끝나면 정리 코드가 돌지 않는다(03의 한계). `at_exit`는 프로세스 단위다.
- 채널은 보내는 쪽과 받는 쪽이 같은 값이라, 보낼 쪽이 다 사라져도 자동으로 닫을 수 없다. 닫기를 잊으면 교착이나 누수다.
- SIGTERM 정상 종료가 없다.
- 태스크마다 운영체제 스레드라서 연결 수천 개, 에이전트 수천 개에서 스레드 한도에 걸린다(E0801).

## 1. 목표 · 비목표 · 반목표

**목표**
- 구조적 동시성을 **유일한** 태스크 생성 방식으로 둔다.
- 기한과 취소를 범위 하나로 통일한다.
- 에러와 취소에도 반드시 도는 정리 장치를 둔다.
- 채널을 보내는 끝과 받는 끝으로 나누고 자동으로 닫는다.
- 엄격한 `atom`을 둔다.
- SIGTERM·SIGINT로 정상 종료한다.
- 런타임을 스택 없는 그린 스레드(M:1) + 이벤트 루프 + 스레드 풀로 바꾼다.

**비목표** (이번에 하지 않는다. 13절 보류 목록)
- M:N(여러 코어에서 fung 코드를 돌리기)
- 요청 하나 안의 CPU 병렬(별도 실행기)
- 오래 걸리는 내장 함수의 차례 넘기기
- `select`, 메일박스
- 요청 단위 컨텍스트 값
- HTTP 서버 자체의 요건(keep-alive, 느린 클라이언트 시간 제한, 최대 연결 수)
- 순환을 회수하는 GC

**반목표** (기술적으로 돌아가도 이렇게 되면 실패다)
- 함수에 색이 생기는 것. async/await, "이 안에서는 저 함수를 부르면 안 된다" 같은 일반 규칙이 그렇다. `atom`의 `f`는 이름 붙은 한 곳의 규칙이라 예외로 친다.
- 두 런타임(운영체제 스레드와 그린 스레드)을 오래 함께 두는 것. 옛 런타임은 R7 안에서 지운다.
- 언어 의미가 M:1에 기대는 것. 예를 들어 "끼어들 수 없으니 원자적" 같은 의미를 두지 않는다. 구현은 M:1을 영구 방침으로 두지만, 의미는 여러 코어에서도 성립해야 한다.
- 숨은 태스크 종류(배경 태스크 같은 것)

## 2. 결정 표

| 항목 | 결정 |
|---|---|
| 태스크 생성 | 범위(`scope`·`supervise`) 안에서만. 자유로운 `spawn(f)`는 지운다 |
| 실패 전파 | `scope`: 자식이 런타임 에러로 죽으면 형제와 주인 본문을 취소하고, 그 에러를 `scope(` 호출에서 다시 낸다. `supervise`: 자식 실패를 격리해서 처리기에 넘긴다 |
| 꺼내지 않은 실패 보고 | 지운다(구조상 생기지 않음). `spawn_awaited`·배경 태스크도 지운다 |
| 기한 | `timeout(d, f)` 범위 하나. `await`·`recv`의 `timeout:`은 지운다 |
| 정리 | `with(acquire, use, release)`. `release`는 정상·`Err` 반환·런타임 에러·취소·`exit` 어느 경우에나 돈다 |
| `at_exit` | 지운다 **(설계자 판단, 5.3절)** |
| 채널 | `(tx, rx) = channel(n)`. 보내는 끝이 모두 사라지면 닫힘, 받는 끝이 모두 사라지면 `send`가 `Err` |
| 공유 상태 | `agent`를 지우고 `atom`으로. `swap`은 비교 후 교체와 재시도, `f`는 순수 계산만(런타임이 강제), atom 안에는 변하는 것을 넣지 못함(O(1) 검사) |
| `select` | 두지 않는다(범위 취소가 대신함) |
| 종료 신호 | 첫 SIGTERM·SIGINT는 **정지 요청**(취소와 별개). `http.serve`는 받기를 멈추고 처리 중인 요청을 `drain` 기한까지 마친다. 정지 요청을 보는 쪽이 없으면 곧바로 루트 취소. 두 번째 신호는 즉시 종료 |
| 풀 작업의 기한 | 기한은 정확히 지킨다. 풀 작업은 버려두고, 외부 프로세스는 취소 때 죽인다 |
| 런타임 | M:1, 스택 없는 그린 스레드, `libc`로 kqueue·epoll을 직접 감싼다(`mio` 안 씀), `outside`는 스레드 풀 |
| 여러 코어 | 여러 프로세스(배포 환경의 복제 수, 같은 호스트면 `SO_REUSEPORT`). M:N은 보류. `Rc`는 그대로 |
| CPU 많이 쓰는 작업 | 보류. 내장 함수 고치기는 최적화로, 별도 실행기는 기능으로 나중에 한다. 지금은 지연 측정 벤치마크만 둔다 |
| 작업 순서 | 언어(L단계)를 지금 런타임에서 먼저 하고, 같은 테스트를 기준으로 런타임(R7)을 바꾼다 |
| 버전 | 호환을 깨는 변경이라 다음 릴리스는 0.3.0 **(설계자 판단)** |

## 3. 범위(scope)

### 3.1 함수

아래 이름과 형태는 이 문서의 제안이다. 문법 확장 없이 평범한 함수로 둔다.

| 함수 | 뜻 |
|---|---|
| `scope(f)` | 범위를 열고 `f(s)`를 부른다(`s`는 범위 핸들). 본문과 자식이 **모두** 끝나야 돌아온다. 결과는 `f`의 반환값 |
| `supervise(f, on_fail)` | 격리하는 범위. 자식의 실패가 형제나 주인에게 번지지 않고 `on_fail(e)`가 불린다(3.3) |
| `spawn(s, g)` | 범위 `s` 안에서 `g()`를 새 태스크로 띄우고 태스크 핸들을 돌려준다 |
| `await(t)` | 태스크의 결과(3.2) |
| `cancel(t)` | 그 태스크만 취소한다(자식에게 전파됨) |
| `cancel(s)` | 범위 전체를 취소한다 **(설계자 판단)**. 서버를 멈추는 코드에 필요하다 |

```
fn load(id) = scope(fn(s):
  user = spawn(s, () => fetch_user(id))
  orders = spawn(s, () => fetch_orders(id))
  {user: await(user), orders: await(orders)}
;;)
```

### 3.2 결과와 실패 (`scope`)

- 자식이 정상으로 끝나면 `await`는 반환값을 그대로 준다. 함수가 `Err` 값을 돌려준 것은 **실패가 아니다**. 그냥 값이다.
- 자식이 **런타임 에러**로 죽으면 범위가 실패한다.
  1. 다른 자식과 주인의 본문을 모두 취소한다.
  2. 모두 끝나기를 기다린다(정리 `release`가 이때 돈다).
  3. 그 에러(번호·문구·호출 경로 그대로)를 `scope(` 호출에서 다시 낸다.

  따라서 `scope` 안에서 `await`가 실패를 값으로 돌려주는 일은 없다. 런타임 에러는 지금처럼 "중단"이고, 그것을 잡는 문법은 여전히 없다.
- 실패가 여럿이면(진짜 실패가 동시에 난 경우) 먼저 난 것이 올라가고, 나머지는 같은 보고 안에 덧붙인다. **버리지 않는다.** 보고 형식은 설계자가 정한다.
- `cancel(t)`로 취소한 자식은 실패가 아니다. `await(t)`는 `Err({kind: 'cancelled})`를 준다.
- **취소는 그것이 겨눈 범위가 받는다 (설계자 판단, Trio의 cancel scope와 같음).** `timeout`과 같은 규칙이다.
  - `cancel(s)`로 취소된 범위는 자식과 본문을 되감은 뒤 `scope(` 호출에서 `Err({kind: 'cancelled})`를 돌려준다. 호출한 쪽은 그다음 줄부터 이어 간다.
  - 바깥에서 온 취소(바깥 범위, `timeout`, 루트)는 그 범위를 지나 계속 되감는다.
  - 그래서 자식이 `cancel(app)`을 부르면 진입 파일은 `scope(` 다음으로 이어 가고, 보통대로 끝나면 종료 코드는 0이다.
- 범위 핸들과 태스크 핸들은 범위 밖으로 나가도 된다. 닫힌 범위의 태스크를 `await`하면 저장된 결과를 준다. **닫힌 범위에 `spawn`하면 런타임 에러**다(새 번호).
  - 범위가 "닫힌" 때는 `scope(`가 돌아온 때다. 본문이 끝나고 자식을 기다리는 동안에는 자식이 같은 범위에 `spawn`해도 된다 **(설계자 판단, Trio의 nursery와 같음)**. 그래서 배경 작업이 스스로 다시 띄울 수 있다.
- 오래 사는 배경 작업(캐시 갱신, 주기 작업)은 그 작업보다 오래 사는 범위를 **인자로 넘겨받아** 그 안에서 띄운다. 예를 들면 진입 파일이 연 앱 범위다. 숨은 종류는 없다.

### 3.3 격리 (`supervise`)

- 자식이 런타임 에러로 죽어도 형제와 주인은 계속 돈다.
- 그 실패는 **언제나** `on_fail(e)`로 간다. `e`는 `{kind: 'error, code, message}`이고, 정확한 필드는 지금 `await`의 에러 맵을 따른다.
- `await(t)`는 그 실패를 `Err(e)`로 준다. 처리기와 `await`가 둘 다 본다. "아무도 확인하지 않은 실패"라는 개념 자체가 없다.
- `on_fail`은 그 `supervise` 범위 안의 **처리기 태스크**에서 실패 순서대로 하나씩 돈다 **(설계자 판단)**. 본문에 끼어들지 않으므로, 본문이 도는 중(예: `serve`의 받기 반복)에도 실패를 바로 처리한다. 처리기 태스크는 실패가 있을 때 런타임이 띄우는 범위의 평범한 자식이다. `on_fail` 자신이 런타임 에러를 내면 그 `supervise` 범위의 실패가 되어 바깥으로 올라간다.
- `http.serve`가 대표적인 사용처다. 연결마다 격리된 자식을 띄우고, 실패를 500과 stderr 한 줄로 바꾼다(지금 동작과 같다).

### 3.4 진입 파일과 루트

- 런타임은 진입 파일 전체를 감싸는 **루트 범위**를 하나 둔다. 사용자는 그 핸들을 얻지 못한다. 신호와 `exit`가 취소하는 대상일 뿐이다.
- `spawn`은 범위 핸들이 있어야 하므로, 태스크를 쓰는 진입 파일은 스스로 `scope`를 연다. "진입 파일이 남은 태스크를 기다린다"는 규칙은 필요 없어진다.
- `fung test`의 `test` 블록 본문과 모듈 초기화도 각각 루트처럼 감싼다. 태스크가 블록 밖으로 새지 않는다.

## 4. 기한: `timeout(d, f)`

- `f()`를 돌려 그 결과를 준다. `d`가 지나면 `f` 안의 모든 것(자식 태스크 포함)을 취소하고, 정리가 끝난 뒤 `Err({kind: 'timeout})`을 준다.
- 기한은 안쪽으로 물려진다. 실제 기한은 바깥과 안쪽 중 이른 쪽이다.
- 바깥 기한이 먼저 지나서 안쪽이 취소되면 안쪽 `timeout`은 `Err`를 돌려주지 않고 그대로 취소된다. 바깥 `timeout`이 `Err`를 준다.
- `await(t, timeout:)`·`recv(rx, timeout:)`은 지운다. `timeout(1s, () => recv(rx))`로 쓴다.
- **HTTP 클라이언트**(`get`·`post`·`request`)는 `timeout = 30s` 매개변수를 **남긴다 (설계자 판단)**.
  - 내부에서 같은 `timeout` 범위로 구현하므로, 실제 기한은 바깥 기한과의 이른 쪽이다.
  - 남기는 이유: 기본 기한이 없으면 죽은 서버를 영원히 기다리게 된다. 반대로 내부 기본값만 두면 바깥에서 더 긴 기한을 줄 수 없다.
  - 이것은 기다리는 원시 연산의 매개변수가 아니라 라이브러리 설정이다.
- **기한은 정확히 지킨다** (2026-10-18 결정; **R3에서 일부 고침**: 15절의 "버리는 일" 줄이 이 항목의 풀 작업 규칙을 대신한다. 경로만 읽는 일과 정규식 컴파일만 곧바로 되감고, 무엇을 바꾸는 일은 시작했으면 끝까지 기다린다. 그래서 아래 "버려진 쓰기·지우기가 끝날 수 있다"는 한계는 없다). 스레드 풀 작업(10.1)을 기다리는 중에 취소되거나 기한이 지나도 태스크는 곧바로 되감는다.
  - 풀 작업은 버려두고, 나중에 온 결과는 버린다. 그래서 버려진 파일 쓰기·지우기가 `Err({kind: 'timeout})` 뒤에 실제로 끝날 수 있다. 이것은 알려진 한계로 매뉴얼에 적는다.
  - 외부 프로세스는 기다리던 태스크가 취소되면 죽인다. 먼저 SIGTERM을 보내고, 잠시 뒤에도 살아 있으면 SIGKILL이다(기다리는 시간은 설계자가 정한다). 이름 조회도 버려두는 작업이다.
  - 버려진 작업이 풀 스레드를 붙잡으므로 풀에 상한과 넘쳤을 때의 정책이 필요하다. 설계자가 정한다. 넘쳐도 기한은 지켜야 한다.
- 취소의 성질은 지금과 같다. 협조적이고, 막히는 연산과 호출·반복 지점에서 확인하며, 런타임 에러처럼 되감는다. 다른 점은 되감는 길에 `with`의 `release`가 돈다는 것이다.

## 5. 정리: `with(acquire, use, release)`

### 5.1 의미

- `r = acquire()` → `use(r)` → `release(r)`. 결과는 `use(r)`의 반환값이다.
- `release`는 `use`가 어떻게 끝나든 돈다. 정상 반환, `Err` 반환, 런타임 에러, 취소(`cancel`·`timeout`·범위 실패·신호), `exit`가 모두 해당한다. 런타임이 보장한다. VM이 되감기 중에 이 프레임을 알아본다.
- `acquire`가 실패하면 `release`는 돌지 않는다. `acquire`가 돌아온 순간과 `release` 등록 사이에는 취소 확인 지점이 없어야 한다. 그사이에 취소되어 자원이 새는 일이 없게 하기 위해서다.
- `release`는 자기를 부른 취소로부터 **차단된 채** 돈다. 그 안에서 소켓을 닫거나 풀에 돌려주는 기다림이 바로 E0701로 끝나지 않는다.
  - 대신 `release`가 영원히 멈추는 경우의 탈출구는 두 번째 종료 신호(7절)와 배포 환경의 강제 종료다 **(설계자 판단)**. 언어 안에 별도 유예 타이머는 두지 않는다.
- `use`가 실패했는데 `release`도 실패하면 `use`의 에러가 올라가고, `release`의 에러는 그 보고에 덧붙인다. `use`가 성공하고 `release`가 실패하면 `release`의 에러가 올라간다.
- `use(r)` 호출은 꼬리 위치가 아니다(03의 꼬리 호출 규칙에 한 줄 추가). `defer`를 기각한 이유(프레임마다 할 일 목록, TCO 충돌)는 함수 하나의 프레임 표시라서 해당하지 않는다.

### 5.2 표준 라이브러리

- `fs.with_open`·`fs.with_temp_dir`를 `with` 위에 다시 짠다. 03의 한계("태스크가 죽으면 감싸는 함수의 정리는 돌지 않는다")가 사라진다.

### 5.3 `at_exit` 삭제 (설계자 판단)

- `exit`·교착·런타임 에러·신호가 모두 "루트 범위 취소 → 되감기"가 된다. 따라서 진입 파일 본문을 `with`로 감싸면 `at_exit`과 같은 일을 한다. 정리 장치를 하나만 두는 규칙(예외가 적음)에 맞춰 `at_exit`는 지운다.
- 대가: 진입 파일 맨 위에서 한 줄로 등록하던 편의가 사라진다. 옮겨 쓰기는 매뉴얼과 CHANGELOG에 적는다.

## 6. 채널

- `channel(n = 0)`은 `(tx, rx)` 튜플을 준다. `n`의 뜻(0이면 받는 쪽이 있을 때까지 `send`가 막힘, 상한 없음)은 그대로다.
- `send(tx, v)`, `recv(rx)`, `close(tx)`. 끝을 잘못 주면(`send(rx, …)`) 인자 타입 에러다. `type_of`는 `'sender`·`'receiver`, 타입 표기는 `sender`·`receiver`.
- 끝은 복사할 수 있다. 여러 일꾼이 같은 `rx`에서 받는 것(여러 생산자, 여러 소비자)이 된다.
- **자동 닫힘**
  - 보내는 끝의 마지막 사본이 사라지면 닫힌다. 받는 쪽은 남은 버퍼를 다 받은 뒤 `Err({kind: 'closed})`를 받는다.
  - 받는 끝의 마지막 사본이 사라지면 `send`는 `Err({kind: 'closed})`이고, 버퍼의 값은 버린다.
- `close(tx)`는 남긴다. 다른 사본이 있어도 지금 닫고 싶을 때 쓴다.
- 순회 규칙(`for x in rx`, `each`·`map` 등이 받는 끝을 받으면 닫힐 때까지)은 05 그대로이고, 받는 끝에만 적용한다.
- E0705(자기 채널의 끝을 자기 채널로 보내기)는 남긴다. 버퍼가 자기 보내는 끝을 쥐면 영원히 닫히지 않기 때문이다. 검사 비용은 7.2절의 "변하는 것을 품었는지" 표시로 줄인다(표시가 없는 값은 훑지 않는다).

## 7. 공유 상태: `atom`

### 7.1 함수

| 함수 | 뜻 |
|---|---|
| `atom(v)` | 칸을 만든다 |
| `deref(a)` | 지금 값. 기다리지 않는다 |
| `swap(a, f)` | 옛 값을 읽고 `f(옛 값)`을 계산한다. 칸이 아직 그 옛 값을 가리키면 바꾸고 새 값을 돌려준다. 그사이 바뀌었으면 새 옛 값으로 `f`를 다시 돌린다 |
| `reset(a, v)` | 무조건 바꾼다 **(설계자 판단: 갱신 태스크 하나가 쓰는 패턴에 필요)** |

- `==`는 같은 칸인지 본다. 출력과 `type_of`(`'atom`)는 설계자가 정한다.
- M:1에서는 다시 도는 일이 드물다. 그래도 의미는 처음부터 비교 후 교체로 정한다. 여러 코어로 가도 바뀌지 않게 하기 위해서다.

### 7.2 규칙

- **`f`는 순수 계산만 한다.** `f`를 도는 동안 다음을 부르면 런타임 에러다(새 번호).
  - 막히는 연산
  - 출력
  - 파일·네트워크·프로세스
  - `spawn`·`send`
  - 다른 atom의 `swap`·`reset`
  - `exit`

  `deref`, 시간 읽기, 환경 변수 읽기는 된다. 기준은 "`f`가 여러 번 돌아도 바깥에서 보이는 차이는 걸린 시간뿐"이다. 내장 함수마다의 분류는 설계자가 표로 정해 테스트로 지킨다. 이 규칙이 E0704를 대신한다.
- **atom 안에는 변하는 것을 넣지 못한다.** atom, 채널 끝, 태스크 핸들, 범위 핸들, 파일·소켓 핸들, 그리고 이것들을 품은 클로저·컬렉션이 해당한다. `atom(v)`·`swap`·`reset`에서 검사하고, 어기면 런타임 에러(새 번호)다.
  - 값을 만들 때 "변하는 것을 품었는지" 표시를 위로 전파해 두어 검사를 O(1)로 한다. 영속 컬렉션의 노드마다 표시를 둔다.
  - 이 규칙 덕분에 atom을 거치는 `Rc` 순환이 원리상 생기지 않는다.
- 대가: 구독자 채널 목록을 atom에 두는 pub/sub은 쓸 수 없다. 그 경우는 목록을 쥔 태스크와 채널로 짠다(매뉴얼 예제).
- **모듈 최상위의 atom은 된다 (설계자 판단).** `cache = atom({})`를 모듈이 내보낼 수 있다.
  - 모듈 참조(최상위 함수가 상수로 보는 가져온 모듈, 03)는 "변하는 것을 품었는지" 표시를 전파하지 않는다. 그래서 모듈의 atom을 쓰는 함수도 atom에 넣을 수 있다.
  - 근거: 모듈은 프로그램이 끝날 때까지 사니, 모듈을 거치는 순환은 어차피 회수할 일이 없어 누수가 자라지 않는다. 표시는 클로저가 붙잡은 값과 컬렉션 원소만 본다.

### 7.3 `agent` 삭제

- `agent`·`swap`·`deref`(에이전트판), `extras/agent.fung`, 배경 태스크, E0704를 지운다. 에러 번호는 카탈로그 규칙대로 "쓰지 않음"으로 남긴다.
- 입출력이 필요한 갱신(토큰 갱신 등)은 갱신 태스크 하나가 `reset`하고 나머지는 `deref`하는 모양으로 쓴다. 매뉴얼 예제로 남긴다.
- 3b에서 atom을 지운 이유와 이번에 되돌리는 이유를 노트에 적는다. 순환과 재진입은 7.2의 두 규칙으로 막는다. 공유 없음 원칙은 내려놓는다.

## 8. 종료와 신호

- 진입 파일이 끝나면 프로그램이 끝난다(범위 밖에 남은 태스크는 있을 수 없다). 종료 코드는 0, 런타임 에러면 1이다.
- `exit(n)`은 어느 태스크에서든 루트를 취소한다. 되감기에서 `release`가 모두 돈 뒤 종료 코드 n으로 끝난다.
- 교착(E0702)은 보고 → 루트 취소 → `release` → 종료 코드 1이다.
- **정지 요청과 취소는 다른 것이다** (2026-10-18 결정). 취소는 "지금 멈춰라"이고 모든 자손에게 간다. 정지 요청은 "하던 일을 마치고 끝내라"이고, 받는 쪽이 스스로 정리한다. Go의 `Server.Shutdown`과 Trio의 관례처럼 정상 종료를 취소와 따로 둔다.
  - `stop_signal()`(이름은 가칭)은 받는 끝 하나를 준다. 첫 종료 신호가 오면 이 끝들이 모두 닫힌다. `recv`하면 `Err({kind: 'closed})`이므로, 기다리거나 순회를 멈추는 데 그대로 쓴다.
  - **보는 쪽**은 `stop_signal()`로 받은 끝이 하나라도 살아 있는 상태를 말한다. 참조 계수로 안다.
- **SIGINT·SIGTERM**
  - 첫 신호는 정지 요청이다.
    - 보는 쪽이 있으면 정지 요청만 알리고 기다린다. 프로그램은 보는 쪽이 일을 마치고 진입 파일이 끝날 때 끝난다.
    - 보는 쪽이 없으면 곧바로 루트를 취소한다. 그래서 정지 요청을 모르는 스크립트의 Ctrl-C는 지금처럼 바로 멈춘다.
  - 두 번째 신호는 정리를 기다리지 않고 즉시 끝낸다.
  - 정지 요청을 받아 스스로 정상적으로 끝내면 종료 코드는 0이다 **(사용자 결정, 2026-10-18: systemd·Kubernetes가 정상 종료를 실패로 적지 않게)**. 보는 쪽이 없어 취소로 끝나거나 두 번째 신호로 끊기면 128 + 신호 번호(130·143)다(셸 관례).
  - 코드에서 정지 요청을 보내는 `request_stop()`을 공개한다 **(사용자 결정)**. 첫 신호와 같다. 보는 쪽이 없으면 `exit(0)`처럼 끝낸다.
  - REPL에서의 Ctrl-C는 지금 규칙(줄 취소)을 따르고, 실행 중인 평가가 있으면 그 평가를 취소한다.
  - SIGPIPE 처리는 그대로다.
- **`http.serve(…, drain = 10s)`** (기본값은 설계자 판단)
  - 안에서 `stop_signal()`을 본다. 정지 요청이 오면 새 연결을 그만 받고, 처리 중인 요청을 `drain`까지 기다린 뒤, 남은 연결만 취소하고 `nil`을 돌려준다.
  - `serve`가 취소되면(바깥 범위, `timeout`) 지금처럼 즉시 멈춘다. 기다리지 않는다.
  - 서버를 코드에서 멈추는 길은 둘이다. 정상 종료는 정지 요청, 즉시 종료는 `cancel(s)`다. 정지 요청을 코드에서 보내는 함수를 둘지는 설계자가 정한다(테스트에는 필요하다).

## 9. 표준 라이브러리 영향

- `conc.pmap(xs, f, limit = 0)`: 안에서 `scope`를 연다. `f`의 런타임 에러는 `pmap`의 실패가 된다(지금은 `Err` 값). `f`가 돌려준 `Err`는 값 그대로 결과에 들어간다.
- `conc.fan_in(s, rxs)`: 전달 태스크를 띄울 범위를 받는다. 받는 끝 하나를 돌려주고, 모든 입력이 닫히면 출력도 닫힌다.
- `conc.retry`: 그대로.
- `http.serve(addr, handler, ready = nil, drain = 10s, reuse_port = false)`: 안에서 `supervise`를 쓰고 정지 요청을 본다(8절). `reuse_port`는 `SO_REUSEPORT`이고, 같은 호스트에서 프로세스 여럿이 한 포트를 받을 때 쓴다 **(설계자 판단)**. macOS에서는 켜지지만 고르게 나누지는 않는다.
- 내부 함수 `_native.conc`의 `spawn_awaited`·`spawn_background`·`try_call`·`set_asker`·`agent_*` 등은 새 원시 연산에 맞게 다시 정리한다. 무엇을 남길지는 설계자가 정한다. 사용자에게 보이는 이름은 이 문서의 것뿐이다.

## 10. 런타임: R7

### 10.1 모양

- **M:1.** 실행 스레드 하나(지금의 진입 스레드처럼 큰 스택)가 모든 fung 태스크를 돈다. fung 값은 이 스레드 밖으로 나가지 않는다. 실행권 잠금(`Token`·`Gate`), 태스크마다의 스레드, `stack.rs`의 태스크 스택 재시도는 지운다.
- **스택 없는 그린 스레드.**
  - 막히는 원시 연산은 "주차" 신호를 돌려준다. VM은 프레임을 그대로 두고 스케줄러로 돌아갔다가, 깨어나면 결과값을 들고 그 자리에서 이어 간다.
  - 람다를 다시 부르는 Rust 내장 함수는 이어 갈 수 있게 바꾼다. 지금 그런 자리는 `prelude.rs`의 `map`, `prelude/collections.rs`의 `fold`·`each`·키 함수들, `native/nat.rs`의 술어 호출, 태스크 시작 정도다(`t.call`·`call_buf`를 부르는 곳).
  - 방법은 설계자가 고른다. Lua 5.2의 `lua_callk`처럼 이어 갈 지점을 프레임에 남기는 방식도 되고, fung으로 옮기는 방식도 된다. 조건은 10.4의 성능 목표다.
- **차례 넘기기.** 명령 수를 세어 넘기는 지금 방식(`Task::tick`, `YIELD_EVERY`)을 유지한다. 넘기는 비용이 싸지므로 값을 다시 잰다.
- **스레드 풀.** `outside`를 지나는 작업을 맡는다. fs 전부, 외부 프로세스, 이름 조회, regex 컴파일, HTTP 본문 읽기 중 막히는 부분이 해당한다. 넘기는 데이터는 fung 값이 아닌 평범한 데이터다. 풀 크기는 설계자가 정한다.
- **이벤트 루프.** `libc`로 kqueue(macOS)·epoll(Linux)을 직접 감싼다. 소켓은 블로킹하지 않는 모드로 쓰고, rustls는 그 위에서 돈다. 표준 입력은 터미널·파이프면 루프에서, 일반 파일이면 풀에서 읽는다. REPL 줄 편집기가 이 루프와 맞물려야 한다.
- **타이머.** `sleep`과 `timeout`의 마감은 스케줄러의 타이머 힙에 넣는다. 루프가 기다리는 시간은 가장 이른 마감까지다.
- **교착 판정.** 실행 대기열, 등록된 입출력, 타이머, 풀 작업이 모두 비었는데 끝나지 않은 태스크가 있으면 E0702다. `Census`의 원자 변수 셈은 지운다.
- 기다림마다의 깨우개 파이프(`vm/watch.rs`)는 루프 하나로 합친다. 이름 조회 스레드는 풀로 들어간다.
- 값이 스레드를 넘지 않게 되므로 `unsafe impl Send`는 없앨 수 있는 만큼 없앤다. 남는 것은 지금 규칙(`// SAFETY:`와 디버그 단언)을 따른다.

### 10.2 언어 의미와의 관계

- R7은 L단계(11절)가 정한 의미를 바꾸지 않는다. L단계의 테스트가 R7의 정답지다.
- 형제 태스크의 실행 순서처럼 보장하지 않던 것은 바뀔 수 있다. 그런 순서에 기대는 테스트는 L단계에서 고친다.

### 10.3 하지 않는 것

- M:N, 태스크별 힙, 클로저 동일성을 복사 뒤에도 유지하는 일(`value/compare.rs`). 13절 보류.

### 10.4 성능 목표

`bench/README.md`의 방법(같은 기계, 9회 중앙값)을 쓰고, 기준선은 open-questions의 2026-10-17 값이다.

| 측정 | 목표 |
|---|---|
| 태스크 생성 (`spawn` 벤치마크) | 태스크 하나에 5 µs 이하 |
| 버퍼 없는 채널 주고받기 (`chan`) | 값 하나에 1 µs 이하 |
| 살아서 기다리는 태스크 2만 개 | 스레드 한도 없이 돌고, 메모리가 태스크 수에 비례하되 작음 |
| 계산 위주 (`fib`·`loop`·`map`·`str`) | 기준선보다 5% 넘게 느려지지 않음 |
| HTTP 서버 동시 연결 | 수천 개 (느린 클라이언트가 붙잡아도 스레드가 늘지 않음) |
| 지연 (새 벤치마크) | 큰 JSON을 파싱하는 요청 옆에서 가벼운 요청의 응답 시간. **기록만**, 목표 없음 |

## 11. 작업 순서

**L단계: 언어를 지금 런타임에서 먼저 바꾼다.** 단계마다 테스트(TDD), 골든과 기대 출력, 매뉴얼, CHANGELOG를 함께 고친다.

1. 범위: `scope`·`supervise`·`spawn(s, g)`·`cancel(s)`. 자유로운 `spawn`, 꺼내지 않은 실패 보고, 진입 파일 대기 규칙을 지운다.
2. 기한: `timeout(d, f)`. 연산마다의 `timeout:`을 지우고, HTTP 클라이언트를 다시 짠다.
3. 정리: `with`. `fs.with_open`·`with_temp_dir`를 다시 짜고 `at_exit`를 지운다.
4. 채널 끝 나누기와 자동 닫힘
5. `atom`. `agent`와 배경 태스크를 지운다.
6. 신호, 정지 요청(`stop_signal`)과 정상 종료. `http.serve`(`drain`), `conc`를 다시 짠다. 외부 프로세스를 취소 때 죽이는 것도 여기서 한다.

순서는 의존 관계를 따랐다. 설계자가 바꿔도 된다. 다만 1이 먼저다.

**R단계: 런타임을 바꾼다.** 정답지는 L단계의 테스트이고, 동시성 50회 반복 검사를 포함한다.

1. 스케줄러, 주차·재개, 타이머, 채널과 범위의 그린 구현
2. 람다를 부르는 내장 함수를 이어 갈 수 있게
3. 스레드 풀(`outside`)
4. 이벤트 루프(소켓, TLS, 표준 입력, REPL)
5. 옛 런타임 삭제, `unsafe` 정리
6. 벤치마크와 노트

- **두 런타임을 함께 두지 않는다.** 스위치 없이 R단계 안에서 제자리 교체한다. 단계는 작업 브랜치에 쌓는다.
- **0.3.0은 R단계가 끝난 뒤에 낸다 (설계자 판단).** L단계만으로 내면 스레드 한도가 그대로인 런타임에 새 의미를 얹은 판을 사용자에게 주게 된다.

L·R 각 단계의 세부 계획은 이 문서를 바탕으로 따로 쓴다(`docs/superpowers/plans/`).

## 15. R단계 결정 (2026-10-18, 14절의 설계자 몫을 사용자와 정함)

R단계 계획 `docs/plans/2026-10-18-concurrency-v2-r2-continuations.md`의 "R단계 지도"가 이 절을 단계별로 나눈다.

| 항목 | 결정 |
|---|---|
| 이어 가는 내장 함수(10.1) | Lua `lua_callk`식. 람다를 부르는 내장 함수는 "이 함수를 불러 달라, 끝나면 이 상태로 이어 달라"를 돌려주고, VM이 이어 가기 프레임을 프레임 스택 옆에 둔다. 되감기도 그 프레임을 지난다(`with`·`timeout`·`scope`). fung으로 옮기지 않는다(`for`가 `map`이고 `fold`가 계산 위주 벤치마크라 5% 목표를 못 지킴) |
| R단계 순서(11절) | **R2 → R1 → R3 → R4 → R5 → R6.** R2는 지금 런타임에서 할 수 있고, R2 없이는 M:1에서 람다 안의 기다림을 주차할 수 없다. 단계마다 전체 시험이 초록이고, 그 사이의 임시 다리(R1의 `outside`·소켓 기다림을 기다림마다 스레드 하나로)는 R3·R4에서 걷어 낸다 |
| 계획 문서 | 단계별. 첫 계획(R2)에 R단계 지도, 뒤 단계의 계획은 그 단계 직전에 쓴다 |
| 스레드 풀 | 필요할 때 만들고 최대 64개, 10초 놀면 끝남. 꽉 차면 FIFO 줄, 버려진 작업은 꺼낼 때 건너뜀. 환경 변수 설정 없음 |
| `YIELD_EVERY` | 호출·점프 수 세기를 유지. 시작값 2,000, R1에서 재서 정한다. 기준(2026-10-19 고침): 계산 위주가 잡음(±2%) 밖으로 느려지지 않고, 더 줄여도 깨어난 태스크의 늦음이 깨움당 0.1 ms 넘게 줄지 않는 값. R1b에서 1,000(500·200은 늦음이 0.03 ms 남짓 줄 뿐 스케줄러로 돌아가는 횟수가 두세 배·다섯 배). `swap`의 함수 안에서는 넘기지 않는다(기아 방지). 입출력을 기다리는 태스크가 있을 때만 넘길 때 이벤트 루프를 시간 제한 0으로 본다 |
| 이벤트 루프 | 준비 상태 기반, one-shot 등록. `kqueue`·`epoll` 두 파일이 같은 작은 API(등록, 해제, 시간 제한 있는 기다림, 다른 스레드에서 깨우기). 깨우개는 `EVFILT_USER`·`eventfd`. 타이머는 스케줄러의 힙 |
| 자식 프로세스 | 끝은 macOS `EVFILT_PROC`, Linux `pidfd_open`(`ENOSYS`이면 신호 스레드가 받는 SIGCHLD, 신호 스레드가 없으면 10 ms마다 보기; L11에서 풀 스레드의 `waitid`를 바꿈). 출력 파이프는 블로킹하지 않는 모드로 루프에(10 ms 폴링과 읽는 스레드 둘을 지움) |
| 표준 입력(10.1을 고침) | 루프에 올리지 않는다. fd 0에 `O_NONBLOCK`을 켜면 같은 열린 파일을 나눠 쓰는 부모 셸과 다른 프로세스에도 걸리기 때문이다. 지금처럼 원할 때만 읽는 전용 스레드 하나(풀 밖)가 읽고 루프 깨우개로 전한다 |
| 표준 출력·에러 | 런타임 스레드에서 동기로 쓴다(지금과 같음). 소비자가 느리면 런타임 전체가 멈추는 것은 알려진 한계 |
| REPL: 멈춘 `release`에서 두 번째 Ctrl-C | 그 평가의 태스크를 정리 없이 버리고 프롬프트로 돌아간다(`release`가 끝나지 않았다는 한 줄) |
| REPL: `request_stop()` | 보는 쪽이 없으면 `exit(0)`처럼 세션을 끝내는 지금 동작을 유지하고 매뉴얼·08에 적는다 |
| 교착 판정 | `Census`를 지운다. 실행 대기열, 입출력 등록, 타이머, 진행 중인 풀 작업이 모두 비었는데 끝나지 않은 태스크가 있으면 E0702. 정지 채널은 지금처럼 바깥에서 깨우는 것 |
| 신호 | `sigwait` 전용 스레드를 남기고 루프 깨우개로 전한다. 신호를 런타임 상태에 남겨 `fung test`의 다음 파일 컴파일 중 신호가 사라지지 않게 한다 |
| 그 밖 | 이름 조회·정규식 컴파일은 풀. `try_spawn`과 `stack.rs`의 태스크 스택 재시도는 R1에서 지운다. `unsafe impl Send`는 0개가 목표. 잔가지(E0707 도우미 이름, 효과 표 전체 분류, E0506 문구)는 R5. rustls 0.23.46은 R4에서 0.23.45로 짠 뒤 2026-10-28 이후 버전만 올린다(같은 0.23의 패치라 API가 같고, 0.23.45의 공지는 우리 설정에 닿지 않음; 2026-10-19 고침) |
| R1을 둘로 (2026-10-18) | **R1a**: 지금 런타임 위에서 막히는 원시 연산을 주차 요청(`Flow::Park`·`Next::Park`)으로, 운영체제 기다림을 `offload(일, 마무리)`로 바꾼다(지금 런타임에서는 주차 요청에 스레드가 잔다). **R1b**: 그 API 아래의 런타임을 바꾼다(실행 스레드 하나, 대기열, 타이머, 스레드 없는 `spawn`, 교착 판정). 계획은 단계마다 하나 |
| kqueue·epoll 핵심 (2026-10-18) | R4에서 소켓과 함께 만든다. R1의 깨우개는 `Mutex`·`Condvar`로 짜되 겉 API는 이벤트 루프와 같은 모양으로 둔다(R1에는 epoll에 등록할 것이 없고, epoll은 Linux CI에서만 돌기 때문) |
| R1a의 기계적 변환 (2026-10-18) | `fs`·`process`+`regex`·`net`의 offload 변환은 파일이 겹치지 않게 서브에이전트에 나눠 병렬로 하고, 결과를 검토해 합친다 |
| R1b의 모양 (2026-10-19) | 계획 하나에 작업 여섯. 앞의 넷은 지금 런타임 위에서 하고 각각 전체 시험이 초록이다: (1) 태스크 끝과 `on_fail` 처리기를 이어 가기로, (2) 표준 입력을 읽기 스레드 위의 주차로, (3) 차례 넘기기를 실행 루프 밖으로 나오는 신호로, (4) offload의 일을 다른 스레드에 맡기고 주차. (5) 런타임 교체, (6) 측정과 문서 |
| `on_fail` 처리기 (2026-10-19) | 지금 의미 그대로("처음 실패한 자식이 처리기가 되어 대기열이 빌 때까지")를 태스크 끝의 이어 가기 상자가 한다 |
| offload 중의 취소 (2026-10-19) | R1b에서는 지금과 같다: 일이 끝날 때까지 기다린 뒤 되감는다(소켓·프로세스는 취소 훅이 일을 끊는다). 일을 버리고 곧바로 되감는 것은 R3 |

| 버리는 일 (R3, 2026-10-19; 4절의 "기한은 정확히 지킨다"를 고침) | 취소·기한에 곧바로 되감고 일은 풀에서 끝까지 돌되 결과를 버리는 것은 **경로만 읽는 일**: `fs.read`·`read_lines`·`exists`·`stat`·`glob`·`walk`, 정규식 컴파일. **바꾸는 일**(`write`·`append`·`mkdir`·`remove`·`remove_all`·`move`·`copy`·`open`·`close`·`temp_dir`, 핸들 읽기 `read_line(f)`·`read_lines(f)`: 위치를 옮김)은 시작했으면 끝까지 기다린다(R1b와 같음). 줄에서 아직 시작하지 않은 일은 종류와 상관없이 버린다. 취소된 쓰기가 나중에 일어나 재시도·정리와 경쟁하지 않게 하려는 것이다(Trio의 스레드 일도 기본은 기다림) |
