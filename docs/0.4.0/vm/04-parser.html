파서: 토큰을 트리로

토큰의 줄에서 문장과 식의 구조를 찾아 나무 모양으로 세운다. 형식 문법을 읽는 법, 재귀 하강 파서, 그리고 우선순위를 숫자 하나로 다루는 Pratt 파서를 본다.

  1. 소스
  2. 토큰
  3. 트리
  4. 코어
  5. 바이트코드
  6. 실행
이 장에서 배울 것
  • 문법을 형식적으로 적는 방법(EBNF)과 읽는 법
  • 트리(AST)가 무엇이고 왜 줄이 아니라 나무인가
  • 재귀 하강 파서: 문법 규칙 하나가 함수 하나
  • 연산자 우선순위와 결합 방향, 그리고 Pratt 파서
  • fung 파서가 줄바꿈을 다루는 법, fung의 균일 트리

왜 트리인가

렉서가 준 것은 토큰의 줄이다. 1 + 2 * 3은 1, +, 2, *, 3 다섯 토큰이 나란히 있을 뿐이다. 그런데 이 식의 뜻은 "1에다, 2와 3을 곱한 것을 더한다"이다. 줄만 봐서는 *가 먼저라는 사실이 드러나지 않는다. 이 관계를 드러내는 모양이 나무다.

      +
     / \
    1   *
       / \
      2   3

*가 +의 자식이다. 자식은 부모보다 먼저 계산된다. 줄 모양에 숨어 있던 "무엇이 무엇의 일부인가"가 가지로 드러났다. 이런 나무를 구문 트리, 또는 추상 구문 트리(AST, abstract syntax tree)라고 한다. "추상"은 괄호나 쉼표처럼 구조를 알려 주는 역할만 하던 토큰이 트리에서 사라진다는 뜻이다. (1 + 2) * 3의 괄호는 트리 모양을 바꿀 뿐, 트리 안에 괄호 노드는 없다.

토큰의 줄에서 트리를 세우는 단계가 파서(parser)이고, 그 일을 파싱(parsing, 구문 분석)이라고 한다.

문법을 적는 법

파서를 만들려면 먼저 "올바른 프로그램이 어떻게 생겼는가"를 정확히 적어야 한다. 말로 "함수 정의는 fn, 이름, 괄호 안 매개변수, 그리고 =과 식"이라고 쓸 수도 있지만, 규칙이 수십 개가 되면 말로는 모호해진다. 그래서 형식 문법(formal grammar)이라는 표기를 쓴다. 가장 흔한 것이 EBNF(Extended Backus–Naur Form)다. fung 문법의 일부를 보자.

fn_def   = "fn" NAME "(" [ params ] ")" fn_body .
fn_body  = "=" expr | block .
params   = param { "," param } [ "," ] .
add      = mul { ( "+" | "-" ) mul } .
mul      = unary { ( "*" | "/" | "//" | "%" ) unary } .
call     = "(" [ arg { "," arg } [ "," ] ] ")" .

읽는 법은 이렇다.

  • 이름 = 정의 .은 "이름은 이렇게 생겼다"는 규칙(rule)이다. 마침표가 규칙의 끝이다.
  • 따옴표 안("fn", "(")은 그 글자의 토큰이 와야 한다는 뜻이다. 대문자 NAME은 토큰 종류(이름 토큰 아무거나)다.
  • 다른 규칙의 이름(params, expr)은 "그 규칙에 맞는 것이 여기 온다"는 뜻이다.
  • a | b는 a 또는 b, [ a ]는 a가 있어도 되고 없어도 된다, { a }는 a가 0번 이상 반복된다.

그러면 fn_def는 "fn 토큰, 이름, (, 매개변수(없어도 됨), ), 그리고 =과 식 또는 블록"이다. fn double(x) = x * 2가 정확히 이 모양이다. add는 "mul 하나, 그 뒤에 +나 -와 mul이 0번 이상"이므로 1 + 2 - 3도 add다.

규칙이 다른 규칙을 부르고, 결국 자기 자신을 부를 수도 있다(식 안에 괄호 식이 있고, 그 안에 또 식이 있다). 이렇게 재귀하는 규칙 덕분에 유한한 규칙 몇십 개로 무한히 많은 프로그램을 적을 수 있다. fung의 전체 문법은 언어 레퍼런스의 형식 문법에 있다.

재귀 하강 파서

문법을 적었으면 그대로 코드로 옮길 수 있다. 가장 직접적인 방법이 재귀 하강(recursive descent) 파서다. 규칙 하나를 함수 하나로 만든다. 규칙의 "순서대로"는 코드의 순서대로, |는 if, { }는 반복문, 다른 규칙은 함수 호출이 된다. add와 mul을 옮기면 이렇다.

add():
  왼쪽 = mul()
  다음 토큰이 + 또는 - 인 동안:
    연산자를 읽는다
    오른쪽 = mul()
    왼쪽 = (연산자 왼쪽 오른쪽)     ← 새 노드를 만든다
  왼쪽을 돌려준다

mul():
  왼쪽 = unary()
  다음 토큰이 * / // % 인 동안: ... (같은 모양)

add가 mul을 부르고, mul이 unary를 부르고, 맨 아래 규칙은 괄호 식을 만나면 다시 맨 위의 expr를 부른다. 함수들이 문법의 위에서 아래로 "내려가며" 서로를 "재귀"로 부르기 때문에 재귀 하강이라는 이름이 붙었다.

파서는 토큰을 앞에서부터 하나씩 소비한다. 함수마다 "지금 토큰"을 보고(이것을 앞보기, peek라고 한다) 어느 갈래로 갈지 정한다. fn 토큰이면 함수 정의, 이름 다음에 =이 오면 대입, 그 밖은 식. fung 파서의 문장 함수가 실제로 이렇게 갈래를 탄다.

우선순위와 결합 방향

재귀 하강으로 식을 파싱할 때 핵심 문제는 우선순위(precedence)와 결합 방향(associativity)이다.

  • 우선순위: 1 + 2 * 3에서 *가 +보다 먼저 묶인다.
  • 결합 방향: 1 - 2 - 3은 (1 - 2) - 3이다(왼쪽 결합). 반면 거듭제곱 2 ** 3 ** 2는 수학 관례대로 2 ** (3 ** 2)다(오른쪽 결합).

위의 add·mul처럼 우선순위 단계마다 규칙을 하나씩 두면 우선순위가 저절로 해결된다. 낮은 단계의 함수가 높은 단계의 함수를 부르므로 높은 쪽이 트리 안쪽에 들어간다. 그런데 fung의 우선순위는 13단계라, 이렇게 하면 비슷하게 생긴 함수가 열 개 넘게 생기고 식 하나를 읽을 때마다 그 함수들을 모두 거친다.

Pratt 파서: 우선순위를 숫자로

Pratt 파서(Vaughan Pratt가 1973년에 소개했다)는 이 층들을 반복문 하나로 접는다. 연산자마다 결합력(binding power)이라는 숫자를 준다. 숫자가 클수록 세게 붙는다. fung 파서의 표는 이렇다(우선순위 표의 순위를 10배 한 값).

연산자왼쪽 결합력오른쪽 결합력
then … else10(양쪽 가지가 완전한 식)
or2021
and3031
== < in …5051
|>6061
+ -9091
* / // %100101
**120120
호출 (), 인덱스 [], 필드 ., ! ?130(뒤에 붙는 것)

파싱 함수는 "최소 결합력"을 인자로 받는다. 뜻은 "이보다 약한 연산자는 내 몫이 아니니 멈춰라"다.

expr(최소):
  왼쪽 = 피연산자 하나(수, 이름, 괄호 식, 단항 - …)
  반복:
    다음 토큰이 연산자이고 그 왼쪽 결합력 ≥ 최소 이면:
      연산자를 읽는다
      오른쪽 = expr(그 연산자의 오른쪽 결합력)
      왼쪽 = (연산자 왼쪽 오른쪽)
    아니면 멈춘다
  왼쪽을 돌려준다

1 + 2 * 3을 expr(0)으로 따라가 보자.

  1. 피연산자 1. 다음은 +(90). 90 ≥ 0이니 읽고, 오른쪽을 expr(91)로 읽는다.
  2. expr(91): 피연산자 2. 다음은 *(100). 100 ≥ 91이니 읽고, 오른쪽을 expr(101)로 읽는다. 3이 나오고 더 없으니 (* 2 3)을 돌려준다.
  3. 다시 바깥: 왼쪽은 (+ 1 (* 2 3)).

*가 +의 오른쪽 안으로 들어갔다. 이번에는 1 - 2 - 3이다.

  1. 피연산자 1, 다음 -(90). 오른쪽을 expr(91)로 읽는다.
  2. expr(91): 피연산자 2, 다음 -는 90. 90 ≥ 91이 아니므로 멈추고 2만 돌려준다.
  3. 바깥: 왼쪽은 (- 1 2). 다음 -(90) ≥ 0이므로 계속해 (- (- 1 2) 3).

오른쪽 결합력을 왼쪽보다 1 크게 준 것이 왼쪽 결합을 만들었다. **는 오른쪽 결합력을 왼쪽과 같게(120) 주었으므로, 안쪽 expr(120)이 다음 **(120 ≥ 120)도 먹어 버려 오른쪽 결합이 된다. 세 식을 실제로 파싱하면 이렇다.

print(1 - 2 - 3, 2 ** 3 ** 2, -2 ** 2)
$ fung dump ast example.fung
(program (call print (binary - (binary - 1 2) 3) (binary ** 2 (binary ** 3 2)) (unary - (binary ** 2 2))))

마지막의 -2 ** 2는 -(2 ** 2), 곧 -4다. 단항 -는 피연산자를 결합력 110 이상으로 읽는데 **(120)가 그보다 세서 먼저 묶인다. 수학 관례를 따른 결정이다.

print(1 - 2 - 3, 2 ** 3 ** 2, -2 ** 2)
-4 512 -4

비교는 연쇄를 금한다. a < b < c는 수학에서는 흔하지만 많은 언어에서 (a < b) < c, 곧 "참/거짓과 c의 비교"가 되는 함정이다. fung 파서는 방금 비교를 묶었는데 다음도 비교면 바로 에러를 낸다.

error[E0111]: comparison operators cannot be chained
  --> example.fung:1:13
  |
1 | print(a < b < c)
  |             ^
  |
 help: split it with `and`: a < b and b < c

줄바꿈은 파서가 정한다

3장에서 렉서는 줄바꿈을 Newline 토큰으로 넘겼다. 파서는 세 규칙으로 그 토큰을 문장 끝으로 볼지 공백으로 볼지 정한다(설계 문서 01).

  1. 괄호 안의 줄바꿈은 공백이다. 파서는 지금 열린 괄호의 깊이를 세다가(nest), 깊이가 0보다 크면 앞보기에서 Newline을 건너뛴다.
  2. 연산자로 끝난 줄은 이어진다. 연산자를 읽은 직후에는 줄바꿈을 건너뛴다.
  3. 다음 줄이 이어짐 전용 토큰으로 시작하면 이어진다. |> . ?? and or then else. 이 토큰들은 문장을 시작할 수 없으므로 모호하지 않다.
xs = [1, 2, 3]
total = xs
  |> map(x => x * 2)
  |> sum
print(total)
12

첫 규칙 때문에 생기는 에러 모양도 알아 두면 좋다. 닫는 괄호를 빠뜨리면 파서는 줄바꿈을 계속 공백으로 보며 괄호가 닫히기를 기다리다가 파일 끝에서야 포기한다. 에러가 문제의 줄이 아니라 파일 끝을 가리킨다.

fn double(x) = x * 2
print(double(21)
error[E0110]: unexpected end of file
  --> example.fung:3:1
  |
3 | 
  | ^
  |

반대로 호출 괄호 (는 같은 줄에서만 호출로 본다. f 다음 줄의 (1)은 호출이 아니라 새 문장이다. 줄을 넘는 호출을 허용하면 앞 줄의 끝이 우연히 이름일 때 다음 줄의 괄호 식이 호출로 붙어 버린다.

되돌리기

재귀 하강 파서는 보통 앞의 토큰 한두 개만 보고 갈래를 정한다. 그런데 fung 문법에는 한참 읽어 봐야 알 수 있는 곳이 있다. 문장이 (a, b)로 시작하면, 그것은 튜플 식일 수도 있고 구조 분해 대입 (a, b) = pair의 왼쪽일 수도 있다. =를 만나야 안다.

fung 파서는 이런 곳에서 되돌리기(backtracking)를 쓴다. 지금 위치를 저장해 두고 패턴으로 읽어 본 뒤, 바로 다음이 =이면 대입으로 확정하고, 아니면 저장한 위치로 돌아가 식으로 다시 읽는다. match 절의 머리(패턴 [when 조건] =>)도 같은 방식이다. 람다의 (a, b) =>는 되돌리기 대신, 괄호 짝을 미리 훑어 닫는 괄호 바로 뒤가 =>인지 본다.

되돌리기는 같은 토큰을 두 번 읽으므로 잘못 쓰면 느려진다. fung에서는 패턴 문법이 작아서 비용이 적다(설계 문서 09).

fung의 트리: 균일 트리

이제 트리를 담는 그릇을 보자. 흔한 방식은 노드 종류마다 다른 구조체를 두는 것이다. "덧셈 노드는 왼쪽과 오른쪽", "함수 정의 노드는 이름, 매개변수 목록, 본문"처럼. fung은 다르게 한다. 모든 노드가 같은 모양 하나다.

Node { head, pos, lit, kids, off, end }
  head  머리 단어: call, binary, fn, block …
  pos   위치(줄:칸)
  lit   리터럴 값(정수 2, 연산자 "*", 함수 정보 …)
  kids  자식 노드들
  off, end  소스의 바이트 구간

fung dump ast가 찍는 S-식(S-expression, 괄호로 감싼 목록) 표기가 이 모양을 그대로 보인다. (binary * x 2)는 머리가 binary, 리터럴이 *, 자식이 x와 2인 노드다.

fn double(x) = x * 2
print(double(21))
$ fung dump ast example.fung
(program (fn double(x) (block (binary * x 2))) (call print (call double 21)))

그림으로 그리면 이렇다.

program
├── fn double(x)
│   └── block
│       └── binary *
│           ├── x
│           └── 2
└── call
    ├── print
    └── call
        ├── double
        └── 21
  • fn double(x) = x * 2의 짧은 본문도 block에 싸였다. 짧은 형과 블록 형(fn double(x): … ;;)이 같은 트리가 된다.
  • 호출은 (call 함수 인자…)다. 첫 자식이 부르는 대상이고 나머지가 인자다. print도 double도 아직 이름일 뿐이다.
  • 괄호와 쉼표는 사라졌다. 추상 구문 트리다.

파서의 에러

파서의 에러도 E01xx이고 첫 번째 하나만 보고한다(설계 문서 08). 문법이 한 번 어긋나면 그 뒤를 어떻게 읽어야 할지 확실하지 않아서, 억지로 이어 읽으면 엉뚱한 에러가 줄줄이 따라 나오기 쉽다.

  • E0110 unexpected …: 이 자리에 올 수 없는 토큰.
  • E0112 expected …, found …: 특정 토큰이 와야 하는 자리(then 뒤의 else 등).
  • E0111: 비교 연쇄.
  • E0802 expression nesting too deep (limit 10000): 식이나 패턴이 만 겹 넘게 중첩됨.

마지막 것은 안전장치다. 재귀 하강 파서는 괄호가 한 겹 깊어질 때마다 함수 호출이 몇 겹 깊어진다. 괄호를 수십만 겹 쌓은 입력을 받으면 파서 자신의 스택이 넘쳐 프로세스가 죽는다. 그래서 깊이를 세다가 10,000에서 fung 에러로 멈춘다(이식 노트 R1).

다른 언어는
  • 파서 생성기: yacc·bison 같은 도구는 문법 파일에서 파서 코드를 만들어 준다(LR 파싱이라는 다른 방식). 오래된 컴파일러가 많이 썼다.
  • Python: 3.9부터 문법 파일(PEG라는 표기)에서 파서를 생성한다. 되돌리기를 기본으로 하는 방식이다.
  • C·C++의 큰 컴파일러(GCC, Clang): 손으로 짠 재귀 하강 파서다. 에러 메시지를 다듬기 쉬워서다.
  • Lua: 손으로 짠 재귀 하강 파서이고, 이항 연산자는 연산자마다 왼쪽·오른쪽 우선순위 숫자를 둔 표 하나로 처리한다. fung의 Pratt 파서와 같은 생각이다.
  • Lisp: 소스 자체가 괄호 목록이라 파서가 거의 없다. 그 괄호 목록이 곧 트리다. fung의 균일 트리가 빌려 온 생각이다.
fung의 선택
  • 문장은 재귀 하강, 식은 Pratt 파서. 우선순위 표를 숫자로 옮긴 것 하나로 모든 이항·단항·후위 연산의 우선순위와 결합 방향을 처리한다(설계 문서 09). 우선순위 표가 곧 파서의 상수 표다.
  • 균일 트리. 노드 종류마다 Rust 구조체를 만들지 않고 Node 하나로 쓴다. 설계 문서 00·09는 이것을 "속은 Lisp"의 실체라고 부른다. dump가 함수 하나로 끝나고, desugar와 이름 해석이 모두 같은 모양 위에서 "트리를 받아 같은 모양의 트리를 돌려주는" 단순한 변환이 되며, 나중에 사용자 매크로를 넣을 자리도 이것이다. 대가는 Rust 컴파일러가 "이 노드에는 자식이 셋이어야 한다"를 검사해 주지 않는다는 것이고, 그 검사는 desugar가 맡는다.
  • 되돌리기는 세 곳만, 패턴 문법이 작아서 싸다(설계 문서 09).
  • 문법 에러는 첫 번째에서 멈춘다(설계 문서 08). 다만 나중에 편집기 지원(LSP)을 위해 문장 경계(NEWLINE ; ;;)에서 다시 맞춰 읽을 수 있게 구조를 둔다는 것이 설계의 방향이다(09). 지금 파서는 다시 맞춰 읽지 않는다.

코드에서 찾아보기

  • crates/fung-front/src/parser.rs: 입구 parse(toks)가 (program …) 트리를 돌려준다. Parser 구조체에 지금 토큰 번호 i, 괄호 깊이 nest, 재귀 깊이 depth가 있다. Parser::peek(괄호 안이면 줄바꿈을 건너뛰는 앞보기), Parser::program, 깊이 한도 MAX_DEPTH(10,000).
  • crates/fung-front/src/parser/expr.rs: Pratt 파서. 결합력 상수 BP_THEN … BP_POSTFIX, 연산자 표 infix, Parser::expr과 Parser::infix_loop(위 의사 코드의 반복문), 이어짐 토큰 continues_line과 Parser::peek_infix, 피연산자 Parser::prefix, 보간 조각을 다시 파싱하는 Parser::string_literal.
  • crates/fung-front/src/parser/stmt.rs: 문장(Parser::statement), 블록 본문, if, 구조 분해를 시도하고 되돌리는 Parser::try_destructure.
  • crates/fung-front/src/parser/fn_.rs: 함수 정의 Parser::fn_def, 람다 Parser::lambda와 앞보기 Parser::lambda_params_ahead.
  • crates/fung-front/src/parser/pattern.rs: 패턴과 match 절의 머리(Parser::arm_head).
  • crates/fung-front/src/tree.rs: 균일 트리 Node, 머리 단어 Head, 리터럴 Lit. Head::as_str가 dump에 찍히는 머리 단어다.
트리 그려 보기

a or b and not c == d의 트리를 손으로 그려 보자. 그다음 fung dump ast로 확인하자. (힌트: 결합력은 or 20, and 30, not 40, == 50.)

풀이 보기

==가 가장 세고, 그다음 not, and, or 순서로 바깥이 된다. 곧 a or (b and (not (c == d)))다.

a = false
b = true
c = 1
d = 2
print(a or b and not c == d)
$ fung dump ast example.fung
(program (assign a false) (assign b true) (assign c 1) (assign d 2) (call print (binary or a (binary and b (unary not (binary == c d))))))

실행하면 c == d는 거짓이고 not이 참으로 바꾸며, b and 참은 참, a or 참은 참이다.

a = false
b = true
c = 1
d = 2
print(a or b and not c == d)
true

정리

  • 파서는 토큰의 줄을 트리로 세운다. 트리는 "무엇이 무엇의 일부인가"를 가지로 드러낸다.
  • 문법은 EBNF로 적는다. |는 또는, [ ]는 선택, { }는 반복이다.
  • 재귀 하강 파서는 문법 규칙 하나를 함수 하나로 옮긴다.
  • Pratt 파서는 연산자마다 결합력 숫자를 두고 반복문 하나로 우선순위와 결합 방향을 처리한다. 오른쪽 결합력을 1 크게 주면 왼쪽 결합, 같게 주면 오른쪽 결합이다.
  • 줄바꿈은 괄호 깊이, 줄 끝 연산자, 이어짐 전용 토큰의 세 규칙으로 파서가 판단한다.
  • fung의 트리는 머리·위치·리터럴·자식만 있는 균일 트리다. 문법 에러는 첫 번째만 보고한다.

다음 장에서는 이 트리를 더 작은 코어 언어로 풀어내는 desugar를 본다. 우선순위 표 전체는 언어 레퍼런스에 있다.
