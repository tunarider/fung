## 동시성이란 {#concurrency}

서버 100대에 `ssh`로 명령을 보내고 답을 모으는 스크립트를 생각하자. 한 대에 1초가 걸리면 하나씩 하면 100초다. 그런데 그 1초의 대부분은 **기다리는 시간**이다. 우리 프로그램은 아무것도 계산하지 않고 상대가 답하기를 기다린다. 기다리는 동안 다음 서버에 요청을 보낼 수 있다면 전체는 몇 초로 줄어든다.

- **동시성**(concurrency)은 여러 일을 **겹쳐서 진행**하는 것이다. 한 일이 기다리는 동안 다른 일을 한다. 실제로 같은 순간에 두 일을 계산하지 않아도 된다.
- **병렬성**(parallelism)은 여러 일을 **같은 순간에 계산**하는 것이다. CPU 코어가 여럿 필요하다.

스크립트와 웹 서비스의 일은 대부분 기다림(네트워크, 디스크, 외부 명령)이다. 그래서 fung이 먼저 필요로 한 것은 동시성이다. 동시에 진행하는 일 하나를 fung에서는 **태스크**(task)라고 부른다.

## 태스크를 무엇으로 만드나 {#models}

언어 런타임이 태스크를 만드는 방법은 크게 셋이다.

**운영체제 스레드(1:1).** 태스크 하나가 운영체제 스레드 하나다. 스레드마다 자기 스택(보통 수 MB를 예약)이 있고, 운영체제가 아무 때나 끼어들어 다른 스레드로 바꾼다(선점형, preemptive). 기다릴 때는 그냥 시스템 호출 안에서 잠들면 되므로 구현이 쉽다. 대신 스레드를 만드는 데 수십 µs, 바꾸는 데 몇 µs가 들고, 프로세스당 스레드 수에 한도가 있다. 느린 클라이언트 수천 개를 붙잡은 서버에는 버겁다.

**그린 스레드**(green thread). 태스크를 언어 런타임이 직접 관리하는 작은 데이터로 만들고, 적은 수의 운영체제 스레드 위에서 번갈아 돌린다. 태스크 M개를 운영체제 스레드 N개 위에서 돌리면 **M:N**, 하나 위에서 돌리면 **M:1**이다. 태스크 전환이 함수 몇 개를 부르는 정도로 싸고, 수만 개도 문제없다. 대신 기다리는 태스크가 운영체제 스레드를 붙잡지 않게 하려면, 런타임이 "기다림"을 직접 다뤄야 한다(13장의 이벤트 루프).

**이벤트 루프와 콜백.** 스레드 하나가 "준비된 일"을 차례로 처리하고, 기다림은 "끝나면 이 함수를 불러 달라"(콜백)로 표현한다. 콜백이 깊어지는 문제를 풀려고 많은 언어가 `async`/`await` 문법을 더했다.

`async`/`await`에는 잘 알려진 대가가 있다. **함수에 색이 생긴다.** `async` 함수 안에서만 `await`할 수 있으므로, 깊은 곳의 함수 하나가 기다리게 되면 그 함수를 부르는 모든 함수가 `async`로 바뀌어야 한다. 보통 함수와 `async` 함수가 섞여 쓰기 어렵다.

:::box other 다른 언어는
- **CPython**의 `threading`은 진짜 운영체제 스레드지만, GIL(Global Interpreter Lock)이라는 잠금 하나를 쥔 스레드만 바이트코드를 실행한다. 기다리는 동안에는 GIL을 내려놓으므로 입출력에는 동시성이 생기지만, 계산은 한 번에 하나다. 계산하는 스레드도 일정 시간(기본 5 ms)마다 GIL을 넘긴다. `asyncio`는 별개의 이벤트 루프 + `async`/`await` 모델이다.
- **JVM**의 전통적인 `Thread`는 1:1이다. Java 21의 가상 스레드(virtual thread)는 M:N이다.
- **JavaScript**(Node.js)는 스레드 하나의 이벤트 루프와 `async`/`await`다. 그 스레드가 계산에 묶이면 모든 요청이 멈춘다.
- **Erlang/BEAM**은 M:N 그린 스레드의 대표다. 프로세스(경량 태스크) 하나가 몇 KB에서 시작하고, 코어마다 스케줄러 스레드가 하나씩 있다. 프로세스는 정해진 양의 reduction(대략 함수 호출 수)을 쓰면 차례를 넘긴다. 프로그래머는 차례 넘기기를 신경 쓰지 않는다.
- **Lua**의 코루틴은 M:1이고 **협력형**(cooperative)이다. 코루틴이 `coroutine.yield`를 불러야만 차례가 넘어간다.
:::

:::box choice fung의 선택: M:1 스택 없는 그린 스레드
- **처음(0.2.0)은 1:1이었다.** 태스크마다 운영체제 스레드 하나, 그리고 fung 값을 여러 스레드가 동시에 만지지 않게 하는 전역 잠금 하나(CPython의 GIL과 같은 모양). 동시에 계산하지도 못하면서 스레드 비용은 다 냈다. 태스크 하나를 만드는 데 약 61 µs, 채널로 값 하나를 넘기는 데 약 2.8 µs였고, 기다리는 태스크 2만 개는 스레드 한도에 걸려 E0801로 끝났다(노트 R7-scheduler의 R단계 요약).
- **동시성 v2에서 전제가 바뀌었다.** fung을 상용 웹서비스를 짜는 언어로도 보기로 했고(설계 스펙 0절), 연결 수천 개에서 스레드 한도에 걸리는 것이 문제가 되었다. 그래서 런타임을 "M:1, 스택 없는 그린 스레드 + 이벤트 루프 + 스레드 풀"로 바꾸었다.
- **함수에 색을 만들지 않는다.** `async`/`await`처럼 "이 안에서는 저 함수를 부를 수 없다"는 일반 규칙은 설계의 반목표다(스펙 1절). fung의 `recv`나 `http.get`은 보통 함수이고, 어디서 불러도 된다. 기다림은 런타임이 알아서 주차로 바꾼다.
- **M:N은 하지 않았다.** fung 값은 원자적이지 않은 `Rc`로 공유하는데(10장), 여러 코어에서 fung 코드를 돌리면 이것이 깨진다. 여러 코어는 **여러 프로세스**로 쓴다(배포 환경의 복제 수, 같은 호스트면 `http.serve`의 `reuse_port`). M:N과 태스크별 힙은 보류 목록에 있다(스펙 2·10.3·13절).
- **의미는 M:1에 기대지 않는다.** "끼어들 수 없으니 원자적" 같은 M:1 전용 의미를 두지 않는다. 그래서 나중에 여러 코어로 가도 프로그램의 뜻이 바뀌지 않는다(스펙 1절의 반목표).
:::

## 태스크는 데이터다 {#fiber}

fung에는 동시성 문법이 없다. `scope`, `spawn`, `await`는 모두 평범한 내장 함수 호출이다.

```dump bytecode
fn double(x) = x * 2

r = scope(s => await(spawn(s, () => double(21))))
print(r)
```

`spawn`이 하는 일은 운영체제 스레드를 만드는 것이 아니다. <strong>`Fiber`라는 구조체 하나</strong>를 만들어 대기열에 넣을 뿐이다(`crates/fung-vm/src/vm.rs`). `Fiber`에는 태스크가 이어 가는 데 필요한 모든 것이 들어 있다.

- 값 스택(`stack`)과 프레임(`frames`): 9장에서 본 그것이다.
- 이어 가기 상자 줄(`conts`): 아래 "주차" 절.
- 취소 노드(`cancel`): 14장.
- 깨움 표시(`waiter`): 아래 "깨우기" 절.
- 다음에 할 일(`todo`): 처음 시작인가, 하던 루프를 이어 가는가, 주차했다가 깨어났는가, 되감아야 하는가.

그리고 `Task`는 "지금 실행 중인 태스크"의 자리다. 실행 루프와 모든 내장 함수가 `&mut Task`를 받는다. 스케줄러는 대기열 맨 앞의 `Fiber`를 `Task`의 필드와 **맞바꿔 넣고**(`Task::exchange`), 실행 루프를 한 차례 돌린 뒤, 다시 맞바꿔 꺼낸다. 필드를 옮길 뿐 할당은 없다. CPU의 레지스터를 바꿔 끼우는 문맥 전환(context switch)을 데이터 수준에서 하는 셈이다.

이 구조 덕에 태스크 하나를 만드는 데 약 1 µs, 기다리는 태스크 하나가 약 2.2 KB다(Apple M2 Max, 릴리스 빌드, 노트 R7-scheduler). 2만 개가 동시에 기다려도 된다.

```fung run
n = 20000
(tx, rx) = channel()

total = scope(fn(s):
  each(0..n, i => spawn(s, () => recv(rx)))
  each(0..n, i => send(tx, i)!)
  n
;;)
print(total, "tasks waited and finished")
```

새 태스크는 언제 처음 도나. 실행 스레드는 하나뿐이므로, **띄운 쪽이 차례를 내놓을 때**다. 다음 예에서 `main: spawned`가 먼저 찍히는 것은 그 때문이다. 본문이 `await(a)`에서 기다리기 시작해서야 `a`와 `b`가 차례로 돈다.

```fung run
fn work(name, n):
  each(1..n + 1, i => print("${name} ${i}"))
  name
;;

r = scope(fn(s):
  a = spawn(s, () => work("a", 3))
  b = spawn(s, () => work("b", 3))
  print("main: spawned")
  [await(a), await(b)]
;;)
print(r)
```

형제 태스크가 도는 순서는 **보장하지 않는다.** 지금 구현에서는 위처럼 정해진 순서로 돌지만, 그 순서에 기대는 프로그램은 경쟁 상태(race condition)다.

## 기다리기: 주차 {#parking}

M:1에서 가장 어려운 일은 "기다리기"다. 운영체제 스레드라면 `recv`가 그 자리에서 잠들면 된다. 하지만 fung에서는 실행 스레드가 하나뿐이다. 한 태스크가 잠들면 모두가 멈춘다. 그래서 기다리는 태스크는 **자기 상태를 어딘가에 치워 두고** 스케줄러에게 돌아가야 한다. 이것을 **주차**(park)라고 한다.

치워 둘 상태는 어디 있나. fung 프레임과 값은 원래 힙의 배열이다(9장). 그런데 한 가지가 남는다. `map(xs, f)`는 Rust로 쓴 내장 함수이고, 원소마다 fung 람다 `f`를 부른다. `f` 안에서 `recv`가 기다리기 시작하면, 그 순간 `map`이 "몇 번째 원소까지 했나", "지금까지 모은 결과"는 **Rust 함수의 지역 변수**, 곧 Rust 스택 위에 있다. Rust는 함수 한가운데의 스택을 저장했다가 이어 가는 기능을 표준으로 주지 않는다(그것이 Rust의 `async`이고, 함수에 색이 생긴다). Lua와 Python이 "C 경계를 넘는 yield" 문제라고 부르는 것이다.

### 이어 가기 상자 {#continuations}

fung은 Lua 5.2가 같은 문제를 푼 방법을 따랐다(노트 R7-scheduler의 R2). Lua에서 C 함수는 `lua_callk`로 Lua 함수를 부르면서 "돌아오면 이 함수(continuation)를 불러 달라"를 함께 넘긴다. C 함수가 기억할 것은 스스로 따로 남긴다.

fung에서 람다를 부르는 내장 함수는 **단계 내장 함수**(`NativeBody::Step`)다. 직접 람다를 부르지 않고, 무엇을 할지 **돌려준다**(`crates/fung-vm/src/vm/cont.rs`).

**상자**(`Box<dyn Cont>`)는 그 내장 함수가 이어 가는 데 필요한 상태다. `map`이라면 "남은 원소, 모은 결과"다. VM은 상자를 태스크의 이어 가기 줄(`Task::conts`, 프레임 스택 옆의 두 번째 스택)에 두고, 부탁받은 함수를 **같은 실행 루프에서** 부른다. 그 함수가 돌아와 프레임 수가 상자를 둔 깊이로 돌아오면 결과를 상자의 `resume`에 준다. 상자는 다음 호출을 부탁하거나(`Next::Call`), 끝나거나(`Next::Done`), 주차를 부탁한다(`Next::Park`). 에러·취소·`exit`가 그 자리를 지나 되감기면 상자의 `unwind`가 본다. 14장의 `with`·`timeout`·`scope`가 여기서 끼어든다.

`map`이 원소 하나를 처리하는 모습은 이렇다.

1. `map`이 시작하며 첫 원소를 스택에 쌓고 `Flow::Call(상자, f, 1)`을 돌려준다.
2. VM이 `f`의 프레임을 그 인자 위에 바로 쌓는다(9장의 빠른 길).
3. `f`가 돌아오면 상자의 `resume`이 결과를 받아 리스트에 넣고, 다음 원소를 쌓고 `Next::Call`.
4. 원소가 떨어지면 `Next::Done(리스트)`. VM은 그 값을 `map`을 부른 쪽 스택에 놓는다.

이렇게 하면 태스크 하나에는 실행 루프가 **하나뿐**이고, 태스크가 쥔 모든 것(프레임, 값, 상자)이 힙에 있다. 그래서 스케줄러가 태스크를 통째로 치워 둘 수 있다. 이것이 "스택 없는"(stackless) 그린 스레드의 뜻이다. 태스크마다 별도의 Rust 스택을 두지 않는다. 덤으로 `map`을 거친 깊은 재귀도 Rust 스택을 쓰지 않는다.

`map`을 fung으로 다시 쓰는 길도 있었다. fung 함수 안의 기다림은 원래 주차할 수 있으니 문제가 사라진다. 하지만 `for`는 `map`이 되고, 계산 위주 벤치마크는 `fold` 300만 번이다. 원소마다 인터프리터가 몇 단계를 더 하면 "계산 위주는 5% 넘게 느려지지 않는다"는 목표를 지키기 어려웠다. 게다가 `with`·`timeout`·`scope`는 되감기에 끼어들어야 해서 어차피 fung으로 쓸 수 없다. 장치가 하나 필요하다면 모두에 같은 장치를 쓰는 편이 예외가 적다(노트 R7-scheduler의 R2 4절). 콜백이 보통 내장 함수(`map(xs, str)`)면 되부를 일이 없으므로 순회 쪽이 그 자리에서 바로 부른다(`Task::call_plain`).

### 깨우기와 잃어버린 깨움 {#waking}

주차한 태스크는 누가 깨우나. 태스크마다 **깨움 표시**(`Waiter`)가 하나 있다. 기다리는 쪽은 자기 `Waiter`를 기다리는 것(채널의 줄, 다른 태스크의 결과 칸, 취소 노드)에 등록하고 `Park`를 돌려준다. 그것을 바꾸는 쪽(값을 보내는 태스크, 끝난 태스크)이 등록된 `Waiter`의 `wake()`를 부르면, 그 태스크 번호가 **실행 대기열**(`Ready`)에 들어간다. 깨어난 태스크의 상자는 `resume`에서 조건을 다시 본다. 받을 값이 정말 있으면 받고, 아니면 다시 주차한다. 깨움은 "다시 보라"는 뜻일 뿐이다.

동시성 코드의 고전적인 버그가 **잃어버린 깨움**(lost wakeup)이다. "값이 없다"를 확인한 뒤 등록하기 **전에** 값이 오면, 깨워 줄 대상이 아직 등록되지 않아 깨움이 사라지고 태스크는 영원히 잔다. fung은 순서로 막는다(`crates/fung-vm/src/vm/block.rs`의 `park_until`).

1. 깨움 표시를 먼저 지운다(`take_woken`).
2. 기다리는 것에 `Waiter`를 등록한다.
3. 그다음 조건을 본다.

조건을 바꾸는 쪽은 등록 **뒤에** 오므로 반드시 깨운다. 그 깨움이 주차 결정보다 먼저 와도 번호가 이미 대기열에 있으니 사라지지 않는다. `wake()`는 표시를 처음 세운 쪽만 대기열에 넣으므로 같은 태스크가 두 번 들어가지도 않는다.

```fung run
(tx, rx) = channel()

scope(fn(s):
  spawn(s, fn():
    each(1..4, i => send(tx, i)!)
    close(tx)
  ;;)
  for x in rx:
    print("got", x)
  ;;
;;)
print("done")
```

버퍼 없는 채널이라 `send`는 받는 쪽이 올 때까지, `for`의 받기는 값이 올 때까지 주차한다. 두 태스크가 서로를 깨우며 번갈아 돈다.

## 차례 넘기기 {#yield}

주차만으로는 부족하다. 기다리지 않고 계산만 하는 태스크가 있으면, 그 태스크가 끝날 때까지 다른 태스크는 영영 차례를 받지 못한다. 협력형 스케줄러의 약점이다.

fung은 사용자가 `yield`를 쓰지 않아도 되게 VM이 대신 센다. <strong>모든 `CALL`·`TAILCALL`에서</strong>(그리고 뒤로 가는 점프가 생기면 거기서도) `Task::tick`이 두 가지를 한다.

- 취소 표시를 본다. 취소됐으면 그 자리에서 E0701로 되감는다(14장).
- 남은 몫(`budget`)을 하나 줄인다. 0이 되면 이번 차례를 끝낸다. 다음 넘김 자리에서 실행 루프를 빠져나와 스케줄러에 "내 차례 끝"을 알리고(`Turn::Yielded`), 대기열 맨 뒤에 다시 선다.

몫은 `YIELD_EVERY` = 1,000이다. fung에는 반복문이 없으므로(반복은 재귀나 `map`·`fold`) 끝없는 계산은 반드시 호출을 지나고, 그래서 이것으로 충분하다.

```fung run
fn step(acc, i):
  if i % 500 == 0:
    print("a at", i)
  ;;
  acc + i
;;

scope(fn(s):
  spawn(s, () => fold(0..2001, 0, step))
  spawn(s, () => print("b: my turn"))
;;)
```

`a`가 `step`을 1,000번쯤 부른 자리에서 차례를 넘겼고, 그때 `b`가 돌았다.

:::box choice 왜 1,000인가
값은 재서 정했다(노트 R7-scheduler의 R1b 6절). 계산하는 태스크 옆에서 `sleep(1ms)`를 200번 하는 태스크가 끝나는 시간(늦음이 없으면 0.2초)을 쟀다.

<table>
  <thead><tr><th><code>YIELD_EVERY</code></th><th>10,000</th><th>2,000</th><th>1,000</th><th>500</th><th>200</th></tr></thead>
  <tbody>
    <tr><td>깨어난 태스크가 늦는 정도(초)</td><td>0.308</td><td>0.226</td><td>0.216</td><td>0.212</td><td>0.210</td></tr>
    <tr><td>계산 위주 벤치마크</td><td colspan="5">어느 값에서나 잡음(±2%) 안</td></tr>
  </tbody>
</table>

1,000 아래로는 깨어난 태스크가 얻는 것이 깨움당 0.03 ms 남짓인데, 스케줄러로 돌아가는 횟수는 다섯 배가 된다. 그래서 1,000이다.
:::

예외가 하나 있다. `atom`의 `swap(a, f)` 안에서는 차례를 넘기지 않는다. `swap`은 "옛 값을 읽고, `f`를 돌리고, 그사이 아무도 안 바꿨으면 새 값을 넣고, 바꿨으면 다시 돌리는" 비교 후 교체(compare-and-swap)다. `f` 도중에 차례를 넘기면 같은 atom을 계속 바꾸는 다른 태스크 때문에 영원히 다시 돌 수 있다. `f`는 효과를 쓸 수 없으므로(E0707) 주차하지 않고 한 차례 안에 끝난다. 그 대신 취소와 기한, 신호는 그 안에서도 확인한다.

```fung run
hits = atom(0)

scope(fn(s):
  each(1..5, _ => spawn(s, () => each(0..500, i => swap(hits, n => n + 1))))
;;)
print(deref(hits))
```

```fung run exit=1 error=E0707
fn noisy(n):
  print("about to add")
  n + 1
;;

hits = atom(0)
swap(hits, noisy)
```

`f`가 두 번 돌 수 있으니 `print`가 두 번 찍히거나 HTTP 요청이 두 번 나갈 수 있다. 그래서 VM은 `f`를 도는 동안(태스크의 `pure` 깊이) 효과 표(`vm/atom.rs`)에 있는 내장 함수를 부르면 E0707을 낸다.

## 스케줄러 한 바퀴 {#loop}

이제 스케줄러(`crates/fung-vm/src/vm/sched.rs`의 `Sched::run`)가 한 바퀴에 하는 일을 순서대로 보자.

1. **바깥 사건 처리.** 신호 스레드나 REPL이 게시한 사건(정지 요청, Ctrl-C)을 처리한다(14장).
2. **새 태스크 받기.** 지난 차례에 `spawn`된 `Fiber`를 표에 넣고 대기열 끝에 세운다. 한 태스크는 큐에 한 번만 선다(`Slot::queued`). 깨움이 겹쳐도 한 바퀴에 차례는 한 번이다.
3. **기한이 된 타이머.** 주차한 태스크의 기한(`sleep`, `timeout`)이 지났으면 대기열에 넣는다. 타이머는 이진 힙(`BinaryHeap`)에 있어서 가장 이른 것을 바로 본다.
4. **깨어난 태스크 옮기기.** 다른 태스크나 다른 스레드가 깨운 번호를 실행 대기열(`Ready`)에서 차례 큐로 옮긴다. `fung test`에서는 2와 4에서 새로 들어오는 태스크들의 순서를 씨앗으로 섞는다(`Runtime::shuffle_schedule`). 언어가 그 순서를 약속하지 않으므로, 기대는 시험을 드러내려는 것이다. 매 바퀴 한다. 계산하는 태스크가 차례를 넘기자마자 큐 끝에 다시 서므로, 큐가 빌 때만 옮기면 깨어난 태스크가 그 계산이 끝날 때까지 밀린다(실제로 있었던 버그다).
5. **입출력 살피기.** 소켓 등을 기다리는 태스크가 있으면, 누가 차례를 넘겼을 때와 256바퀴마다 이벤트 루프를 시간 제한 0으로 본다(13장). 한 번이 시스템 호출 하나라서 매 바퀴 하지 않는다.
6. **한 차례.** 큐 맨 앞의 태스크를 `Task`에 맞바꿔 넣고 `turn`. 끝나면 결과를 적고, 주차하면 기한과 함께 주차 표에, 차례를 넘겼으면 큐 끝에 넣는다.
7. **할 일이 없으면.** 모든 태스크가 주차했다. 그중 타이머나 바깥이 깨울 것(`Wake::timed`: `sleep`, 기한, 스레드 풀의 일, 표준 입력, 정지 채널, 소켓)이 하나도 없으면 교착이다(아래). 있으면 가장 이른 타이머까지 이벤트 루프에서 잔다.

다른 스레드(풀의 일, 표준 입력 읽기, 신호)는 fung 값을 만지지 않는다. 그들이 할 수 있는 것은 대기열에 **태스크 번호**를 넣거나 사건을 게시하는 것뿐이다. 대기열은 `Mutex` 뒤에 있고, 실행 스레드가 자고 있으면 이벤트 루프의 깨우개를 당긴다. 13장에서 자세히 본다.

## 교착 판정 {#deadlock}

**교착**(deadlock)은 모든 태스크가 서로를 기다려 아무도 다시 돌 수 없는 상태다. 운영체제 스레드 런타임은 이것을 정확히 알기 어렵다. 스레드가 "잠들었다"는 것과 "곧 깨어날 것이다"를 구분하려면 모든 스레드의 상태를 한순간에 봐야 하는데, 스레드들은 그사이에도 움직인다. 그래서 "한동안 아무도 움직이지 않으면"처럼 시간 유예를 두거나, 원자 변수로 셈을 맞추는 복잡한 장치가 필요하다. fung의 0.2.0도 원자 변수로 "자는 스레드 수"를 셌다.

M:1에서는 정확하다. 모든 태스크는 셋 중 하나다. 도는 중, 대기열에 있음, 주차함. 그리고 이 셋은 **실행 스레드에서만** 바뀐다. 그래서 대기열이 비었을 때 주차한 태스크 중 타이머나 바깥이 깨울 것이 하나도 없으면, 그것이 정확히 교착이다. 유예 시간도 원자 변수도 없이 그 자리에서 E0702를 보고하고, 프로그램의 루트를 취소하고, 종료 코드 1로 끝낸다. 깨워졌지만 아직 돌지 않은 태스크는 대기열에 있으므로 막힌 것으로 세지 않는다.

```fung run exit=1 error=E0702
(tx, rx) = channel()

scope(fn(s):
  spawn(s, () => recv(rx))
  recv(rx)
;;)
```

주차한 태스크의 상태는 모두 힙에 있으므로, 보고는 따로 기록해 둔 것 없이 **원래 있던 것을 읽는다.** 스케줄러가 태스크마다 `Fiber`를 `Task`에 잠깐 맞바꿔 넣고, 런타임 에러와 같은 함수(호출 경로, 사용자 코드의 위치)로 읽은 뒤 다시 꺼낸다. 무엇을 기다리는지는 맨 위 이어 가기 상자가 어느 내장 함수의 것인지로 안다. 실행 루트는 런타임 에러처럼, 나머지는 같은 종류·위치끼리 묶어 10줄까지 보인다.

```fung run exit=1 error=E0702
fn worker(rx) = for job in rx:
  print("job", job)
;;

(tx, rx) = channel()
scope(fn(s):
  each(0..1000, _ => spawn(s, () => worker(rx)))
  send(tx, 1)!
;;)
```

일꾼 1,000개가 `for job in rx`에서 다음 값을 기다리는데, 최상위의 `tx`가 프로그램 끝까지 살아 있어 채널이 닫히지 않는다(10장 "지역 변수의 수명": 최상위 변수는 끝까지 산다). 태스크 범위는 일꾼이 끝나기를 기다리고, 일꾼은 채널이 닫히기를 기다린다.

## 한계 {#limits}

M:1을 고른 대가도 분명히 알아 두자.

- **계산은 코어 하나다.** 실행 스레드가 하나라서 계산만 하는 태스크 여럿은 번갈아 돌 뿐 동시에 돌지 않는다. 여러 코어는 여러 프로세스로 쓴다.
- **긴 내장 함수 하나는 차례를 넘기지 않는다.** 차례 넘기기는 fung 코드의 호출에서 일어난다. Rust로 쓴 내장 함수 하나(큰 `json.parse`, 콜백 없는 큰 `sort`)는 끝날 때까지 실행 스레드를 쥔다. 같은 프로그램 안의 서버에서 약 6 MB JSON을 파싱하는 요청 옆의 가벼운 요청은 파싱 시간(약 72 ms)만큼 늦었다. 스펙은 이것을 기록만 하기로 했다.
- **띄운 태스크는 띄운 쪽이 차례를 넘기거나 주차하기 전에는 돌지 못한다.** 범위가 자식을 기다리므로 자식은 언젠가 돈다. 다만 첫 차례 전에 범위가 취소되면 그 자식은 한 줄도 돌지 않는다.
- **공정성.** 순서를 보장하지 않을 뿐 굶기지는 않는다. 차례는 한 바퀴에 한 번이고, 연결의 읽기·쓰기 차례는 놓을 때 줄의 맨 앞 태스크에 넘긴다(곧바로 다음 연산을 시작한 태스크가 다시 잡지 못하게).
- **끝없이 도는 태스크는 다른 태스크들 사이의 교착을 가린다.** 교착은 모든 태스크가 멈췄을 때만 판정한다. 도는 태스크가 막힌 태스크를 앞으로 깨울 수 있는지는 그 코드가 읽을 수 있는 전역까지 따라가야 알 수 있어서, 오탐 없이 판정할 규칙이 없다.

- `crates/fung-vm/src/vm.rs`: 쉬는 태스크 `Fiber`, 실행 중인 태스크 `Task`, 맞바꾸기 `Task::exchange`, 한 차례 `Task::turn`과 `drive`, 다음 할 일 `Todo`, 차례의 끝 `Turn`.
- `crates/fung-vm/src/vm/cont.rs`: 이어 가기 상자 `Cont`(`resume`·`unwind`), `Flow`, `Next`, `Wake`, 상자의 자리 `ContFrame`.
- `crates/fung-vm/src/vm/block.rs`: 깨움 표시 `Waiter`, 기다리는 쪽 목록 `WaitList`, 흔한 주차 `park_until`, 차례 넘기기 `Task::tick`과 `YIELD_EVERY`.
- `crates/fung-vm/src/vm/deadlock.rs`: 교착 판정과 보고 `judge`.
- `crates/fung-vm/src/vm/channel.rs`: 채널 `Channel`, 두 끝 `Sender`·`Receiver`, 받기·보내기의 기다림 `RecvWait`·`SendWait`.
- `crates/fung-vm/src/vm/atom.rs`: `Atom`, `swap`의 상자 `Swap`, 효과 표.
- `crates/fung-vm/src/vm/scope.rs`: 태스크 범위와 `spawn`, 태스크의 끝 상자 `TaskEnd`(14장).

:::exercise 교착 고치기
위 "교착 판정" 절의 일꾼 예를 고쳐서, 일꾼 셋이 작업 1·2·3을 나눠 받고 모두 끝난 뒤 `all workers finished`가 찍히게 하자. 태스크 범위는 왜 그때까지 돌아오지 않았나?

:::solution
```fung run
fn worker(rx) = for job in rx:
  print("job", job)
;;

(tx, rx) = channel()
scope(fn(s):
  each(0..3, _ => spawn(s, () => worker(rx)))
  each(1..4, i => send(tx, i)!)
  close(tx)
;;)
print("all workers finished")
```

`for job in rx`는 채널이 **닫혀야** 끝난다. 채널은 보내는 끝의 마지막 사본이 사라지거나 `close(tx)`를 부르면 닫힌다. 최상위 변수 `tx`는 프로그램 끝까지 살아 있으므로 저절로는 닫히지 않는다. 그래서 일꾼은 영원히 다음 값을 기다리고, 태스크 범위는 일꾼이 끝나기를 기다려 교착이 됐다. 다 보낸 뒤 `close(tx)`를 부르면 일꾼들의 `for`가 끝나고, 범위가 닫힌다.
:::
:::

## 정리 {#summary}

- 동시성은 기다리는 동안 다른 일을 하는 것이고, 병렬성은 같은 순간에 계산하는 것이다. fung이 먼저 필요로 한 것은 동시성이다.
- fung의 태스크는 운영체제 스레드가 아니라 `Fiber`라는 데이터다. 실행 스레드 하나가 대기열의 태스크를 `Task`에 맞바꿔 넣으며 차례로 돌린다(M:1). 태스크 하나는 약 1 µs, 2.2 KB다.
- 기다리는 태스크는 주차한다. 람다를 부르는 내장 함수는 이어 가기 상자를 돌려주므로(`lua_callk` 방식), 태스크의 모든 상태가 힙에 있고 Rust 스택에 남는 것이 없다.
- 잃어버린 깨움은 "표시를 지우고, 등록하고, 조건을 본다"는 순서로 막는다.
- 계산하는 태스크는 호출 1,000번마다 차례를 넘긴다. `swap`의 함수 안은 예외다.
- 모든 상태가 실행 스레드에서만 바뀌므로 교착을 유예 없이 정확히 판정하고, 기다리는 자리를 보여 준다.
- 대가: 계산은 코어 하나, 긴 내장 함수는 차례를 넘기지 않는다.

레퍼런스: [동시성 함수](../reference/prelude/concurrency.html), [E0702](../reference/errors.html#E0702). 다음 장은 "운영체제를 기다리는 일"(소켓, 외부 명령, 파일)을 이 스레드 하나 위에서 어떻게 기다리는지 본다.
