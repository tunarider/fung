# 인터프리터, 컴파일러, VM

:::goals
- 인터프리터와 컴파일러가 각각 무엇을 하는가
- 트리 순회 인터프리터와 바이트코드 VM의 차이
- JIT가 무엇이고 fung은 왜 쓰지 않는가
- fung이 바이트코드 VM을 고른 이유와 꼬리 호출과의 관계
:::

## 두 가지 일: 옮기기와 실행하기 {#two-jobs}

1장에서 소스가 실행되려면 누군가 뜻을 찾아 CPU가 할 수 있는 일로 바꿔야 한다고 했다. 이 "누군가"에는 성격이 다른 두 종류가 있다.

**컴파일러**(compiler)는 프로그램을 **다른 언어로 옮긴다**. 입력도 프로그램이고 출력도 프로그램이다. 옮기기만 하고 실행하지는 않는다. C 컴파일러는 C 소스를 기계어 파일로 옮기고, 그 파일을 실행하는 것은 나중의 일이다. 옮기는 대상이 꼭 기계어일 필요는 없다. 다른 고수준 언어로 옮기는 것(TypeScript를 JavaScript로)도 컴파일러다.

**인터프리터**(interpreter)는 프로그램을 받아 **그 자리에서 실행한다**. 출력은 프로그램이 아니라 실행 결과다. `print(1 + 2)`를 받으면 `3`을 찍는다.

둘은 통역과 번역의 차이와 비슷하다. 번역가는 책 한 권을 미리 다 옮겨 두고, 독자는 나중에 옮긴 책을 읽는다. 통역사는 말을 들으며 바로 옮겨 말한다. 번역은 준비가 오래 걸리지만 읽는 동안은 빠르고, 통역은 바로 시작하지만 매번 통역사가 있어야 한다.

## 트리 순회 인터프리터 {#tree-walking}

가장 단순한 인터프리터는 파서가 만든 트리를 **위에서부터 걸어 다니며** 계산한다. 이것을 **트리 순회 인터프리터**(tree-walking interpreter)라고 한다. `1 + 2 * 3`의 트리는 이렇다.

```plain
      +
     / \
    1   *
       / \
      2   3
```

인터프리터는 노드마다 "이 노드는 무엇인가"를 묻고 그에 맞게 계산한다. 의사 코드로 쓰면 다음과 같다.

```plain
계산(노드):
  노드가 수이면        → 그 수
  노드가 + 이면        → 계산(왼쪽) + 계산(오른쪽)
  노드가 * 이면        → 계산(왼쪽) * 계산(오른쪽)
  노드가 함수 호출이면 → 인자를 계산하고, 함수 본문 트리를 계산(...)
```

만들기 아주 쉽다. 언어 구현 입문서들이 대개 이것부터 만드는 이유다. 그러나 약점이 셋 있다.

- **느리다.** 노드를 하나 지날 때마다 "무슨 노드지?"를 묻고, 자식을 따라 메모리 여기저기를 뛰어다닌다.
- **구현 언어의 재귀에 기댄다.** `계산`이 `계산`을 부르므로, fung 함수가 재귀를 백만 번 하면 구현 언어의 함수도 백만 번 겹쳐 불린다. 구현 언어의 스택(함수 호출을 쌓는 메모리)이 넘치면 인터프리터째로 죽는다.
- **중간에 멈췄다가 이어 가기 어렵다.** 계산하던 위치가 구현 언어의 스택 깊숙이 흩어져 있어서, "여기서 잠깐 멈추고 다른 일을 하다 돌아오기"를 하려면 그 스택을 통째로 보관해야 한다.

## 바이트코드 VM {#bytecode-vm}

많은 언어는 중간 길을 간다. 먼저 **컴파일러**가 트리를 **바이트코드**라는 평평한 명령 목록으로 옮긴다. 그리고 그 명령 목록을 실행하는 작은 **인터프리터**를 둔다. 이 인터프리터는 실제 CPU처럼 명령을 하나씩 읽어 수행하기 때문에 **가상 기계**(virtual machine), 줄여서 **VM**이라고 부른다. 바이트코드는 이 가상 CPU의 기계어인 셈이다.

`1 + 2 * 3`을 fung의 바이트코드로 옮기면 이렇다.

```dump bytecode
print(1 + 2 * 3)
```

트리 대신 위에서 아래로 읽는 목록이다. VM은 반복문 하나로 이 목록을 돈다. "명령을 하나 읽는다 → 종류에 따라 할 일을 한다 → 다음 명령으로"의 반복이다. 이것을 **디스패치 루프**(dispatch loop), 또는 실행 루프라고 한다.

트리 순회와 비교하면 이렇게 달라진다.

- 명령이 배열에 나란히 있어서 다음 명령이 바로 옆에 있다. 노드 종류를 묻는 대신 명령 번호 하나로 갈래를 탄다.
- fung의 함수 호출이 구현 언어의 함수 호출이 되지 않는다. VM은 "지금 실행 중인 함수들"을 자기 목록(프레임 목록, 8장)에 쌓는다. 실행 루프는 그냥 반복문이다.
- 실행 상태가 전부 VM의 자료구조 안에 있다. "지금 몇 번 명령, 스택에는 이런 값들"을 보관해 두면 언제든 멈췄다가 이어 갈 수 있다. 4부의 태스크 스케줄러가 여기에 기댄다.

"바이트코드"라는 이름은 전통적으로 명령 하나를 1바이트 번호로 나타냈던 데서 왔다. fung은 명령 하나를 32비트 단어 하나로 나타낸다(8장). 이름만 물려받았다.

## JIT: 실행 중에 기계어로 {#jit}

바이트코드 VM도 결국 "명령을 읽고 종류를 묻는" 비용이 남는다. 이것까지 없애려는 기법이 **JIT**(just-in-time) 컴파일이다. 실행하면서 자주 도는 부분을 찾아, 그 부분의 바이트코드를 **실행 중에** 진짜 기계어로 컴파일해 두고 다음부터는 그 기계어를 바로 실행한다. 웹 브라우저의 JavaScript 엔진이 빠른 이유가 이것이다.

대가가 크다. 실행 중에 기계어를 만들어 메모리에 올리고 실행 권한을 주는 일, CPU 종류(x86, ARM …)마다 다른 기계어를 만드는 일, 값의 타입이 바뀌면 만들어 둔 기계어를 버리는 일을 모두 해야 한다. JIT 하나가 언어 구현 전체보다 커지는 경우도 흔하다.

    <tr><td>바이트코드 + JIT</td><td>JVM, V8(JavaScript), LuaJIT</td><td>긴 프로그램에서 아주 빠르다</td><td>구현이 매우 크고 복잡하다. 시작이 느릴 수 있다</td></tr>
  </tbody>

:::box other 다른 언어는
- **CPython**: 바이트코드 VM. 명령이 값 스택을 쓰는 스택 머신이다(8장). 소스를 고치지 않으면 다음 실행 때 쓰려고 바이트코드를 `.pyc` 파일로 저장해 둔다.
- **Lua**: 바이트코드 VM이지만 5.0부터 **레지스터 머신**이다(8장에서 비교). LuaJIT라는 별도 구현은 JIT를 더했다.
- **JVM**(Java): 컴파일러 `javac`가 바이트코드(`.class`)를 파일로 만들고, JVM이 그것을 해석하다가 자주 도는 부분을 JIT로 기계어로 바꾼다.
- **Ruby**: 1.8까지 트리 순회 인터프리터였고, 1.9부터 YARV라는 바이트코드 VM으로 바뀌었다.
- **bash**: 명령을 하나씩 읽어 바로 실행한다. 바이트코드가 없다.
:::

:::box choice fung의 선택: 바이트코드 VM, JIT는 없음
설계 문서 00은 "Rust로 구현, 바이트코드 VM"이라고 정하면서 이렇게 적었다. 트리 순회 인터프리터가 더 단순하다는 것을 **알고** 고른 선택이다. 목적이 컴파일러와 VM의 동작 원리를 배우는 것이고, 꼬리 호출 최적화(아래)도 VM 쪽이 자연스럽다. 대신 처음 세 마일스톤(계산기·변수·함수)의 구현량이 두 배 정도 늘었다.

JIT는 하지 않는 쪽으로 기울어 있다(open-questions "성능"). 실행 가능한 메모리 관리, 대상 아키텍처마다의 코드 생성, 메모리 회수·스케줄러와의 상호작용 비용이 fung의 용도(입출력 위주 스크립트)에 비해 크다는 이유다. 바이트코드를 파일로 저장해 두는 방식(`.pyc` 같은 것)도 쓰지 않는다. 컴파일이 10ms 미만이라 저장해 두어도 속도 이득이 없기 때문이다. 바이트코드는 실행할 때마다 메모리에서 새로 만든다.
:::

## 왜 꼬리 호출이 VM에서 자연스러운가 {#tail-calls}

fung에는 `while` 같은 반복문이 없다. 상태가 있는 반복(재시도, 누적, 폴링)은 **꼬리 재귀**로 쓴다(설계 문서 00). 꼬리 재귀란 함수가 마지막에 하는 일이 "자기 자신을 부르고 그 결과를 그대로 돌려주기"인 재귀다.

```fung run
fn count(n, acc) = n == 0 then acc else count(n - 1, acc + 1)
print(count(1000000, 0))
```

백만 번 재귀했는데 멀쩡하다. `count(n - 1, acc + 1)`을 부른 뒤에 `count`가 할 일이 남아 있지 않으므로, 지금 함수의 자리를 그대로 새 호출에 물려줘도 된다. 이것을 **꼬리 호출 최적화**(tail call optimization, TCO)라고 한다. 설계 문서 00은 "꼬리 호출 최적화는 선택 기능이 아니라 이 결정의 전제 조건"이라고 적었다. 반복을 재귀로 쓰라고 해 놓고 재귀가 깊어지면 죽는다면 말이 안 되기 때문이다.

트리 순회 인터프리터에서 이것을 하려면, fung 함수 호출이 곧 구현 언어의 함수 호출이므로 구현 언어의 스택을 다시 써야 한다. 할 수는 있지만 꼬이기 쉽다. 바이트코드 VM에서는 fung의 프레임이 VM이 직접 관리하는 목록의 원소라서, "새 프레임을 쌓지 말고 지금 프레임의 칸을 새 인자로 채운 뒤 명령 0번으로 돌아가라"는 명령(`TAILCALL`) 하나면 된다. fung의 재귀가 Rust의 재귀가 아니기 때문에 Rust의 스택도 넘치지 않는다(마일스톤 노트 M3).

꼬리가 아닌 재귀는 다르다. `1 + depth(n - 1)`은 돌아온 뒤에 `1 +`를 해야 하므로 프레임이 쌓인다. 프레임이 100,000개를 넘으면 VM이 스스로 멈추고 알려 준다.

```fung run exit=1 error=E0804
fn depth(n) = n == 0 then 0 else 1 + depth(n - 1)
print(depth(10))
print(depth(200000))
```

프로세스가 죽는 대신 fung 에러(`E0804`)가 나고, 도움말이 꼬리 재귀나 `fold`를 권한다. 한도를 둔 이유와 프레임의 생김새는 8장과 9장에서 본다.

## 따라가기: 두 줄은 언제 컴파일되나 {#follow}

`fung run double.fung`을 실행하면 `fung`은 먼저 앞단 전체를 돌려 바이트코드를 만든다. 이 단계가 끝나기 전에는 한 줄도 실행하지 않는다. 그다음 VM이 `<main>`이라는 이름의 명령 목록(파일 본문)을 0번부터 실행한다.

```dump bytecode
fn double(x) = x * 2
print(double(21))
```

목록이 둘이다. 파일 본문 `<main>`과 함수 `double`. 컴파일러는 함수마다 명령 목록을 하나씩 만든다. `<main>`의 `CALL`이 `double`을 부르면 VM은 `double`의 목록으로 건너가 0번부터 실행하고, `RETURN`에서 돌아온다. 이 흐름은 8장에서 명령 하나하나 따라간다.

정리하면 fung은 "실행할 때마다 컴파일하는 바이트코드 VM"이다. 사용자 눈에는 인터프리터처럼 보이지만(`fung script.fung`만으로 돈다), 안에서는 컴파일러와 VM이 차례로 일한다.

## 코드에서 찾아보기 {#source}

- `crates/fung-front/src/compiler.rs`의 `compile`: 이름이 정해진 코어 트리(`Resolved`)를 받아 파일 본문의 `Proto`(함수 원형, 8장)를 만든다. 함수마다 자식 `Proto`가 생긴다.
- `crates/fung-vm/src/vm/link.rs`의 `link`: 앞단이 만든 `Proto`를 VM이 쓰는 `RtProto`로 바꾼다. 앞단은 실행 시점의 값을 모르므로 `print` 같은 내장 함수 자리를 이름으로 남겨 두고, 여기서 실제 함수 값으로 채운다.
- `crates/fung-vm/src/vm.rs`의 `Task::step_loop`: 디스패치 루프. `loop` 안에서 맨 위 프레임의 명령을 하나 읽고 `match instr.op()`로 갈래를 탄다.
- `crates/fung-vm/src/vm/call.rs`: 호출과 꼬리 호출. 프레임 한도 `MAX_FRAMES`(100,000)도 여기 있다.

아래 함수는 1부터 n까지 더한다. `sum_to(200000)`을 부르면 `E0804`가 난다. 누적값을 인자로 넘기는 꼬리 재귀로 바꿔서 `sum_to(200000)`이 `20000100000`을 찍게 해 보자.

```fung frag
fn sum_to(n) = n == 0 then 0 else n + sum_to(n - 1)
```

누적값 `acc`를 두 번째 인자로 받으면, 재귀 호출이 함수가 마지막에 하는 일이 된다.

```fung run
fn sum_to(n, acc = 0) = n == 0 then acc else sum_to(n - 1, acc + n)
print(sum_to(200000))
```

`fung dump bytecode`로 보면 재귀 호출 자리에 `CALL` 대신 `TAILCALL`이 있다.

```dump bytecode
fn sum_to(n, acc = 0) = n == 0 then acc else sum_to(n - 1, acc + n)
print(sum_to(200000))
```

## 정리 {#summary}

- 컴파일러는 프로그램을 다른 언어로 옮기고, 인터프리터는 프로그램을 바로 실행한다.
- 트리 순회 인터프리터는 만들기 쉽지만 느리고 구현 언어의 재귀에 기댄다.
- 바이트코드 VM은 트리를 평평한 명령 목록으로 컴파일한 뒤, 가상 CPU처럼 반복문 하나로 실행한다. 실행 상태가 VM 안에 있어서 멈추고 이어 가기 쉽다.
- JIT는 실행 중에 기계어를 만든다. fung은 용도에 비해 비용이 커서 쓰지 않는다.
- fung은 배우는 것이 목적이고 꼬리 호출이 자연스럽다는 이유로 바이트코드 VM을 골랐다. 반복을 꼬리 재귀로 쓰는 언어라 꼬리 호출 최적화가 필수다.
