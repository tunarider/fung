# 프로그램이 실행되기까지

:::goals
- 컴퓨터가 소스 코드를 바로 이해하지 못하는 이유
- 소스가 실행되기까지 거치는 여섯 단계와 각 단계의 이름
- 컴파일 시점과 실행 시점의 차이, 에러가 어느 쪽에서 나는지
- `fung dump`로 단계마다 모양을 직접 보는 법
:::

## 컴퓨터는 글자를 모른다 {#letters}

`fn double(x) = x * 2`라는 줄은 사람에게는 뜻이 분명하다. "x를 받아 두 배를 돌려주는 함수 double". 그런데 컴퓨터의 두뇌인 CPU가 할 줄 아는 것은 이런 것이 아니다. CPU는 "메모리 몇 번지의 수를 레지스터로 가져와라", "두 레지스터를 더해라", "몇 번 명령으로 뛰어라" 같은 아주 작은 명령만 실행한다. 이 명령들을 숫자로 적은 것을 **기계어**(machine code)라고 한다.

소스 코드는 그냥 글자들이다. 파일 안에는 `f`, `n`, 공백, `d`, `o` … 같은 글자가 한 줄로 늘어서 있을 뿐이다. "함수", "변수", "곱하기" 같은 뜻은 글자 안에 들어 있지 않다. 그 뜻을 찾아내고, 결국 CPU가 할 수 있는 일로 바꾸는 프로그램이 따로 있어야 한다. 그것이 **언어 구현**(language implementation)이다. `fung`이라는 실행 파일이 바로 fung의 언어 구현이다.

이 책은 그 실행 파일 안에서 무슨 일이 일어나는지를 따라간다. 언어 구현을 처음 보는 사람을 위해 쓴 책이라, 일반적인 개념을 먼저 설명하고, 다른 언어들은 어떻게 하는지 견준 다음, fung이 무엇을 골랐고 왜 그랬는지를 실제 출력으로 보인다.

## 번역에 비유하면 {#analogy}

영어 문장 하나를 한국어로 옮긴다고 해 보자. 사람은 대략 이런 순서로 일한다.

1. 글자를 **단어**로 나눈다. "The cat sat"은 "The", "cat", "sat" 세 단어다.
2. 단어들이 이루는 **문장 구조**를 본다. 무엇이 주어이고 무엇이 동사인가.
3. 숙어나 줄임말을 **기본 표현으로 푼다**. "gonna"는 "going to"다.
4. 각 단어가 **무엇을 가리키는지** 정한다. 앞 문장의 "it"은 무엇이었나.
5. 목표 언어로 **옮겨 적는다**.
6. 옮긴 글을 **읽고 행동한다**.

프로그래밍 언어의 구현도 거의 같은 순서로 일한다. 단계마다 이름이 있다.

<ol class="stages"><li>소스</li><li>토큰</li><li>트리</li><li>코어</li><li>바이트코드</li><li>실행</li></ol>

- **소스**(source): 사람이 쓴 글자 그대로.
- **토큰**(token): 렉서(lexer)가 글자를 단어 단위로 자른 것. `fn`, `double`, `(`, `x` … (3장)
- **트리**(tree): 파서(parser)가 토큰들의 구조를 나무 모양으로 만든 것. "이 곱셈은 이 함수의 본문이다" 같은 관계가 가지로 드러난다. (4장)
- **코어**(core): 편의 문법을 몇 안 되는 기본 형태로 푼 트리(5장). 이때 모든 이름이 "어디에 사는 값인지"도 정해진다(6장).
- **바이트코드**(bytecode): 컴파일러(compiler)가 트리를 평평한 명령 목록으로 옮긴 것. (8장)
- **실행**: 가상 기계(VM, virtual machine)가 그 명령을 하나씩 수행한다. (8장 이후)

여섯 단계 가운데 앞의 넷을 **앞단**(front end), 바이트코드를 만들고 실행하는 쪽을 **뒷단**(back end)이라고 부른다. 실행에 필요한 나머지 장치(메모리 관리, 태스크, 이벤트 루프 등)는 **런타임**(runtime)이라고 한다. 이 책의 2부가 앞단, 3부가 뒷단, 4부가 런타임이다.

## 이 책이 따라갈 두 줄 {#example}

책 전체에서 같은 프로그램 하나를 끝까지 따라간다.

```fung run
fn double(x) = x * 2
print(double(21))
```

`fung`은 이 두 줄을 받아 위의 여섯 단계를 차례로 거친 뒤 `42`를 찍는다. 단계 사이의 중간 결과는 버려지지 않고 `fung dump` 명령으로 볼 수 있다. 미리 보기로 세 가지를 모두 찍어 보자. 지금은 읽지 못해도 된다. 장마다 하나씩 읽는 법을 배운다.

파서가 만든 트리(`fung dump ast`):

```dump ast
fn double(x) = x * 2
print(double(21))
```

편의 문법을 풀고 이름을 정한 코어 트리(`fung dump core`):

```dump core
fn double(x) = x * 2
print(double(21))
```

컴파일러가 만든 바이트코드(`fung dump bytecode`):

```dump bytecode
fn double(x) = x * 2
print(double(21))
```

모양이 단계마다 다르다는 것만 눈여겨보자. 첫 줄은 아직 `double`, `x`, `print` 같은 이름이 그대로 있다. 둘째 줄에서는 이름이 `(global 0)`, `(local 0)`, `(prelude print)`로 바뀌었다. 셋째는 더 이상 나무가 아니라 번호가 붙은 명령의 목록이다. `MUL`이 곱하기, `CALL`이 함수 호출이다.

## 컴파일 시점과 실행 시점 {#time}

단계는 크게 둘로 나뉜다. 바이트코드를 만들기까지를 **컴파일 시점**(compile time), 바이트코드를 실행하는 동안을 **실행 시점**(run time)이라고 한다. 둘을 구분하는 것이 중요한 까닭은 에러가 어느 쪽에서 나느냐에 따라 프로그램의 운명이 다르기 때문이다.

컴파일 시점의 에러는 프로그램을 **한 줄도 실행하기 전에** 난다. 괄호를 하나 더 닫은 프로그램을 돌리면 이렇게 된다.

```fung run exit=2 error=E0110
fn double(x) = x * 2
print(double(21)))
```

파서가 트리를 만들다가 멈췄다. 아무것도 실행되지 않았고, `fung`은 종료 코드 2로 끝난다.

실행 시점의 에러는 트리도 바이트코드도 멀쩡한데, 실제로 계산해 보니 문제가 생긴 경우다. 문자열을 정수로 곱하려 하면 VM이 그 명령을 수행하는 순간 멈춘다.

```fung run exit=1 error=E0501
fn double(x) = x * 2
print("before")
print(double("21"))
```

`before`는 이미 찍혔다. 실행이 시작된 뒤에 난 에러이기 때문이다. 종료 코드는 1이다. 에러 메시지에는 어느 함수가 어느 함수를 불러서 여기까지 왔는지(호출 경로, call path)가 붙는다. 실행 시점에만 있는 정보다.

<table>
  <thead><tr><th></th><th>컴파일 시점</th><th>실행 시점</th></tr></thead>
  <tbody>
    <tr><td>언제</td><td>실행 전, 렉서·파서·desugar·이름 해석·컴파일러</td><td>VM이 명령을 수행하는 동안</td></tr>
    <tr><td>예</td><td>괄호 짝, 모르는 이름, 블록 밖에서 변수 바꾸기</td><td>0으로 나누기, 타입이 맞지 않는 연산, 정수 넘침</td></tr>
    <tr><td>에러 번호</td><td><code>E01xx</code>~<code>E03xx</code></td><td>대부분 <code>E04xx</code>~<code>E08xx</code></td></tr>
    <tr><td>종료 코드</td><td>2</td><td>1</td></tr>
  </tbody>
</table>

에러 번호와 종료 코드를 어떻게 정했는지는 7장에서 다룬다. `fung check`는 컴파일 시점까지만 돌고 실행하지 않는 명령이다. 실행하면 위험한 스크립트(파일을 지우는 것 등)도 문법과 이름은 미리 검사할 수 있다.

:::box learn 왜 굳이 컴파일 시점에 잡는가
같은 실수라도 일찍 잡을수록 싸다. 백 줄짜리 정리 스크립트가 아흔 줄째에서 모르는 이름 때문에 멈추면, 앞의 여든아홉 줄이 한 일(파일 이동, 서버 재시작)은 이미 일어났다. 컴파일 시점에 잡으면 아무 일도 일어나기 전에 멈춘다. 그래서 언어를 설계할 때 "이 실수는 실행 전에 알 수 있는가"를 늘 묻는다. fung은 이름과 스코프에 관한 실수를 모두 실행 전에 잡는다(6장).
:::

## 단계를 나누는 이유 {#why-stages}

한 프로그램이 소스를 읽으며 바로 실행해도 된다. 실제로 그렇게 동작하는 언어 구현도 있다. 그런데 대부분의 구현은 단계를 나눈다. 이유는 소프트웨어를 나누는 이유와 같다.

- **한 단계는 한 가지 일만 한다.** 렉서는 글자만, 파서는 구조만 본다. 렉서는 "이 숫자 뒤에 `s`가 붙었으니 기간이다"를 알지만, 그 기간이 함수 인자인지는 모른다. 각 단계가 작아서 이해하고 고치기 쉽다.
- **에러의 종류가 단계와 맞는다.** 글자 수준의 실수는 렉서가, 괄호 짝은 파서가, 이름은 이름 해석이 잡는다. 에러 번호의 앞자리가 단계를 알려 준다(7장).
- **단계마다 결과를 눈으로 볼 수 있다.** `fung dump`가 그 창이다. 저장소의 테스트(`crates/fung-cli/tests/dump_expected.rs`)는 저장소 안 모든 `.fung` 파일의 세 단계 출력을 기대 출력 파일과 비교한다. 한 단계를 고쳤는데 다른 곳의 출력이 바뀌면 바로 드러난다.
- **앞쪽을 다시 쓰지 않고 뒤쪽을 바꿀 수 있다.** 새 편의 문법을 더할 때 desugar만 고치면 컴파일러와 VM은 그대로다(5장).

:::box other 다른 언어는
- **Python**(CPython): 소스를 토큰으로 자르고, 트리(AST)를 만들고, 바이트코드로 컴파일한 뒤 VM에서 돌린다. fung과 거의 같은 길이다. `.pyc` 파일이 그 바이트코드를 저장해 둔 것이다.
- **C**: 컴파일러가 앞단을 거친 뒤 바이트코드가 아니라 **기계어**를 만든다. 실행 파일을 만드는 일과 실행하는 일이 완전히 나뉘어 있다. 실행할 때는 컴파일러가 없어도 된다.
- **bash 같은 쉘**: 스크립트를 한 줄(정확히는 한 명령)씩 읽으며 바로 실행한다. 그래서 스크립트 아래쪽의 문법 에러는 위쪽이 이미 실행된 뒤에야 드러난다.
- **JavaScript 엔진**(V8 등): 바이트코드로 시작해 자주 도는 부분은 실행 중에 기계어로 다시 컴파일한다(JIT, 2장).
:::

:::box choice fung의 선택: 단계는 트리를 받아 새 트리를 돌려준다
fung의 파이프라인은 "렉서 → 파서 → 균일 트리 → 코어 언어로 풀어내기(desugar) → 바이트코드 컴파일 → VM"이다(설계 문서 00). 각 단계는 앞 단계의 트리를 **읽기만 하고** 새 트리를 만들어 돌려준다. 이식 노트(R1)는 이유를 셋 든다. 입력을 건드리지 않는다는 규칙이 있으면 "이 값이 언제 바뀌었지?"를 묻지 않아도 되어 버그 찾기가 쉽다. 구현 언어인 Rust에서 트리를 읽으면서 동시에 고치려 하면 컴파일러가 막으므로 새로 만드는 쪽이 언어와 잘 맞는다. 비용은 복사인데, 스크립트 언어의 앞단에서는 문제가 되지 않는다. 덕분에 desugar가 끝난 뒤에도 파서의 트리가 그대로 남아 `dump ast`와 `dump core`를 나란히 볼 수 있다.
:::

## 코드에서 찾아보기 {#source}

- `crates/fung-front/src/loader.rs`: 파일 하나를 끝까지 컴파일하는 곳. `State::compile_file`이 `lex` → `parse` → `desugar` → `resolve::resolve` → `compiler::compile`을 차례로 부른다. 어디까지 갈지는 `Stage`(`Ast`·`Core`·`All`)가 정한다. `fung dump ast`는 `Stage::Ast`에서 멈춘 결과다.
- `crates/fung-cli/src/main.rs`의 `dump`: `fung dump`가 단계별 결과를 찍는 곳.
- `crates/fung-cli/src/run.rs`의 `execute`: `fung run`. `Loader::compile`로 바이트코드를 얻고, `Runtime`의 `boot`·`load`·`run`으로 실행한다.
- 크레이트(Rust의 빌드 단위) 셋: `crates/fung-front`(앞단과 컴파일러, 외부 크레이트 0개), `crates/fung-vm`(값과 VM과 런타임), `crates/fung-cli`(실행 파일 `fung`).

:::exercise 단계 하나씩 보기
`print(1 + 2 * 3)` 한 줄을 파일에 저장하고 `fung dump ast`, `fung dump core`, `fung dump bytecode`로 세 단계를 찍어 보자. 트리 안에서 `*`가 `+`보다 안쪽에 있는가? 바이트코드에서 `MUL`과 `ADD` 중 어느 것이 먼저 나오는가?

:::solution
실행 결과는 7이다.

```fung run
print(1 + 2 * 3)
```

```dump ast
print(1 + 2 * 3)
```

```dump bytecode
print(1 + 2 * 3)
```

트리에서 `(binary * 2 3)`이 `(binary + 1 …)`의 자식이다. 곱셈이 먼저 묶였다는 뜻이다. 바이트코드도 `MUL`이 `ADD`보다 먼저 나온다. 트리의 안쪽부터 계산하기 때문이다. 이 순서가 어떻게 정해지는지는 4장(우선순위)과 8장(스택 머신)에서 본다.
:::

:::

## 정리 {#summary}

- CPU는 기계어만 실행한다. 소스의 뜻을 찾아 실행 가능한 형태로 바꾸는 프로그램이 언어 구현이다.
- fung은 소스 → 토큰 → 트리 → 코어 → 바이트코드 → 실행의 여섯 단계를 거친다. 앞의 넷이 앞단, 바이트코드와 VM이 뒷단이다.
- 컴파일 시점의 에러는 실행 전에 나고 종료 코드 2, 실행 시점의 에러는 실행 중에 나고 종료 코드 1이다.
- `fung dump ast|core|bytecode`로 단계마다 결과를 볼 수 있다. 각 단계는 앞 단계의 트리를 읽기만 하고 새 트리를 만든다.

다음 장에서는 마지막 두 단계, "바이트코드와 VM"이라는 선택이 인터프리터·컴파일러와 어떻게 다른지 본다. 명령 설명은 [명령줄 레퍼런스](../reference/cli.html)에 있다.
